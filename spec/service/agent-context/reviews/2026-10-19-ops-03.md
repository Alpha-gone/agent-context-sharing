# TLS·신뢰 프록시·실제 상대 해석 검토

- 기준: [OPS-03](../development-plan/operations.md#ops-03), [기동과 종료](../sdd/operations.md#기동과-종료), [배포 구성](../sdd/operations.md#배포-구성), [공개 로그인·가입 보호](../sdd/authentication.md#공개-로그인가입-자원-보호), `FR-AGENT_CONTEXT-140`.
- 범위: direct/proxy 구성 검증·라우팅 전 TLS 판정·실제 접속 상대·단일 전달 헤더·방문자 주소·Secure 쿠키·프로브 예외.
- 분리: 운영 Compose·실제 프록시 상대·Cloudflare Tunnel·공개 HTTPS·전 구간 TLS·운영 배포는 이번 모듈 인수에 포함하지 않는다. 미등록 OAuth·MCP는 바깥 TLS 판정과 현재 404만 확인하며 실제 프로토콜·인증 인수로 간주하지 않는다.

## 발견 사항과 반영

기존 바깥 ServeMux는 경로를 정규화하여 TLS 검사 전에 리디렉션할 수 있었다. TLS 검사를 라우터 앞으로 옮기고 정확한 `/healthz`·`/readyz`의 GET·HEAD만 예외로 뒀다. 미등록 경로·점 경로·중복 슬래시·메서드 안내도 같은 판정 뒤에서 처리한다.

기존 전달 헤더는 Unicode 공백을 제거하고 Unicode case folding으로 비교하여 비 ASCII 유사 문자도 HTTPS로 받아들였다. SP·HTAB과 ASCII 대소문자만 정규화하고 단일 https 토큰을 요구하도록 고쳤다. 방문자 주소도 같은 ASCII 공백 경계를 적용하며 잘못된 값은 실제 상대를 사용한다. `RemoteAddr`는 IP와 숫자 포트를 함께 해석하여 누락/잘못된 포트·zone·호스트 이름을 신뢰 근거로 쓰지 않는다. IPv4-mapped 주소는 계속 IPv4로 정규화한다. 방문자·범용 전달 헤더는 전송 신뢰 근거로 사용하지 않는다.

직접 TLS는 연결의 TLS 상태만, 프록시는 좁은 실제 접속 상대와 단일 HTTPS 전달 값만 사용한다. 같은 판정이 쿠키의 Secure 속성에도 주입된다. 구성·신뢰 대역·Compose·환경 예시를 변경하거나 Docker/Cloudflare 전체 대역 신뢰를 추가하지 않았다.

## 새 검증 근거

- 라우팅 순서 16개 하위 시험: 로그인·가입·웹·JWKS·미등록 MCP/메타데이터·OAuth 경로와 점/중복 슬래시·프로브 유사 경로는 확인되지 않은 평문에서 리디렉션·쿠키 없이 400이다. CF-Visitor·Forwarded·CF-Connecting-IP로 전송 판정을 우회하지 못한다.
- 전달 헤더 13개 하위 시험: 정상·혼합 ASCII 대소문자·SP/HTAB만 허용하고 누락·빈 값·HTTP·쉼표 목록·동일/서로 다른 복수 값·Unicode 공백·long s·개행을 거부했다. proxy 모드에서 직접 연결의 TLS 값만으로 우회하지 않으며 주소 해석도 같은 판정을 따른다.
- 실제 상대 14개 하위 시험: IPv4·IPv6·mapped·포트 경계와 누락/빈/이름/범위 밖/음수 포트·호스트 이름·zone·맨 IPv6·빈 값을 대조했다. 해석 실패에는 방문자 주소를 대신 신뢰하지 않는다.
- 프로브 20개 하위 시험: direct/proxy의 두 경로에서 GET·HEAD만 애플리케이션 TLS 예외다. POST·OPTIONS·DELETE는 같은 평문 거부를 받는다.
- 방문자 주소 12개 하위 시험: IPv4·IPv6·mapped·SP/HTAB과 누락·빈/복수/목록·zone·Unicode 공백·호스트 이름·포트 포함을 대조했다. 잘못된 값에는 실제 상대를 쓰고 다른 전달 주소는 읽지 않는다.
- 종단 구성 13개 하위 시험: direct/proxy의 정상 조합과 모드·신뢰 대역·인증서/키 누락·잘못된 혼합을 자원 시작 전에 구분했다. 파일 내용·실제 운영 인증서 유효성의 검증은 아니다.
- 실제 루프백 3모드·각 20개 하위 시험: TLS 수신기, 신뢰된 HTTP 원본 프록시, 신뢰 대역 밖 프록시를 사용했다. 상태·공개 경로·로그인/가입·JWKS·보호 웹·미등록 MCP/메타데이터·잘못된/복수 전달 헤더와 경로 정규화를 실제 HTTP 클라이언트로 대조했다. 허용된 로그인만 Secure·HttpOnly·SameSite=Lax·Path=/ 쿠키를 만들고 실제 상대/방문자 해석이 일치한다. 직접 TLS 수신기는 평문 healthz도 거부하며 별도 평문 수신기를 만들지 않는다.
- 별도 양식 관찰 시험은 TLS 거부가 양식 읽기·자격 대조 전에 끝남을 확인했다. 원본 HTTP 루프백의 Secure 쿠키는 프록시 신뢰 판정의 증거이며 로컬 구간 암호화나 전 구간 TLS의 증거가 아니다.
