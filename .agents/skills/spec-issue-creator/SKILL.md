# Spec Issue Creator

## 개요

서비스 명세의 범위와 추적 ID를 보존하면서 독립적으로 구현·검증할 수 있는 GitHub 이슈 초안을 작성한다. 이슈 생성, 기존 이슈 수정과 명세의 추적 링크 변경은 각각 승인된 경우에만 수행한다.

이슈 초안을 작성하기 전에 [이슈 작성 기준](references/issue-structure.md)을 읽고 적용한다.

## 필수 입력

| 입력                                              | 사용 방법                                                   |
|:--------------------------------------------------|:------------------------------------------------------------|
| `spec/service/README.md`                          | 서비스 경계와 문서 진입점을 확인한다.                       |
| 대상 서비스의 `SRS.md`, `SDD.md`                  | 요구사항, 설계 범위, 추적 ID와 검증 기준의 근거로 사용한다. |
| `reference.md`, `suggestion.md`, `logs/prompt.md` | 출처, 채택된 제안과 사용자 결정의 보조 근거로 사용한다.     |
| 기존 GitHub 이슈                                  | 중복, 선행 작업, 연결 이슈와 완료 여부를 확인한다.          |
| 저장소의 라벨과 마일스톤                          | 실제 존재하고 범위와 일치하는 값만 후보로 사용한다.         |

필수 명세가 없거나 대상 서비스가 불명확하면 임의로 이슈를 만들지 말고 필요한 입력을 확인한다.

## 작업 절차

1. 저장소 루트와 GitHub 저장소를 식별하고 현재 브랜치의 upstream 상태를 확인한다.
2. 루트부터 대상 경로까지 적용되는 `AGENTS.md` 체인과 `spec/DICTIONARY.md`를 읽는다.
3. 대상 명세와 연결 문서를 읽고 확인된 사실, 사용자 결정, 채택된 제안, 미정 사항을 분리한다.
4. 요구사항 ID와 설계 추적 ID를 보존한 채 구현 산출물과 검증 경계를 추출한다.
5. 구현을 막는 미정 사항은 구현 범위에 숨기지 말고 조사·결정 이슈 후보로 분리한다.
6. GitHub 연결 도구를 우선 사용해 열린 이슈와 닫힌 이슈를 검색하고 중복 가능성을 비교한다.
7. 하나의 이슈가 독립적으로 구현·검증 가능한지 확인하고, 결합 이유가 없는 범위는 분리한다.
8. `references/issue-structure.md` 형식으로 초안을 작성하고 근거 문서와 추적 ID를 연결한다.
9. 라벨과 마일스톤은 저장소에서 재조회한 값 중 범위와 일치하는 후보만 제시한다. 새 값 생성을 추측하지 않는다.
10. 생성할 저장소, 제목, 본문, 라벨, 마일스톤, 담당자를 사용자에게 제시하고 명시적인 승인을 받는다.
11. 승인된 경우에만 GitHub 이슈를 생성하고 번호, URL, 제목, 본문, 상태와 메타데이터를 재조회한다.
12. 명세의 `관련 이슈` 갱신이 필요하면 대상 파일과 행을 별도 변경 범위로 제시하고 승인 후 해당 문서 소유 스킬을 사용한다.
13. 로컬 파일을 변경했다면 프로젝트 작업 로그를 기록하고 완료 전 DOX pass를 수행한다.

## 분할 기준

- 하나의 이슈는 하나의 명확한 결과와 검증 가능한 인수 조건을 가져야 한다.
- 동일한 요구사항 ID를 여러 이슈가 다룰 수 있지만 각 이슈의 책임과 제외 범위가 겹치지 않아야 한다.
- 구현, 데이터 이관, 조사, 정책 결정과 문서 갱신이 독립적으로 완료될 수 있으면 별도 이슈로 나눈다.
- 선행 결정이 없으면 구현 방법이 달라지는 경우 먼저 조사·결정 이슈를 제시한다.
- 기존 이슈가 같은 결과와 인수 조건을 포함하면 새 이슈를 만들지 말고 중복 근거를 보고한다.

## 승인 경계

- 초안 작성과 중복 조회는 읽기 작업으로 수행할 수 있다.
- GitHub 이슈 생성·수정, 라벨·마일스톤 변경, 명세 파일 갱신은 실행 전에 정확한 대상을 제시하고 승인받는다.
- 사용자가 여러 변경을 한 번에 승인하면 제시한 대상과 내용에 한해서만 묶어 수행한다.
- 생성 승인과 명세 추적 링크 갱신 승인을 서로 대신하는 것으로 해석하지 않는다.

## 실패 처리

| 상황                          | 처리                                                                 |
|:------------------------------|:---------------------------------------------------------------------|
| 저장소 또는 서비스가 불명확함 | 가능한 후보와 차이를 제시하고 확인 전 생성을 중단한다.               |
| 명세끼리 충돌함               | 충돌 위치와 영향을 보고하고 어느 쪽도 확정 사실로 선택하지 않는다.   |
| 중복 이슈가 발견됨            | 기존 이슈의 번호, 상태와 겹치는 범위를 제시한다.                     |
| GitHub 조회가 실패함          | 중복·라벨·마일스톤 확인 불가를 명시하고 쓰기 작업을 수행하지 않는다. |
| 이슈 생성 후 재조회가 실패함  | 생성 성공을 단정하지 말고 반환된 정보와 미검증 항목을 구분한다.      |

## 제외 범위

- 명세 근거가 없는 일정, 버전, 우선순위, 라벨 또는 마일스톤 생성
- 승인되지 않은 GitHub 이슈 등록·수정
- 이슈 생성만으로 요구사항 상태를 `확정` 또는 `완료`로 변경
- 기존 요구사항 ID, 체크리스트, 링크 또는 사용자 작성 내용의 임의 삭제

## 검증

- 이슈의 모든 범위와 인수 조건을 명세 또는 확인된 사용자 결정으로 추적한다.
- 기존 이슈와의 중복 여부, 라벨·마일스톤의 실제 존재 여부를 확인한다.
- 생성 후 이슈를 재조회해 대상 저장소, 번호, 제목, 본문, 상태와 URL을 검증한다.
- Markdown 링크, 체크리스트, 맞춤법과 자연스러운 한국어 표현을 확인한다.
- 수행하지 못한 조회나 검증을 성공으로 기록하지 않는다.
