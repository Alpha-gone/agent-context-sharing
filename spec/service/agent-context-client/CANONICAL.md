## 정본 문서와 책임

이 문서는 클라이언트 개발에서 참조할 정본의 위치와 변경 경로를 안내한다. 동작·프로토콜·구현 결정을 다시 정의하지 않으며, 세부 내용이 다르면 아래 소유 문서를 따른다.

| 판단 대상 | 정본 | 개발 때 확인할 내용 |
|-----------|------|---------------------|
| 클라이언트 제품 범위, 호스트·원격 경계, 기능·비기능 요구사항, 출시 완료 기준 | [클라이언트 SRS](./SRS.md) | 「제품 기준선」, 요구사항 표, 「도구 중계 계약」, 「출시 완료 기준」 |
| 실행 명령, 패키지 경계, 인증·중계·재시도·자원 상한의 구현 설계 | [클라이언트 SDD](./SDD.md) | 「패키지 경계」부터 「테스트 전략」, 「요구사항 추적표」 |
| 원격 도구 13종, 데이터와 도메인 오류·권한의 공개 계약 | [서버 SRS](../agent-context/SRS.md), [서버 SDD](../agent-context/SDD.md) | 「MCP 연산 매핑」과 「MCP 표면」 등 공개 경계 |
| 공통 서비스 용어 | [용어 정리집](../../DICTIONARY.md) | 클라이언트·에이전트 호스트·서비스 전용 DPoP 인증 프로필의 정의 |
| 배포 환경 변수 이름과 예시 | [`.env.example`](../../../.env.example) | 클라이언트 SDD 「배포 구성」과 목록 일치 여부 |
| 구현 순서, 실제 진행 상태와 단계별 완료 기준 | [개발 계획](./DEVELOPMENT_PLAN.md) | 현재 단계의 작업과 검증 근거 |

클라이언트 SRS·SDD는 확정된 목표 계약이다. 계획에 적힌 예정 작업이나 체크박스가 현재 코드의 구현 완료를 뜻하지 않는다. 구현 여부는 실제 코드와 검증 결과로 판단하고 계획에 반영한다.

## 개발 경계

| 경계 | 클라이언트 책임 | 다른 정본의 책임 |
|------|-----------------|------------------|
| 에이전트 호스트 → 로컬 프로세스 | MCP `2026-07-28` `stdio`의 `server/discover`, `tools/list`, `tools/call`, 요청 상관과 결과 전달 | 호스트의 실행·도구 사용 판단 |
| 로컬 프로세스 → 인가 서버 | 브라우저 PKCE, loopback callback, ES256 DPoP proof, 토큰 결합·갱신 검증 | 인가 서버의 계정 인증·토큰 발급 정책 |
| 로컬 프로세스 → MCP 리소스 서버 | 보호된 Streamable HTTP, 원격 계약 검증, 제한된 재시도, 도구 공개 정책과 응답 보존 | 서버의 권한·도메인 연산·검색·도구 결과 |

호스트 경계의 MCP 공식 적합성과 원격 경계의 MCP 메시지·수명주기·도구 계약은 따로 확인한다. 원격 DPoP는 서비스 전용 인증 프로필이므로 그 결과는 별도로 기록한다. 정확한 헤더, 오류, 재시도와 보안 조건은 SRS·SDD를 따른다.

## 변경 경로

1. 서버의 도구, 인증, 오류 또는 공개 MCP 계약이 달라지면 서버 SRS·SDD에서 먼저 확정하고 클라이언트 SRS의 영향을 확인한다.
2. 클라이언트의 관찰 가능한 동작이나 출시 조건이 달라지면 클라이언트 SRS를 갱신한 뒤 SDD의 구현 선택과 요구사항 추적표를 맞춘다.
3. 요구사항은 유지하면서 구현 구조가 달라지면 클라이언트 SDD를 먼저 갱신한다.
4. 승인된 계약에 맞춰 구현하고 관련 검증을 수행한 뒤 개발 계획의 작업·완료 기준·단계 상태를 실제 결과에 맞춰 갱신한다.

새 용어가 필요하면 용어 정리집에서 기존 표기를 확인한다. `AGENTS.md` 계층은 각 경로의 작업 계약이며, 이 문서는 그 지침을 대신하지 않는다.

## 검증 진입점

- 요구사항별 설계·검증 대응은 [SDD 「요구사항 추적표」](./SDD.md#요구사항-추적표)를 따른다.
- 시험 계층과 필수 오류 주입은 [SDD 「테스트 전략」](./SDD.md#테스트-전략)을 따른다.
- 출시 판정은 [SRS 「출시 완료 기준」](./SRS.md#출시-완료-기준)을 따른다.
- 실제 실행 결과와 미완료 항목은 개발 계획의 해당 단계에 기록한다. 아직 수행하지 않은 시험을 통과로 표시하지 않는다.
