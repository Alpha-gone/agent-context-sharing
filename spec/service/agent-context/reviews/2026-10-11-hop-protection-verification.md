# 홉 작업량 보호 검증 보완

## 대상과 결과

- [#123](https://github.com/Alpha-gone/agent-context-sharing/issues/123), 기준 `dev`의 `05fb56c`에서 홉 조회의 연결 반환·공통 시간 예산·참조 적재량 검증을 보완했다. 기존 운영 연결 누수나 시간 제한 실패를 재현한 작업으로 해석하지 않는다.
- `referenceRows`를 근거·구성원 묶음 조회의 별도 지표로 추가했다. 기존 입력 상한과 참조 목록, 결과 상한·정렬·절단·간선 완전성 및 공개 응답 계약은 유지한다. #121의 간선 스캔 최적화나 #124의 동시 삭제 정책을 변경하지 않았다.
- Go 1.27.1·darwin/arm64, 개발 PostgreSQL 18.6·AGE 1.8.0·pgvector 0.8.6의 새 전용 DB `issue123_test_20261011`에 정식 `001_init.sql`을 적용했다. 적용 이력은 1개다. 기존 개발 DB·서명 키·컨테이너·볼륨·`.env`는 수정하지 않았다. DB를 사용하는 모든 아래 시험은 `TEST_DATABASE_REQUIRED=1`로 실행했다.

## 연결 반환과 공통 예산

- 잠금으로 실제 조회를 막은 뒤 호출자의 100ms 마감·실행 중 취소를 두 공개 진입점과 일반 풀·스냅숏에서 검사했다. 오류 원인은 `errors.Is`로 대조하고 결과 전체가 빈 `HopResult`인지 확인한다. 스냅숏의 참조 조립·읽기 연결 반환 뒤 접근 기록에서도 취소 오류가 빈 결과로 전파되는지 별도로 검사했다.
- 후속 조회 전에 잠금 연결을 포함한 획득 연결 수가 기준값으로 돌아오는지 직접 확인한다. pgx의 지연 정리를 최대 5초 동안 허용한다. 스냅숏에서는 읽기 자리 0개·활성 트랜잭션 1개(조정 연결)를 함께 대조하고, 잠금 해제·후속 조회·스냅숏 종료 후에도 각각 연결 수를 확인한다. 여러 연결 중 다른 연결을 쓰는 후속 성공만으로 반환을 판단하지 않는다.
- race 계측에서 시작 조회를 막은 일반 풀의 실제 내부 예산은 30.002075708초, 후보 조회를 막은 스냅숏은 30.001776333초에 소진되었다. 더 짧은 호출자 취소·마감은 100.603458~102.586958ms에 종료되었다. 일반 풀은 획득 연결 0개로, 열린 스냅숏은 조정 연결 1개·읽기 자리 0개로 회복했다. 스냅숏 종료 뒤에는 0개로 회복했다. 운영의 절대 벽시계 상한을 보장하는 수치는 아니다.
- pgx 질의 추적으로 두 진입점·일반 풀/스냅숏·상한 0/2·호출자 예산 40초/3초의 16개 조합을 관찰했다. 첫 질의를 75ms 지연시키고 시작 조회부터 후보·본문·간선·참조·접근 기록까지 동일한 마감인지 대조한다. 40초 감시 마감에서는 내부 30초 예산을, 3초 마감에서는 호출자 마감의 우선을 확인한다. 취소 없이 수행하는 트랜잭션 정리는 마감 동등성 대조에서 제외한다.
- 운영 파일을 변경하지 않는 Go overlay로 `HopContextsFrom` 내부 예산 제거, `HopContexts` 시작 조회 예산 제거, 시작 조회 뒤 예산 재시작의 세 회귀를 각각 주입했다. 앞의 두 회귀는 첫 조회 예산이 약 40초임을, 마지막 회귀는 질의별 마감 불일치를 검출하여 모두 예상대로 실패했다. 이를 정상 코드의 실패로 합산하지 않는다. 운영 코드에 시험 전용 시간 분기·가변 timeout을 추가하지 않았다.

## 지표 정의와 최대 정상 참조 표본

지표의 정본은 SDD의 「고연결 노드의 조회·적재 보호」다. `identifierRows`는 초과 확인용 후보를 포함하고, `bodyRows`·`bodyBytes`는 호출자가 이미 제공한 시작 노드를 제외한 새 정점 본문만 센다. `edgeRows`는 내부 간선 질의의 중복 제거 전 수신 행, `referenceRows`는 별도 `DERIVED_FROM`·`HAS_MEMBER` 묶음 질의의 수신 행 합이다. 내부 간선과 참조 목록에서 같은 참조를 읽으면 서로 다른 작업으로 각각 센다. 참조 대상 본문·선행 시작 조회·임베딩 접근 기록·DB 내부 스캔은 이 지표 밖이다.

원천 1,000개 중 처음 100개를 파생 근거로, 전체 1,000개를 사건 구성원으로 사용했다. 원천은 탐색 표본용 묶음 생성이며 파생·사건은 정식 생성 경로로 참조 검증을 거쳤다. 기존 전체 BFS 기준선과 결과 속성·참조·노드 순서·거리·간선·절단을 대조하고 참조 식별자 전체를 원본 목록과 비교했다. 다음 값은 race 실행에서 측정한 애플리케이션 수신량이다.

| 표본 / 응답 상한 | 반환 노드 / 간선 | 후보 행 | 새 본문 행 / UTF-8 바이트 | 내부 간선 행 | 참조 행 |
|---|---|---|---|---|---|
| 원천만 / 1 | 1 / 0 | 1 | 0 / 0 | 0 | 0 |
| 새 파생 선택 / 2 | 2 / 1 | 1 | 1 / 13 | 1 | 100 |
| 새 사건 선택 / 2 | 2 / 1 | 1 | 1 / 13 | 1 | 1,000 |
| 새 파생·사건 선택 / 3 | 3 / 2 | 2 | 2 / 26 | 2 | 1,100 |
| 파생 시작 / 1 | 1 / 0 | 1 | 0 / 0 | 0 | 100 |
| 사건 시작 / 1 | 1 / 0 | 1 | 0 / 0 | 0 | 1,000 |
| 파생·사건 시작 / 2 | 2 / 0 | 1 | 0 / 0 | 0 | 1,100 |
| 중복 `derived_from` label / 2 | 2 / 1 | 1 | 1 / 13 | 2 | 100 |

참조 대상 대부분이 응답 노드 집합 밖이어도 목록은 완전하게 유지했다. 응답 노드 상한이 참조 적재 행 수를 같은 수로 제한하지 않음을 확인했다. 전체 BFS 기준선의 본문·간선 행은 반복 이웃·제외 후보를 포함하며 양수 상한 구현의 지표와 의미가 다르다. 참조 행은 두 구현 모두 같은 묶음 질의에서 대조하고 기존 허브 benchmark에도 `refrows/op`를 추가했다.

## 재현과 검증 범위

```shell
# 새 전용 DB에 정식 마이그레이션을 적용하고 TEST_DATABASE_URL을 지정한다.
TEST_DATABASE_REQUIRED=1 go test -race -count=1 ./internal/store \
  -run '^(TestHopOwnBudgetAndConnectionIntegration|TestHopSharedBudgetIntegration|TestHopAssemblyCancellationIntegration|TestHopMaxReferencesWorkIntegration|TestHopBoundedDeadlineReleasesConnectionIntegration)$' -v

# 실제 30초 소진 시험을 별도 실행한 경우에만 중복 실행을 제외한다.
TEST_DATABASE_REQUIRED=1 go test -race -count=1 -json ./internal/store \
  -run '^(TestHop|TestSnapshot)' -skip '^TestHopOwnBudgetAndConnectionIntegration$'
```

- 실제 내부 예산·자원 회복 시험은 10개 하위 시험과 상위 시험 1개가 race 계측에서 통과했다. 이어 실행한 기존 홉·스냅숏 및 새 공통 예산·조립 중 취소·최대 참조 회귀는 상위 시험 22개, 하위 시험을 포함한 67건이 142.945초에 통과했다. 기존 900개 조합의 전체 BFS 기준선 대조도 포함한다. 두 실행을 합쳐 23개 상위 시험·78건이며 실패·건너뜀은 0건이다. 30초 소진 시험은 첫 실행에서 이미 수행했으므로 두 번째 실행에서는 `-skip`으로 선택 대상에서 제외했으며 DB 설정 부재로 건너뛴 것이 아니다.
- 서버·클라이언트 각 모듈의 `go build ./...`·`go vet ./...`, 저장소 루트의 `gofmt -l .`·`git diff --check`를 통과했다. 최초 새 참조 시험의 컴파일에서는 존재하지 않는 정렬 비교 함수 이름을 발견해 실제 식별자 문자열 비교로 수정했다. 그 실패를 통과로 세지 않았다.
- 최대 참조 표본은 입력 상한·응답 완전성·적재량의 회귀 시험이며 통계적 성능 개선, 운영 SLA, CPU·RSS·WAL 또는 DB 내부 스캔의 상한을 입증하지 않는다. 서버·클라이언트 전체 테스트, 외부 API·실제 브라우저·운영 배포는 이번 검증 범위가 아니다.

## DOX pass

- 루트·spec·service·서비스 DOX 체인을 확인하고 루트의 SDD 소유 참조와 서비스의 홉 보호 검증 계약을 갱신했다. SDD에는 포함·제외 질의, 참조의 정상 상한과 시간·자원 회복 검증 기준을 동기화했다.
- 새로운 소유 경계·하위 DOX·workflow를 만들지 않아 부모 Child DOX Index의 경로와 책임 설명은 유지한다. 기존 SRS·용어 정리집·README·OPERATIONS·마이그레이션·클라이언트·MCP·웹 계약은 변경할 이유가 없다.
- 기존 IDEA 설정의 staging은 보존했으며 커밋·push·PR·이슈 직접 종료는 수행하지 않았다.
- 이번 작업에서 생성한 시험 DB는 검증 종료 뒤 잔여 연결 0개를 확인한 후 삭제했다. `pg_database`의 잔여 항목도 0건이다. 삭제한 합성 시험 데이터는 복구하지 않으며 정식 마이그레이션과 fixture로 다시 생성할 수 있다.
- 문서 6개의 한국어 내용·코드 블록 경계·상대 링크 2개·Child DOX 경로 8개와 새 측정 표의 열 수를 검사했다. 변경한 문장·주석의 맞춤법·띄어쓰기·용어를 검토했고 마지막 `git diff --check`·`gofmt -l .`도 통과했다.
