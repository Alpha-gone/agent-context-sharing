# #155 진단 정리 guard의 DB 대기 마감

- 대상: [이슈 #155](https://github.com/Alpha-gone/agent-context-sharing/issues/155).
- 기준: `dev`의 `ddb361d`, 작업 브랜치 `fix/155-diagnostic-maintenance-deadline`.

## 변경과 계약

단일 진단 기록 루프가 시간 기반 정리의 guard를 호출할 때 회차마다 1초 마감 context를 전달한다. 기존 조립의 `Store.WithTryAdvisoryLock`은 이 context를 연결 2개 예약·풀 연결 획득·자문 잠금 질의에 전달한다. DB 포화로 예약이 풀리지 않아도 마감 뒤 이벤트 기록으로 돌아오며, 다음 회차는 새 마감으로 시도한다.

마감은 기존 `MaintenanceFailures`·첫 오류·stderr 알림 경계에 남긴다. StopMaintenance의 의도적 취소와 동반 오류 구분, 실행권 범위·예약 반환·자문 잠금 해제의 별도 정리 예산과 파일 잠금·단일 루프 소유권은 유지한다. 파일 I/O를 강제로 중단하거나 임의 부하에서 대기열 무누락을 보장하지 않는다.

적용 판의 공급자 근거는 Go 1.27.1 SDK `src/context/context.go`의 WithTimeout/WithDeadline 문서, `golang.org/x/sync@v0.22.0/semaphore/semaphore.go`의 Acquire 문서와 `github.com/jackc/pgx/v5@v5.10.0/pgxpool/pool.go`의 Acquire 구현에서 확인했다. 예약은 context 종료 시 대기를 중단하며 풀도 `p.p.Acquire(ctx)`에 같은 context를 전달한다.

## 검증

- 원본 `recorder.go`를 Go overlay로 대조한 새 회귀에서 예약을 계속 점유하자 3초 뒤에도 64건이 대기열에 남아 실패했다. cleanup으로 대기 context를 취소해 시험 자원을 반환했다.
- 수정 후 `TestMaintenanceGuardSaturationKeepsRecording`은 예약을 해제하지 않은 상태에서 64건 기록·이벤트 누락 0건·정리 실패 1건을 확인했다. 실행권을 못 얻은 동안 정리 callback은 호출되지 않았고, 예약 해제 뒤 다음 회차는 같은 scope로 정리하고 예약을 반환했다. Close에도 최초 마감 원인이 보존됐다.
- `TestPeriodicGuardSaturatedReservationDeadline`은 실제 Store의 예약을 모두 점유하고 `WithTryAdvisoryLock`의 2개 예약 대기에 마감을 주입했다. 풀 연결·정리 callback 전에 DeadlineExceeded가 반환되고 전체 예약량이 회복됨을 확인했다. 이 시험은 DB 없이 예약 단계만 실행한다.
- macOS 진단 전체 `go test -race -count=1 -json ./internal/diagnostic`: 171건 통과, DB 실행권 시험 1건은 환경 미설정으로 건너뜀, 21.998초.
- Store의 새 포화 시험과 기존 `TestConnectionBudgetRangeAndCancelCause`: race 2건 통과, 건너뜀 없음.
- 서버 주기 작업·종료 회귀(`^Test(Periodic|OPS04Periodic|Shutdown|CloseWorkers|NormalShutdown)`): race 18건 통과, 건너뜀 없음.
- `GO_BINARY=.../go1.27.1/bin/go sh internal/diagnostic/test-linux.sh`: Linux 모듈 179건과 읽기 전용 마운트·first/restart/replacement 4건 통과. DB 실행권 1건과 자식 helper 직접 실행 1건은 건너뜀이다. 기존 ENOSPC·EMFILE helper는 부모 시험에서 각각 실행했다.
- Go 1.27.1 `go build ./...`, `go vet ./...`, `gofmt -l .`, `git diff --check` 통과.

건수는 하위 사례를 포함한다. 결과는 `/private/tmp/acs-155-{diagnostic,store,server}.json`과 Linux 결과 디렉터리 `acs-obs08-results-HfZpJv`에 보관했다. 실제 DB 풀 포화·DB 자문 잠금 연동 인수는 이번에 실행하지 않았으며 건너뛴 DB 시험을 통과로 집계하지 않았다.

## 문서와 범위

마감의 정본은 [운영 설계](../sdd/operations.md#진단-정리의-실행-범위)에 유지했다. 기존 [관측성 설계](../sdd/observability.md#기동실행-중-실패와-종료)는 운영 설계의 실행권·DB 종료 경계를 이미 참조하므로 중복 정의하지 않았다. 공개 구성·스키마·패키지 소유권·DOX 구조와 색인은 바뀌지 않았다. 개인 IDE 파일은 보존했다.
