# MCP-08 오류 계층·시간 예산·HTTP 취소 검토

- 기준: 2026-10-20, `feat/mcp-auth`의 `dfe439f` 이후 작업 트리.
- 대상: [MCP-08](../development-plan/mcp.md#mcp-08), [요청 시간 예산과 오류 경계](../sdd/mcp.md#요청-시간-예산과-오류-경계), [DB 연결·예약](../sdd/architecture.md#데이터베이스-연결).
- 판정: 오류·시간 예산·HTTP 취소 모듈 인수 완료. 전체 67/124개 완료. 다음 권장 작업은 [AUTH-10](../development-plan/authentication.md#auth-10)이며 MCP-09에는 ARCH-07·TEST-07이 추가로 필요하다.

## 구현과 계약

보호 MCP의 도구 경계에서 처리기 오류와 누락 결과를 사상한다. 등급·필드·현재 판·한도·대체 채널의 기존 값을 보존하고 내부 의존 장애·예상 밖 오류·취소는 고정 internal 완료 결과로 바꾼다. 내부 장애의 원인에 필드·부재 오류가 있어도 내부 장애가 우선한다. 정상 부분 결과는 그대로 유지한다. SDK에 원래 오류 문자열을 전달하지 않으며 인증·scope·HTTP/JSON-RPC 외피 오류는 별도 계층으로 남긴다.

서버의 `newMCPHandler`는 본문 수신·인증·도구 실행에 같은 30초 context 예산을 적용한다. 호출자의 더 짧은 마감과 취소가 우선하며 같은 마감을 본문 읽기에 전달한다. 이 값은 소유 SDD에 먼저 반영했으며 새 배포 키는 추가하지 않았다. 예산 소진으로 응답 없이 반환한 경우에만 HTTP 500 server_error·no-store를 반환하고 이미 시작한 응답을 덧쓰지 않는다. 본문 읽기 마감은 HTTP 500·JSON-RPC -32603으로 구분한다. 내부 장애를 WWW-Authenticate나 반복 인가 신호로 바꾸지 않는다.

SDK의 PropagateRequestCancellation을 유지하고 표준 취소 알림을 요구하지 않는다. HTTP 반환과 저장소 정리를 따로 관찰한다. 기존 저장소의 취소 독립 롤백·스냅숏·연결 예약과 커밋 후 최초 결과 보존 경계는 변경하지 않았다. 새로운 goroutine으로 처리기 실행을 감싸거나 context를 무시하는 작업의 강제 종료를 구현하지 않았다.

## 검증

- Go 1.27.1·MCP Go SDK v1.8.0. 적용 판의 context·Request.Context·ResponseController·SDK 취소 전파와 MCP 취소 계약을 [공식 근거](../reference.md)에 기록했다.
- MCP 전체 **424건**, 선별 인증 **10건**, 선별 서버 **15건**, 선별 저장 **9건**, 부모 시험 포함·중복 제외 총 **458건 통과, 실패 0건·건너뜀 0건**, 각 범위 race 통과.
- 실제 SDK HTTP에서 예상 밖 오류·결과 누락·도메인 오류와 부가 정보를 검증했다. 9007199254740993의 판·한도 값 정밀도, 필요한 editor 등급·body 필드·web 대체 채널과 내부 원문 비노출을 확인했다. 정상 절단·일부 채널 실패는 complete·isError=false다.
- 실제 Bearer 검증·보호 MCP를 연결한 인증 대역 저장소 표본에서 부재/잘못된/만료 자격의 401, scope의 403, 키/폐기 저장 장애의 500과 WWW-Authenticate를 대조했다. 인증 전에는 JSON을 해석하지 않아 같은 잘못된 본문도 미인증이면 401, 인증을 통과하면 JSON-RPC -32700이다. 기존 실제 OAuth·DB·TLS의 MCP-02 및 MCP-06 쓰기 표본도 회귀 검증했다.
- 두 HTTP 인스턴스에서 24개 발견·목록·도구 호출을 두 인증 맥락으로 병행했다. 응답의 private·ttlMs=0·HTTP no-store, 요청별 실제 계정/client, 이후 폐기 자격의 401과 총 26회의 인증을 확인했다. 이 캐시 표본의 인증은 대역이고 실제 OAuth/TLS 표본과 구분한다.
- 기본 30초 deadline이 도구 context까지 전달되고 부모의 더 짧은 마감을 늘리지 않는지 확인했다. 짧은 동일 구현 예산을 사용해 응답 없는 만료·이미 시작한 응답 보존·읽기 마감 설정 장애를 검증했다. 실제 HTTP/1.1 소켓에서 본문을 미완성으로 보내 읽기 마감의 500·-32603과 인증/도구 미호출을 확인했다. 30초 전체의 실제 벽시계 소진을 측정한 시험은 아니다.
- 실제 DB·검색·TLS 처리기에서 짧은 서버 예산을 소진시켜 질의 임베딩 HTTP 호출의 context와 제공자 측 요청이 종료됨을 확인했다. 제공자는 로컬 HTTP 대역이고 외부 Gemini는 호출하지 않았다.
- 최소 풀 4개인 저장소의 실제 HTTP/SDK 자원 표본은 예약 대기·스냅숏 읽기·커밋 전·커밋 후를 각각 클라이언트 단절과 서버 마감으로 중단했다. 모든 하위 작업이 유한 시간 안에 끝난 뒤 획득 연결 0·활성 읽기 0·읽기 자리 0과 예약 총량 재획득을 직접 대조했다. 예약 대기는 연결을 먼저 잡지 않으며 열린 idle in transaction도 없었다.
- 커밋 전에는 그래프·소유권·멱등성 행이 모두 없었고 커밋 후에는 세 행이 유지됐다. 별도 Store 인스턴스에서 같은 키로 최초 결과를 회수하고 업무 콜백이 다시 호출되지 않음을 확인했다. 자원 표본은 HTTP context와 실제 저장 경계를 연결하는 시험용 처리기이며 도구별 인자 변환·전체 서버 조립 인수를 대신하지 않는다.
- `check-go.sh`: 의존성 확인·전체 go build·go vet·gofmt 통과. 변경 문서 10개·로컬 링크/앵커 351개·Markdown fence와 124개 작업 중 완료 67개·미착수 57개를 검증했고 DOX pass를 수행했다.

모듈 시험 명령은 다음과 같다. DB 명령은 격리된 TEST_DATABASE_URL과 TEST_DATABASE_REQUIRED=1로 실행했다.

```sh
go test -race -json -count=1 ./internal/mcp
go test -race -json -count=1 -run '^TestMCP08' ./internal/authz
go test -timeout=180s -race -json -count=1 -run '^Test(MCP08.*|MCP02ProtectedTLSIntegration|MCP06ProtectedWriteTLSIntegration|PackageDependenciesMatchDesign)$' ./cmd/server
go test -timeout=180s -race -json -count=1 -run '^TestMCP08.*$' ./internal/store
```

초기 도메인 오류 표본의 위반 필드 JSON 키 기대값을 수정하고 MCP 모듈을 재검증했다. 최초 형식 검사에서 시험 파일 하나의 import 정렬을 발견해 gofmt 후 전체 정적 검사를 다시 통과했다. 초기 실패를 통과 수에 포함하지 않았다.

DB 시험은 임의 이름의 suite DB에 정식 마이그레이션을 적용했다. 서버는 시험별 자식 DB, 저장소는 suite의 합성 자료를 사용했으며 소유 DB 정리와 suite 부재를 확인했다. 개발 DB·볼륨·적용 이력은 유지했다.

## 남은 범위와 DOX pass

단일 JSON 응답의 원격 단절을 즉시 감지한다고 보장하지 않는다. 단절 표본도 서버 마감으로 정리할 수 있으며 HTTP 반환 시점과 DB 정리 완료 시점은 다를 수 있다. 연결·예약·읽기 자리 회복은 해당 자원 표본에서 직접 확인한 범위다. context를 무시하는 의존성·전체 운영 부하·외부 제공자·전체 서버·실제 호스트 인수로 확대하지 않는다.

기동 경로 전체 조립은 ARCH-06·07, 전체 스냅샷·서버 계약은 MCP-09·TEST-07, 실제 호스트는 TEST-08의 범위다. main에 임시 처리기를 넣어 /mcp를 활성화하지 않았다.

소유 SDD·개발 계획·검토·상태 진입점·README와 요청/근거 기록을 갱신했다. 새 패키지·소유권·요구사항·프로젝트 용어·물리 스키마·배포 키가 없어 DOX 색인·SRS·용어집·마이그레이션·환경 예시는 유지했다. 사용자 Compose·IDE 변경을 보존했고 pull·commit·push·PR 갱신·배포는 하지 않았다.
