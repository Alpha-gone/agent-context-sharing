# #159 진단 회전·정리의 전역 잠금 비용

- 대상: [이슈 #159](https://github.com/Alpha-gone/agent-context-sharing/issues/159).
- 기준: `dev`의 `a16d10b`, 작업 브랜치 `perf/159-diagnostic-retention-lock`.
- 2026-10-30 구현·인수를 진행한 뒤 2026-10-31 재개하여 결과·원격 상태를 확인하고 마무리했다.

## 변경과 안전 경계

검사한 회전 파일의 요약을 device/inode·크기·나노초 mtime/ctime과 다음 이벤트 만료 경계로 재사용한다. 파일을 열 때의 경로·권한·소유·단일 링크 검사는 생략하지 않는다. 활성 파일·새 파일·변경된 파일·만료 경계에 도달한 파일은 재검사하고, 캐시를 최대 저장소 항목 수로 제한하며 삭제/사라진 파일의 항목을 제거한다. ctime의 나노초 성분이 0이면 보수적으로 캐시를 저장하지 않는다.

캐시 미스 회전 파일은 로컬 gate와 열린 fd를 유지한 채 전역 잠금을 양보하고 JSON을 해석한다. 기존 1초 예산으로 재획득한 뒤 자기 저장소 경로 결합과 읽은 파일/디렉터리의 정체성·크기·수정/변경 시각을 다시 검증한다. 읽는 중 바뀐 요약은 해당 파일만 최대 3회 재개방해 검증하며, 계속 변하면 실패한다. 열기 전에 이미 압축된 파일은 현재 fd 크기로 검사하고 sourceSize를 압축 호출부에도 전달한다. 재획득에 실패한 회차는 잠금 없이 변경을 계속하지 않는다. 다른 기록자가 정상 퇴거한 파일/표식은 저장소·잠금·활성 파일·인스턴스 경로와 해당 basename 부재를 다시 확인한 경우에만 건너뛴다.

저장량 예약·삭제·교체·유효 행 복사는 기존 전역 잠금 안에서 수행한다. 따라서 불변 회전 파일 총량을 반복 해석하는 잠금 비용은 제거했지만, 바뀐 파일의 실제 압축·파일 시스템 I/O에 절대 지연 상한을 보장하는 변경은 아니다. 메타데이터 캐시는 기존 파일 시스템의 일관된 시각/정체성과 소유권·잠금 계약을 전제로 하며 내용 해시를 대신하는 새 저장 형식은 아니다.

[관측성 정본](../sdd/observability.md#회전보존과-총상한)에 재사용·무효화·잠금 양보/재검증 계약을, [공급자 근거](../reference.md#2026-10-31-159-진단-회전-파일의-검사-재사용)에 파일 상태·flock 의미를 유지했다. 측정은 로컬 gate 아래의 해석 대상 바이트와 연속 잠금 점유 계측을 사용하며 공개 API·구성·스키마·DOX 소유권/색인은 바뀌지 않았다.

## 약 1 GiB 볼륨 인수와 대조

Go 1.27.1, 기존 고정 arm64 Linux 이미지 `sha256:2b6d51048c03dae147064683f5b078690f1525365d561fd80b78f74de8c3c697`, 외부 네트워크 없는 별도 Docker 볼륨을 사용했다. 두 인스턴스·여섯 종류별 8개 회전 파일, 합계 1,005,060,096바이트(958.5 MiB, 1 GiB 상한의 약 93.6%)를 구성했다. 각 행은 개행 포함 16 KiB의 유효한 합성 JSON이다. 두 인스턴스의 회전·기록 후 새 상관 식별자의 행이 종류별로 정확히 3개씩 남는지 대조했다.

캐시 조회와 잠금 양보만 제거한 소스 호환 Go overlay로 기존의 전체 재해석/연속 잠금 동작을 대조했다. 같은 고정 파일 수·총량에서 다음 표본을 얻었다. 해석량은 성공한 전체 행 검사에 전달한 바이트이며 물리 장치 I/O 측정치로 확대하지 않는다.

- 대조: 초기 검사 합계 643.908ms, 최대 연속 잠금 323.867ms. 이후 두 인스턴스의 정리 10회는 3.197초, 재해석 10,050,600,960바이트로 회귀 기준에 실패했다.
- 최종: 초기 검사 합계 643.605ms, 최대 연속 잠금 2.516ms. 같은 정리 10회는 12.508ms, 불변 회전 파일 재해석 0바이트였다.
- 최종 동시 기록/회전: 두 인스턴스가 각각 12개 후속 이벤트를 기록하는 구간은 최대 60.086ms였고, 준비 기록을 포함한 새 이벤트 총 36개를 모두 확인했다. 정리/기록 단계의 최대 연속 잠금은 6.091ms, 추가 해석은 새 회전/활성 파일 38,032바이트에 한정됐다. storage_lock_timeout이나 기록 오류는 없었다.

위 수치는 특정 로컬 표본이다. 캐시가 없는 첫 검사 자체의 총 해석 시간은 남지만, 그 동안 전역 잠금을 계속 보유하지 않는다. 실제 압축·퇴거·동시 변경량·마운트가 달라지면 수치는 달라질 수 있다.

## 회귀와 정적 검증

- macOS 진단 전체 `go test -race -count=1 -json ./internal/diagnostic`: 207건 통과, 23.620초. DB 실행권 시험 1건은 TEST_DATABASE_URL 미설정으로 건너뜀.
- 최종 `internal/diagnostic/test-linux.sh`: 모듈 216건 통과, 읽기 전용 마운트 1건·컨테이너 first/restart/replacement 각 1건 통과. DB 실행권 1건과 자식 helper 직접 실행 1건은 건너뜀이다. helper는 기존 ENOSPC·EMFILE 부모 사례에서 실행했다.
- 같은 길이 덮어쓰기 후 mtime 복원, inode 교체, 손상 추가, 권한 변경의 캐시 무효화/거부와 만료 경계의 재검사·유효 행 보존·삭제 캐시 정리를 검증했다. 잠금 양보 중 다른 인스턴스 기록, 재획득 취소와 이후 다른 인스턴스의 잠금 사용, 잠금/활성 파일 바인딩 실패와 정상 퇴거의 구분, 다른 기록자가 압축한 파일의 이전 크기 스냅숏 처리도 통과했다.
- Go 1.27.1 `go build ./...`, `go vet ./...`, `gofmt -l .`, `git diff --check` 통과. 재개 후 build·vet·포맷·diff를 다시 확인했다. 건수에는 하위 사례를 포함한다.

예비 대용량 시험의 반복문 구문 오류를 바로잡고 최종 전체 인수를 실행했다. 최종 Linux 결과는 `acs-obs08-results-6zw8D3`, 대조 결과는 `acs-obs08-results-pk5r8o`, macOS JSON은 `/private/tmp/acs-159-macos-final.json`에 보관했다. 스크립트는 성공·대조 실패 모두 자신이 만든 자원만 정리했으며 재개 시 해당 시험 컨테이너·볼륨의 잔류가 없음을 확인했다. 기존 개발 자원·개인 IDE 파일 두 개는 보존했다. 실제 운영 볼륨이나 DB는 변경하지 않았다.

## 독립 검토 보완

읽기 전용 독립 검토에서 일반 ENOENT 예외가 checkBindings의 잠금/활성 파일 손실을 숨길 수 있는 경로를 발견했다. 정상 회전 파일 부재만 좁은 sentinel로 구분하도록 수정하고, 잠금·활성 파일 손실은 실패한다는 회귀를 추가했다. 다른 기록자가 먼저 표식을 퇴거하거나 이후 순회할 파일을 압축한 정상 경합도 안전한 no-op·현재 fd 크기 전달·파일별 재개방으로 보완했다. Retention race 회귀와 영향 구간 재검토를 거쳤으며 추가 Critical/Important 발견 사항은 없었다. 메타데이터/잠금 전제를 어긴 환경·운영 배포·절대 I/O 시간 보장은 검토 범위 밖으로 명시했다.
