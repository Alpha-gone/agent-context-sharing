# #182 WAL 보관 명령의 재보관·원자성 계약

## 결정과 변경

개발·운영·PITR 시험 구성의 `archive_command`는 `test ! -f .../%f && cp %p .../%f`였다. 이 명령은 같은 이름의 보관본이 있으면 내용이 같아도 실패했다. 그래서 복사 뒤 `.done` 기록 전에 중단된 WAL을 다시 보관할 때 영구 실패하여 `pg_wal`이 계속 커질 수 있었다. 또 `cp`는 원자적이지 않고 fsync하지 않아 부분 파일이 보관본 이름으로 남을 수 있었다.

공용 DB 이미지에 `docker-wal-archive.sh`를 `/usr/local/bin/agent-context-wal-archive`로 넣고 세 구성이 `archive_command=/usr/local/bin/agent-context-wal-archive %p %f`를 사용하게 했다. [PostgreSQL 18 연속 보관](https://www.postgresql.org/docs/18/continuous-archiving.html)의 계약을 따른다.

- 같은 이름의 보관본이 있으면 `cmp`로 대조한다. 같으면 파일·디렉터리를 fsync하고 0을 반환한다. 다르면 기존 보관본을 바꾸지 않고 사유를 stderr에 남긴 뒤 실패한다.
- 새 보관본은 같은 디렉터리의 `.{WAL}.partial`에 복사·fsync한 뒤 하드 링크(`ln`, 대상이 있으면 실패)로 공개하고 디렉터리를 fsync한다. 공개 경쟁에서 대상이 먼저 생기면 같은 내용 대조로 판정한다. 같은 WAL의 이전 임시 파일은 다음 시도가 지운다.
- 이전 명령이 이미 남긴 부분 보관본은 내용 불일치로 거부된다. 자동으로 덮어쓰지 않고 [운영 매뉴얼](../../../../OPERATIONS.md)에 확인 절차를 적었다.

[운영 설계](../sdd/operations.md)에 보관 명령 계약과 정적 검사 범위를, [시험 설계](../sdd/testing.md)에 검증 항목을 추가했다. 요구사항·추적표·DOX의 소유권과 구성은 바뀌지 않아 유지했다. 새 스크립트는 루트 DOX가 소유하는 공용 이미지·기동 래퍼 경계 안에 있다.

## 검증

- `test-wal-archive.sh`에 계약 검사를 추가했다. 결과: `contract: same_content=accepted different_content=rejected partial_removed=true rearchive_failed=0`.
  - 같은 이름·같은 내용의 재보관은 성공했다. 같은 상황에서 기존 명령은 실패했다.
  - 다른 내용의 재보관은 거부되었고 기존 보관본의 SHA-256은 그대로였다.
  - 남은 임시 파일은 정리되었다.
  - 보관된 WAL의 상태 파일을 `.done`에서 `.ready`로 되돌려 `.done` 기록 전 중단을 재현했다. PostgreSQL이 같은 WAL을 다시 보관했고 `archived_count`는 늘고 `failed_count`는 늘지 않았다.
  - 기존 새 볼륨·기존 볼륨·보관 재개·WAL 재활용·보관본 정리 검사도 모두 통과했다(92초).
- `test-pitr.sh`: 새 명령으로 보관한 WAL로 물리 백업·manifest/WAL 검증·손상 거부·목표 일시 정지·승격·전체 감사가 통과했다.
- `test-prod-compose.sh`: 운영 구성의 보관 명령, 세 구성의 명령 일치, 이미지 포함을 확인한다. HEAD의 이전 구성은 이 일치 검사에서 거부됨을 확인했다.
- `test-dev-compose.sh` 정적·`--runtime`, `test-prod-runtime.sh` 격리 기동이 모두 통과했다. 개발 정적 검사의 기대 명령도 새 명령으로 바꿨다.
- 모든 실행은 자기 Compose 프로젝트의 컨테이너·볼륨·네트워크·이미지만 만들고 정리했다. 기존 개발·운영 DB와 보관본은 변경하지 않았다.
- 실제 호스트·컨테이너 강제 종료 중 보관은 재현하지 않았다. 상태 파일 되돌림으로 같은 재보관 경로를 확인했다.
