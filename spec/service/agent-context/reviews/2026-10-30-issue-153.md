# #153 진단 파일 회전 실패 후 복구

- 대상: [이슈 #153](https://github.com/Alpha-gone/agent-context-sharing/issues/153).
- 기준: `dev`의 `1aa5d15`, 작업 브랜치 `fix/153-diagnostic-rotation-recovery`.

## 변경과 근거

회전 중 close 이후 활성 핸들을 잃으면 해당 종류의 다음 append에서 공유 잠금 아래 다시 연다. rename 실패로 basename이 남으면 기존 안전성 검사와 append 방식을 사용한다. 생성이 필요한 경우 파일 개수·저장량을 먼저 예약하고 파일·디렉터리를 sync한다. 부분 행 복구보다 먼저 핸들을 복구하며, 기존 누락·원인과 stderr 집계는 유지한다.

Close 오류에서도 닫힌 핸들을 맵에 남기지 않는다. Go 1.27.1 SDK의 `src/os/file_posix.go`에 있는 File.Close 계약과 `src/os/file_unix.go` 구현에서 Close 이후 핸들의 재사용 불가를 확인했다. 누락된 한 종류 때문에 여섯 종류 전체를 거부하던 개수 검사를 제거하고, 정리에서는 핸들이 없는 자기 활성 파일을 건너뛰어 해당 종류의 append 복구에 맡긴다. 경로 안전성·잠금·용량 검사 실패를 무시하지 않는다.

## 검증

- 수정 전 두 구현 파일을 `go test -overlay`로 대조한 `TestRotationRecoveryWithExistingActive`의 `reopen_failed`·`close_failed`는 모두 다른 종류의 `file_unavailable`로 실패했다. 수정 후 기존 행 보존·다른 다섯 종류 기록·동일 종류의 복구를 확인했다.
- Linux의 `internal/diagnostic/test-linux.sh` 전체 인수는 고정된 기존 arm64 이미지에서 통과했다. 모듈 178건, 읽기 전용 마운트 1건, 컨테이너 first/restart/replacement 각 1건이 통과했다. 건수는 하위 사례를 포함한다. DB 실행권 시험 1건은 환경 미설정으로, 새 자식 전용 helper의 직접 실행 1건은 의도적으로 건너뛰었다. helper는 ENOSPC·EMFILE 부모 사례에서 각각 실제 실행했다.
- 새 Linux 시험은 자식 프로세스에만 seccomp를 설치해 회전 디렉터리 fd의 exclusive 생성에 실제 ENOSPC·EMFILE을 반환한다. 검증된 slot fd를 통한 복구는 허용한다. 두 경우 모두 수락 7건·기록 6건·누락 1건과 기존 원인 보존·stderr 알림, 종류별 파일의 기존/후속 행을 확인했다. 호스트 전체 디스크나 fd를 소진하지 않았다.
- macOS `go test -race -count=1 -json ./internal/diagnostic`: 170건 통과, DB 실행권 시험 1건 환경 미설정으로 건너뜀, 패키지 21.223초. 실패 없음.
- Go 1.27.1의 `go build ./...`, `go vet ./...`, `gofmt -l .`과 `git diff --check` 통과.

예비 실행의 Filename 반환형 컴파일 오류와 알림 필드명 검사를 보완했다. 이를 최종 통과로 집계하지 않았다. Linux 결과는 `acs-obs08-results-AECDCb`, macOS JSON은 `/private/tmp/acs-153-macos.json`에 보관했다.
