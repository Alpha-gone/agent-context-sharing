# #189 원천 중복 판정의 인덱스 사용

- 대상: [이슈 #189](https://github.com/Alpha-gone/agent-context-sharing/issues/189).
- 기준: `dev`의 `5ea51c2`, 브랜치 `perf/189-source-reference-index`.

## 원인과 변경

`findSourceWith`의 openCypher 속성 접근은 `agtype_access_operator`로 번역되어 `properties ->>` 표현식인 기존 원천 부분 유일 인덱스와 일치하지 않았다. 같은 label을 공유하는 다른 그래프의 Context 정점까지 순차 탐색했다.

기존 `context_source_ref_idx`와 같은 SQL 식으로 그래프·locator를 바인딩하고 layer=source를 고정한다. 조회한 property를 고정 Context 외피에 넣어 기존 `parseContext`의 그래프·형식 검증을 재사용한다. ErrNotFound와 context_query/context_decode 오류 분류, UTF-8·NUL의 불일치 처리, 폐기 원천의 중복 반환을 유지한다. 생성 트랜잭션의 선조회와 23505 뒤 새 트랜잭션의 재조회가 같은 helper를 계속 사용한다. 새 인덱스·마이그레이션·환경 변수는 추가하지 않았다.

[데이터 인덱스](../sdd/data.md#인덱스)와 [시험 설계](../sdd/testing.md#테스트-계층)에서 실제 사용 질의와 검증 범위를 정합화했다. DOX pass에서 구조·소유권·색인이 바뀌지 않아 기존 DOX를 유지했다.

## 실행 계획 대조

Go 1.27.1, 별도 합성 PostgreSQL/AGE 컨테이너의 고정 로컬 이미지 `sha256:2b6d51048c03dae147064683f5b078690f1525365d561fd80b78f74de8c3c697`를 사용했다. 대상 그래프에 원천 1,000개와 조회 원천 1개, 다른 그래프에 원천 1,000개 또는 10,000개와 같은 locator의 원천 1개를 넣고 ANALYZE했다. 독립 DB를 쓰며 운영·개발 DB나 기존 적용 이력을 변경하지 않았다.

`indexPlanQueryer`가 실제 helper의 QueryRow SQL과 인자를 수집하고 `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)`로 실행한다. 인덱스·플래너 선택을 강제하지 않는다. 수정 전 대조는 기준 commit의 context.go를 Go overlay로 적용하여 같은 표본·시험을 실행했다.

- 2,002행 표본의 활성/미존재/폐기 조회: 기존 Seq Scan 2,002행·143~144 shared buffers·1.058~1.121ms. 변경 후 context_source_ref_idx Index Scan 0~1행·2~3 buffers·0.007~0.024ms.
- 11,002행 표본: 기존 Seq Scan 11,002행·786 buffers·3.814~4.137ms. 변경 후 같은 Index Scan 0~1행·3~4 buffers·0.006~0.011ms.
- 최초 대상 그래프가 한 행뿐인 예비 표본에서는 변경 후 더 작은 graph_id 인덱스로 1행을 읽었다. source_ref 복합 인덱스의 사용을 검사하는 최종 표본은 대상 그래프의 1,000개 원천을 고정하고 다른 그래프만 늘린다.

지연은 해당 로컬 환경의 단일 실행 표본이며 운영 지연 보장으로 확대하지 않는다. 주된 완료 근거는 전체 Context 읽기가 없어지고 인덱스 접근으로 0~1행만 읽는 실제 계획이다.

## 회귀와 검토

- 수정 전 활성·미존재·폐기 × 두 크기의 6개 계획 검사가 전체 순차 탐색으로 실패했다. 수정 후 관련 DB/race 153건이 실패·건너뜀 없이 통과했다.
- 같은 locator의 타 그래프 원천을 분리하고 apostrophe·dollar-quote 토큰이 포함된 locator를 그대로 비교했다. 폐기 여부·원래 식별자·본문·locator 및 없음 결과를 대조했다.
