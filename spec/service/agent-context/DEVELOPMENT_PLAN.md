## 목적

이 문서는 `SRS.md`의 기능 요구사항 149건과 비기능 요구사항 13건을 `SDD.md`의 패키지 경계, 처리 흐름, 데이터 모델, 인터페이스와 테스트 전략에 따라 구현하는 순서를 정의한다.

일정이나 담당자는 정해진 입력이 없으므로 추정하지 않는다. 각 단계는 선행 조건과 완료 기준을 충족한 뒤 다음 단계로 넘어가며, 작업을 시작하거나 완료할 때 해당 체크박스를 현재 상태와 일치하도록 갱신한다.

## 개발 원칙

이 절은 한 번 끝내고 표시하는 작업이 아니라 모든 변경에 적용하는 규칙이다. 그래서 체크박스를 두지 않는다. 규칙을 지켰는지 장치로 확인할 수 있는 둘은 10단계의 검증 항목으로 두었다.

- 구현은 `SRS.md`와 `SDD.md`의 확정된 계약을 따른다.
- 설계와 다른 구현이 필요하면 구현 전에 `SDD.md`를 갱신하고 승인받는다.
- 요구사항 수준의 변경이 필요하면 `SRS.md`를 먼저 갱신하고 승인받는다.
- `SDD.md`가 정한 열 개 패키지 경계와 단방향 의존을 유지한다.
- 데이터베이스 연결과 질의 실행기를 `store` 밖으로 노출하지 않는다.
- 그래프 데이터 접근 함수는 `graph_id`를 필수 인자로 받고 응답 전에 격리를 재검사한다.
- 비그래프 기준선을 먼저 구현한 뒤 그래프 기능을 단계별로 추가해 효과를 비교한다.
- 접근 토큰, 세션 쿠키, 비밀번호, 비밀번호 해시와 컨텍스트 `body`를 운영 로그에 남기지 않는다.
- 요구사항에 없는 확장 지점, 설정, 외부 의존성과 범용화를 추가하지 않는다.
- 단계별 구현·테스트·문서화·DOX 검증이 모두 끝나야 해당 단계를 완료한다.

## 패키지 의존 순서

```text
      model
        ↓
       plan
        ↓
      store
        ↓
perm · authz · index · search
        ↓
      mcp · web
```

`perm`과 `search`는 필요한 기능을 인터페이스로 받으므로 `store`를 타입으로 의존하지 않는다. 실행 시점의 호출 방향은 그림과 같고, 두 패키지의 단위 테스트가 데이터베이스 없이 도는 것이 그 결과다. 같은 이유로 `search`는 `index`를 부르지 않고 질의 임베딩을 인터페이스로 받는다.

`store`가 `plan`을 부르는 이유는 누적 한도를 값이 늘어나는 트랜잭션 안에서 판정해야 하기 때문이다. 근거는 `SDD.md`의 「패키지 경계」에 있다.

`config`는 조립 시점에 각 패키지로 값을 주입하고 실행 중인 업무 패키지를 호출하지 않는다. 예외는 `plan` 하나이며, `ACCOUNT_PLAN_LIMITS`의 계정별 플랜 값을 기동 전에 해석하고 검증하려면 항목 정의를 소유한 패키지가 필요하기 때문이다. 마이그레이션 실행기는 애플리케이션의 열 개 패키지 밖에 두며 `store`를 통하지 않는다.

## 4단계: MCP 전송 계층과 핵심 CRUD

### 목표

### 현재 진행 상황

2026-09-12 기준으로 `/mcp` POST 경로와 보호 리소스·인가 서버 discovery 문서를 서버 조립 경로에 연결했다. 리소스 서버 URL, 인가 서버 URL과 허용 Origin은 요청 `Host`가 아닌 배포 구성으로 고정해 토큰 `aud`, JWT `iss`와 metadata 문서가 프록시 또는 조작된 헤더에 따라 바뀌지 않게 했다. 전송 계층은 `Origin`→메서드→필수 MCP 헤더→헤더·본문 대조→protocol revision→RPC 메서드 순서로 검증하고, `tools/call`의 `Mcp-Name`도 본문과 대조한다. 토큰이 없거나 `Basic`처럼 Bearer 형식이 아닌 인증 헤더가 오면 `401` 및 보호 리소스 메타데이터를 가리키는 `WWW-Authenticate`를 반환하고, Bearer 형식으로 제시된 토큰의 검증 실패는 `unauthenticated` 도구 결과로 처리한다. `tools/list`는 인증을 거쳐 최상위 `tools` 필드에 13개 도구의 이름·설명·완전한 `inputSchema`를 반환한다. `tools/call`은 웹 전용 삭제·권한·팀 관리 요청을 입력 검증보다 먼저 `not_supported`와 대체 채널로 처리하고, 나머지 요청은 입력 형식·길이·개수 상한을 다시 검증한 뒤 호출 처리기로 분배한다.

그래프·노드 CRUD 처리기를 구현해 호출 분배에 연결했다. `graph_create`는 그래프 행 생성과 생성 계정의 소유자 등급 부여를 한 트랜잭션으로 묶고, 노드 쓰기 연산은 정점·참조 간선 변경, 색인 작업 등록, 그래프 활동 갱신, 관리 연산 기록을 같은 트랜잭션에 둔다. `node_discard`는 폐기한 컨텍스트를 근거로 가리키는 파생에 무효 표시를 한 단계만 전파하고, `node_restore`는 연산으로 폐기된 컨텍스트만 복구하며 웹 삭제분은 웹 대체 채널로 안내한다. 원천 중복은 기존 원천을 그대로 반환하고 새 기록·활동 갱신을 만들지 않으며, 거부된 관리 연산은 트랜잭션 밖에 거부 시점 대상 판 번호로 기록한다. `relation_list`·`relation_confirm`·`relation_discard`·`context_flow_get`은 아직 처리기가 없어 `not_supported`로 응답하며 5~7단계에서 구현한다.

### 공통 검증 명령

아래 명령은 IntelliJ IDEA에 설치·등록된 프로젝트 Go SDK 1.27.1을 선택한 실행 구성 또는 해당 SDK를 사용하는 IDE 통합 터미널에서 실행한다. 기본 셸의 `PATH`에 `go`가 없어도 IntelliJ IDEA의 Go SDK를 사용하며, SDK 버전이 `1.27.1`인지 먼저 확인한다.

```shell
go version
go test ./...
go build ./...
go vet ./...
gofmt -l .
```

데이터베이스가 필요한 테스트는 다음 환경 변수를 사용한다. 지속 통합에서는 `TEST_DATABASE_REQUIRED`를 설정해 조용한 건너뛰기를 금지한다.

```text
TEST_DATABASE_URL=<테스트 데이터베이스 접속 정보>
TEST_DATABASE_REQUIRED=1
```

로컬에서도 `.env`를 현재 셸에 내보내면 실제 AGE 통합 테스트를 강제할 수 있다.

```shell
set -a
. ./.env
set +a
TEST_DATABASE_URL="${TEST_DATABASE_URL:-$DATABASE_URL}" \
TEST_DATABASE_REQUIRED=1 \
go test ./...
```

마이그레이션 검증은 빈 개발 볼륨에서 시작한다.

```shell
docker compose down -v
docker compose up -d --build
go run ./cmd/migrate up
go run ./cmd/migrate up
```

## 단계 간 병렬화

진행 방식을 정한 규칙이므로 체크박스를 두지 않는다.

- 1단계의 `model` 계약과 2단계의 `store` 공개 계약이 안정된 뒤 `authz`·`perm`과 `index` 기반 작업을 병렬로 진행한다.
- MCP 전송 계층은 도메인 오류 타입과 인증 미들웨어 계약이 정해진 뒤 CRUD 구현과 병렬로 진행한다.
- 웹 화면 골격은 인증·권한 계약이 안정된 뒤 만들되 실제 데이터 연결은 해당 업무 연산 완료 후 수행한다.
- 주기 작업은 각 대상 상태 전이가 구현된 순서대로 추가하고 9단계에서 다중 인스턴스 동작을 통합 검증한다.
- 검색 품질 데이터셋과 평가 자동화는 6단계의 비그래프 기준선이 완성되는 시점부터 검색 구현과 병렬로 진행한다.

## 변경 단위 원칙

모든 변경에 적용하는 규칙이므로 체크박스를 두지 않는다.

- 하나의 이슈나 변경은 하나의 검증 가능한 목적을 갖게 한다.
- 스키마 변경은 `SDD.md`를 먼저 갱신하고 새 마이그레이션으로 추가한다.
- 초기 스키마가 안정되기 전 `001_init.sql`을 고치면 개발 볼륨을 지우고 처음부터 검증한다.
- 기존에 적용된 마이그레이션의 체크섬을 임의로 바꾸지 않는다.
- 각 변경에서 관련 단위 테스트와 데이터베이스 테스트를 함께 작성한다.
- 구현 변경마다 빌드, 정적 검사, 형식 검사와 DOX pass를 수행한다.
- 관련 없는 리팩터링, 설정과 의존성 변경은 별도 작업으로 분리한다.
