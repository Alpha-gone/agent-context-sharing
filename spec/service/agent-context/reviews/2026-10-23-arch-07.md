## 변경과 책임

기존 서버는 웹 경로를 `/`로 포괄 위임하여 미등록 POST도 웹 출처 검사에 들어갔고, 일부 상태 경로의 미지원 메서드는 404였다. 상태·공개 키·발견·OAuth·MCP·웹·내장 자산의 24개 경로를 ServeMux에 명시하고 메서드별로 등록했다. 등록 경로의 미지원 메서드는 405/Allow, 미등록 경로는 웹 세션·출처 검사 전에 no-store 404를 반환한다. 미지원 상태 확인 POST도 HTTPS에서 405이며 평문에서는 400이다. TLS 판정은 라우터의 메서드 안내·경로 정규화보다 먼저다.

- 정확한 상태 확인 GET·HEAD만 TLS 예외다. Go GET 패턴의 암묵적 HEAD가 기존 웹 계약을 넓히지 않도록 웹 HEAD를 명시적으로 거부한다. 공개 키·발견·자산의 HEAD는 유지한다.
- 기존 GET 로그아웃 확인·POST 그래프 복구 요청, `/access`·`/connections`·공개 자산 허용 목록을 SDD 경로 표에 보완했다. 실제 업무·세션·출처 처리는 기존 web을 사용하며 MCP Origin 우선 검사·Bearer 도전·오류 외피와 토큰의 OAuth 메서드 오류를 유지한다.
- 기존 서버 발급 상관 ID를 응답·진단·모델 context에 공유한다. 외부 상관 헤더·Host·전달 Host를 내부 ID나 공개 issuer로 채택하지 않는다.
- 기존 MCP 예산 구현을 공통 요청 예산으로 재사용하여 전체 경로에 30초 context·수신 읽기 마감을 연결했다. 더 짧은 상위 마감·취소를 보존하고 사전 취소는 업무를 시작하지 않으며 반환 뒤 context를 정리한다. 본문은 먼저 해석하지 않고 공통 10 MiB MaxBytesReader 아래 채널별 8 KiB·64 KiB·4 MiB가 더 좁게 제한한다.
- 응답이 없는 예산 소진·마감 설정 실패는 no-store 500이며 토큰·MCP는 server_error, 나머지는 internal_error 상태 본문이다. 이미 시작한 상태·본문은 덧쓰지 않는다. 읽기 마감이 context 타이머보다 먼저 깨어나는 경우도 같은 예산 소진으로 처리한다.
- 소켓 읽기 마감은 net/http가 응답 뒤 잔여 본문 정리와 다음 요청까지 관리하게 한다. 처리기 반환 시 마감을 지우면 자동 drain이 미완성 본문을 기다릴 수 있어 해제하지 않는다. 새 환경 키·DB 스키마·외부 의존성은 추가하지 않았다.

## 실행과 증거

Go 1.27.1·macOS arm64에서 실행했다. DB 시험은 TEST_DATABASE_URL·TEST_DATABASE_REQUIRED를 함께 사용하고 새 빈 시험 DB·정식 마이그레이션·자기 자원 정리를 적용했다. provider는 검증을 유지한 로컬 TLS 수신기로 구성했으며 이 HTTP 진입점 표본에서 임베딩 호출은 없음을 확인했다.

| 범위 | 실행 | 결과 |
|---|---|---|
| 공통 HTTP 모듈·전송 회귀 | `go test -race -json -p=1 -count=1 -timeout=180s -run '^(TestARCH07\|TestMCP08RequestBudget\|TestMCP08SlowBody\|TestOPS03\|TestStatus\|TestHealth\|TestTransport\|TestRequestLog\|TestPublicKey)' ./cmd/server` | **382건 통과**. 마지막 keep-alive 표본 추가 전 실행 |
| 서버 패키지 전체 | `go test -race -json -p=1 -count=1 -timeout=180s ./cmd/server` | **573건 통과**, 신규 ARCH-07 **204건 포함** |
| 공통 정적 검사 | `GO_BINARY=/Users/alphagone/sdk/go1.27.1/bin/go GOCACHE=/private/tmp/acs-obs02-go-cache sh ./check-go.sh` | 의존성 검증/빌드·전체 build·vet·gofmt 통과 |

최종 서버 전체의 실패·건너뜀·race 오류는 0이다. 건수는 상위 시험·하위 사례의 pass 이벤트 합계이며 모듈 표본을 전체에 다시 더하지 않는다. 원시 결과는 `/private/tmp/acs-arch07-server.json`·`/private/tmp/acs-arch07-server-full.json`에 남겼다.

1. 실제 조립·DB·TLS 수신기의 24개 경로에 GET·HEAD·POST·PUT·DELETE·OPTIONS를 보내 상태·Allow·캐시·서버 UUIDv7·HEAD 빈 본문을 대조했다. 같은 경로/메서드의 평문 요청은 상태 확인 예외 외에 본문·메서드 안내·리디렉션·쿠키 없이 먼저 거부됐다. 신뢰 프록시·위조/중복 전달 헤더·경로 정규화는 기존 OPS-03 실제 수신 회귀도 포함한다.
2. 공격자 Host·전달 Host에서도 발견 응답은 구성의 고정 issuer를 유지했다. 실제 계정·웹 세션으로 연결 목록을 조회했다. 전체 서버 회귀에는 기존 OAuth·Bearer·14종 MCP 조립·embedded/external 프로세스·기동/종료 시험이 포함된다.
3. 관찰 가능한 본문을 사용해 평문→MCP Origin→메서드→선언/실제 바이트→Bearer→JSON 순서를 대조했다. 미등록·알 수 없는 자산/그래프 하위 경로의 교차 출처 POST는 404이고 읽지 않았다. 선언 초과는 읽기 전에, 길이 미상 초과는 제한된 읽기 뒤 413이며 인증 없는 잘못된 JSON은 401이다. 일반 관리 양식은 10 MiB+1바이트에서 멈추고 기존 400을 유지했다.
4. 하위 준비 확인에 전달된 context의 마감·진단/모델 상관 ID와 반환 후 취소를 직접 관찰했다. 실제 TLS 클라이언트의 취소가 준비 확인에 전파되고 후속 healthz가 성공했다. 시간 예산·읽기 마감 설정 실패·시작한 응답 보존·채널별 안전한 500도 대조했다.
5. 프록시 경계의 실제 TCP 수신에서 미완성 토큰 본문을 보내 40ms 시험 예산으로 읽기가 중단되고 안전한 500을 반환함을 확인했다. 다른 TLS 시험은 요청 완료 뒤 해당 40ms보다 오래 기다렸다가 같은 keep-alive 연결을 재사용하여 서버가 다음 요청의 마감을 다시 설정함을 확인했다. 실제 기본 30초 context는 수신한 하위 context에서 관찰했으며 소켓 회귀는 같은 구현에 짧은 예산을 적용했다.

최초 샌드박스 실행은 로컬 DB 접근·포트 바인딩 제한으로 통합 시험을 수행하지 못했다. 허용된 로컬 실행 환경에서 조건을 유지해 다시 검증했다. 느린 본문 시험의 첫 실패는 읽기 마감을 해제한 뒤 net/http의 자동 drain이 기다리는 현상이었다. 마감 소유권을 위와 같이 수정하고 모듈 표본과 서버 전체를 재실행하여 통과했다. 기존 상태 POST의 기대값은 새 명시적 메서드 계약에 따라 HTTPS 404에서 405로 갱신했다.

## 제한과 정합성

- 이번 판정은 서버 HTTP 진입점과 공통 요청 모듈이다. 전체 운영 실패·작업자/풀 수명은 OPS-05, 무상태성·전체 배치 인수는 ARCH-08, 전체 도구 계약·외부 호스트는 MCP-09·TEST-08에서 이어간다. 전체 저장소 시험·Linux 실행·실제 브라우저·외부 Gemini·호스트·운영 배포를 실행하지 않았다.
- context를 무시하는 하위 코드의 강제 중단, 클라이언트 단절의 즉시 감지, 응답 쓰기 전체의 벽시계 상한은 보장하지 않는다. 수신 헤더·본문/업무·종료의 예산은 구분하며 서버 WriteTimeout은 추가하지 않았다.
- 경로·공통 마감의 정본은 아키텍처, 좁은 양식/전송/인증 순서는 각 분야 SDD를 유지했다. 계획·진입점·색인·검토·요청 기록·공식 근거를 정합화했다. DOX pass에서 기존 cmd/server 안의 변경이며 패키지/문서 소유권·지속 경계·구성 키가 바뀌지 않아 하위 DOX·부모 색인 갱신은 필요하지 않음을 확인했다.
- 기존 Compose·IDE 변경을 보존했다. 이 작업은 미커밋이며 push·배포는 수행하지 않았다.
