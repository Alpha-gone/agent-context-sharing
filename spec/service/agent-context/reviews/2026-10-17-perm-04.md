- 기준: [PERM-04](../development-plan/authorization.md#perm-04), [팀 관리](../sdd/authorization.md#팀-관리), [팀 절차](../SRS.md#권한과-팀-관리-절차), [참조 검사](../sdd/data.md#참조와-검증-책임), [판정의 직렬화](../sdd/context-lifecycle.md#판정의-직렬화), [웹 화면 계약](../sdd/web.md#웹-화면-계약).
- 시작 상태: `feat/implementation-improve`, `409295f`. upstream이 없는 로컬 브랜치이며 선행 PERM-02·LIFE-06은 완료다. 기존 Compose·IDE 변경은 보존했다.
- 범위: 팀 생성·관리자 범위 조회·구성원 변경·소프트 삭제/복구, 계정 참조와 직접/상속 접근, 다중 그래프 잠금·유예·웹 감사 원자성의 새 모듈 증거.

## 발견 사항과 구현

| ID | 영향도 | 발견 사항 | 처리·검증 |
|---|---|---|---|
| PERM04-R1 | 높음 | 팀 생성자와 추가할 구성원의 계정 존재 검사가 없어 부재 계정의 관리자/구성원 참조가 저장될 수 있었다. | 같은 저장 트랜잭션에서 실제 계정을 확인한다. 그래프 부여와 같은 의미의 참조 검사를 공유했다. 부재 생성자·구성원 거부와 팀·감사 보존을 확인했다. |
| PERM04-R2 | 높음 | 접근 계정 집계가 부재 계정의 직접·구성원 참조를 세어 유예 시작을 막거나 복구 때 유예를 취소할 수 있었다. | 직접 부여와 활성 팀 구성원을 실제 account 행과 결합해 고유 계정을 센다. 과거 잘못된 참조를 합성한 삭제·복구에서 고정 유예를 유지했다. 자동 보정·행 삭제는 추가하지 않았다. |
| PERM04-R3 | 중간 | 팀 변경의 저장 장애가 모두 400 또는 409로 표시되고 구성원 계정 조회 장애도 입력 오류로 처리됐다. | 입력 400, 대상/관리자 범위 404, 상태 409, 저장/감사/커밋 500으로 구분한다. 래핑된 오류·원문 비노출·조회 실패 시 변경 호출 차단과 그래프 없는 성공 이동을 확인했다. |

- 팀 관리자의 변경 경로는 추가하지 않았다. 생성 계정이 고정 관리자이며 자동으로 구성원이 되지 않는다. 그래프 없는 계정의 생성과 다른 관리자의 팀·구성원 제외, 정렬된 구성원 목록을 확인했다.
- 삭제된 팀의 구성원과 그래프 등급은 보존된다. 상속은 삭제 즉시 무효, 복구 즉시 유효다. 삭제 팀의 구성원을 추가해도 유예가 취소되지 않으며 실제 접근이 회복된 복구·구성원 추가에서만 취소된다.
- 기존 팀 행→ID 오름차순 그래프 잠금을 유지했다. 두 팀이 같은 두 그래프에서 마지막 구성원을 제거하거나 팀을 삭제·복구하는 3개 동시 조합을 실제 두 요청의 잠금 대기와 겹쳐 실행했다. 교착 없이 두 변경과 각 감사가 커밋됐고 최종 접근 상태에 맞는 유예를 확인했다.
- 팀 생성·구성원 추가·구성원 제거·삭제·복구의 5개 동작에 감사 삽입 실패와 지연 커밋 실패를 각각 주입했다. 10개 조합 모두 팀·구성원·등급·그래프 유예·감사 지문이 보존됐다. 구성원 추가/복구는 접근이 없는 유예 상태, 제거/삭제는 유예가 없는 활성 상태를 준비해 시작과 취소의 롤백을 각각 확인했다.
- 패키지 경계·SQL 스키마·의존성·DOX 소유권은 바뀌지 않아 해당 계약과 마이그레이션을 유지했다. 권한·웹 SDD에 실제 계정 참조와 오류 의미를 정합화했다. HTML·CSS·클라이언트 JavaScript는 변경하지 않았다.
