# #317 Go 1.27.4 보안 판올림

## 범위와 결정

- PR #315의 CI `build`가 `govulncheck`에서 실패했다. 원인은 Go 1.27.3 표준 라이브러리 `net/http`의 [GO-2026-6859](https://pkg.go.dev/vuln/GO-2026-6859)이며 2026-11-11에 공개되어 2026-11-09의 `dev` 마지막 성공 실행 뒤에 생긴 실패다. 해당 PR의 변경과 무관하다.
- 2026-11-14 사용자 승인으로 저장소 기준 Go를 1.27.4로 올렸다. `go.mod`, 빌드 이미지 태그와 다중 아키텍처 digest, `test-prod-compose.sh`의 기대값, Go 판을 고정 검사하는 `test-pitr.sh`·`test-transition.sh`와 TEST-08 시험 코드의 대상 판을 함께 바꿨다.
- 의존 모듈은 바꾸지 않았다. `go.sum`은 변경이 없다.
- 현재 기준 문서(루트 DOX·README·운영 매뉴얼·아키텍처·시험 설계·SRS·개발 계획)를 동기화했다. 과거 검토·요청 기록과 공식 근거의 Go 1.27.3 표기는 당시 결과로 보존했다. 기존 호스트 인수 결과를 Go 1.27.4의 재인수로 확대하지 않는다.
- [공식 근거](../reference.md#317-go-1274-보안-판올림-2026-11-14)를 기록했다.

## 검증

- Go 1.27.4 공식 도구 체인으로 `check-go.sh` 전체가 통과했다. 모듈 다운로드·체크섬 검증·SDK 의존성 빌드·전체 build·vet·gofmt·govulncheck를 포함하며 호출 경로상 취약점은 1건에서 0건이 되었다.
- 호출하지 않는 모듈 수준 경고 1건은 #277 때와 같이 남으며 검사 예외를 추가하지 않았다.
- `golang:1.27.4-trixie`의 index digest를 레지스트리에서 조회해 `Dockerfile.server`와 `test-prod-compose.sh`에 반영했고 `test-prod-compose.sh`가 통과했다.
- `go mod tidy -diff`에 차이가 없고 수정한 셸 스크립트 3개의 `sh -n`과 `git diff --check`가 통과했다.
- DB 없이 `go test -count=1 ./...`를 실행했다. 16개 패키지 중 14개가 통과했고 아래 2건이 실패했다. DB 통합 시험은 접속 정보가 없어 건너뛰었으며 통과로 집계하지 않는다.

## 판올림과 무관한 기존 실패

두 실패는 `dev`(68452a7)와 Go 1.27.3에서도 같은 내용으로 재현되어 이번 변경이 원인이 아니다. 이번 작업에서 고치지 않았다.

- `cmd/server`의 `TestPackageDependenciesMatchDesign`: 「설계 업무 패키지 수: 12, want 11」. #311 설계 문서가 `relinfer` 패키지를 더했고 구현은 `dev`에 아직 없다. `feat/311-relation-inference-implementation`(a6bba9c)에서는 통과한다.
- `internal/mcp`의 `TestPublicCompactionKeepsSchemaMeaning`: 「compaction changed literal/default data」로 간헐 실패한다. 10회 반복에서 Go 1.27.4는 2회, `dev`와 Go 1.27.3은 1회 실패했다. 원인은 조사하지 않았다.

CI는 `check-go.sh`만 실행하므로 이 두 시험은 CI 통과 여부에 영향을 주지 않는다.

## 제한

새 Docker 이미지의 실제 빌드와 배포는 수행하지 않았다. 레지스트리 digest, 운영 정적 검사와 같은 SDK의 전체 Go 빌드로 검증했다. 셸의 `GOROOT`가 이전 SDK를 가리키면 `GO_BINARY`를 지정해도 컴파일러 판이 섞여 실패하므로 검증은 `GOROOT`를 해제하고 실행했다. 실제 서버에서 GO-2026-6859의 panic 재현 여부는 확인하지 않았다.
