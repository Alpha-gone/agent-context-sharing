# 연결 풀 교착과 불변식 쓰기 검사 비용 결함

## 목적과 조건

- 검사일: 2026-09-28
- 목적: 12단계(`505ac0c`)부터 19단계(`70ff73b`)까지의 구현 코드를 결함 관점에서 검사하고, 확인한 결함을 `SDD.md`에 먼저 반영한 뒤 고친다.
- 데이터베이스: PostgreSQL 18.6, Apache AGE 1.8.0, pgvector 0.8.6, 로컬 Docker 개발 데이터베이스(`Context` 정점 약 2만 개, 간선 약 1만 9천 개)

## 발견 사항

| 번호 | 결함 | 도입 단계 | 상태 |
|------|------|-----------|------|
| 1 | 쓰기 멱등성 예약 트랜잭션이 연결을 쥔 채 권한·대상 조회의 풀 연결을 기다려, 동시 멱등성 쓰기가 풀 상한에 이르면 모두 멈춘다 | 18단계 | 처리함 |
| 2 | 동기화 스냅숏이 조정 연결을 쥔 채 경계 안 읽기 연결을 기다려, 동시 검색이 풀 상한에 이르면 모두 멈춘다 | 15단계 | 처리함 |
| 3 | 그래프 불변식 쓰기 검사가 영향 주변부가 아니라 모든 그래프의 간선과 `Context` 정점 전체를 해시 조인한다 | 16단계 | 처리함 |

- 1과 2는 풀 상한을 2로 둔 저장소에서 동시 요청 2건으로 재현했다. 두 요청 모두 두 번째 연결을 얻지 못하고 제한 시간에 끝났다. 서버는 요청 단위 제한 시간을 두지 않으므로 운영에서는 클라이언트가 끊을 때까지 멈추고, 같은 풀을 쓰는 웹·색인 작업자·주기 작업도 함께 멈춘다.
- 2의 기존 부하 측정(`2026-09-27-consistent-read.md`)은 로컬 임베딩 제공자가 처리량을 초당 약 9건으로 제한한 조건이라 이 상태에 이르지 않았다. 임베딩을 거치지 않는 `scope=global` 요청이나 더 빠른 제공자에서는 도달한다.
- 3은 실행 계획으로 확인했다. 쓰기 한 번의 간선 조회가 21ms였고 비용이 데이터베이스 전체 크기에 비례했다. `go test ./...` 중 이 질의가 병렬 해시 조인의 공유 메모리를 늘리지 못해 `No space left on device`로 한 번 실패했다.

## 조치

- 1·2: `SDD.md`의 「데이터베이스 연결」에 연결 예약을 정했다. 동기화 스냅숏은 4개, 멱등성 예약 트랜잭션은 2개를 시작 전에 예약하고, 예약 총량은 풀 상한에서 4를 뺀 값(최소 4)이다. 스냅숏은 경계 안 읽기 트랜잭션을 동시에 3개까지만 연다. `pool_max_conns`가 4보다 작으면 저장소를 준비하지 않는다.
- 3: `migrations/006_invariant_scope_indexes.sql`이 openCypher 속성 접근과 같은 `agtype` 표현식으로 `Context`의 `context_id`와 `PRECEDES`·`CAUSES`·`PART_OF`의 `graph_id`에 인덱스를 걸고 통계를 모은다. 쓰기 검사는 나가는 간선과 들어오는 간선을 두 질의로 나눠 읽는다.

## 검증

- 회귀 테스트 `TestConnectionReservationPreventsPoolStarvationIntegration`은 풀 상한 4에서 스냅숏 검색 8건과 멱등성 쓰기 8건을 동시에 실행한다. 예약을 켜면 1.4초에 통과했고, 예약을 끄면 20초 제한 시간에 실패했다.
- `TestReadSnapshotLimitsConcurrentReadsIntegration`은 한 스냅숏의 네 번째 경계 안 읽기가 앞선 읽기가 끝날 때까지 기다리고 동시 연결이 4개를 넘지 않는지 확인한다.
- 방향별 간선 조회의 실행 계획은 `context_context_id_agtype_idx`와 간선 label의 `start_id`·`end_id` 인덱스를 썼고 0.1~0.2ms였다.
- `BenchmarkAuditGraphIntegration`을 조건마다 20회씩 3번 반복한 결과는 아래와 같다.

| 노드 | 전체 감사 | 쓰기 한 번의 영향 주변부 검사 | 2026-09-27 쓰기 검사 |
|-----:|----------:|------------------------------:|---------------------:|
| 100 | 29.6~30.3ms | 2.4~2.7ms | 14.1ms |
| 400 | 33.8~34.8ms | 2.6~2.8ms | 16.3ms |
| 1,600 | 51.2~51.5ms | 3.1~3.2ms | 20.8ms |

- 전체 감사 경로는 바꾸지 않았다. 전날보다 값이 큰 것은 개발 데이터베이스가 커졌기 때문이며, 그래프 조건을 `OR`로 묶은 전체 감사 간선 조회는 여전히 데이터베이스 전체 크기에 비례한다. 전체 감사는 복구·마이그레이션 뒤에만 실행하므로 이번 범위에서 고치지 않았다.
- `TEST_DATABASE_REQUIRED=1 go test ./...`, `go build ./...`, `go vet ./...`, `gofmt -l .`가 모두 통과했다. 빈 볼륨이 아닌 개발 데이터베이스에서 `go run ./cmd/migrate up`이 006을 적용했고 두 번째 실행은 변경이 없었다.

## 남은 사항

- 연결 예약은 연결을 하나만 쥐고 기다리지 않는 요청을 전제로 한다. 컨텍스트 갱신·폐기의 판 번호 충돌 경로(`asVersionConflict`, `deletionConflict`)는 멱등성 밖에서도 트랜잭션을 연 채 풀에서 현재 판을 다시 읽는다. 이 경로는 12단계 이전부터 있었고 예약하지 않는 요청의 몫 4개 안에서만 겹치지만, 같은 방식으로 연결을 더 기다리는 경로다.
- 요청 단위 제한 시간은 두지 않았다. 연결 예약은 교착을 없애지만 느린 데이터베이스가 요청을 오래 붙잡는 것은 막지 않는다.
