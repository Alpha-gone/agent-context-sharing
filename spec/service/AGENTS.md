# 서비스 명세 영역

## 목적

- `spec/service/`는 서비스 색인과 서비스별 요구사항·설계·근거·요청 기록을 보관한다.

## 소유권

- `spec/AGENTS.md`가 명세 문서 공통 계약과 이 영역의 경계를 소유한다.
- 이 문서는 서비스 색인과 서비스별 문서의 공통 작업 계약을 소유한다.
- 각 서비스 폴더의 `AGENTS.md`가 해당 서비스의 범위와 로컬 계약을 소유한다.

## 로컬 계약

- `README.md`에는 서비스 목록, 역할, 상태와 주요 문서 링크를 현재 상태로 유지한다.
- 서비스별 요구사항은 해당 폴더의 `SRS.md`에 추적 가능한 ID와 상태로 기록한다.
- 확정된 요구사항의 상세 설계는 같은 폴더의 `SDD.md`에 기록하고 모든 설계 요소를 요구사항 ID 또는 채택된 제안 ID로 추적한다.
- `SDD.md`는 요구사항을 신설하거나 변경하지 않는다. 설계 과정에서 요구사항 변경이 필요하면 `SRS.md`를 먼저 고친다.
- 요구사항 ID는 `FR-{서비스식별자}-NNN`, `NFR-{서비스식별자}-NNN`, `TBD-{서비스식별자}-NNN` 형식을 사용한다.
- `SDD.md`의 설계 미정 사항은 새 형식을 만들지 않고 `SRS.md`가 쓴 `TBD-{서비스식별자}-NNN` 번호에 이어서 부여한다.
- 확정되지 않은 기능, 정책과 기술 선택은 `미정 사항`에 두고 확정 내용으로 서술하지 않는다.
- 요구사항 수준의 미정 사항은 `SRS.md`가, 어느 쪽을 골라도 요구사항을 충족하는 설계 선택은 `SDD.md`의 `설계 미정 사항`이 소유한다. 두 문서의 미정 사항은 `README.md`가 합쳐 보여준다.
- 외부 자료를 사용하면 서비스별 `reference.md`에 출처, URL, 조회 시각과 반영 위치를 기록한다.
- 서비스 기획 요청과 결과는 서비스별 `logs/prompt.md`에 누적한다.
- 범위 밖 제안은 필요한 경우에만 `suggestion.md`에 기록하며 사용자 채택 전 명세에 반영하지 않는다.
- 구현 검사 결과는 서비스별 `reviews/YYYY-MM-DD-대상.md`에 기록한다. 특정 시점의 기록이지 명세가 아니므로 계약을 바꾸지 않으며, 발견 사항을 처리하면 해당 항목의 상태를 갱신하고 계약 변경이 필요하면 `SRS.md` 또는 `SDD.md`를 따로 고친다.

## 작업 지침

- 서비스 문서를 수정하기 전에 루트, `spec/`, `spec/service/`와 대상 서비스의 DOX 체인을 읽는다.
- 새 서비스 추가나 서비스 역할 변경 시 `README.md`를 함께 갱신한다.
- 상세 설계는 요구사항과 주요 미정 사항이 충분히 확정된 뒤 `service-design` 스킬로 작성한다.
- 새 용어는 `spec/DICTIONARY.md`에서 확인하고 등록되지 않았으면 `project-glossary` 스킬로 갱신한다.
- 관계 시각화가 문장이나 표보다 이해를 개선할 때만 `service-design` 스킬로 작성한다.

## 검증

- 서비스 색인과 서비스별 문서의 경로, 이름, 역할과 상태가 일치하는지 확인한다.
- 요구사항 ID의 중복·누락과 상태의 잘못된 승격이 없는지 확인한다.
- `SDD.md`가 있으면 요구사항 추적표가 `SRS.md`의 설계 대상 요구사항을 빠짐없이 담고, 채택되지 않은 제안이 설계에 반영되지 않았는지 확인한다.
- 외부 근거 링크, Markdown 표, 맞춤법과 한국어 표현을 확인한다.
- 완료 전 DOX pass로 부모와 자식의 Child DOX Index를 확인한다.

## Child DOX Index

- `agent-context/AGENTS.md`: MCP 기반 에이전트 컨텍스트 관리 서비스와 인가 경계·임베딩 제공자·개발 환경 설계의 로컬 작업 계약을 정의한다.
- `agent-context-client/AGENTS.md`: 에이전트 컨텍스트 MCP 클라이언트 서비스의 로컬 작업 계약을 정의한다.
