## 구현과 보호 경계

`PrepareFiles`는 구성 루트·배포 슬롯과 같은 기동의 Source를 받아 요청 수신 전에 실제 여섯 파일을 준비한다. Files는 파일·디렉터리 fd·잠금을 비공개로 소유하며 Close가 파일을 닫은 뒤 잠금을 반환한다. 비동기 Sink와 대기열은 아직 연결하지 않았다.

- 절대 정규 경로·임시/공개 자산 경로와 슬롯 형식을 재검사한다. 부모는 미리 존재해야 하며 root 또는 실행 주체 소유이고 다른 주체가 쓰지 못해야 한다. 구성 요소마다 디렉터리 fd와 O_NOFOLLOW로 열어 심볼릭 링크를 따르지 않는다.
- 루트/슬롯은 실행 주체 소유의 0700, 여섯 일반 파일과 잠금은 0600·단일 하드 링크만 받는다. 기존 권한을 바꾸지 않고 모든 기존 파일을 사전 검사한 뒤 없는 파일만 배타적으로 생성한다. append·CLOEXEC로 열고 fd와 경로의 inode 결합을 확인한다.
- `.writer.lock`의 배타적 비차단 잠금은 슬롯의 수명 동안 유지한다. `.storage.lock`은 로컬 gate와 별개의 OS 잠금으로 같은 루트의 모든 인스턴스를 직렬화한다. 로컬/OS 획득 대기를 합쳐 최대 1초이며 짧은 요청 취소·마감을 따른다. 잠금 파일을 삭제하지 않아 과거/새 inode로 잠금이 분리되지 않는다.
- 기동·잠금 경계에서 경로 교체를 다시 검사한다. 이미 열린 파일·잠금이 다른 inode로 교체되면 실행하지 않는다. 준비 실패의 모든 열린 자원과 잠금은 정리하며 기존 기록을 truncate하지 않는다.
- Linux의 알려진 메모리/가상 FS·overlay, macOS의 알려진 메모리/가상 FS와 읽기 전용 마운트를 거부한다. 파일·디렉터리 sync 가능 여부를 확인한다. 저장소 검사만으로 배포 재생성 후 볼륨 보존이나 다중 호스트 잠금 일관성을 보장하지 않는다.
- FileError는 고정 Code만 문자열로 노출하고 원인은 Unwrap으로 보존한다. 파일 경로·OS 오류 원문은 오류 메시지에 복제하지 않는다.

이미 사용 중인 `golang.org/x/sys v0.41.0`의 Unix API를 직접 사용하도록 go.mod의 indirect 표기를 조정했다. 새 판·새 모듈·업무 패키지 import·DB 스키마·환경 변수는 추가하지 않았다. Go os.Root는 내부 심볼릭 링크를 따르므로 이 경계에서는 구성 요소별 openat를 사용했다.

## 검증 — 2026-10-21

- **macOS/arm64 진단 패키지 98건 통과**, race 포함, 실패 0·건너뜀 0. 기존 OBS-01 회귀와 OBS-02의 실제 파일·메타데이터·append·CLOEXEC·재기동·보존·잠금·취소·기동 실패 자원 회복을 검사했다.
- **Linux/arm64 진단 패키지 100건 통과**, 실패 0·건너뜀 0. CGO 없는 시험 바이너리의 일반 UID 501/GID 20 실행 99건과 별도 읽기 전용 마운트 1건이다. Linux에서는 race를 실행하지 않았다. 두 OS의 공통 시험은 같은 논리 항목을 반복한 것이므로 고유 항목 수로 합산하지 않는다.
- **서버 의존성 검사 1건 통과**, race 포함. diagnostic의 업무 패키지 의존 없음과 열한 패키지의 허용 import를 확인했다.
- 별도 자식 프로세스가 슬롯 잠금을 보유할 때 중복 기동을 거부했다. 공용 잠금 보유 중 다른 프로세스의 기동은 1초 안에 실패했다. 정상 종료·강제 종료 뒤 같은 슬롯의 재준비와 여섯 파일에 남은 세 기동의 서로 다른 boot·기존 행 보존을 대조했다.
- 두 인스턴스의 실제 OS 공용 잠금으로 임계 구역이 겹치지 않는지 확인했다. 로컬 gate/OS 잠금 각각의 1초 대기, 짧은 요청 마감, 이후 자리 반환을 검사했다.
- 기존 디렉터리/파일/잠금의 권한 오류·읽기 전용 모드, 심볼릭/하드 링크·FIFO·디렉터리 위장·inode 교체를 거부했다. 현재 UID 소유 파일을 실제로 검사하고 다른 UID의 메타데이터도 대조했다. 실패 뒤 기존 행이 유지되고 수정한 안전 fixture로 같은 슬롯을 다시 열 수 있음을 확인했다.
- Linux 실제 tmpfs는 `volatile_storage`, 실제 읽기 전용 bind는 `storage_read_only`로 거부했다. 최초 읽기 전용 시험의 마운트가 Docker에서 UID 0으로 표시되어 일반 UID에서는 소유권 검사에서 먼저 거부됐다. 해당 단일 시험을 UID 0·전체 읽기 전용 컨테이너에서 다시 실행해 FS 검사에 도달하도록 했다. 일반 파일·잠금 99건은 일반 UID에서 실행했다.
- 기존 로컬 이미지 `agent_context_sharing-db:latest` (`sha256:2b6d51048c03dae147064683f5b078690f1525365d561fd80b78f74de8c3c697`, Linux/arm64)를 시험 바이너리 실행에만 사용했다. 네트워크·DB·기존 볼륨을 사용하지 않고 소유한 임시 경로와 컨테이너만 생성했다.

## 범위·문서·남은 조건

이번 인수는 파일 준비 모듈이다. 생산 코드의 유한 대기열·JSON Lines/16 KiB는 OBS-03, 회전·보존·총상한은 OBS-04, 계측은 OBS-05, stderr·부분 쓰기·종료는 OBS-07, 배포 볼륨·다중 인스턴스를 포함한 전체 파일 저장 인수는 OBS-08에서 이어간다. 원시 파일을 공개 API·자산·MCP로 제공하지 않았다.

관측성 SDD에는 경로·메타데이터·잠금 파일과 검사 한계를, 계획에는 완료 상태를, 이 기록에는 실행 근거를 유지한다. 소유 정본은 기존 internal DOX의 diagnostic 경계에 있으며 새 Child DOX나 내부 import를 추가할 이유가 없어 기존 색인을 유지했다. upstream이 없어 원격 뒤처짐을 판정하지 못했으며 기존 Compose·IDE 변경을 보존했다. 이번 작업에서 commit·push·PR·배포는 수행하지 않았다.
