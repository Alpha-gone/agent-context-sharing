# #175 공백 본문의 문서 색인 계약

## 결정과 변경

선택지 (b)를 적용했다. 기존 저장·MCP 계약이 허용하는 비어 있지 않은 공백 본문은 원문 그대로 문서 색인 제공자에 보낸다. 문서에서만 공백 전용 입력 거부를 제거하고, 질의의 공백 거부와 공통 UTF-8·8000자·빈 문자열 검증은 유지한다. 전송 입력을 trim하거나 정규화하지 않으며 기존 문서 접두사 뒤에 결합한다.

저장 검증을 강화하는 방식은 기존 공백 데이터의 조회·수정·복구에도 영향을 줄 수 있어 채택하지 않았다. 저장소·논리 모델·DB 스키마는 유지하며 SRS·색인/MCP 설계·도구 설명/스냅샷·추적표를 정합화했다. DOX의 소유권과 구성은 바뀌지 않아 유지했다.

기존 failed 작업을 자동 재등록하지 않는다. 본문 갱신·기존 수동 재색인으로 다시 처리한다. 실제 제공자가 HTTP/응답 오류를 반환할 때의 #199 진단 분류·재시도 정책도 유지하며, 실제 제공자 수용·검색 품질은 합성 시험의 보장 범위가 아니다.

## 검증

- 수정 전 embedding.go를 Go overlay로 사용하면 TestGeminiInputContract와 실제 DB 공백 본문 공개 회귀가 실패했다. 저장은 성공하지만 제공자에 문서가 전달되기 전에 거부되는 기존 문제를 검출했다.
- Go 1.27.1, 작업 전용 합성 DB, TEST_DATABASE_REQUIRED=1의 DB/race: index 157·MCP 514·서버 730개 시험 및 하위 사례 통과. 서버의 별도 환경 인수 21개는 건너뛰었으며 미실행을 통과로 처리하지 않는다.
- 실제 원천·사건 생성과 사건 갱신 뒤 pending→합성 TLS 제공자→벡터 공개/교체→작업 제거·completed/INFO 진단을 공백·개행·Unicode 공백 각각에서 대조했다. 문서 원문과 질의 공백 거부·길이 경계 및 MCP 생성·갱신의 수용·원문 보존도 확인했다.
- 두 스냅샷을 생성 절차로 갱신한 뒤 갱신 변수를 끄고 스냅샷 시험을 다시 실행하여 일치를 확인했다. 변경은 body 설명 각 두 곳뿐이다.
- check-go.sh의 의존성·build·vet·gofmt, 변경 Markdown 링크·구조·SRS ID·diff 공백 검사 통과. 독립 검토에서 차단 결함 없음.
- 기존 개발 DB 대신 작업 소유 합성 컨테이너·볼륨만 사용했다. 실제 외부 제공자·호스트·운영 배포는 미실행이다.
- 검증 후 소유 라벨을 확인하여 합성 컨테이너·볼륨을 제거했고 해당 라벨의 잔여 컨테이너가 없음을 확인했다.
