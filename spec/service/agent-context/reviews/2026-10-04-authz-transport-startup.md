# 인가·MCP 전송·기동 실패 경로 회귀 검증

## 대상과 확인 근거

[GitHub #58](https://github.com/Alpha-gone/agent-context-sharing/issues/58)의 다섯 항목을 `dev`의 `680607c`에서 만든 `fix/authz-transport-startup_#58` 브랜치에서 처리했다. 적용 DOX와 용어를 확인하고 SDD를 먼저 정합화했다. 코딩 표준·Modern Go 지침은 구현과 회귀 시험에, service-design은 SDD 정합화에, work-history는 계획·요청·검증 기록에 적용했다.

수정 전 결정적 채널 제어 시험은 로컬 폐기와 더 최신 적재를 이전 DB 조회가 덮어쓰는 경우에 실패했다. 코드 조회·소비·서명 키 조회·생성·형식 및 재사용 폐기 장애는 `400`, `invalid_grant`로 잘못 응답했다. 캐시를 먼저 채운 재사용 토큰도 즉시 차단되지 않았다. 불리언 ID는 전송 거부 대신 인증 단계로 진행했다. 실제 DB의 서버 조립에서는 검색·인가·수신 실패의 내장·분리 배치 여섯 조합에서 작업자 고루틴이 남았으며 닫힌 풀 접근 로그도 확인했다.

## 해결한 결함

- 폐기 캐시: 로컬 폐기와 적재마다 세대 번호를 증가시킨다. 조회 중 세대가 바뀌면 이전 스냅숏을 게시하지 않고 조회 결과·최신 캐시의 폐기를 모두 확인한다. 로컬 폐기는 적재 시각을 연장하지 않으므로 다음 요청이 DB를 다시 읽는다. 만료 항목은 이후 정상 적재에서 빠진다. 맵 판정도 잠금 안에서 수행한다.
- 코드 교환 오류: 저장소의 `ErrNotFound`와 `CodeUsedError`만 코드 실패로 분류하고 그 밖의 내부 실패와 토큰 발급 실패는 원인을 보존한 `ErrUnavailable`로 반환한다. HTTP 응답은 기존 처리기의 안전한 `server_error` 외피만 노출한다. 복구 후 새 DPoP proof로 같은 미소비 코드를 교환할 수 있음을 시험했다. 커밋 결과를 알 수 없는 실제 연결 장애에서 코드가 반드시 미소비 상태라고 주장하지는 않는다.
- 재사용 처리: 기존 토큰을 `Revoke` 경로로 폐기해 DB와 로컬 캐시를 함께 갱신한다. 조회 시 재사용과 조건부 소비 시 동시 사용을 모두 검증했다. 폐기 저장 실패는 서버 장애로 반환하며 코드 재사용 거부·발급 토큰 폐기 계약은 유지한다.
- 해시 정합화: 새 형식은 SHA-256의 패딩 없는 표준 Base64 43바이트를 bcrypt에 넣는 `bcrypt-sha256-b64-v2:`다. 128자 한국어 비밀번호의 저장 결과를 이 형식으로 독립 대조했다. 기존 v1·직접 bcrypt의 로그인·조건부 승격 회귀도 유지했다. 이번 작업은 형식 불일치 수정이며 해시 알고리즘 교체나 인증 고도화의 전체 안전성 인증이 아니다.
- MCP ID: `jsontext.Value.Kind`로 문자열·숫자만 받는다. 누락·null·불리언·객체·배열은 인증·처리기 호출 없이 `400`, `-32600`, `id: null`로 거부한다. 빈 문자열·음수·소수·지수·정밀도 상한을 넘는 정수의 ID 원문 보존을 확인했다. 일반 JSON-RPC의 null 허용과 이 MCP 프로필의 더 좁은 정책은 SDD에서 구분했다.
- 서버 생명주기: 작업자 시작 전에 풀의 defer보다 나중에 정리를 등록해 조립·수신 실패에도 먼저 종료한다. 정상 종료는 기존 트래픽 이탈·요청 대기·작업자 종료 순서를 유지하고 닫은 목록을 비워 중복 종료하지 않는다. 공통 종료 함수가 실제 정리 시점에 10초 예산을 만들므로 요청 대기에 시간을 쓰거나 실패해도 작업자 종료를 시도한다. 구성 읽기와 조립을 비공개 함수로 나눠 실제 조립의 실패를 주입하며 새 공개 API·의존성·배포 구성은 없다.

## 개발 DB 초기화와 검증

사용자가 작업 전 초기화를 명시했다. Compose 프로젝트·작업 디렉터리·실제 마운트를 확인한 뒤 `db`, `wal_cleanup`만 정지·제거하고 `agent_context_sharing_db_data`를 삭제·재생성했다. 전체 `down -v`로 Ollama 모델까지 지우지 않았다. 기존 DB 데이터와 볼륨 안 WAL 보관 파일은 삭제되었고 별도 백업은 만들지 않았다. 기존 데이터의 복구를 제공한다고 주장하지 않는다.

재기동한 DB는 `127.0.0.1:5432`에서 정상 상태이며 개발 DB에 001·007·008을 적용하고 추가 적용할 판이 없음을 확인했다. 회귀·전체 시험은 같은 개발 PostgreSQL 인스턴스에 별도 생성한 `issue58_regression`, `issue58_suite`, `issue58_audit`, `issue58_final` DB를 사용하여 초기화한 애플리케이션 DB에는 합성 데이터를 넣지 않았다. 시험 DB는 검증 후 삭제했으며 마이그레이션과 테스트로 다시 만들 수 있다. `.env`는 로컬 접속·스키마 구성을 읽는 데만 사용했고 파일이나 비밀값은 변경·출력하지 않았다. 임베딩 호출은 로컬 HTTP 대역을 사용했다.

Go 1.27.1 `darwin/arm64`로 다음을 실행했다. DB 시험에는 `TEST_DATABASE_URL`, `TEST_DATABASE_REQUIRED=1`을 설정했다.

```shell
go test -race -p 1 ./internal/authz ./internal/mcp ./cmd/server -count=10
go test -race ./cmd/server -run TestShutdown -count=10
go test -race -p 1 -count=1 -json ./...
# 루트와 client/에서 각각
go build ./...
go vet ./...
# client/에서
go test -race ./...
# 루트에서
gofmt -l .
git diff --check
```

관련 패키지의 실제 DB·단위 회귀 10회와 종료 순서·시간 예산 회귀 10회가 통과했다. 최종 새 DB의 서버 전체 race 검사에서 테스트 항목 737개가 통과했고 실패·테스트 건너뛰기는 없었다. 테스트 파일이 없는 세 패키지의 JSON `skip` 이벤트는 개별 테스트 건너뛰기와 구분했다. 클라이언트 전체 race·공유 계약, 양쪽 모듈 build·vet와 형식 검사가 통과했다. 수정 전 재현 실패는 수정 후 성공과 구분하며 최종 전체 검사의 실패는 없었다.

## DOX pass와 제한

- 루트에 기동 실패 시 작업자·풀의 종료 책임을, `internal/mcp/AGENTS.md`에 ID 전송 계약을 반영했다. 부모 Child DOX Index의 대상 경로는 그대로 유효하다.
- spec 부모·서비스 AGENTS, SRS·용어집·마이그레이션·클라이언트 계약은 소유권·구조·요구사항·용어·스키마·공개 도구 변경이 없어 유지했다. 계획·근거·요청 기록을 동기화했다. Markdown 구조·상대 링크·한국어 표현과 맞춤법을 검토했다.
- 기존 Ollama 컨테이너·모델은 보존했다. 해당 컨테이너는 이전 구성의 전체 인터페이스 공개와 `latest` 태그로 실행 중이므로 #56의 loopback·고정 버전 적용은 별도 재생성 작업으로 남는다.
- v2 Base64는 원시 다이제스트의 NUL 문제를 피하지만 다른 경로에서 유출된 사전 해시와 결합되는 위험까지 제거하지 않는다. 더 넓은 인증 고도화는 기존 `TBD-AGENT_CONTEXT-048`의 범위이며 이번 작업에서 선택·구현하지 않았다.
- `client_live` 실제 브라우저·시스템 클라이언트 종단 간 시험, 외부 임베딩 API·과금, 운영 DB·배포, 커밋·푸시·PR·이슈 종료는 수행하지 않았다. #58 범위의 미해결 결함은 없다.
