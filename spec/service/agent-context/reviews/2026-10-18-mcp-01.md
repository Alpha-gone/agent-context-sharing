# MCP 최소 SDK 적합성 검토

- 기준: [MCP-01](../development-plan/mcp.md#mcp-01), [SDK와 수명주기](../sdd/mcp.md#sdk와-수명주기), [표준 MCP 경계](../sdd/mcp.md#표준-mcp-경계).
- 시작 상태: 2026-10-18, `dev`의 `c666715`에서 작업 계열 브랜치 `feat/mcp-auth`를 생성했다. 로컬 origin/dev와 차이는 없으나 GitHub DNS 실패로 최신 원격 상태는 확인하지 못했다. 기존 Compose·IDE 변경은 보존했다.
- 범위: Go 1.27.1·공식 Go SDK v1.8.0·revision 2026-07-28의 최소 서버와 실제 루프백 HTTP 교환이다. 업무 도구·DB·OAuth·실제 호스트·운영 경로에는 연결하지 않는다.
- 현재 상태: 아래 최초 관찰 이후 [서비스 진입 경계 보완과 최종 인수](#서비스-진입-경계-보완과-최종-인수)를 완료했다. 공급자 단독 차이는 관찰 기록으로 보존하며 MCP-01은 완료 상태다.

## 최소 서버와 확인한 계약

`internal/mcp/sdk_contract_test.go`의 시험 전용 서버에 합성 도구 하나를 등록한다. Stateless·JSONResponse를 사용하고 SupportedProtocolVersions를 목표 revision 하나로 제한하며 SetCacheable에서 ttlMs=0·cacheScope=private를 명시한다. capabilities는 tools만 광고하고 listChanged·구독·기타 기능을 광고하지 않는다.

- 별개의 두 서버 모두 발견·initialize 없이 첫 도구 호출을 처리했다. 요청마다 다른 clientInfo를 주고 이후 이를 생략했을 때 앞 요청의 값을 재사용하지 않았다.
- tools/list를 발견 전후에 호출하고 server/discover의 지원 revision·서버 정보·instructions·기능을 확인했다. 발견/목록은 complete 외피와 private/0 캐시를 반환했다.
- 도구 결과의 structuredContent와 JSON text content는 같은 값이며 세션 식별자와 SSE 응답을 사용하지 않았다.
- 현재 revision의 필수 메타데이터·표준 헤더 누락/불일치는 400/-32602 또는 400/-32020으로 구분됐다. 미래 revision은 400/-32022와 supported/requested, 알 수 없는 RPC는 404/-32601을 반환했다. GET·DELETE는 405와 Allow: POST였다.

## 서비스 계약과 다른 공급자 동작

다음은 SDK를 감싸지 않은 서버의 **관찰 결과**다. TestSDKCompatibilityGaps의 통과는 아래 차이를 재현했다는 뜻이며 서비스 계약 충족을 뜻하지 않는다.

| 입력 | 실제 SDK v1.8.0 응답 | 필요한 서비스 동작 |
|---|---|---|
| 헤더·표준 _meta 없는 이전 initialize | 200, protocolVersion=2025-11-25로 협상 | 필수 외피 누락 또는 미지원 RPC로 거부. 자동 하향 금지 |
| 헤더·표준 _meta 없는 tools/list | 200, 이전 형식의 목록 | 발견 이력과 관계없이 필수 외피 검사·거부 |
| 이전 revision의 HTTP 헤더 | 400 text/plain | 계약의 JSON-RPC 오류와 지원 revision 정보 유지 |
| 올바른 Base64 sentinel의 Mcp-Name=probe | 400/-32020, 원문 헤더와 본문 비교 | 표준 sentinel 해독 후 본문 이름과 대조하여 정상 처리 |

추가로 Base64 Mcp-Method도 400/-32020으로 관찰했다. 공식 표준의 sentinel 해독 의무는 Mcp-Name·Mcp-Param 값에 명시되어 있으므로 이 추가 표본을 공식 method 인코딩 위반으로 분류하지 않는다. 서비스 SDD의 헤더 정규화 범위와 함께 후속 시험에서 구분한다.

SDK의 SupportedProtocolVersions는 이전 initialize 자체를 비활성화하는 기능이 아니다. 이 사실을 반영해 소유 SDD에 서비스 진입 경계의 사전 검증·이름 정규화 책임을 명시했다. SDK 교체·fork·의존성 변경·이전 revision 허용은 수행하지 않았다.

## 최초 SDK 단독 검토의 상태

최초 검토 당시 **MCP-01 진행 중**이었다. 최소 서버의 정상 교환만으로는 목표 거부·정규화 계약과 같지 않아 완료 체크박스를 올리지 않았다. 당시 전체 49/124개 완료·75개 미완료였으며 그중 MCP-01 진행 중·74개 미착수였다.

다음은 SDK를 직접 노출하지 않는 최소 진입 경계를 구현하여 위 네 차이를 목표 결과로 재검증하는 작업이다. MCP-02 전체의 OAuth 의존성을 이 최소 시험으로 완료 처리하지 않는다. 이후 MCP-03은 MCP-01 완료 후 착수할 수 있으며 MCP-02 전체 연결에는 AUTH-08이 필요하다.

실제 Bearer/OAuth·14종 도구·DB 쓰기·HTTP 취소·Origin 정책·본문 상한·실제 Codex CLI 지원은 이번 인수 범위가 아니다. TBD-064는 계속 열어 둔다.

DOX pass에서 패키지·소유권·공개 API·스키마·용어·환경 구성 변경이 없음을 확인했다. 기존 DOX·SRS·환경 예시는 유지하고 상세 설계의 보완 책임·검증 상태와 관련 계획·색인·근거·요청 기록만 정합화했다.

## 서비스 진입 경계 보완과 최종 인수

2026-10-18, 사용자 후속 진행 지시에 따라 `feat/mcp-auth`의 `ad1a462`에서 네 차이를 보완했다. 브랜치는 upstream이 없어 최신 원격 대비 상태를 확인할 수 없었으며 기존 Compose·IDE 변경은 보존했다.

- `internal/mcp/sdk_transport.go`의 비공개 `newSDKTransport`는 단일 JSON-RPC 요청·필수 메타데이터·표준 헤더·revision을 먼저 검사하고 발견·도구 목록·도구 호출만 SDK에 전달한다. 이전 initialize·구독·ping은 표준 외피가 있어도 미지원 RPC로 거부한다. 표준 외피가 없으면 SDK의 이전 수명주기로 들어가기 전에 -32602로 거부한다.
- 이전/미래 revision 모두 JSON-RPC -32022와 supported/requested를 반환한다. 본문과 헤더의 revision이 다르면 -32020으로 구분한다. SDK의 이전 revision 일반 텍스트 오류 경로로 진입하지 않는다.
- 중복 헤더를 첫 값으로 축약하지 않고 거부한다. Mcp-Name의 표준 Base64를 한 번 해독하여 본문과 대조한 뒤 요청 사본의 헤더에만 전달한다. 잘못된 Base64·비정규 패딩 비트·유효하지 않은 UTF-8과 이름 불일치를 거부한다. Mcp-Method와 revision은 Base64 이름 규칙의 대상이 아님을 SDD에 명시했다.
- SDK와 앞단 검사 모두 호출자가 지정한 같은 양수 본문 상한을 사용한다. 합성 최소 서버에서는 SDK의 기존 4 MiB 상한을 사용하며 새 환경 변수·운영 기본값은 추가하지 않았다. 배치·응답 POST·수명주기 알림·부적합 ID·중복 키·연속 JSON 값도 SDK에 위임하기 전에 거부한다. 정상 인자는 원문 바이트로 전달한다.
- 서로 다른 두 최소 서버에서 발견 전 도구 호출과 발견 전후 목록·완료 외피·private/0 캐시를 재확인했다. clientInfo가 있는 요청 뒤 생략 요청에 이전 정보가 남지 않았다. ASCII·한글·sentinel 자체를 이름으로 쓰는 합성 도구의 인코딩 호출과 원본 헤더 보존을 확인했다.

최종 실행 결과:

- Go 1.27.1, `GOCACHE=/private/tmp/agent-context-sharing-go-cache /Users/alphagone/sdk/go1.27.1/bin/go test -race -json -count=1 ./internal/mcp`: 최상위 12건·하위 75건, **87건 통과·실패 0건·건너뜀 0건**. 이 중 49건은 이번 보완 인수이며 기존 SDK 단독 관찰 시험도 유지했다. 로그는 `/private/tmp/acs-mcp01-boundary-test.json`이다.

**MCP-01 완료**, 전체 **50/124개 완료·74개 미착수**다. 최소 SDK 진입 경계가 목표 교환과 일치한다는 판정이며 실제 서버의 공개 MCP 경로·Origin·인증·업무 도구·DB·취소·실제 호스트 인수는 포함하지 않는다. 처리기는 아직 조립 지점에 연결하지 않았고 외부에서 사용할 공개 생성자도 추가하지 않았다. MCP-02·TBD-064는 미완료 상태를 유지한다. 다음 착수 가능한 MCP 작업은 [MCP-03](../development-plan/mcp.md#mcp-03)이고 MCP-02 전체 구현에는 AUTH-08이 필요하다.

DOX pass에서 기존 `internal/mcp`의 소유 경계 안의 구현임을 확인했다. 새로운 패키지·공개 API·스키마·구성·용어가 없어 DOX·SRS·환경 예시는 유지했다. SDD의 헤더 정규화 범위와 검증 상태·계획·추적표·서비스 색인·공식 근거·요청 기록을 정합화했다.
