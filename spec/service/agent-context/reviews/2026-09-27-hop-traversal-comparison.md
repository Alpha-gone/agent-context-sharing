# 홉 탐색 구현 비교

## 목적과 조건

- 측정일: 2026-09-27
- 목적: `SUG-AGENT_CONTEXT-21`에 따라 현재 깊이별·관계 label별 너비 우선 탐색과 Apache AGE 내장 경로 질의를 같은 결과 조건에서 비교하고 대체 여부를 판정한다.
- 데이터베이스: PostgreSQL 18.6, Apache AGE 1.8.0, pgvector 0.8.6
- 개발 이미지: `agent_context_sharing-db` 이미지 ID `sha256:d9a079231e9b09929bfcb670da7cb6ff545f87e17f5751914fd77dd59bc14ea7`, `apache/age:release_PG18_1.8.0` 기반
- 기준 태그의 현재 레지스트리 digest: `sha256:47a0b054c3663a3e64a25fc0c5a982f1b58348019274b326a691cdf77f78eb58`. 개발 이미지는 3주 전에 빌드되어, 빌드 당시의 digest와 같은지는 확인하지 못했다.
- 실행 환경: Apple M4 Pro 개발 장비와 로컬 Docker 개발 데이터베이스

## 후보 선정

계획한 `shortest_path`·`all_shortest_paths`는 고정한 이미지에서 결과 조건을 표현할 수 없어 후보에서 뺐다.

| 기능 | 확인 결과 |
|------|-----------|
| Cypher `shortestPath`·`allShortestPaths` | 구문 오류로 거부된다 |
| SQL `age_shortest_path`·`age_all_shortest_paths` | 두 정점 사이 경로만 구한다. `proposed` 관계를 지나고, label 목록을 무시하며, 간선 속성 조건 인자를 `argument must be a scalar`로 거부한다 |
| 가변 길이 간선 `[e:R*1..k {state:'confirmed'}]` | label 하나와 속성 조건을 지원한다. 여러 label을 섞은 경로는 표현하지 못한다 |
| 경로 노드 조건 `all(n IN nodes(p) ...)` | 지원하지 않는다 |

비교 후보는 가변 길이 간선에 `graph_id` 조건만 걸어 시작점에서 `k-1`홉 안의 정점을 모으고, 그 정점들의 인접 간선을 같은 질의에서 가져온다. 그 뒤 기준선과 같은 너비 우선 루프를 메모리에서 실행한다. 확장 질의는 깊이 × label 수에서 한 번으로 줄어든다. 구현은 `internal/store/hop.go`의 `hopContextsPrefetched`이며 기준선과 `traverseHops`를 공유한다.

## 결과 동등성

`TestHopImplementationsReturnSameResultIntegration`이 두 구현을 같은 표본에서 432개 조합으로 대조해 모두 같았다.

- 표본: 원천·파생·사건, 확정·제안 관계, 사건 관계 순환, 삭제된 중간 노드와 같은 모양의 다른 그래프
- 조합: 시작점 3종 × 방향 3종 × 필터 4종 × 홉 1·2·3·상한 없음 × 결과 상한 없음·3·6
- 대조 항목: 컨텍스트와 그 순서·속성, 최단 홉 거리, 간선 집합과 정렬, 절단 여부와 경계, 다른 그래프 노드의 혼입
- 표본 조건 확인: 기준선에서 절단이 일어났고, 삭제 노드와 제안 관계 너머의 사건은 결과에 나오지 않았다.

## 왕복과 지연

`BenchmarkHopImplementationsIntegration`으로 조건마다 10회 반복한 평균이다. 표본은 원천 둘·파생·사건으로 된 묶음을 사건끼리 확정 `precedes`와 세 묶음 뒤 `relates_to`로 이은 사슬이고, 가운데 묶음의 파생과 사건에서 양방향으로 탐색한다. 왕복은 확장 질의 수이며 두 구현이 공유하는 참조 채우기와 접근 시각 갱신은 뺐다.

전체 30개 조건 중 후보가 실행된 24개 모두에서 후보가 더 느렸다. 차이는 1홉에서 1.8~4.4배, 6홉·관계 유형 1개에서 약 39~45배다. 후보의 지연은 관계 유형 수와 거의 무관하고 홉 수와 그래프 크기에 따라 늘었다. 가변 길이 간선이 label 조건 없이 경로를 모두 나열하기 때문이다. 기준선은 왕복이 늘어도 질의마다 frontier만 다루어 지연이 작다.

상한 없는 탐색에서 후보는 100노드 표본에서도 경로 나열의 임시 파일이 데이터베이스 볼륨을 모두 채워 `No space left on device`로 실패했다. 실패 뒤 임시 파일은 정리됐고 볼륨 여유 공간은 106GB로 돌아왔다. 벤치마크는 이 조건을 후보에서 뺀다.

## 판정

- 너비 우선 탐색을 유지한다. 결과는 같지만 지연이 모든 조건에서 나빠져 「홉 탐색 구현 비교」의 대체 조건을 넘지 못했다.
- 비교 후보 `hopContextsPrefetched`와 동등성 테스트·벤치마크는 저장소에 남긴다. 운영 경로는 이 후보를 호출하지 않는다. 다음 PG18 호환 공식 안정판에서 같은 비교를 반복하라는 계약을 같은 표본과 조건으로 재현하기 위해서다.

## 한계와 후속 확인

- 표본은 한 가지 모양의 사슬 그래프다. 실제 운영 그래프의 차수 분포에서 절대 지연은 달라질 수 있지만, 경로 나열 비용이 frontier 확장보다 빠르게 커지는 경향은 표본 크기와 무관하게 같았다.
- 기준선의 상한 없는 탐색은 1,600노드 연결 요소 전체를 497번 왕복해 2.3초가 걸렸다. 이번 비교의 판정 대상은 아니지만, 결과 상한이 없는 플랜에서 지연 요인이 될 수 있다.
- 다음 안정판에서 `shortestPath` 구문이나 label 목록·속성 조건을 받는 경로 함수가 생기면 후보 선정부터 다시 확인한다.
