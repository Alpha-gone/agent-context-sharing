## 구현 결과

`internal/authz.Refresh`는 현재 등록의 client/resource와 선택 scope를 대조하고 32바이트의 canonical base64url 갱신 값을 SHA-256으로 조회한다. 빈 scope는 생략과 같이 기존 범위를 유지하고 확대는 invalid_scope다. 잘못된 결합·없는/만료/폐기 자격은 invalid_grant, 내부 키·저장 장애는 안전한 unavailable/server_error로 구분하며 실패 응답에 접근·갱신 자격을 넣지 않는다.

최초 코드 교환과 갱신 회전은 같은 ES256 발급 경계를 사용한다. 키는 저장 트랜잭션 전에 읽어 잠금 중 추가 풀 연결을 확보하지 않는다. 매 성공마다 새로운 jti·1시간 접근 JWT와 32바이트 난수 갱신 값을 만들고 계정/client/resource/scope/grant 결합을 유지한다. 원문은 token 응답에만 반환하며 저장 콜백은 해시만 돌려준다.

`internal/store.RotateOAuthRefreshToken`은 해시로 계열을 찾고 계열 행→해당 토큰 행 순서로 잠근다. 두 잠금을 얻은 뒤 현재 시각·결합·폐기·30일 절대/7일 비활동·토큰 만료와 저장 수명을 재검사한다. 이전 토큰 소비·후속 해시 삽입·접근 서명·최근 회전 시각·비활동 만료·보존 종료를 한 커밋으로 반영한다. 절대 만료는 유지하고 보존 종료는 기존 값·절대 만료+1시간·새 접근 만료 중 최댓값을 유지한다. 서명·저장·취소·커밋 실패는 이전 자격을 소비하지 않는다.

올바른 결합의 소비 토큰 재사용은 자체 만료 뒤에도 보존 중인 계열을 폐기하고 커밋 후 invalid_grant를 반환한다. 폐기 커밋 실패는 서버 장애이며 폐기가 완료됐다고 보고하지 않는다. 성공 응답 유실 뒤 이전 토큰을 재전송하거나 같은 자격을 병행 갱신하면 계열 폐기로 이어질 수 있다. 실제 호스트의 직렬화·안전 저장 인수는 별도다. 정상 도구 인증·로그인·웹 세션·실패 갱신은 비활동 수명을 연장하지 않는다. 이미 유효한 접근 토큰은 갱신 자격 만료와 별도로 자체 만료까지 허용하되 계열 폐기는 즉시 반영한다.

`/token`은 기존 단일 URL-encoded POST·query 병합 거부·중복 거부·64 KiB 제한·no-store/no-cache를 두 grant에 적용한다. 갱신 응답은 Bearer 외피이며 세션 쿠키·리디렉션·재인증 도전을 만들지 않는다. 기존 TLS→로그인→명시적 동의→최초 교환 시험에 갱신→새 접근 검증→이전 갱신 재사용→계열 차단을 연결하고 원문·SHA-256 해시·verifier·쿠키·비밀번호·state의 로그 비노출을 확인했다. 실제 업무 /mcp 처리기는 연결하지 않았다.

## 모듈 시험과 검증

Go 1.27.1에서 TEST_DATABASE_REQUIRED=1과 전용 TEST_DATABASE_URL로 `-timeout=120s -race -json -count=1`을 실행했다.

- 인증 **402건**: `go test -timeout=120s -race -json -count=1 ./internal/authz`. 형식·등록·scope·HTTP/64 KiB 경계·오류 원인/비노출·취소·서명과 기존 인증 회귀를 포함한다. 실제 DB에서 30일/7일 정각·만료 후 남은 행 거부·절대 만료 유지·접근 수명 독립·재시작·응답 유실·8건 동시 갱신·만료 후 소비 재사용·두 종류의 행 잠금 대기 후 만료·대기 중 폐기·취소 회복을 검증했다. 서명 콜백 실패와 후속 INSERT·이전 소비 UPDATE·계열 UPDATE·지연 제약의 COMMIT 실패를 주입해 전체 롤백과 이전 자격 재사용 가능성을 확인했다. 재사용 폐기의 COMMIT 실패→재시도 성공도 확인했다.
- 선별 서버 **65건**: `go test -timeout=120s -race -json -count=1 -run '^(TestOAuth.*|TestWebSession.*|TestWebCredentialErrorMapping|TestTransportSecurity.*)$' ./cmd/server`. 실제 TLS의 최초 인가·갱신·재사용 폐기와 웹 세션 독립·라우팅 전 TLS 등 관련 회귀를 포함한다.
- 해시 로그 비노출을 보강한 뒤 `TestOAuthAuthorizationTLSIntegration` **1건**만 재검증했다. 위 65건에 포함된 같은 이름의 시험이므로 중복 가산하지 않았다.
- **중복 제외 총 467건 통과·건너뜀 0건·race 통과**. 전체 저장소·인증 분야 전체 통합·실제 브라우저/호스트 인수와 구분한다.
- 루트 `check-go.sh`: 의존성 검증·SDK 링크·전체 build·vet·gofmt 검사 통과. `/private/tmp/acs-auth09-check-go.log`.
- 시험 로그: `/private/tmp/acs-auth09-authz.json`, `/private/tmp/acs-auth09-server.json`, `/private/tmp/acs-auth09-additional-server.json`.

Docker 접근 권한을 갖춘 실행기는 postgres 관리 DB에서 이번 실행의 무작위 auth09_suite DB만 생성·정리했다. 모든 TEST_DATABASE_URL을 그 전용 DB로 고정했고 시험 준비 함수가 다시 시험별 자식 DB와 실제 DB명 대조·정식 마이그레이션으로 격리했다. 두 실행 모두 suite DB 삭제·부재를 확인했다. 기존 개발·운영 DB의 스키마·계정·키는 시험 준비에 사용하지 않았다.
