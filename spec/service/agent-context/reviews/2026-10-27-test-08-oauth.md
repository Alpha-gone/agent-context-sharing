# TEST-08 실제 CLI OAuth·업무 호출·장애 경계 후속 검토

## 범위와 판정

2026-10-27 macOS/arm64·Go 1.27.1·Codex CLI 0.160.1 `exec`와 Chrome 156.0.8078.48에서 실제 브라우저의 로그인·동의·고정 callback·issuer/state 결합과 코드 교환을 인수했다. 시험 구성은 `test08-oauth-v3`, MCP Go SDK는 v1.8.0, revision은 2026-07-28이다. 기능 활성 전송의 이전 근거는 [2026-10-26 검토](2026-10-26-test-08.md)에 있다.

최초 verifier·인가 코드·접근/갱신 자격은 시험이 대신 발급하지 않는다. 실제 CLI와 브라우저가 교환·저장하며, 별도 CLI 프로세스가 저장 자격을 읽어 실제 조립 서버를 호출한다. 파일 저장 모드를 선택했고 `.credentials.json`의 0600을 확인했다. 사용자 Codex 설정·자격·브라우저 프로필은 사용하지 않는다.

**통제한 호스트 흐름의 후속 인수이며 TEST-08 전체 완료는 아니다.** 실제 서버 발급 접근 토큰의 1시간 만료 후 호스트 갱신과 기존 만료 토큰 거부과 나머지 필수 오류/취소·현재 권한 재검사 흐름은 후속이다. `TBD-AGENT_CONTEXT-064`는 미해소이고 전체 **116개 완료·2개 진행·6개 미착수**를 유지한다. keyring·TUI·앱·IDE로 지원을 확대하지 않는다.

## 구현과 실행 격리

- `cmd/server/codex_oauth_test.go`: 여섯 독립 OAuth 표본과 실제 CLI·Chrome 수명, 서버/인스턴스별 요청·토큰 교환 상태, 장애/응답 유실·저장 상태를 대조한다. 실패해도 자식 프로세스·시험 DB·서버·기록기를 정리한다.
- `cmd/server/codex_model_test.go`: 실제 도구 목록의 namespace와 서버가 반환한 식별자로 고정된 업무 순서를 구동하는 로컬 Responses 대역이다. 모델 추론이나 에이전트 업무 효과를 측정하지 않는다. 불확정 쓰기는 같은 request_id·expected_version·본문을 보존해 다른 인스턴스로 재생한다.
- `cmd/server/testdata/codex-oauth.cjs`: 독립 Chrome 프로필에서 로그인·명시적 동의·CLI loopback callback을 수행하고 issuer/state 일치 여부만 보고한다. URI·코드·쿠키·자격·페이지 본문은 출력하지 않는다. 기존 namespace 처리와 브라우저 시험 변경을 이어서 보강했다.
- `cmd/server/codex_interop_test.go`: 실제 CLI 경로·정확한 판 검사를 OAuth 시험과 공유한다. PATH의 현재 wrapper는 0.164.0이어서 초기 판 검사를 통과하지 못했고, 기존 캐시에 남은 0.160.1 바이너리를 명시적으로 선택했다. 설치·판올림·목표 판 변경을 하지 않았다.

고정 이미지 `sha256:2b6d51048c03dae147064683f5b078690f1525365d561fd80b78f74de8c3c697`로 새 `acs-test08-followup-db`를 만들고 임시 loopback 포트를 사용했다. PostgreSQL 18.6·AGE 1.8.0·pgvector 0.8.6의 합성 DB이며 시험마다 별도 DB를 생성·마이그레이션한다. 기존 개발 DB와 작업 시작 전에 있던 `acs-test08-oauth-db`는 사용하거나 정리하지 않았다. 외부 모델·임베딩 API와 유료 호출은 없다.

## 관찰한 여섯 시나리오

모든 표본에서 최초 브라우저 OAuth, 새 CLI 프로세스의 자격 재사용, 등록→목록→그래프/노드 생성→조회→속성 갱신→현재 판 재조회, 클라이언트 만료 표본의 단일 회전을 먼저 확인한다. 일반 표본은 업무 호출 8회이며 불확정 쓰기 표본은 같은 갱신의 재생을 포함해 9회다.

| 표본 | 실제 관찰과 판정 |
|---|---|
| 서버 교체·폐기 | 동일 origin에서 TLS 수신기·애플리케이션을 닫고 새로 조립한 뒤 자격 재사용을 확인했다. 두 인스턴스에 각각 성공한 보호 요청을 대조했다. 키 회전 후 이전 키 자격과 전파 시간 이후 새 키 갱신, 실제 연결 풀 장애의 500·자격 파일 바이트 보존과 재조립 복구, 본인 계열 폐기 후 접근/갱신 거부를 확인했다. 폐기는 연결 관리 서비스 경계에서 수행했으며 UI 조작 인수로 확대하지 않는다. |
| 유휴 만료 | 격리 DB의 계열·갱신 시각을 함께 8일 이동했다. 아직 유효한 접근 토큰은 사용되지만 클라이언트 만료 표본의 실제 갱신은 거부되고 last_rotated_at·idle_expires_at을 연장하지 않았다. |
| 절대 만료 | 같은 방식으로 31일 이동해 절대 만료 거부와 실패 갱신의 시각 보존을 확인했다. 실제 31일을 기다린 장기 시험으로 해석하지 않는다. |
| 갱신 응답 유실 | 서버의 소비·후속 발급 커밋 후 첫 응답 전송 전에 TLS 연결을 닫았다. 이전 자격의 다음 재사용은 refresh_token_reuse로 계열 전체를 폐기했다. 초기 코드·기준 갱신·유실 갱신의 성공 3회, 전체 token 시도 4회·거부 1회였다. |
| 두 프로세스의 갱신 | 같은 상태 루트·만료 자격을 두 CLI 프로세스가 동시에 사용했다. 첫 token 요청을 최대 1초 대기시켜 경합 기회를 두었으며 실제 추가 갱신은 1회, 전체 token 시도 3회·거부 0회·계열 폐기 없음이고 두 프로세스 모두 보호 요청을 완료했다. 관찰한 구성의 직렬화 근거이며 다른 저장 모드/호스트 전체의 보장은 아니다. |
| 불확정 쓰기 | 첫 graph_update 커밋 뒤 응답 전송 전에 연결을 닫고, 같은 키·지문을 다른 인스턴스로 재생했다. 최초 결과·그래프 version=2와 갱신 재생 기록 1개를 유지했다. |

갱신을 유도할 때에는 시험 소유 자격 파일의 `expires_at`만 과거로 옮긴다. 접근/갱신 자격 원문은 유지하고 그 값은 기록하지 않는다. 이 조건은 실제 접근 JWT의 1시간 만료와 구분한다. 초기 키 회전 표본은 다른 인스턴스의 정상 키 적재 직후에 새 kid를 사용해 401 2회·성공 token 교환 4회를 관찰했다. [인증 정본](../sdd/authentication.md#토큰-검증)의 1초 부재 재조회 제한을 확인한 뒤, 이전 키의 즉시 사용과 1.1초 전파 대기 후 새 키 갱신을 분리해 최종 인수했다. 제품 동작을 바꾸거나 이 예비 실행을 최종 통과 수에 더하지 않았다.

## 남은 인수와 문서 정합성

1. 실제 서버가 발급한 접근 토큰의 1시간 만료 후 호스트 갱신·자격 복원과 기존 만료 토큰 거부 흐름을 확인한다. 현재의 클라이언트 메타데이터 표본으로 완료 처리하지 않는다.
2. 호스트의 callback/resource/issuer 위반, scope 403·내부 오류, HTTP 취소와 현재 권한 회수 뒤 재생 거부 등 나머지 필수 대조를 [첫 호스트 시험](../sdd/testing.md#첫-codex-cli-상호운용-시험)에 대조한다. 기존 서버 계약 통과와 실제 호스트 인수를 구분한다.
3. TEST-06의 Safari·실제 VoiceOver와 OPS-09의 격리 운영 장애 인수는 별도 작업으로 유지한다.

DOX pass에서 제품 동작·패키지·스키마·배포 구성·소유권이 유지되어 DOX와 SRS는 변경하지 않았다. 현재 진행과 남은 조건을 개발 계획·시험 SDD/추적표·SDD 진입 상태·서비스 색인·README와 요청/공식 근거 기록에 연결했다. 변경은 미커밋이며 현재 `feat/evaluation-and-operations`에는 upstream이 없어 원격 대비를 확인하지 못했다. 기존 개인 IDE 파일 두 개를 보존했다.
