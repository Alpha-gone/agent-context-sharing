# Issue Based Spec

## 개요

GitHub 이슈의 확정 범위를 요구사항, 상세 설계, 결정, 제안, 미정 사항과 구현 작업으로 분류한 뒤 기존 명세에 추적 가능하게 반영한다. 승인된 작업 단위별로 변경·검증·커밋을 완료하고 실제로 처리된 이슈
체크리스트를 갱신한 뒤 결과를 재조회한다. 이 스킬은 Issue 대응 작업의 실행을 조정하며 `SRS.md`와 `SDD.md`의 작성 계약을 새로 정의하지 않는다.

분류와 반영 위치를 결정하기 전에 [이슈-명세 매핑 기준](references/spec-mapping.md)을 읽고 적용한다.

## 필수 입력

| 입력                                              | 사용 방법                                                                 |
|:--------------------------------------------------|:--------------------------------------------------------------------------|
| GitHub 저장소와 이슈 번호                         | 원문을 재조회하는 식별자로 사용한다.                                      |
| 이슈 제목, 본문, 체크리스트, 댓글, 라벨과 상태    | 확정 범위와 작업 맥락을 분류한다. 상태만으로 확정 여부를 추론하지 않는다. |
| 대상 서비스의 `SRS.md`, `SDD.md`                  | 기존 요구사항, 설계, 추적 ID와 충돌 여부를 확인한다.                      |
| `reference.md`, `suggestion.md`, `logs/prompt.md` | 출처, 제안 채택 여부와 사용자 결정의 보조 근거로 사용한다.                |
| 프로젝트 스킬과 DOX                               | 문서별 소유권, 승인, 기록과 검증 계약을 적용한다.                         |
| 현재 Git 브랜치와 작업 트리                       | 단계별 변경 격리, 커밋 대상과 기존 사용자 변경을 확인한다.                |

저장소, 이슈 또는 대상 서비스가 불명확하면 후보를 제시하고 확인 전 파일을 변경하지 않는다.

## 작업 절차

1. 저장소 루트와 GitHub 저장소를 식별하고 현재 브랜치의 upstream 상태를 확인한다.
2. 루트부터 대상 경로까지 적용되는 `AGENTS.md` 체인과 `spec/DICTIONARY.md`를 읽는다.
3. GitHub 연결 도구를 우선 사용해 이슈 원문, 체크리스트, 댓글, 라벨, 상태와 연결 이슈를 재조회한다.
4. 댓글은 작성자와 문맥을 확인하고, 명시적 결정인지 제안인지 구분한다. 반응 수나 이슈 상태만으로 결정으로 승격하지 않는다.
5. 이슈 내용을 `references/spec-mapping.md`에 따라 요구사항, 상세 설계, 결정, 제안, 미정 사항과 구현 작업으로 분류한다.
6. 기존 `SRS.md`, `SDD.md`와 보조 문서를 읽고 요구사항 ID, 상태, 설계 결정과 미정 사항을 비교한다.
7. 이슈와 명세가 충돌하면 충돌 위치, 가능한 선택지와 영향 범위를 보고하고 사용자 결정 전 변경을 중단한다.
8. 작업 단계를 나누고 단계별 대상 파일, 반영 항목, 완료 조건, 검증, 커밋 메시지, 보존할 ID, 새 ID, 추적 링크, 제외 범위와 작업 후 갱신할 이슈 체크리스트를 제시해 명시적인 승인을 받는다.
9. 요구사항 변경은 `service-design`, 상세 설계 변경은 `detailed-design`, 관계 시각화는 `diagram-creator`, 새 용어는 `dictionary` 스킬의 현재 계약을
   사용한다.
10. 기존 추적 ID를 보존하고 신규 ID는 대상 서비스의 경로 기반 규칙을 따른다.
11. 반영한 요구사항 또는 설계 항목에서 원본 이슈 번호나 URL을 추적할 수 있게 한다.
12. `spec/service/README.md`, `logs/prompt.md`, `reference.md`, `suggestion.md`와 DOX의 갱신 필요성을 각 소유 계약에 따라 판단한다.
13. 승인된 작업 단위별로 파일을 변경하고 해당 단계의 완료 조건과 문서 검증을 수행한다.
14. 검증에 성공한 단계의 승인 파일만 경로를 명시해 스테이징하고 staged diff, 포함 파일과 비밀 정보 가능성을 다시 확인한다.
15. 승인된 메시지로 단계 커밋을 생성하고 커밋 SHA, 포함 파일과 작업 트리 상태를 확인한다. 검증 실패 또는 범위 밖 변경이 있으면 해당 단계를 커밋하지 않는다.
16. 다음 단계가 있으면 13~15단계를 반복하고, 모든 승인 단위가 완료되면 커밋별 변경과 검증 근거를 모은다.
17. 승인된 이슈 체크리스트와 실제 커밋·검증 근거를 항목별로 대조한다.
18. 근거가 충족된 체크리스트만 완료 처리하고 미완료·실패·범위 외 항목은 원래 상태로 보존한다. 사전 승인 범위에 없던 이슈 수정이 필요하면 정확한 변경 내용을 제시하고 별도 승인을 받는다.
19. GitHub 이슈를 재조회해 체크리스트 반영 여부와 의도하지 않은 본문·라벨·상태 변경이 없는지 확인한다. 이슈 종료는 PR 병합 정책이나 사용자의 별도 지시에 따른다.
20. 프로젝트 작업 로그를 기록하고 완료 전 DOX pass를 수행한다.

## 단계별 커밋 원칙

- 파일 변경이 없는 분석, 승인과 GitHub 후처리 단계는 커밋하지 않는다.
- 하나의 커밋은 독립적으로 검토·복구 가능한 하나의 작업 단위를 나타내야 한다.
- 단순 오탈자나 직전 단계의 누락을 의미 없는 별도 커밋으로 분리하지 않는다.
- `git add .` 또는 포괄적 glob을 사용하지 않고 승인된 파일 경로만 스테이징한다.
- 기존 사용자 커밋을 별도 승인 없이 amend, rebase 또는 재작성하지 않는다.
- 커밋 생성은 이 스킬이 담당하고 원격 push와 Pull Request 생성·갱신은 `pr-creator`에 위임한다.
- GitHub Issue에 커밋 링크를 기록해야 하면 `pr-creator`가 push한 원격 SHA를 확인한 뒤 갱신한다.

## 소유 스킬 위임

| 변경 유형                                    | 소유 스킬         | 이 스킬의 책임                                    |
|:---------------------------------------------|:------------------|:--------------------------------------------------|
| 요구사항, 정책, 사용자 흐름, 서비스 색인     | `service-design`  | 이슈 근거와 추적 링크를 전달하고 충돌을 정리한다. |
| 아키텍처, 인터페이스, 데이터 모델, 처리 흐름 | `detailed-design` | 확정 요구사항과 설계 범위를 전달한다.             |
| 구조, 상호작용, 상태, 데이터 관계 시각화     | `diagram-creator` | 문서 근거와 시각화할 질문을 전달한다.             |
| 신규 프로젝트 용어                           | `dictionary`      | 용어 후보와 실제 사용 맥락을 전달한다.            |

한 변경이 여러 유형에 걸치면 각 소유 스킬의 계약을 순서대로 적용하고 결과의 추적 ID와 용어를 일치시킨다.

## 승인 경계

- 이슈와 명세의 읽기·분류·충돌 분석은 파일 변경 없이 수행할 수 있다.
- 명세와 보조 문서 변경, 스테이징과 커밋은 단계별 대상 파일, 검증과 커밋 메시지를 제시하고 승인받은 뒤 수행한다.
- 작업 계획에 이슈 체크리스트 갱신 대상과 조건을 명시해 사전 승인받는다. 승인 범위를 벗어난 본문, 체크리스트, 라벨 또는 상태 변경은 정확한 수정 내용을 다시 승인받는다.
- 완료 근거가 있는 체크리스트 갱신은 작업 후 필수로 수행하지만, 이슈 종료는 자동으로 수행하지 않는다.
- 사용자가 확정하지 않은 제안은 `SRS.md`나 `SDD.md`의 확정 내용으로 승격하지 않는다.

## 실패 처리

| 상황                  | 처리                                                                                      |
|:----------------------|:------------------------------------------------------------------------------------------|
| GitHub 원문 조회 실패 | 캐시나 기억을 최신 원문처럼 사용하지 않고 작업을 중단하거나 한계를 보고한다.              |
| 대상 서비스 불명확    | 후보 경로와 차이를 제시하고 확인 전 변경하지 않는다.                                      |
| 이슈와 명세 충돌      | 어느 한쪽을 임의로 선택하지 않고 결정이 필요한 지점을 보고한다.                           |
| 추적 ID 충돌          | 기존 ID를 재번호화하지 않고 신규 ID 후보와 충돌 원인을 제시한다.                          |
| 검증 실패             | 실패 결과를 보존하고 이슈 체크리스트 완료 후보에서 제외한다.                              |
| 이슈 수정 실패        | 로컬 결과를 되돌리거나 성공으로 보고하지 않고 오류와 미반영 항목을 보고한다.              |
| dirty worktree 충돌   | 승인 범위 밖 변경을 스테이징하지 않고 단계 커밋을 중단해 파일별 충돌을 보고한다.          |
| 커밋 실패             | 오류와 staged 상태를 확인하고 성공한 것처럼 SHA를 기록하거나 다음 단계로 넘어가지 않는다. |

## 제외 범위

- 이슈 문구를 근거 없이 요구사항이나 설계 결정으로 확대 해석
- 이슈 상태만 보고 명세 상태를 `확정` 또는 `완료`로 변경
- 기존 `SRS.md`와 `SDD.md`의 일괄 재구성 또는 추적 ID 재번호화
- 채택되지 않은 제안이나 구현 작업을 확정 명세로 기록
- 승인되지 않은 파일 또는 GitHub 이슈 수정
- `git add .`, 사용자 커밋 재작성, force push
- 원격 push 또는 Pull Request 생성·갱신

## 검증

- 변경 전후 요구사항 ID, 상태와 이슈 추적 링크를 비교한다.
- `service-design` 또는 `detailed-design`의 문서별 검증을 수행한다.
- Mermaid가 변경되면 `diagram-creator`의 구문·의미 검증을 수행한다.
- Markdown 표, 내부·외부 링크, 맞춤법과 자연스러운 한국어 표현을 확인한다.
- 실제 검증 근거가 없는 이슈 체크리스트는 완료 처리하지 않는다.
- 이슈 재조회 결과를 수정 전 상태와 비교해 승인된 체크리스트 외 항목이 바뀌지 않았는지 확인한다.
- 커밋 전 `git diff --cached --check`를 실행하고 staged 파일이 승인된 단계 범위와 일치하는지 확인한다.
- 커밋 후 SHA, 커밋에 포함된 파일과 남은 작업 트리 변경을 확인한다.
