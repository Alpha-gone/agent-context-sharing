# Dictionary

## Overview

프로젝트 전반에서 사용하는 용어를 수집해 `$(project_root)/spec/DICTIONARY.md`에 Markdown 표로 정리한다. 서비스에서 쓰는 용어와 기획 용어를 분리한다. 결과는 자연스러운 한국어 정의를 우선하되, 고유명사와 코드 식별자는 원문을 유지한다.

## Workflow

1. 프로젝트 루트를 정한다.
    - 우선 현재 작업 디렉터리의 Git 루트를 사용한다.
    - 현재 Git 루트 자체가 `spec` 디렉터리라면 그 디렉터리를 `$(project_root)/spec`로 취급한다.
    - 상위 디렉터리에 `spec/`가 있고 그 아래가 현재 작업 영역이면 상위 디렉터리를 `project_root`로 취급한다.

2. 용어 후보를 수집한다.
    - `rg --files`로 프로젝트 파일을 훑되 `.git`, 빌드 산출물, 의존성 디렉터리, IDE 캐시, 바이너리 파일은 제외한다.
    - README, 기획 문서, API 명세, 설정 파일, 코드, 테스트, UI 문자열을 우선 확인한다.
    - 다음 유형을 포함한다: 도메인 용어, 화면/기능명, 데이터 모델명, API/엔드포인트명, 외부 서비스명, 설정 키, 반복적으로 등장하는 약어와 약칭.
    - 일반적인 프로그래밍 예약어, 너무 평범한 조사/동사/형용사, 일회성 파일명은 제외한다.

3. 각 용어를 정리한다.
    - `서비스 용어`: 서비스 사용자, 서비스 화면, 서비스 기능, 서비스 도메인 모델, 사용자 역할, 사용자 행동, 서비스 정책, 외부에 설명되는 제품 개념을 포함한다.
    - `기획 용어`: 저장소 운영, DOX, 스킬, 문서 파일명, 설계 workflow, 임시 명칭, 미정 상태, 내부 작업 절차처럼 현재 명세 작성과 기획 협업을 위해 쓰는 용어를 포함한다.
    - 같은 단어가 두 범주에서 모두 쓰이면 실제 서비스 의미를 `서비스 용어`에 두고, 기획상 사용법은 `기획 용어`에 별도 항목으로 두거나 `비고`에서 구분한다.
    - 분류가 불확실하면 사용자에게 노출되는 서비스 개념인지 먼저 판단하고, 확정할 수 없으면 `기획 용어`에 두되 `비고`에 확인 필요 사항을 남긴다.
    - `단어`: 프로젝트에서 실제로 쓰는 표기를 사용한다.
    - `정의`: 프로젝트 맥락에서 의미가 분명한 자연스러운 한국어로 쓴다.
    - `비고`: 필요한 경우 출처 파일, 관련 개념, 표기 주의사항, 영문 원문, 동의어, 사용 위치를 짧게 적는다.
    - 정의가 불확실하면 추측으로 단정하지 말고 `비고`에 확인 필요 사항을 남긴다.

4. `$(project_root)/spec/DICTIONARY.md`를 작성하거나 갱신한다.
    - 파일이 없으면 새로 만든다.
    - 파일이 있으면 기존 항목을 보존하면서 중복을 병합하고 정의를 보강한다.
    - `## 서비스 용어`와 `## 기획 용어` 섹션을 만들고, 각 섹션 아래에 Markdown 테이블을 둔다.
    - 기존 파일이 단일 표라면 항목을 두 섹션으로 재분류한다.
    - Markdown 테이블 형식을 반드시 유지한다.

```markdown
# 용어 정리집

## 서비스 용어

| 단어 | 정의 | 비고 |
| :- | :- | :- |
| 서비스에서 쓰는 단어가 들어갑니다. | 서비스 맥락의 정의가 들어갑니다. | 출처, 관련 개념, 표기 주의사항이 들어갑니다. |

## 기획 용어

| 단어 | 정의 | 비고 |
| :- | :- | :- |
| 기획에서 쓰는 단어가 들어갑니다. | 기획 협업 또는 문서화 맥락의 정의가 들어갑니다. | 출처, 관련 문서, 확인 필요 사항이 들어갑니다. |
```

## Quality Bar

최종 용어집은 프로젝트 구성원이 바로 참고할 수 있어야 한다. 용어는 각 섹션 안에서 가능한 한 가나다순 또는 알파벳순으로 정렬하고, 동일 개념의 표기가 여러 개라면 대표 표기를 `단어`에 두고 다른 표기는 `비고`에 남긴다. 서비스 용어와 기획 용어가 섞여 보이면 분류 기준을 다시 적용해 섹션을 조정한다.
