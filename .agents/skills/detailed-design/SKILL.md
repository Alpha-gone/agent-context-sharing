# Detailed Design

## 개요

`service-design` 산출물을 근거로 서비스별 `SDD.md`를 작성하고 유지한다. 요구사항을 구현 가능한 구성 요소, 계약, 데이터 구조, 처리 흐름과 검증 기준으로 구체화하되 근거가 없는 설계를 확정하지 않는다.

문서 구조와 표현 규칙은 [문서 작성 기준](references/document-guidance.md)을 읽고 적용한다. 관계 시각화가 필요하면 `diagram-creator` 스킬을 함께 사용한다.

## 필수 입력

대상 서비스 폴더에서 다음 파일을 확인한다.

| 우선순위 | 파일 | 사용 방법 |
| :- | :- | :- |
| 필수 | `SRS.md` | 범위, 요구사항, 정책, 제약, 미정 사항과 추적 ID의 기준으로 사용한다. |
| 조건부 | `reference.md` | 기술 선택과 외부 계약의 근거로 사용한다. 없는 내용을 추측해 보충하지 않는다. |
| 조건부 | `suggestion.md` | `채택 여부`가 정확히 `채택`인 행만 설계 입력으로 사용한다. `미검토`, `미채택`, 빈 상태의 제안은 본문에 반영하지 않는다. |
| 조건부 | `logs/prompt.md` | 사용자 결정과 변경 맥락을 확인한다. 현재 `SRS.md`와 충돌하면 현재 명세를 우선하고 충돌을 보고한다. |

입력 파일이 없거나 서로 모순되어 설계 결과가 달라질 수 있으면 임의로 선택하지 말고 가능한 선택지와 영향을 사용자에게 보고한다.

## 작업 절차

1. 적용되는 `AGENTS.md` 체인과 `spec/DICTIONARY.md`를 읽는다.
2. 대상 서비스와 `SDD.md` 경로를 식별한다. 기본 경로는 `SRS.md`와 같은 폴더의 `SDD.md`이다.
3. 필수 입력을 읽고 요구사항 ID, 확정 사항, 미정 사항, 제약과 채택된 제안을 분리한다.
4. `suggestion.md`를 읽을 때 헤더 이름으로 `채택 여부` 열을 찾고 값이 `채택`인 행만 별도 목록에 수집한다. 부분 문자열이나 문맥으로 채택 여부를 추론하지 않는다.
5. 각 설계 결정을 하나 이상의 요구사항 ID 또는 채택 제안 ID에 연결한다. 근거가 없으면 `설계 미정 사항`으로 남긴다.
6. 구조, 런타임 상호작용, 상태 변화, 데이터 관계처럼 관계 파악이 중요한 부분은 `diagram-creator` 스킬로 시각화하고 검증한다.
7. `diagram-creator`가 반환한 다이어그램과 설명이 요구사항 상태와 설계 결정에 일치하는지 상세 설계 관점에서 확인한다.
8. 보충 설명이 필요한 본문 위치에 문서 내부 링크형 주석 표식을 추가하고, 모든 주석 본문은 문서 하단 `주석` 섹션에 모은다.
9. 요구사항 추적표에서 모든 설계 대상 요구사항의 반영 위치와 검증 방법을 확인한다.
10. `SDD.md`의 Markdown, 내부 링크, 맞춤법과 한국어 표현을 검증하고 Mermaid 검증 결과는 `diagram-creator`의 기준을 따른다.
11. 작업 기록을 적용되는 프로젝트 규칙에 따라 남기고 완료 전 DOX pass를 수행한다.

## 설계 원칙

- 요구사항의 `확정`, `초안`, `검토 필요`, `미확정` 상태를 보존하고 설계에서 임의로 승격하지 않는다.
- 구현 언어, 프레임워크, 저장소, 통신 방식이 확정되지 않았다면 단일 기술을 사실처럼 선택하지 않는다.
- 여러 선택지가 가능하면 선택지별 장단점, 영향받는 요구사항과 결정 필요 항목을 제시한다.
- API, 이벤트, 데이터 모델에는 이름, 책임, 입력, 출력, 오류, 권한, 멱등성, 트랜잭션 경계를 필요한 수준까지 명시한다.
- 성능, 보안, 가용성, 관측성과 운영 요구사항은 측정 또는 검증 가능한 설계로 연결한다.
- 기존 `SDD.md`를 수정할 때 사용자 작성 내용과 유효한 설계 결정을 보존한다.

## 산출물

대상 서비스 폴더에 `SDD.md`를 작성한다. 문서에는 최소한 다음 내용을 포함한다.

- 문서 정보와 설계 범위
- 설계 입력과 채택 제안
- 시스템 컨텍스트와 아키텍처
- 구성 요소별 책임
- 주요 처리 흐름과 상태 전이
- 인터페이스와 API 계약
- 데이터 모델과 저장 전략
- 오류 처리, 보안, 권한, 관측성
- 배포·운영 및 비기능 설계
- 요구사항 추적표
- 설계 미정 사항
- 문서 하단 주석

서비스 특성상 해당하지 않는 섹션은 억지로 채우지 말고 제외 사유를 짧게 적는다.

## 품질 기준

- 본문 문단과 표, `diagram-creator`로 작성한 다이어그램이 서로 같은 설계를 설명해야 한다.
- 모든 주석 링크는 하단 주석으로 이동하고, 각 주석에는 본문으로 돌아가는 링크가 있어야 한다.
- 채택되지 않은 제안이 설계 결정, 다이어그램, 추적표에 포함되지 않아야 한다.
- 요구사항별 반영 위치와 검증 방법을 추적할 수 있어야 한다.
- 문서는 자연스러운 한국어로 작성하되 기술 식별자는 원문을 유지한다.
