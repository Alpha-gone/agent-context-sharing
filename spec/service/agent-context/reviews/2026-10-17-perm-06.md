- 시작 상태: `feat/permission-improve`, `3228f58`. upstream이 없는 로컬 브랜치이며 선행 PERM-01·DATA-03은 완료다. 기존 Compose·IDE 변경은 보존했다.
- 범위: 계정별 생성·수정 빈도, 고정 창·원자성·멱등성·시간/정수 경계, 보존 정책 전달·비소급 유예와 기록 보존의 새 실행 증거.

## 발견 사항과 구현

| ID | 영향도 | 발견 사항 | 처리·검증 |
|---|---|---|---|
| PERM06-R1 | 중간 | 제한이 양수여도 요청 계정이 없거나 UUIDv7가 아니면 빈도 검사를 건너뛰었다. | 생성·일반 수정·대체 생성은 연결 예약 전 요청 계정을 필수 검사한다. 기여 계정·에이전트 대신 전달된 요청 계정만 센다. |
| PERM06-R2 | 중간 | 공통 삭제 전이에서 폐기·복구도 빈도를 소비하여 한도 소진 뒤 상태 전이를 막았다. | 생성·수정·대체에만 카운터를 적용한다. 폐기·복구·그래프 생성·읽기·무제한 호출이 카운터를 바꾸지 않는지 실제 DB에서 확인했다. 복구 저장량 한도는 기존 계약을 따른다. |
| PERM06-R3 | 낮음 | 원천 중복 확인보다 빈도 검사가 먼저여서 소진 뒤 기존 원천 반환도 거부될 수 있었다. | 원천 자연 키 조회 뒤 새 쓰기에만 빈도를 적용한다. 소진 상태에서도 기존 정점을 반환하고 빈도·업무 상태를 늘리지 않는다. |
| PERM06-R4 | 낮음 | 내부 빈도 경로에서 bigint 한도를 int로 변환하고 빈 기준 시각을 허용했다. | 내부 갱신·반환을 int64로 유지하고 잘못된 기준 시각을 DB 접근 전 거부한다. MaxInt64 직전 증가와 상한에서의 거부를 확인했다. 기존 int 공개 API는 유지했다. |

- 기존 조건부 UPSERT와 쓰기·멱등성 저장점의 커밋 경계를 사용한다. 별도 카운터 트랜잭션·새 테이블·공개 로그인 시도 예산을 추가하지 않았다.
- 기존 `RetentionDays` 주입과 운영 회차의 적용/감사·거부 보존 콜백, 플랜의 달력 6개월 타입과 유예 만료 고정 방식을 유지하고 새 표본으로 검증했다. 콜백·패키지·SQL 소유권이 바뀌지 않아 DOX와 마이그레이션은 유지했다.
- SRS의 14개 항목·기본값은 유지했다. 소유 SDD에 빈도 대상·요청 계정 필수·현재 값 적용·롤백/재생·보존 전달을 정합화하고, 트랜잭션 안의 명령이 네트워크 왕복을 없앤다는 부정확한 설명을 바로잡았다.

## 검증 결과 — 2026-10-17

- Go 1.27.1 darwin/arm64. 고정 Dockerfile로 소유 라벨이 있는 전용 이미지·컨테이너·새 볼륨·임시 IPv4 loopback 포트를 사용했다. PostgreSQL 18.6 / AGE 1.8.0 / pgvector 0.8.6, Linux aarch64를 확인했다. 기존 개발 DB·운영 자료·실제 자격은 사용하지 않았다.
- 새 DB에 정식 `001/009/010/011/012`를 적용했다. `agent_context`·vector/128·`all_layers`, tablespace 지정 없음이다.
- **고유 시험·하위 시험 37건 통과**: store 28·plan 7·server 2, 최상위 13·하위 24. `-race -count=1`, DB 범위는 `TEST_DATABASE_REQUIRED=1`을 사용했다. 재실행은 최종 결과로 교체하여 중복 합산하지 않았으며 최종 실패·건너뜀은 0이다.
- UTC 같은 분의 다른 시간대·분 경계 직전/직후·윤일 다음 달, 계정 격리와 상향/하향·무제한 전환을 확인했다. 무제한은 기존 행도 갱신하지 않으며 다시 제한해도 현재 창의 수가 초기화되지 않는다.
- 생성·일반 수정·대체 생성은 요청 계정에 합산되고 기여 계정에는 기록되지 않았다. 한도 소진 뒤 기존 원천 반환·읽기·그래프 생성·폐기·복구와 무제한 생성은 카운터를 바꾸지 않았다.
- 판 충돌·저장량 거부·적용 기록 실패, 업무 저장점 해제 뒤 바깥 실패와 멱등성 결과 JSON 저장 실패에서 본문·누계·색인·감사·카운터를 대조했다. 바깥 실패 표본은 실제 업무 저장 뒤 실패 지점에 도달했고 멱등성 예약도 남지 않았다. 최초 성공은 한 번만 차감되며 소진 뒤 같은 키의 세 번 재생은 업무 함수·카운터를 다시 실행하지 않았다.
- 서로 다른 키의 두 요청이 같은 카운터 행을 실제로 기다리는 것을 관찰한 뒤 잠금을 해제했다. 남은 한 건만 성공하고 다른 요청은 `writes_per_minute`·현재/허용 3을 반환했다. 실제 카운터 잠금 대기 중 취소에서도 상태·빈도가 남지 않았고 4연결 풀의 획득 연결·예약이 모두 회복됐다.
- 적용 기록의 유한/무기한, 거부 기록의 기본 달력 6개월/명시한 30일, 경계와 1마이크로초 뒤, 팀 감사의 행위 계정 정책을 대조했다. 현재 폐기의 복구 근거와 만료된 파생·기존 본문은 유지했다. 유예 시작 시 고정한 만료 시각이 플랜 변경 뒤 소급되지 않고 무기한 유예가 만료되지 않는 것도 재검증했다.
- 운영 조립 대역에서 세 계정의 적용/감사·거부 보존 값과 하나의 UTC 회차 기준 시각을 확인했다. 실제 9종 운영 회차 전체의 인수를 수행한 것은 아니다.
