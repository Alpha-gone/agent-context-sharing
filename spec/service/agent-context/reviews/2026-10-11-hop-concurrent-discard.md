# 홉 조회 중 동시 폐기 검토

## 범위와 근거

- 분석일: 2026-10-11
- 대상: [#124](https://github.com/Alpha-gone/agent-context-sharing/issues/124), `internal/store/hop.go`, `consistency.go`, `hop_bounded.go`
- 요구사항: `FR-AGENT_CONTEXT-052`·`053`·`054`, SRS 「홉 범위 조회」·「요청 단위 일관 읽기」
- 설계 정본: SDD 「고연결 노드의 조회·적재 보호」·「데이터베이스 연결」
- 환경: Go 1.27.1, 개발 DB 컨테이너의 PostgreSQL 18.6·AGE 1.8.0·pgvector 0.8.6. 별도 임시 DB `issue124_test_20261011`에 정식 `cmd/migrate up`을 적용하고 `TEST_DATABASE_REQUIRED=1`로 실행했다. 기존 개발 그래프와 비밀 설정은 사용하지 않았다.

## 재현과 원인

`HopContexts`와 `HopContextsFrom`의 양수 상한 조회에서 후보 선택이 끝난 뒤 본문 묶음 조회 직전에 pgx tracer로 실행을 멈췄다. 원천·파생·근거 간선은 정식 생성 API로 만들었으며, 별도 `DiscardContext` 트랜잭션의 커밋을 완료한 다음 본문 조회를 재개했다. 실행 순서는 신호 채널로 동기화하고 10초의 감시 마감을 두었다.

수정 전에는 스냅숏 없는 두 진입점 모두 이웃 식별자를 지목하는 `missingContextError`를 반환했다. `errors.Is(err, ErrNotFound)=true`와 빈 `HopResult`를 직접 관찰했다. 같은 시험의 검색 스냅숏 경로 두 개는 통과했다. MCP `mapError`는 이 원인을 `not_found`로 사상하므로 시작 노드 부재와 구별되지 않았다. 이 사상은 코드 및 기존 MCP 테스트로 확인했으며, 최초 재현 시험 자체는 저장소 호출을 대상으로 했다.

원인은 스냅숏 없는 후보 선택과 본문 조회가 각각 다른 커밋 상태를 읽는 것이다. 이웃을 건너뛰어 성공시키면 이미 선택한 집합의 거리·절단과 내부 간선 완전성을 보장할 수 없다.

## 설계 선택

단일 홉만 읽기 전용 `REPEATABLE READ` 트랜잭션으로 묶었다. 시작 노드·후보·본문·간선·참조가 하나의 상태를 읽으며, 그 뒤의 폐기는 진행 중인 읽기에 섞이지 않는다. 스냅숏 없는 `HopContextsFrom`은 시작 식별자도 다시 읽어 호출자가 제공한 오래된 본문을 섞지 않는다. 검색은 기존 요청 스냅숏을 재사용하고 다른 직접 읽기의 계약은 바꾸지 않는다.

명시적 오류 정책만 바꾸면 혼합 상태를 제거하지 못한다. 유한 재시도는 동시 쓰기가 반복될 때 작업량을 늘리고 실패 가능성을 남긴다. 홉 하나는 순차 읽기이므로 조정 연결을 추가하는 동기화 스냅숏 대신 한 연결의 읽기 경계를 선택했다. 임베딩 접근 기록은 읽기 연결 반환 뒤 실행하므로 추가 연결을 쥔 채 기다리지 않고, 검색의 예약 수 4개와 읽기 자리 종료 경계도 유지한다.

시작 노드가 읽기 상태에서 없거나 폐기되어 있으면 기존 `not_found`를 유지한다. 읽기·접근 기록 오류와 시간 예산 소진은 빈 결과와 원인을 전파한다. 응답 형식·도구 계약·마이그레이션·배포 구성 변경은 없다. 읽기 연결의 보유 시간이 홉 조립 전체로 늘어나는 대신 기존 30초 공통 예산을 유지하며, DB 취소·정리의 정확한 벽시계 상한이나 성능 개선은 주장하지 않는다.

## 검증

- 신규 회귀 3종을 `go test -race ./internal/store -run 'Test(HopConcurrentDiscard|HopStartReadBoundary|StandaloneHopFitsSmallPool)Integration' -count=10`으로 반복하여 통과했다.
- 동시 폐기 8개 경우: 두 진입점·단일 읽기/검색 스냅숏·양수 상한/한도 없음. 양수 상한은 후보·본문 사이, 한도 없음은 확장·참조 사이를 동기화한다. 본문·노드 순서·거리·간선·참조·절단이 폐기 전 결과와 같으며, 새 조회는 이웃을 제외한다.
- 시작 경계 4개 경우: 두 진입점·두 상한. 새 조회의 시작 부재·폐기는 빈 결과와 `ErrNotFound`이고, 검색 스냅숏은 이전 활성 상태를 유지한다.
- 최소 풀 4개 연결에서 두 진입점의 12개 동시 요청이 모두 완료하고 획득 연결이 0으로 회복했다. 검색 경로는 읽기 자리·활성 트랜잭션이 회복되며 조정 연결 하나만 남는 것을 대조했다.
- 기존 `TestHopSharedBudgetIntegration`·`TestHopAssemblyCancellationIntegration`의 race 실행이 통과했다.
- 작업 파일을 변경하지 않는 overlay에서 단일 홉 트랜잭션만 `Read Committed`로 낮추자 양수 상한의 두 진입점이 다시 `not_found`·빈 결과로 실패했다. 격리 수준의 회귀를 검출하는 것을 확인했다.
- 서버·클라이언트 `go build ./...`, `go vet ./...`와 클라이언트 전체 race 테스트가 통과했다.
- `TEST_DATABASE_REQUIRED=1 go test -race -json ./... -count=1` — 서버 전체 14개 시험 패키지, 테스트·하위 사례 1,227개 통과. 실패와 개별 시험 건너뜀이 없다. 시험이 없는 두 패키지의 JSON `skip`은 통합 시험 건너뜀이 아니다. 마지막에 추가한 최소 풀 회귀는 위 신규 회귀 3종의 10회 반복으로 따로 검증했다.
- `gofmt -l .`·`git diff --check` — 출력·오류 없음. 문서의 한국어·맞춤법·용어·Markdown 구조·상대 링크·Child DOX Index를 확인했다.
- 검증 종료 후 임시 DB의 연결이 0개임을 확인하고 DB와 합성 시험 데이터를 제거했다. 같은 마이그레이션과 시험으로 다시 만들 수 있으며 기존 개발 DB는 변경하지 않았다.

## 결함 상태와 DOX

`DEF-20261011-124`(영향도: 중간)은 위 재현으로 확인되었고 관련 회귀에서 해결을 검증했다. 이 범위에서 남아 있는 미해결 결함은 없다.

루트·서비스 DOX와 SDD에 홉 읽기 경계·동시 폐기·검증 계약을 반영하고 부모의 Child DOX Index 설명을 함께 갱신했다. SRS의 탐색·삭제 제외·간선 완전성 요구를 충족하는 구현 경계의 선택이므로 요구사항을 새로 만들지 않았다. 용어집의 기존 홉 범위 조회·폐기·요청 단위 일관 읽기를 사용하며 정의를 바꾸지 않았다. MCP와 클라이언트는 공개 계약 변경이 없어 수정하지 않았다. 소유권·경로와 하위 문서 구조는 바꾸지 않았다.
