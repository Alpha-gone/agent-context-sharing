# #260 커밋 후 관계 제안 예산과 응답 보존 검토

- 요청: [#260](https://github.com/Alpha-gone/agent-context-sharing/issues/260)을 별도 브랜치에서 수정·검증하고 PR을 생성한다.
- 기준: 저장 후 관계 제안의 실패는 완료 쓰기의 응답을 바꾸지 않는다는 수명주기 계약.

## 재현과 원인

기존 멱등 경로는 관계 제안을 WithoutCancel로 실행해 부모 요청의 마감과 취소를 제거했다. 별도 세션이 커밋 직후 그래프 행을 잠그면 실제 제안이 FOR UPDATE에서 요청 마감 이후에도 대기했다. 회귀 시험에서 3초의 관찰 상한을 넘긴 뒤 잠금을 풀었을 때 커밋 결과가 idempotency 마감 오류로 바뀜을 확인했다. 기존 postcommit cancel 시험도 완료 결과가 아닌 취소 오류를 기대하고 있었다.

키 없는 ExecuteWrite도 apply 내부의 제안이 끝난 뒤 ctx.Err를 검사하고 있어, 두 경로를 공통 완료 후처리 경계로 정리했다.

## 변경

- 저장 후 제안은 요청 취소·더 짧은 요청 마감을 유지한 최대 1초의 실행 예산을 사용한다. 마감 없는 호출에도 상한이 있고 타이머를 반환한다. 기존 트랜잭션 정리의 독립 5초 예산은 유지한다.
- 키 없는 쓰기도 apply 성공·완료 JSON 검증 뒤 후처리 큐를 실행한다. 실패·불완전 결과·진행 중 취소에는 큐를 실행하지 않는다.
- 멱등 쓰기는 실제 커밋 성공 뒤 연결 예약을 반환하고 큐를 실행한다. 그 뒤 제안 때문에 지난 마감·취소로 확정 결과를 덮지 않는다. 커밋 전 실패·취소와 결과가 불확실한 커밋 오류의 경로는 유지한다.
- 후보 비교 루프도 요청 취소를 확인한다. 제안 실패는 기존 고정 reason_code=proposal_failed 진단으로만 남는다. 새 환경 변수·스키마·백그라운드 작업은 없다.

## 검증

- TestPostCommitProposalBudgetIntegration: 사건 생성·갱신 × 키 유무 × 마감·취소·마감 없는 호출의 12개 실제 DB 경합 경로 통과. 커밋 뒤 별도 세션의 그래프 행 잠금과 pg_blocking_pids를 관찰한다. 성공 결과·저장 판·후보 미생성·고정 실패 진단, 대기 중 예약 반환·처리 후 연결 반환과 멱등 결과 재생을 대조했다.
- TestUnkeyedWriteRunsPostCommitOnlyAfterCompletion과 기존 TestMCP05PostCommitCancellationDatabase로 완료 후 취소의 성공 반환, apply 실패·불완전 결과·진행 중 취소의 큐 미실행과 재생을 확인했다.
- 위 경합·완료/취소 시험의 race 검사 통과.
- Go 1.27.3의 go build ./...·go vet ./...·gofmt -l . 통과.
- 전용 DB를 생성·전체 마이그레이션한 저장소·MCP 전체 회귀는 MCP 통과, store 최상위 시험 56건 실패다. 55건은 기존 newEmbeddingContractStore의 적용 수 기대값 8과 016 포함 실제 9의 불일치이고, 나머지는 TestHopStaleStatisticsHubIntegration/stale/both/2의 40067행 적재 상한 실패다. 아래에 실패 이름을 보존한다.
- 기준 dev 7c497f2의 별도 임시 체크아웃·새 전용 DB에서 TestEmbeddingStorageModelsIntegration과 위 홉 사례를 실행해 같은 두 실패를 재현했다. 이번 수정과 분리하며 해당 시험 코드는 변경하지 않았다.
- 초기 접속 대상 DB에 기본 스키마가 없어 난 실패는 별도로 구분한다. 넓은 회귀와 기준 비교 모두 새 작업 전용 DB에 전체 마이그레이션 후 실행하고 자신이 만든 DB만 정리했다.
- 최종 관련 회귀: `go test ./internal/store -run 'TestMCP05|TestPostCommit|TestUnkeyed|TestLifeProposal(OuterCommit|FailurePreservesSave|RankingAndRetention|StrictSubset|RechecksLockedState)' -count=1`을 초기화된 전용 DB·필수 설정으로 통과했다. 위 race 검사도 통과했다.
- 독립 읽기 전용 검토에서 Critical/Important 발견 사항은 없었다. 단독 쓰기의 진단은 실제 단독 커밋, 멱등 저장점의 진단은 바깥 커밋 결과로 유지됨을 확인했다.

## 범위와 기록

수명주기·MCP·시험 설계와 공식 context 근거를 동기화했다. 내부 store의 실행 경계와 기존 소유 문서만 바뀌므로 DOX 구조·색인은 유지한다. 실제 운영 환경과 배포는 변경하지 않았다. 요청 전송 자체가 단절된 경우의 응답 전달 보장을 새로 선언하지 않는다.
