# 요청 단위 일관 읽기 비교

## 목적과 조건

- 측정일: 2026-09-27
- 목적: `FR-AGENT_CONTEXT-152`에 따라 현행 `Read Committed` 검색, 동기화 스냅숏과 내용 판 재시도를 같은 그래프·질의·검색 구성에서 비교하고 운영 방식을 판정한다.
- 데이터베이스: PostgreSQL 18.6, Apache AGE 1.8.0, pgvector 0.8.6, 로컬 Docker 개발 데이터베이스
- 검색 구성: `SEARCH_GRAPH_STAGE=references`, 자동 전역 전환, 채널별 후보 상한 50, 의미 유사도 하한 0.50, 예산 4,000자, 최대 4홉, 홉 노드 상한 200
- 임베딩: `bge-m3:vector:1024`
- 실행 방식: 세 구성 각각을 병렬·순차 실행으로 나눠 여섯 구성을 비교했다.

```shell
go run ./cmd/eval -consistency -consistency-requests 100 -consistency-write-pauses 0,50,250 \
  -contexts <컨텍스트 집합>.json -queries <질의 집합>.json -budget 4000 -max-hops 4 -max-hop-nodes 200 -out <결과>.json
```

## 구현

- 동기화 스냅숏: 조정 연결이 읽기 전용 `REPEATABLE READ` 트랜잭션에서 `pg_export_snapshot()`을 내보낸다. 검색이 부르는 여섯 저장소 읽기는 요청 컨텍스트에 실린 스냅숏을 자기 읽기 전용 트랜잭션에서 `SET TRANSACTION SNAPSHOT`으로 가져온다. 여섯 읽기는 세 진입 채널, 전역 요약, 홉 확장과 출처 조립이다. 조정 트랜잭션은 출처 조립이 끝날 때까지 열어 둔다.
- 내용 판 재시도: `migrations/002_content_revision.sql`이 `context_graph.content_revision`을 더한다. 컨텍스트 생성·갱신·폐기·복구, 관계 확정·폐기, 임베딩 공개와 색인 대상에서 빠진 임베딩 제거 트랜잭션이 값을 올린다. 검색은 전후 값이 다르면 흐름 전체를 다시 실행하며 5회까지만 시도한다.
- 두 후보 모두 질의 임베딩을 먼저 받은 뒤 읽기 경계를 연다. 접근 시각 갱신처럼 쓰기에 해당하는 부작용은 경계 밖 연결에서 실행한다.

## 결과 동등성

동시 쓰기가 없는 상태에서 `own-events-50q` 질의 50건을 여섯 구성으로 실행했다. 컨텍스트·순위·기여 채널·출처·홉 거리·간선·진입점·예산·절단·채널 실패를 대조했고, 모든 구성이 기준 구성과 같았다.

## 동시 쓰기 일관성

표본 그래프는 허브 원천 하나, 허브를 근거로 한 파생 20개와 허브를 구성원으로 한 사건 둘이다. 쓰기 작업자는 세 가지 쓰기를 차례로 돌린다.

- 파생 하나의 폐기 또는 복구
- 사건 관계의 확정 또는 폐기
- 임시 파생의 생성·색인 공개 또는 폐기

쓰기 사이 휴지를 0·50·250ms로 바꿔 구성마다 요청 100건을 보냈다.

판정 기준은 다음과 같다. 활성 컨텍스트 수가 채널 후보 상한보다 작으므로, 한 커밋 상태에서는 활성 컨텍스트가 모두 시간 필터 후보가 된다. 따라서 그래프 경로 채널만 낸 컨텍스트가 응답에 있으면, 확장이 시간 필터와 다른 상태를 읽어 그 사이에 공개된 컨텍스트를 본 것이다. 이 판정은 한 방향의 불일치만 잡으므로 불일치 수는 하한이다.

- 현행 검색은 쓰기가 잦을수록 두 상태를 섞은 응답이 늘어, 병렬 실행에서 최대 35%였다.

- 내용 판 재시도는 초당 10회 이상의 쓰기에서 요청 대부분이 5회 안에 한 판의 결과를 얻지 못했다. 쓰기가 드문 초당 3.3회에서도 요청의 68~72%가 다시 실행되어 평균 지연이 현행의 약 1.5~1.9배였다. 이 방식은 한 그래프의 어떤 쓰기든 요청 전체를 무효로 만들기 때문이다.

- 현행 순차 10회/초 조건의 최댓값 3,757.9ms 한 건이 평균을 끌어올렸다. 다른 조건에서는 재현되지 않았다.

## 판정

- 동기화 스냅숏을 운영 방식으로 채택한다. 결과 동등성과 일관성을 모두 만족했고, 지연이 현행 검색과 같은 수준이며, 재시도 없이 연결 하나를 더 쓰는 비용이 내용 판 재시도보다 작다.
- 내용 판 재시도는 채택하지 않는다. 일관성은 지켰지만 쓰기가 있는 조건에서 결과를 내지 못하거나 지연이 크게 늘었다.
- 서버는 `search.ConsistencySnapshot`을 쓴다. 배포 구성으로 열지 않으며 새 MCP 입력도 없다.
- `content_revision` 열과 증가 지점, 내용 판 재시도 구현은 평가 실행기의 재비교를 위해 남긴다. 운영 검색은 내용 판을 읽지 않는다.

## 한계와 후속 확인

- 검색 서비스 수준 목표의 지연 상한이 아직 정해지지 않았다. 채택은 스냅숏의 지연이 현행과 같은 수준이라는 근거에 기댄다.
- 현행과 내용 판 구성의 요청당 연결 수는 계측하지 않았다. 스냅숏만 읽기 경계에서 연결을 연다. 현행 병렬 실행도 진입 채널 셋을 동시에 실행하므로 동시 연결 차이는 조정 연결 하나로 본다.
- 불일치 판정은 확장이 진입 채널보다 늦은 상태를 읽는 방향만 잡는다. 반대 방향과 출처 조립의 어긋남은 세지 않으므로 현행 검색의 실제 불일치율은 표보다 높을 수 있다.
- 동시 쓰기 표본은 한 그래프에 한 작업자만 쓴다. 여러 요청이 동시에 스냅숏을 붙잡을 때의 연결 풀 포화는 재지 않았다. 풀 하한은 16이고 요청당 동시 연결은 최대 4다.
