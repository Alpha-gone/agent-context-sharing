- 기준: 2026-10-23, `feat/web-foundation`의 `0b922f4` 이후 작업 트리.
- 대상: [OBS-08](../development-plan/observability.md#obs-08), [파일 저장 인수](../sdd/observability.md#파일-저장-인수), [SRS 진단 로그](../SRS.md#종류별-진단-로그).
- 판정: 격리 저장소의 구현·분야 인수 완료. 관측성 8개 작업 완료, 전체 **78/124개 완료·46개 미착수**. 다음 권장은 ARCH-06의 전체 조립이다.

## 산출물과 발견 사항

`acceptance_unix_test.go`는 실제 여섯 파일의 정상·경고·실패와 요청/인가/비동기/독립 작업·test_run·instance·boot를 대조한다. 두 번의 재기동과 슬롯 교체에서도 과거 행·종류·권한을 보존하고, 토큰·본문·질의·URI 표본이 파일과 수집한 stderr에 없는지 확인한다. 기존 OBS-01~07의 전체 시험도 현재 기록기로 다시 실행해 모든 상한·날짜/크기 회전·7일 만료·혼합 파일·잠금·원문 제한을 함께 검증했다.

실제 공유 잠금을 5초 이상 점유한 상태에서 12개 이벤트를 수락하고 기본 5초 Close를 실행했다. 잠금 시간 초과와 종료 마감의 원인을 실제 stderr에서 수집했고 수락 12·기록 0·누락 12, 대기 건수/바이트 0과 작업자 종료를 확인했다. 잠금 해제와 같은 슬롯 재시작 뒤에는 새 boot의 한 행만 저장되어 이전 누락이 재생되지 않았다.

Linux는 다음 방법으로 파일 장애를 검증한다. Go 대역이 성공/실패를 반환하는 것으로 대신하지 않고, 실제 파일을 쓰는 프로세스의 커널 경계를 사용한다.

- ENOSPC·EROFS: 시험 자식 프로세스의 해당 파일 fd에만 seccomp TSYNC 필터로 write 오류를 반환한다. 다른 fd·시스템 호출은 그대로 허용한다. no_new_privs와 일반 UID를 사용하며 추가 특권이나 호스트 마운트 변경은 필요하지 않다. 필터는 시험 자식이 종료되면 함께 끝난다.
- 부분 쓰기: 자식의 RLIMIT_FSIZE 소프트 상한을 한 행의 절반으로 낮춰 실제 파일에 반쪽 행만 남긴다. 상한을 복구한 다음 append가 격리 표식을 남기고 독립 JSON 행으로 회복되는지 검사한다.
- 각 장애에서 첫 이벤트의 누락·원래 커널 오류를 보존하고, 회복한 두 번째 이벤트만 Written으로 센다. 실제 stderr의 고정 원인과 정상 파일의 단일 행을 함께 대조한다.

이 과정에서 0바이트 ENOSPC·EROFS까지 모두 partial_write로 표시하던 구현을 발견했다. 각각 storage_full·storage_read_only로 구분하고 오류 원인을 보존하도록 수정했다. 실제 일부 바이트가 쓰인 경우는 기존 partial_write·격리 복구를 유지한다. 새 설정·외부 의존성·DB 스키마는 없다.

## Linux 재현과 자원 격리

```sh
GO_BINARY=/Users/alphagone/sdk/go1.27.1/bin/go \
GOCACHE=/private/tmp/acs-obs02-go-cache \
sh internal/diagnostic/test-linux.sh
```

Docker 29.8.2와 기존 로컬 Linux/arm64 이미지 `sha256:2b6d51048c03dae147064683f5b078690f1525365d561fd80b78f74de8c3c697`를 사용했다. 이미지가 없으면 내려받지 않고 실패하며 ACS_OBS08_IMAGE로 이미 설치된 Linux arm64/amd64 이미지를 지정할 수 있다. 테스트 바이너리만 읽기 전용 bind하고 기록은 시험 전용 Docker 볼륨에 둔다. 업무 DB·기존 Compose·기존 볼륨·외부 네트워크는 사용하지 않는다.

기본 실행은 UID 501/GID 20, --network none·--read-only·--cap-drop ALL·no-new-privileges다. 빈 볼륨의 시험 하위 경로를 준비하는 한 번의 초기화에만 CHOWN capability를 주며, 기록기는 일반 UID로 실행한다. 처음 생성한 blue 슬롯에서 파일당 3행, 두 번째 컨테이너의 같은 슬롯에서 6행, 세 번째 green 교체에서 새 3행과 이전 blue 6행을 확인했다. 각 컨테이너의 기동 UUID는 새 값이다. 원시 stderr도 별도 파일로 수집했다.

스크립트는 고유 이름·레이블의 시험 컨테이너와 볼륨을 만들고 정상·실패·신호 종료 때 자기 자원만 정리한다. 실제 실행 후 해당 자원의 잔여가 없는지 확인했다. 결과 경로는 0700, 결과 파일은 0600의 임시 디렉터리에 남기며 자격 증명을 주입하지 않는다.

첫 Linux 실행에서는 ENOSPC/EROFS 원인 구분과 시험의 복구 알림 연결 누락을 발견했다. 이를 수정한 뒤 전체를 재실행했다. 같은 초기 host bind 실행에서 기존 종류 상한 시험 하나가 ownership_invalid로 실패했으며, 최종 인수는 파일 공유 계층 대신 시험 전용 Linux 볼륨으로 고정했다. 해당 Docker Desktop host bind의 소유권 동작은 이번 합격 범위에 포함하지 않는다. 최종 스크립트의 전체·읽기 전용·재생성·교체 회차는 모두 실패·건너뜀 없이 통과했다.

## 제한과 문서 정합성

- 디스크 부족은 커널 ENOSPC 주입으로 검증했으며 물리 디스크를 채우거나 실제 저장 매체 손상·전원 차단을 재현하지 않았다.
- 컨테이너 파일·재시작·볼륨 보존은 위 단일 Docker 환경의 결과다. 실제 운영 Compose·Tunnel·다중 호스트 공유 파일 시스템·외부 stderr 수집기의 영속 보관을 완료로 판정하지 않는다.
- DB 감사의 성공을 파일 인수로 대신하지 않았다. 전체 저장소 시험·실제 호스트·운영 배포는 수행하지 않았다.
- DOX pass: 실행 스크립트는 기존 diagnostic 영역의 시험 자산이다. 내부 DOX에 그 소유권을 추가했고 새 하위 DOX 경계나 부모 색인 변경은 필요하지 않다. 실패 계약은 관측성 SDD, 시험 범위는 테스트 SDD, 실행 안내는 README, 현재 상태는 계획·서비스/설계 진입점에 반영했다. SRS는 요구사항 변경 없이 실제 저장 검증 대기 상태만 근거 링크로 갱신했다.

변경 Markdown 12개·상대 링크/앵커 398개, UTF-8·fence·공백과 diff 검사, 실행 스크립트의 sh 구문 검사가 통과했다. 계획 체크박스는 완료 78개·미착수 46개로 일치한다. 시험 결과 디렉터리/파일의 0700/0600과 수집 stderr의 비밀 표본 부재, 시험 컨테이너·볼륨·빌드 임시 경로의 정리도 확인했다.
