# 개발 Compose 노출과 버전 고정 회귀 검증

## 대상과 수정

GitHub 이슈 [#56](https://github.com/Alpha-gone/agent-context-sharing/issues/56)을 대상으로 개발 DB와 Ollama의 호스트 공개 주소를 제한하고 재빌드 시 버전이 바뀌는 경로를 제거했다. 수정 전 Compose 해석 결과에는 `host_ip`가 없었으며 실제 기존 컨테이너의 호스트 바인딩도 빈 주소였다. 새 회귀 스크립트는 수정 전 구성에서 종료 코드 1로 실패했다.

SDD의 개발 환경 경계를 먼저 정리하고 `compose.yaml`의 두 공개 주소를 `127.0.0.1`로 고정했다. `POSTGRES_PORT`·`OLLAMA_PORT`는 포트 번호만 재정의한다. 기본 DB 자격 증명은 로컬 개발용으로 유지하며 `.env.example`에 운영·외부 공개 환경에서 사용하지 않도록 명시했다. HTTP 애플리케이션의 수신 주소·인증·배포 계약은 바꾸지 않았다.

기존 실행 환경에서 확인한 pgvector 패키지 `0.8.6-1.pgdg13+1`과 Ollama `0.33.3`을 사용하여 무관한 버전 업그레이드를 피했다. `Dockerfile`은 전체 패키지 버전을, Compose는 Ollama 태그와 다중 아키텍처 인덱스 digest `sha256:32931b46719f673c05fdbaa81ccb26da18ea4a1c57590a754874ab28ba269eb2`를 고정한다. 레지스트리 조회에서 이 digest와 기존 Ollama 이미지의 RepoDigest가 일치했다. PGDG 인덱스에 해당 패키지 버전이 있음을 확인했고, 패키지가 없어지면 최신 판으로 대체하지 않고 빌드가 실패하도록 했다. 모든 전이 의존성과 외부 패키지 저장소 자체를 영구 보존한 완전한 재현 빌드를 주장하지 않는다.

## 회귀와 결과

Docker Compose v5.4.0, Linux arm64 시험 컨테이너와 Go 1.27.1 SDK를 사용했다.

```shell
sh -n test-dev-compose.sh
sh test-dev-compose.sh
sh test-dev-compose.sh --runtime
sh test-wal-archive.sh
# 서버 루트와 client/에서 각각
go build ./...
go vet ./...
# 저장소 루트
gofmt -l .
git diff --check
```

- 기본 DB 5432·Ollama 11434와 재정의한 15432·21434 모두에서 `host_ip=127.0.0.1`, 대상 포트 유지와 서비스별 공개 포트 하나를 확인했다. WAL 정리 서비스에는 공개 포트가 없다.
- `.env`를 읽지 않는 별도 Compose 프로젝트에서 호스트 포트 0을 지정하여 충돌 없는 임시 포트를 배정받았다. 실제 두 컨테이너의 공개 주소가 모두 `127.0.0.1` 하나임을 Docker inspect로 확인했다.
- 캐시 없는 DB 빌드가 고정 PGDG 패키지로 성공했다. 실제 설치 버전과 `vector=0.8.6`·`age=1.8.0`, pgvector 코사인 거리 연산을 확인했다.
- 두 서비스의 healthcheck가 통과했고, 프록시를 우회한 호스트 loopback의 Ollama `/api/version` 응답이 `0.33.3`이었다. 모델 다운로드·임베딩 호출은 하지 않았다.
- 최초 기동 시험은 베이스 이미지가 AGE를 이미 생성하여 시험의 중복 확장 생성이 실패했다. `IF NOT EXISTS`로 수정하고 최종 스크립트의 전체 기동 검증을 재실행하여 통과했다. 실패 실행의 자원도 정리됐다.
- 기존 WAL 회귀가 새 볼륨·경로 준비 실패 시 기동 차단·기존 볼륨의 데이터 보존·보관 재개·원본 WAL 재활용·보관본 정리를 모두 통과했다. 결함 재현에서 약 176MiB였던 WAL이 복구 뒤 64MiB로 줄고 13개 합성 행이 보존됐으며 복구 뒤 새로운 보관 실패는 없었다.
- 서버·독립 클라이언트 모듈의 build·vet가 통과했고 gofmt 미정리 파일은 없었다. 서버·클라이언트 전체 Go 테스트와 실제 서비스 종단 간 시험은 이번 개발 구성 변경에서 재실행하지 않았다. amd64 실제 기동·모델 추론·운영 배포·다른 호스트에서의 접속 시험도 수행하지 않았다.

## DOX와 적용 경계

루트와 `spec`→`spec/service`→`agent-context`의 DOX 체인을 재확인했다. 루트 `AGENTS.md`에 개발 바인딩·버전 고정과 격리 검사 책임을 기록하고 SDD·개발 계획·공식 근거·요청 기록을 동기화했다. 한국어 표현·맞춤법·Markdown 구조와 상대 링크를 점검했다. 요구사항·도메인 용어·서비스 소유권·MCP 계약·DB 스키마는 바뀌지 않아 SRS·DICTIONARY·서비스 AGENTS와 Child DOX Index는 유지했다.

시험은 별도 프로젝트의 테스트 자격 증명과 새 볼륨만 사용했다. 종료 후 시험 컨테이너·네트워크·볼륨과 프로젝트 전용 DB 이미지를 정리하고 잔여 시험 컨테이너·볼륨이 없음을 확인했다. 기존 DB·WAL 정리·Ollama 컨테이너의 ID·시작 시각·호스트 포트가 검사 전후 동일했다. 기존 `.env`·모델·볼륨·운영 데이터는 변경하지 않았다. 외부 임베딩 API 호출·커밋·푸시·PR 생성·GitHub 이슈 종료는 수행하지 않았다.

기존 실행 컨테이너에는 수정된 바인딩이 아직 적용되지 않았으며 종전의 모든 인터페이스 공개가 남아 있다. 파일 변경만으로는 해소되지 않으므로 적용 시 데이터를 유지하여 다음 명령으로 재생성한다. 이번 작업에서는 실행하지 않았다.

```shell
docker compose up -d --build --force-recreate db wal_cleanup ollama
```

이 변경을 적용하기 위해 `down -v`로 기존 데이터를 삭제할 필요는 없다. 운영 배포의 네트워크·자격 증명·접근 제어는 별도 범위다.
