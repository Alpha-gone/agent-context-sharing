## 발견 사항과 반영

기존 JWKS는 저장된 공개 키 JSON을 해석한 그대로 응답하여 해당 열에 개인 키가 들어가면 공개할 수 있었다. JWKS와 캐시에 같은 ES256·P-256 공개 키 검증을 적용했다. 저장 행과 JWK의 kid·알고리즘·서명 용도를 대조하며 개인/대칭 키·다른 곡선·잘못된 JSON은 고정된 `ErrUnavailable`로 거부한다. 오류에 JSON 해석 원문을 포함하지 않는다. 발급도 저장된 공개·개인 키 쌍과 메타데이터를 확인한다.

기존의 활성 키 유일 제약과 트랜잭션 회전은 유지하고 새 시험에서 실제 저장소와 연결했다. 알려진 공개 키 보존·알 수 없는 kid의 1초 부재 재조회 제한·병행 조회 합치기·로컬 회전 무효화와 웹 폐기 목록 10초 재조회 정책을 상세 설계에 명시했다. 다른 인스턴스의 회전 직후 새 키 반영은 기존 1초 제한 뒤일 수 있다. 목표 Bearer의 매 요청 공유 폐기 확인은 별도다.

## 새 검증 근거

- 공개 키 손상 8개 하위 시험: 공개 열의 개인 키·대칭 키·잘못된 JSON·kid 불일치·행/JWK 알고리즘·용도·곡선을 거부했다. JWKS는 부분 결과를 반환하지 않고 캐시는 적재·정상 부재 시각을 갱신하지 않는다. 검증 오류는 자격 불일치와 구분하고 진단은 고정된 장애 코드, HTTP는 no-store와 일반 server_error만 반환한다.
- 개인 키 손상 5개 하위 시험: 공개 키만 있는 개인 열·잘못된 JSON·kid·알고리즘·키 쌍 불일치는 토큰 발급 없이 거부한다. 합성 키 원문을 실패 메시지에 출력하지 않는다.
- 금지 알고리즘 2개 하위 시험: 실제 HS256·ES384 서명의 형식상 정상 클레임을 키 조회 전에 거부했다. HS256은 공개 자료를 대칭 비밀로 제시하는 표본이다.
- 정상 키의 40개 병행 조회를 하나의 저장 조회로 합치고 취소한 대기 요청이 공유 조회를 취소하지 않음을 확인했다. 만료된 웹 폐기 캐시의 저장소 장애를 오래된 성공으로 바꾸지 않으며 회복 뒤 공유 폐기를 반영한다. 기존 부재 캐시·장애 회복·로컬 폐기와 병행 폐기 조회 회귀도 함께 실행했다.
- 실제 DB의 새 4개 하위 시험: 두 저장소·서비스가 모두 활성 키 부재를 읽은 뒤 동시에 JWKS를 시작하도록 장벽을 두어 하나의 활성 키로 수렴시켰다. 유일 제약·상호 서명 검증·회전 전후 토큰·서비스 재생성·독립 go-jose/JWKS 검증·개인 성분 비노출·활성 1/은퇴 1·취소 회전의 무변경을 확인했다. 별도 기존 저장소 시험 두 건에서 kid 조회와 테이블 잠금 뒤 동시 회전 1성공/1경합을 재검증했다.

## 시험 준비 실패와 복구

첫 실행은 임시 DB 구성의 `ConnConfig.Database`를 바꾼 뒤 `ConnString()`을 다시 사용한 제 실수로 원래 DB에 연결됐다. 이 메서드는 최초 해석한 문자열을 반환하므로 설정 변경을 직렬화하지 않는다. init 마이그레이션 이력 중복 오류로 해당 마이그레이션 트랜잭션이 롤백됐으며 서명 키 시험 본문에는 도달하지 않았다. 키 초기화·회전·행 변경은 실행되지 않았다. 이 준비 실패를 통과로 합산하지 않았다.

시험 URL의 DB 경로를 직접 바꾸고 마이그레이션 전에 `current_database()`가 생성한 고유 DB 이름인지 검사하도록 고쳤다. 정식 마이그레이션·두 저장소는 검증된 같은 URL을 사용한다. 취소와 독립된 제한 시간으로 자신이 만든 DB만 삭제하며 모든 풀을 먼저 닫는다. 최종 실행 후 `auth02_*`와 기존 키 시험의 `signing_key_test_*` DB 잔여 **0개**를 확인했다. 공유 DB의 키를 준비 상태로 만들기 위해 읽거나 변경하지 않는다.
