# #176 관계 후보 보존 정리의 그래프 직렬화

## 원인과 변경

보존 정리는 그래프별로 proposed 목록을 읽고 풀의 자동 커밋 질의로 바로 삭제했다. 확정·폐기가 이미 획득한 context_graph 행 잠금과 충돌하지 않아 판단의 조회·갱신 사이에 후보를 지울 수 있었다. 갱신 0행도 pgx.ErrNoRows 상태로 올라가 내부 오류가 될 수 있었다.

목록의 기존 페이지·순서를 유지하고 삭제할 후보마다 짧은 Read Committed 트랜잭션을 연다. 같은 그래프의 행 잠금 뒤 관계를 다시 읽고 proposed 상태와 ProposedAt 보존 시각을 재확인한다. 조건에 맞는 후보만 같은 트랜잭션에서 삭제·커밋하며 건수는 커밋 성공 후 반영한다. 없어진 후보와 먼저 판단된 관계·새 제안 시각은 무변경으로 처리한다. 삭제 그래프도 보존 정리를 수행하므로 활성 조건 없이 그래프 행을 잠근다. 그래프당 해석·삭제 오류를 모으고 다음 그래프를 계속하는 #160의 경계는 유지했다.

하위 삭제 함수는 pgx.Tx를 요구하여 자동 커밋 호출을 제거했다. updateRelation의 0행은 relationByID와 같은 ErrNotFound로 사상한다. [관계 수명주기](../sdd/context-lifecycle.md#관계-후보-제안과-확정)·[판정의 직렬화](../sdd/context-lifecycle.md#판정의-직렬화)·[운영 참조](../sdd/operations.md#주기-작업)·[시험 설계](../sdd/testing.md#관계-후보-보존-정리의-경합-시험)와 [공식 근거](../reference.md#176-관계-후보-정리와-판단의-직렬화)를 정합화했다. 요구사항·계획·용어·스키마·환경 키·DOX 소유권은 변경할 이유가 없어 유지했다.

## 재현과 AGE 미확인 사항

Go 1.27.3, PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2), AGE 1.8.0을 사용했다. AGE 이미지 판은 Dockerfile의 release_PG18_1.8.0 고정과 일치한다. .env에서 TEST_DATABASE_URL·TEST_DATABASE_REQUIRED=1을 읽고 새 경합 시험마다 전용 DB에 정식 마이그레이션을 적용했다. 시험이 만든 DB만 정리하며 기존 공유 DB의 스키마·데이터 형상을 바꾸지 않았다.

수정 전 그래프 행을 다른 트랜잭션이 잠근 상태에서도 정리가 기다리지 않고 삭제 1건으로 완료되는 것을 재현했다. 수정 후 같은 시험은 public.context_graph의 FOR UPDATE 대기를 실제 차단 세션과 SQL로 확인하고 잠금 해제 뒤에만 삭제했다.

이슈의 반대 순서는 그래프 잠금을 의도적으로 우회한 별도 트랜잭션으로 확인했다. 첫 트랜잭션이 기존 proposed 간선을 confirmed로 갱신한 뒤 커밋을 보류했다. 두 번째 트랜잭션은 아직 보이는 옛 proposed 판에 Cypher DELETE를 실행하여 첫 트랜잭션에 차단됐다. 첫 트랜잭션을 커밋하자 두 번째 DELETE는 삭제 0건과 `XX000: Entity could not be locked for updating` 오류를 반환했다. 두 번째 트랜잭션을 롤백한 뒤 조회에서 confirmed 관계가 남아 있음을 확인했다. 이 판·순서에서는 최신 확정 판 삭제가 관찰되지 않았다. 다른 AGE 판·다른 문장 배치나 직접 SQL까지 일반화하지 않으며, 수정은 해당 엔진 동작에 의존하지 않고 공개 연산을 그래프 행에서 직렬화한다.

## 회귀와 결과

- precedes·relates_to에서 확정·폐기 × 정리 선행/후행의 8개 조합을 실제 Store 메서드로 실행했다. 판단 선행이면 후행 정리는 0건이고 confirmed·discarded 상태가 보존됐다. 정리 선행이면 확정은 정상 처리되고 폐기는 ErrNotFound였다. 행 잠금 대기 없이 단순 지연으로 순서를 추정하지 않았다.
- 목록을 읽고 실제 그래프 잠금에 대기한 뒤 ProposedAt를 새 시각으로 바꿔 커밋했다. 정리가 최신 시각을 다시 읽어 0건 처리하고 후보를 보존했다.
- 그래프 잠금 대기 취소는 취소 원인을 보존하고, 삭제 질의 완료 직후 커밋 전 취소는 삭제를 롤백했다. 두 경우 건수 0·후보 proposed 유지·획득 연결 반환을 확인했다.
- 삭제 그래프의 후보도 정상 정리하고, 0행 갱신은 ErrNotFound로 판정했다. 기존 보존 조건·제안 신호·관계 순환/정체성·동시 판단·사건 폐기 직렬화와 #160의 다음 그래프 계속 처리 회귀도 통과했다.
- `go test -race -json -count=1 -run 'Test(ProposalCleanup|AGERawProposal|CleanupExpiredProposals|DeleteProposedRelation|Periodic|LifeProposal|Concurrent.*Relation|ReconfirmDiscardedRelation|Relation|SimilarProposal|EventDeletionSerialization|LifeEventRelation)' ./internal/store`: 하위 사례 포함 126건 통과.
- `go test -race -json -count=1 -run 'Test(MCP08ToolErrorBoundary|RelationEndpointFailureGuidance|Write)' ./internal/mcp`: 90건 통과. not_found 사상·거부 처리·의존성 실패 우선순위의 기존 경계를 확인했다.

합계 216건이며 실패·건너뜀 없음. check-go.sh의 전체 의존성 검증·build·vet·gofmt·govulncheck와 독립 코드 리뷰가 통과했다. 리뷰에서 확인된 결함은 없었다. 변경 문서의 링크·내부 앵커·용어·Markdown과 git diff --check를 확인했으며 소유 경계가 같아 DOX와 부모 색인을 유지했다.

전체 저장소 시험·실제 운영 부하·배포는 수행하지 않았다. 기존 .env.example·IDE 변경은 포함하지 않는다.
