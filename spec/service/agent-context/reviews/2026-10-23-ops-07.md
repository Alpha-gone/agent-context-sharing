## 산출물과 범위

기존 [기동 래퍼](../../../../docker-db-entrypoint.sh)와 [WAL 회귀](../../../../test-wal-archive.sh)를 새로 실행했다. 이 작업에서 래퍼·개발 보존 정책과 DB 이미지를 변경하지 않았다. [PITR 실행기](../../../../test-pitr.sh)와 [전용 Compose](../../../../compose.pitr-test.yaml), [서버 패키지의 전용 시험](../../../../cmd/server/backup_acceptance_test.go)을 추가하여 실제 물리 백업·WAL 복구·전체 감사를 연결했다. 새 DB에서 정식 마이그레이션을 적용하며 과거 시험 결과를 이번 완료 증거로 승계하지 않는다.

두 실행은 개발 `.env`·기존 볼륨·호스트 공개 포트·외부 API를 사용하지 않는다. PITR은 원본 데이터·cold tablespace·WAL·백업·복구 데이터·복구 cold를 서로 분리한 여섯 전용 볼륨을 사용한다. 새로운 자원 이름은 임시 디렉터리에서 만들고 종료 시 해당 프로젝트의 자원만 정리한다. 서명 키·세션 원문은 합성 클러스터 안에서만 사용하고 출력하지 않는다.

## 검증 결과

환경은 Go 1.27.1, Docker Engine 29.8.2·Compose v5.6.0, Linux ARM64 컨테이너·PostgreSQL 18.6이다. 저장소의 고정 AGE/pgvector DB Dockerfile을 빌드했다. 임베딩은 실제 제공자를 호출하지 않는 128차원 합성 벡터이며 현재 서비스의 `gemini-embedding-2` 모델 ID 계약을 사용한다.

| 검증 | 명령 | 결과 |
|---|---|---|
| WAL 보관 모듈 | `sh test-wal-archive.sh` | 새/기존 볼륨·준비 실패·재기동·보관 재개·재활용·개발 정리 통과 |
| 물리 백업·시점 복구 | `GO_BINARY=/Users/alphagone/sdk/go1.27.1/bin/go GOCACHE=/private/tmp/acs-obs02-go-cache sh test-pitr.sh` | seed·목표 pause·승격 후의 전용 시험과 실제 `cmd/audit` 통과, 생성 자원 정리 통과 |
| 공통 정적 검사 | `GO_BINARY=/Users/alphagone/sdk/go1.27.1/bin/go GOCACHE=/private/tmp/acs-obs02-go-cache sh check-go.sh` | 의존성 검증/빌드·전체 build·vet·gofmt 통과 |
| 셸 문법 | `sh -n docker-db-entrypoint.sh test-wal-archive.sh test-pitr.sh` | 통과 |

PITR의 `TestOPS07PhysicalRecovery`는 하나의 인수 흐름에서 seed·pause·승격 후 세 번 실행하는 시험이다. 이를 서로 독립된 세 인수나 전체 서버 시험 통과 건수로 합산하지 않는다. 원시 로그는 `/private/tmp/acs-ops07-wal.log`, `/private/tmp/acs-ops07-pitr-final.log`, `/private/tmp/acs-ops07-static-final.log`에 남겼다.

1. WAL 회귀에서 새 볼륨은 `archived=2`, `failed=0`, 소유 `postgres`·권한 `0700`이었다. 경로 준비 실패는 DB 기동을 차단했다. 결함을 재현한 기존 시험 볼륨은 보관 대기 11개·WAL 201326592바이트였고, 래퍼 재기동 뒤 원래 12행과 추가 1행을 보존했다. 보관 15개·대기 0개·새 실패 0회, 체크포인트 뒤 WAL 67108864바이트를 확인했다. 누적 실패 6회는 결함 재현 중의 과거 값이다. 10일 된 합성 보관본은 제거하고 최근 파일은 보존했다.
2. 별도 cold tablespace를 포함한 plain `pg_basebackup`과 WAL 스트림을 받았다. tablespace는 백업 경로로 매핑했고 `pg_verifybackup`으로 manifest·기본 백업의 필요 WAL을 검증했다. `PG_VERSION`을 손상시킨 사본은 거부했으며 원래 파일 복원 뒤 검증이 다시 성공했다.
3. 기본 백업 이후 그래프 이름 변경을 커밋한 뒤 `pg_create_restore_point('ops07_target')`를 기록했다. 다시 이름을 바꾸고 큐를 삭제하는 목표 이후 변경을 커밋한 다음 WAL을 전환·보관했다. 복구본은 목표의 이름과 원래 큐를 포함했고 목표 이후 변경은 제외했다. 원본의 목표 이후 상태는 그대로 유지됐다.
4. 새 데이터·cold 볼륨에 백업을 복사하고 `pg_tblspc/<OID>`를 복원 cold 마운트로 연결했다. 같은 DB 이미지에서 실제 WAL을 재생했고 `pg_is_in_recovery()`·`pg_is_wal_replay_paused()`가 참인 상태와 목표 데이터를 함께 대조했다. 준비 상태만으로 목표 도달을 판정하지 않았다.
5. 일시 정지 중 계정·등급·등록·키·큐·임베딩·그래프와 AGE 정점/파생 간선의 SHA-256 지문이 기준과 일치했다. 실제 Cypher 파생 관계, hot/cold HNSW 실행 계획과 cold 경로, 기본 백업 전에 발급한 세션의 서명·계정 검증 및 전체 불변식 감사도 성공했다. 작은 표본의 강제 계획은 성능 결과가 아니다.
6. 명시적 재개 뒤 recovery가 거짓인 것을 확인했다. 실제 저장소 검색이 두 계층의 노드를 반환했고 복원된 pending 작업을 합성 처리기로 소비한 뒤 색인 준비 검사를 통과했다. 독립 `cmd/audit`는 그래프 1개·위반 0개로 종료했다. 각 시험 프로젝트의 자원을 정리했고 기존 개발 DB·정리 컨테이너 ID `92c7e1cbedef`·`a723cdb82258`은 유지됐다.

## 시험 준비 보완과 제한

초기 시험 준비에서 세 가지를 수정했다. 일반 검색이 cold를 hot으로 옮기는 접근 기록을 남기므로 pause 중에는 읽기 전용 검사만 수행하고 실제 검색은 승격 뒤로 옮겼다. 한 `psql -c`의 복수 문장은 암묵 트랜잭션이므로 목표 이전 변경·복구 지점과 목표 이후 커밋·WAL 전환을 각각 분리했다. 감사 실행기의 실제 Gemini 메타데이터 검증에 맞춰 임의 8차원/옛 모델 대신 현재 모델·128차원을 사용했다. 마지막 실행에서는 모두 통과했으며 서비스 정책이나 감사 검증을 완화하지 않았다.

전체 서버/저장소 시험·race·Linux AMD64 runtime·실제 브라우저/호스트·외부 제공자·전체 운영 장애·운영 배포는 실행하지 않았다. WAL 회귀의 작은 크기 설정은 개발 시험 전용이며 디스크 상한·복구 시간·손실 허용 시간·외부 보관 완결성을 보장하지 않는다. 운영에서는 백업과 연속 WAL·timeline history를 외부에 보호하고 실제 대상·보존 범위를 별도로 확인해야 한다.

DOX pass에서 루트에 두 격리 실행기의 소유권을 기록했다. 새 지속 영역이나 환경 키는 추가하지 않아 하위 DOX·Child DOX Index·환경 예시·SRS는 유지했다. 운영/시험 SDD는 복원·검사 경계를, OPERATIONS는 실행 절차를, 계획·진입점·README·서비스 색인은 실제 진행 상태를 소유하도록 갱신했다. 기존 Compose·IDE 변경은 보존했고 이번 변경은 미커밋이다. upstream이 없어 원격 비교·push는 수행하지 않았다.

최종 문서 검사에서 Markdown 12개의 상대 링크·앵커 488개와 개발 체크박스 124개(완료 84·미착수 40), UTF-8·한글 표기 및 git diff 공백 검사가 통과했다. OPS-08의 미완료 선행 OPS-02를 확인해 다음 권장을 정합화했다.
