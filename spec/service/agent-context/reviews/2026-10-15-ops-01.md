# OPS-01 고정 이미지·개발 DB 격리 환경 검토

## 범위와 선행 조건

2026-10-15에 [OPS-01](../development-plan/operations.md#ops-01)을 완료했다. 시작 커밋은 `7bc09a7`, 브랜치는 `feat/data-schema-contract`다. 원격 fetch 후 upstream인 `origin/dev` 대비 뒤처짐 0·앞섬 1을 확인했다. 선행 [ARCH-01](../development-plan/architecture.md#arch-01)은 완료 상태이며, DATA-01에서 지정한 DATA-02 이전 개발 DB 준비를 수행했다.

기준은 [운영 환경 경계](../sdd/operations.md#개발운영-환경-경계)·[WAL 경로](../sdd/operations.md#백업과-복구)·[고정 버전](../sdd/architecture.md#버전-요구)이다. 기존 파일의 존재나 과거 시험을 완료 근거로 승계하지 않고, 현재 구성에 대한 정적 검사와 새 프로젝트의 캐시 없는 빌드·DB 질의를 실행했다.

## 구현과 확인한 계약

- DB Dockerfile의 AGE tag/digest와 PGDG 완전 패키지 판을 유지했다. 공식 레지스트리에서 고정 digest와 `linux/amd64`·`linux/arm64` manifest를 확인했고 실제 실행은 `linux/arm64`에서 수행했다. Dockerfile의 설계 참조 주석을 분야별 SDD 이름에 맞췄다.
- 개발 Compose와 DB 기동 래퍼는 계약에 맞아 유지했다. 기본 서비스는 DB·WAL 정리뿐이며, 서버/마이그레이션은 `server` profile이다. DB는 기본 5432·재정의 15432·runtime 임시 포트 모두 IPv4 loopback만 사용한다. 별도 모델 서비스·profile·볼륨은 없다.
- `test-dev-compose.sh`에 DB 빌드 구성·프로젝트 전용 볼륨/네트워크·AGE preload·WAL 보관 명령·정리 사용자/주기·기동 의존 검사를 추가했다. 서버 profile의 기본 80→8080 공개·기동 순서·공유 앱 이미지·터널 네트워크와 좁은 신뢰 경로도 대조한다.
- 정적 검사는 `--env-file /dev/null`·합성 DB 자격과 `--no-env-resolution`을 사용한다. runtime은 시험 override의 `env_file: !reset []`로 비활성 migrate/server의 `.env` 참조도 제거한다. `.dockerignore`의 `.env`·`.env.*` 제외를 검사하여 빌드 입력에 실제 자격 파일을 넣지 않는다.
- runtime에서 DB와 WAL 정리 이미지를 모두 `--no-cache`로 빌드하고 `up --no-build`로 실행한다. 새 볼륨·컨테이너의 프로젝트 label, 실제 loopback 포트, PostgreSQL 주 판·확장/패키지 판·WAL 디렉터리의 postgres 소유/0700·preload/archive 설정을 검사한다. 합성 그래프를 생성하고 AGE 반환값 42와 코사인 거리 0을 확인한다.
- 성공·실패 종료에서 시험 프로젝트만 `down --volumes --rmi local`로 정리한다. 컨테이너·볼륨·네트워크 목록 조회 실패나 잔여 자원은 실패로 판정하며, 자원 반환 확인 뒤에만 정리 성공을 출력한다.
- `.env.example`에 전용 시험 DB와 필수 실행 설정의 의미를 명시하고 README의 격리 검사 범위·정리·별도 인수를 갱신했다.

## 새 검증 결과

실행 환경은 Docker Engine `29.7.2`, Docker Compose `v5.4.0`, DB 플랫폼 `linux/arm64`다.

| 검증 | 결과·관찰 |
|---|---|
| `sh -n test-dev-compose.sh` | 통과 |
| `sh ./test-dev-compose.sh` | 기본/재정의 DB 포트·profile·WAL·네트워크·이미지/패키지 고정·빌드 비밀 제외 검사 통과 |
| `sh ./test-dev-compose.sh --runtime` | 최종 코드로 `dev-compose-test-gtgspm` 프로젝트의 캐시 없는 두 이미지 빌드·기동·SQL·정리 통과 |
| DB 설치 판 | PostgreSQL 18, AGE 1.8.0, vector 0.8.6, PGDG `0.8.6-1.pgdg13+1` 일치 |
| 실제 AGE/벡터 SQL | `ops01_test` 그래프의 Probe 값 42, 동일 벡터 코사인 거리 0 |
| 격리·권한 | 프로젝트 전용 새 볼륨, 양의 임시 loopback 포트, WAL 경로 postgres:postgres:700, archive_mode=on·preload=age |
| 정리 | 시험 컨테이너 두 개·이미지 두 개·볼륨·네트워크 제거, 프로젝트 label의 잔여 컨테이너·볼륨·네트워크 없음 |
| 합성 정적 fixture 6건 | 잘못된 합성 `.env`는 무시해 통과. 공개 DB 바인딩·넓은 프록시 신뢰·잘못된 pgvector 판·꺼진 WAL·외부 볼륨은 각각 실패로 거부 |

첫 실행에서는 레지스트리 메타데이터 조회 지연이 있었으나 빌드·runtime·정리가 통과했다. 이후 `.env` 참조 제거와 자원 검사 보강을 포함한 최종 코드로 다시 실행해 위 결과를 확보했다. 엔진 재시작이나 기존 컨테이너·볼륨 변경은 수행하지 않았다.

## 완료 판정과 후속 범위

OPS-01의 기본 기동·캐시 없는 DB 빌드·설치 판·loopback·SQL 응답 조건을 충족했다. 다음 준비된 항목은 [DATA-02](../development-plan/data.md#data-02)의 새 번호 스키마·마이그레이션 실행기다.

서버 이미지·실제 server/Tunnel 접속 상대·외부 HTTPS·Gemini·OAuth/MCP·진단 볼륨·운영 배포는 실행하지 않았다. WAL 생성/보관 재개·체크포인트 재활용·보관본 정리·물리 백업/시점 복구는 OPS-07에서 인수하며, 이번 WAL 설정/권한 확인으로 완료 처리하지 않았다. `linux/amd64`와 다른 Compose 판의 runtime도 미실행이다. Go·SQL 변경이 없어 Go 빌드/시험과 마이그레이션 DB 시험은 실행하지 않았다.

DOX pass에서 소유권·경로·안정적인 작업 계약이 바뀌지 않았음을 확인하여 DOX·Child DOX Index·SRS·SDD·용어집을 유지했다. 사용자 변경인 운영 Compose의 두 줄과 IDE 파일은 보존했다. 운영 템플릿·진단 구성은 OPS-02의 별도 범위다.
