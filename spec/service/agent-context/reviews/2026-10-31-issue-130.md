# #130 관계 끝점 거부 원인과 연결 경로 안내

## 확인한 사실

- 실패한 실제 요청과 원본 응답은 확보하지 못했다. 이슈에 첨부된 서버 로그에는 `POST /mcp`의 HTTP 200만 남아 있다. MCP 도구 거부는 HTTP 200의 완료 결과(`isError=true`)로 반환되므로 로그로는 도구·인자·응답을 구분할 수 없다.
- MCP 도구 중 `from_context_id`를 입력으로 받는 것은 `relation_confirm`뿐이다. `node_create`는 이 필드를 받지 않으므로 사용자가 받은 `field: from_context_id`는 `relation_confirm`의 거부다.
- `relation_confirm`이 `invalid_argument`·`field: from_context_id`를 반환하는 조건은 다음과 같다. 모두 같은 고정 문구 "도구 입력을 확인해 주십시오."로 응답했다.
  - 시작 끝이 사건(`layer=event`)이 아님. 저장소의 계층 검사와 모델 검증이 같은 필드로 거부한다.
  - 시작 사건이 폐기됨.
  - `precedes`·`causes`의 시작 사건이 대상보다 늦게 시작함.
  - 입력 형식 오류(UUIDv7 아님 등)의 도구 입력 검증.
- 관계 확정은 노드 생성과 별도 도구 호출이다. 관계가 거부되어도 앞서 성공한 `node_create`는 되돌리지 않는다.

보고된 "관계 연결이 안 되고 별도 소스로 생성됨"은 다음 호출 순서와 맞는다. 에이전트가 새 원천을 만든 뒤 원천 또는 다른 비사건 노드를 `relation_confirm`의 끝으로 지정했고, 계층 검사에서 거부되어 원천만 남았다. 원본 요청이 없으므로 이 경로를 추정으로만 기록한다. 원천·파생을 기존 노드에 연결하는 계약상 경로는 생성 때의 `derived_from`(파생 근거)·`member_refs`(사건 구성원)이며, 사건 관계는 활성 사건 사이에만 있다.

## 결정과 변경

- 모델에 관계 끝점 거부 원인 세 가지(`ErrRelationEndpointNotEvent`·`ErrRelationEndpointDiscarded`·`ErrRelationTimeOrder`)를 두고 `FieldError.Cause`로 담는다. 저장소의 계층 검사도 같은 원인을 담는다. 검증 메시지와 필드 이름은 바꾸지 않았다.
- MCP 쓰기 거부 사상은 `invalid_argument`·필드를 유지하면서 원인별 고정 안내 문구를 고른다. 사건이 아닌 끝점에는 `derived_from`·`member_refs` 연결 경로와 "앞서 만든 노드는 그대로 남는다"는 부분 성공 상태를 안내한다. 폐기된 끝점에는 활성 사건 지정을, 시간·포함 제약 위반에는 관계 유형별 시간 조건을 안내한다. 입력 원문과 모델 메시지는 응답에 넣지 않는다. 오류 코드·부가 정보 종류는 늘리지 않았다. SRS는 상세 메시지를 구현이 정하도록 두었다.
- 도구 설명을 보완했다. `node_create`는 기존 노드 연결을 생성 때의 계층별 참조로 지정하고 사건 사이 관계만 생성 뒤 확정한다고 설명한다. `relation_confirm`과 두 끝점 필드는 활성 사건 조건, `part_of`의 부분·전체 방향, 거부가 노드 생성을 되돌리지 않음을 설명한다. 이슈 댓글이 가리킨 Go MCP SDK의 필드 설명(`jsonschema`)과 같은 목적이며, 이 서버는 명시 스키마의 `description`으로 제공한다.
- [MCP 설계](../sdd/mcp.md)의 도구 설명·도메인 실패 절과 [시험 설계](../sdd/testing.md)를 갱신했다. 두 도구 스냅샷(`internal/mcp/testdata/tools.json`·`cmd/server/testdata/mcp09_contract.json`)은 생성 절차로 갱신했으며 바뀐 것은 두 도구의 설명 문자열뿐이다. 요구사항·추적표·DOX의 소유권과 구성은 바뀌지 않아 유지했다.

## 검증

- 모델 단위 시험은 원천 끝·폐기된 끝·시간 역전이 같은 필드에서 서로 섞이지 않는 원인으로 거부되는지 확인한다.
- MCP 단위 시험은 네 원인 사례의 코드·필드·안내 문구와 입력 원문 비노출, 다른 필드의 기존 고정 문구를 대조한다. 수정 전 `write_handlers.go`를 overlay로 쓰면 네 원인 사례가 실패했다.
- 실제 DB 시험은 원천을 시작·대상 끝으로 지정한 확정, 시간이 뒤집힌 `precedes`, 폐기된 끝의 원인과 필드를 대조하고, 유효한 사건 관계 확정이 성공하는지 확인한다.
- Go 1.27.1, 작업 전용 합성 DB 컨테이너(정식 마이그레이션 적용), `TEST_DATABASE_REQUIRED=1`, `-p 1`의 필터 없는 `model`·`store`·`mcp`·`cmd/server`·`web` 실행: 4071건 통과, 실패 0건. 건너뜀 21건은 서버의 물리 복구·전환·Codex CLI 실제 환경 인수이며 통과로 보고하지 않는다.
- 두 스냅샷을 갱신 변수로 생성한 뒤 갱신 변수 없이 다시 실행하여 일치를 확인했다. `check-go.sh`의 의존성·`go build`·`go vet`·`gofmt` 검사, 변경 Markdown의 링크·앵커를 확인했다. 검증 후 소유 라벨의 합성 컨테이너와 익명 볼륨을 제거했다.
- 실제 호스트에서 같은 요청을 재현하지는 않았다. 원본 요청을 확보하면 위 추정 경로와 대조한다.
