## 구현 결과

`internal/web`는 사전 등록과 code·단일 scope·S256을 확인하고, 웹 세션이 없으면 기존 로그인에 내부 next를 전달한다. 로그인 뒤 요청을 복원하고 유효 세션에도 명시적 동의를 요구한다. GET은 코드를 생성하지 않으며 POST는 기존 출처 검사·공유 예산·8 KiB 본문 보호 뒤 세션·요청·허용/거절을 확인한다. 계정은 쿠키 검증 결과만 사용한다. 오류·성공 리디렉션은 검증된 callback에만 state·고정 iss를 반환한다. 중복/잘못된 query·미등록 결합은 로컬 오류로 종료한다.

동의 화면은 의미 있는 form·fieldset·legend·허용/거절 submit 버튼을 사용한다. no-store·no-cache·no-referrer·프레임 차단을 적용했다. form-action self는 POST 뒤 등록 callback 이동까지 제한할 수 있어 적용하지 않고 양식 action을 내부 경로에 고정했다. 브라우저 구현 간 차이의 실제 인수는 후속 범위다. 웹에서 authz를 직접 import하지 않으며 서버 어댑터가 좁은 인가 인터페이스를 연결한다.

`internal/authz`는 난수 코드의 SHA-256과 60초 수명·계정/client/callback/resource/scope/challenge 결합을 저장한다. `/token`은 중복 없는 URL-encoded POST 본문만 받고 query 병합·다른 인증 방식·64 KiB 초과를 거부한다. 최초 성공은 ES256 접근 JWT(1시간·고정 issuer/resource·계정·jti·scope·client_id·grant_id), Bearer 외피와 32바이트 난수의 불투명 갱신 값을 반환한다. 갱신 원문은 저장하지 않는다.

`internal/store`는 코드 소비·서명·계열·첫 갱신 해시를 한 트랜잭션에 묶는다. 키는 잠금 전에 읽고 서명 콜백은 추가 DB 연결을 확보하지 않는다. 만료는 행 잠금을 얻은 뒤 현재 시각으로 재판정한다. 소비 경합 뒤에는 트랜잭션을 다시 열어 계열→코드 잠금 순서를 유지한다. 올바른 결합의 코드 재사용은 60초 자체 만료 뒤에도 연결한 계열의 폐기를 커밋하고 invalid_grant를 반환한다. 잘못된 verifier는 계열을 폐기하지 않는다. 최초 계열은 코드 발급 시각 기준 30일 절대·7일 비활동·절대 만료+1시간 보존을 기록한다. 이 수명의 최초 저장 인수와 갱신 회전 인수를 구분한다.

서명·저장·취소 실패는 최초 교환을 롤백하고 응답 자격을 비운다. 내부 오류는 고정된 unavailable/server_error로 사상하며 원인은 내부 체인으로 보존한다. HTTP 로그에는 경로만 기록하고 코드·토큰·verifier·쿠키·비밀번호·state를 기록하지 않는다. 정식 010 스키마를 사용했고 마이그레이션·환경 구성·Compose를 바꾸지 않았다.

## 모듈 시험과 실행 결과

Go 1.27.1, `-count=1 -race -json`, DB 필수 설정으로 아래 범위를 실행했다. 재검증은 새 테스트·실패 수정 또는 영향을 받은 범위로 한정했다. 아래 건수는 최종 성공 결과를 테스트 이름으로 합친 중복 제외 값이며 실패 실행을 포함하지 않는다.

- 인증 **248건**: 요청/PKCE 형식, 난수·해시·수명, 안전한 오류·취소, token JSON·메서드·중복·본문 형식·64 KiB 미만/정확/초과와 기존 인증 회귀. 실제 DB에서 결합 위반·60초 만료·행 잠금 대기 후 만료·독립 서명/클레임·갱신 해시/수명·8건 동시 교환·만료 후 재사용·재시작·서명/저장 장애·취소 롤백을 확인했다.
- 웹 **436건**: 명시적 동의 GET/POST·허용/거절·로그인 복원·쿠키 계정·출처 거부·미등록 결합·중복·scope/PKCE 오류의 state/iss·본문 상한·공유 로그인 예산·장애·취소와 기존 웹 회귀. 기존 Node.js 화면 시험과 격리 DB 권한 시험도 실행됐다.
- 선별 서버 **239건**: 정규식 `^(TestOAuth.*|TestWebSession.*|TestWebCredentialErrorMapping|TestPublicAuthentication.*|TestOPS03.*|TestTransportSecurity.*|TestClientAddress.*)$`. 실제 TLS 로그인→동의 화면→거절/허용→코드 교환→재사용 오류, 웹 세션 독립성·자격 비노출·라우팅 전 TLS와 기존 관련 회귀를 확인했다.

- 루트 `check-go.sh`: 의존성 검증·SDK 링크·`go build ./...`·`go vet ./...`·`gofmt -l .` 통과. 로그 `/private/tmp/acs-auth07-check-go.log`.

## 실패·복구와 격리

최초 실행은 sandbox의 Docker socket 접근 거부로 시험에 진입하지 못했다. 기존 개발 DB 주소를 넘기는 실행기도 자동 승인 검토에서 격리 근거 부족으로 거부됐다. 실행기를 수정하여 postgres 관리 DB에서는 이번 실행의 무작위 auth07_suite DB만 생성/정리하고, Go 시험의 TEST_DATABASE_URL은 그 전용 DB로 고정했다. 기존 시험 준비 함수도 실제 업무·키 작업 전에 시험별 자식 DB를 만들고 정식 마이그레이션과 DB명 대조를 수행함을 확인했다. 승인 후 실행했으며 각 실행의 suite DB 삭제·부재를 확인했다. 공유 개발 DB를 스키마·계정·키 준비 대상으로 사용하지 않았다.

첫 정적 검사에서 시험의 미사용 import를 제거했다. 실제 교환 시험에서는 go-jose v4.1.1의 Claims가 map[string]string을 받지 않아 최초 발급이 실패했다. 적용 판 공식 builder 소스로 map[string]any/struct 계약을 확인해 수정한 뒤 관련 모듈·실제 TLS 시험을 통과했다. 추가한 잠금 대기·정확한 본문 경계와 최종 CSP 보완도 영향을 받은 범위에서 재검증했다.
