## 구현과 범위

- `event.go`: 여섯 종류의 고정 basename, 공통 JSON 외피와 검증, Source를 받는 Reporter. 기존 소비자의 `RecordDiagnostic` 인터페이스는 유지하고 안전 필드를 받는 `RecordFields`를 추가했다. NewReporter 생성자는 조립 Source를 필수로 받도록 바꿨으며 기존 제품 코드에는 해당 생성자의 호출부가 없었다.
- `fields.go`: 요청·인증·검색·색인·관리·시스템의 값 필드와 허용 코드 목록. 실제 14종 MCP 도구·다섯 검색 채널과 현재 검색 경로/이유를 대조했다. 검증 필드명 `body`·`password`·`request_id`는 고정 필드명이며 값·해시를 받는 자리는 없다.
- `trace.go`: 표준 uuid.NewV7로 발급한 요청·작업·시험 ID, 이미 확인한 비밀이 아닌 인가 흐름의 연결과 context 값 전파. 사용자 request_id나 헤더를 correlation_id로 가져오는 API는 제공하지 않는다.
- 확인한 계정·그래프·컨텍스트·관계·계열·작업 ID는 정규 UUIDv7만 허용한다. 공개 client 이름은 사전 등록 확인을 호출자에게 요구하며 안전한 이름 범위 밖의 선택 ID는 생략한다. UUID 형식 검사나 identity_verified 표시는 실제 인증·대상 조회를 대신하지 않는다.
- 진단 누락의 false를 호출자에게 그대로 돌려준다. 커밋·롤백 결과를 임의 추정하지 않고 호출 지점이 전달한 허용 상태를 보존한다.

실제 파일 준비·권한·잠금·append는 OBS-02, 대기열·16 KiB 제한은 OBS-03, 회전·보존·상한은 OBS-04, 실제 처리 지점의 계측·큐 메타데이터 연결은 OBS-05, 파일 장애·stderr·종료는 OBS-07, 파일 통합 인수는 OBS-08 범위다. 이번 인수는 파일 저장 완료를 주장하지 않는다. DB·네트워크·배포 설정·업무 감사 계약은 변경하지 않았다.

## 문서·DOX와 남은 조건

안전 필드와 흐름의 구현 세부는 관측성 SDD, 진행 상태는 개발 계획, 검증 증거는 이 기록에 유지했다. SDD 진입점·README·서비스 색인과 요청/근거 기록을 동기화했다. diagnostic의 책임·소유 정본은 기존 internal DOX에 있으므로 중복 하위 DOX를 추가하지 않았다. 새 패키지·내부 import·저장 스키마·환경 변수는 추가하지 않았다.

현재 브랜치에는 upstream이 없어 원격 뒤처짐을 판정하지 못했다. 기존 compose.prod.yaml·IDE 변경은 보존했으며 이번 작업에서 commit·push·PR·배포는 수행하지 않았다.
