# #198 재색인 진행률 UUID 조회와 관측 주기

- 대상: [이슈 #198](https://github.com/Alpha-gone/agent-context-sharing/issues/198).
- 기준: `dev`의 `beb6e8a`, 브랜치 `perf/198-reindex-progress-join`.

## 변경과 결정

기존 진행률은 embedding UUID 열을 text로 바꿔 targets와 조인하여 context_id 인덱스를 쓰지 못했다. targets의 식별자를 UUID로 한 번 변환하고 임베딩 UUID 열 자체를 비교한다. 대상이 64건 이하이면 UUID 배열로 두 파티션을 한 번 조회한 vectors 집합을 옛 모델·미색인 계산에 재사용한다. 64건을 넘으면 CASE의 집합 조인/NOT EXISTS 경로를 실행하고 vectors·UUID 배열은 실행하지 않는다. 큰 활성 집합의 대상별 반복 probe와 무제한 배열을 피하기 위한 내부 고정 상한이며 최적점이나 운영 지연 보장은 아니다.

UUID 변환만 바꾼 예비 질의는 그래프 범위에서는 인덱스를 쓰지만 전체 범위에서는 보관 행의 순차 집계를 계속 선택했다. 대상별 반복 집계는 보관 행이 많은 경우를 개선했으나 활성 대상 10,005건에서 약 50,871 buffers를 사용하여 채택하지 않았다. 최종 경로는 작은 묶음의 인덱스 접근과 큰 집합의 플래너 선택을 구분한다. 전체 대상·작업을 열거하는 비용은 남는다.

옛 모델 행·미색인·대기·실패의 집계 및 그래프·원천 제외 범위는 유지한다. 특히 제외 계층·삭제된 정점의 보관 벡터는 대상에서 빼되 남은 작업의 실패/리스는 숨기지 않는다. 전체 항목이 0이어도 새 미색인·대기·실패를 관측해야 하므로 기동 및 1분 관측 주기는 유지한다. 손상된 비UUID 속성은 조회 오류가 될 수 있으며 기존 UUIDv7 저장 계약을 전제로 한다. 스키마·새 인덱스·공개 설정은 추가하지 않았다.

[색인 정본](../sdd/indexing.md#전환복귀-경계)과 [시험 설계](../sdd/testing.md#테스트-계층)에 반영했다. DOX pass에서 소유권·구조·색인 변경이 없어 기존 DOX를 유지했다.

## 실행 계획과 값

Go 1.27.1, PostgreSQL/AGE 고정 로컬 이미지 `sha256:2b6d51048c03dae147064683f5b078690f1525365d561fd80b78f74de8c3c697`의 별도 합성 컨테이너를 사용했다. vector/halfvec 각각 독립 DB에서 활성 대상 5건·hot/cold 보관 벡터 1,000/10,000행을 준비하고 ANALYZE했다. 실제 SQL/인자를 pgx tracer로 수집하여 강제 플래너 설정 없이 EXPLAIN ANALYZE/BUFFERS를 실행했다.

- 수정 전에는 두 UUID context_id 인덱스를 사용하지 않아 16개 작은 집합 계획 사례가 실패했다. 진행률 값 자체는 기대값과 일치했다.
- vector·보관 10,000행·전체·원천 포함 기준: 기존 임베딩 읽기 20,008행·333 buffers·1.690ms, 최종 4행·9 buffers·0.062ms. hot/cold context_id 인덱스를 사용한다. Context 대상 읽기 5행은 유지한다.
- 같은 표본의 진행률은 변경 전후 OldModelEmbeddings=3, Missing=4, Pending=4, Failed=1이다. 그래프 범위는 2/3/3/1이며 원천 제외의 옛 모델/미색인은 1/2다. 원천을 제외해도 기존 대기/실패 집계는 유지한다.
- halfvec·같은 전체 표본은 최종 4행·9 buffers·0.072ms였다. 그래프/전체·원천 포함/제외의 각 기대값을 대조했다.
- 활성 대상 10,005건의 vector 전체 집계는 기존 20,008행·1,177 buffers·6.777ms, 최종 20,008행·1,179 buffers·8.868ms였다. 큰 집합에서 보관 행 감소를 주장하지 않으며 같은 집합 집계 경로와 추가 분기 비용을 기록한다. halfvec 최종은 8.064ms·1,137 buffers였다.
- 63/64/65건 경계와 빈 대상도 값이 같았고 작은 경계의 인덱스 사용을 확인했다. 65건에서는 대량 집계 경로를 허용한다. 대상이 없는 경우에도 진행률 0과 남은 작업 집계의 기존 동작을 유지한다.

시간은 로컬 단일 실행 표본이며 시스템 부하·통계에 따라 달라진다. 기준 원본은 수정 전 질의를 실행한 `/tmp/acs198-red.log` 및 기준 index.go의 Go overlay로 동일 dense 표본을 실행한 결과다. 원본 집계와 새 집계가 같은 값인 것을 우선 검증하고 실제 행·버퍼와 지연을 구분해 기록했다.

같은 SQL을 named PREPARE로 8회 반복한 대조에서는 generic plan의 대량 조회가 23.047ms·100,893 buffers의 반복 인덱스 접근으로 바뀌었다. 이 질의만 `pgx.QueryExecModeExec`로 실행하여 named plan 재사용을 피하고, 그래프 조건의 UUID cast를 명시했다. 마지막 회귀는 실제 tracer 인자의 실행 모드와 대량 상태 8회 반복의 값 일치를 검증한다. SQL에는 Go 기본형 인자만 사용하며 pgx의 text 인코딩·서버 타입 추론 계약을 확인했다. 다른 저장소 질의의 캐시 정책은 바꾸지 않았다.

## 검증과 검토

- 계획 캐시 보완 전 관련 DB/race 125건이 실패·건너뜀 없이 통과했다. 모델/입력 판·원천 제외·재색인 등록·취소·형상 전환과 진행률 범위 계약도 포함한다.
- 읽기 전용 독립 검토에서 CASE/CTE의 수요 실행, graph_id 재검사, 중복 물리 행·대상·공집합 및 단일 SQL 스냅숏 의미를 확인했고 수정이 필요한 결함은 발견되지 않았다. 검토자는 DB 접근이나 추가 시험을 실행하지 않았다.
- 계획 캐시 보완 전 `go test -race -p 1 -json ./internal/store ./internal/index -count=1 -timeout=15m`에서 저장소 전체 1,793건이 통과했다. 그 뒤 이 함수의 실행 모드·명시 cast를 보완하고 `-run 'Reindex|QueryIndex|IndexReadiness|IndexTargets|^TestWorker'`의 저장소 관련 136건을 최종 코드에서 다시 검증했다. 보완 후 저장소 전체를 다시 실행하지 않았으며 관련 경계 재검증과 구분한다.
- 예비 색인 인수는 8차원 기반 DB가 Gemini 구성의 최소 차원 조건과 맞지 않아 7건 실패했다. 전용 128차원 합성 DB를 새로 구성한 최종 `go test -race -json ./internal/index -count=1 -timeout=5m`은 전체 129건이 실패·건너뜀 없이 통과했다. 최종 관련 저장소도 실패·건너뜀 없음이다.
- `go build ./...`, `go vet ./...`, `gofmt -l .`, `git diff --check` 통과. 최종 실행 모드와 타입 추론의 독립 재검토에서도 결함은 발견되지 않았다.
- 문서의 로컬 링크·앵커를 확인했다. 전용 합성 컨테이너와 연결된 익명 볼륨만 정리한 뒤 issue198 label 컨테이너와 해당 볼륨이 남지 않은 것을 확인했다. 기존 개발·다른 시험 자원은 유지했다.
