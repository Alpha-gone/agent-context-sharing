# 현재 노드 삭제 채널과 감사 기록 보존 검증

## 범위와 처리 결과

2026-10-10에 [GitHub #104](https://github.com/Alpha-gone/agent-context-sharing/issues/104)를 처리했다. 기준은 원격 `dev`와 일치하는 `7b383a9`이며 작업 브랜치는 `fix/issue-104-restore-channel`이다. 기존 사용자 IDE 설정 staging은 보존했다.

처리기의 `HasAppliedDiscard`는 같은 대상에 과거 적용 폐기 기록이 하나라도 있으면 복구를 허용했다. 현재 `deleted_at`과 연결되지 않아 MCP 폐기→복구→웹 삭제 뒤에도 MCP 복구가 가능했고, 일반 감사 정리는 현재 폐기의 복구 근거도 지웠다.

- SDD의 「폐기와 복구의 채널」을 먼저 정합화했다. 별도 채널 속성이나 기록 식별자 참조를 추가하는 방안과 기존 기록으로 판정하는 방안을 비교하고, 현재 삭제 시각 이후에 같은 트랜잭션에서 남긴 적용 폐기 기록을 근거로 사용하는 방식을 채택했다. 별도 채널 값과 스키마는 추가하지 않았다.
- MCP 복구 허용 판정을 처리기 사전 조회에서 저장소 상태 변경 트랜잭션으로 옮겼다. 모든 계층의 삭제·복구가 대상 정점을 잠근 뒤 현재 상태를 다시 읽고, 사건은 기존 그래프→정점 잠금 순서를 유지한다. 복구의 조건부 갱신은 정확한 삭제 시각도 대조하여 원천의 고정 판 번호 1에서 삭제 회차가 바뀌는 경우를 구분한다.
- 현재 폐기의 적용 기록은 보존 기간이 지나도 유지한다. 정리 질의가 정점과 기록을 한 명령에서 대조하며, 복구가 끝나거나 새 웹 삭제로 이전 근거가 끝나면 만료 기록을 정리한다. 거부 기록과 관계 기록은 이 보존 예외에 포함하지 않는다.
- 웹 복구가 필요한 거부는 MCP 응답과 거부 감사 기록 모두 `not_supported`로 사상하고 `alternative_channel=web`을 반환한다. 공개 도구 이름·입력·오류 코드 집합은 유지했다.
- 이전 정리에서 이미 소실된 폐기 근거는 자동 재생성하지 않는다. 현재 삭제와 대응하는 기록이 없으면 웹 복구로 안내한다. 이는 이미 소실된 출처를 추측해서 MCP 권한을 넓히지 않기 위한 제한이다.

## 검증

Go 1.27.1 `darwin/arm64` SDK를 사용했다. 개발 PostgreSQL 서버에 별도 시험 DB `issue104_test_20261010`을 생성하고 정식 `001_init` 마이그레이션을 적용했다. `TEST_DATABASE_URL`, `TEST_DATABASE_REQUIRED=1`을 사용했으며 기존 개발 DB와 키·컨테이너 구성은 변경하지 않았다. 시험 실행마다 전용 DB를 삭제했다.

- 원천·파생·사건 각각의 MCP 폐기→복구→웹 삭제→MCP 복구 거부, 보존 기간 이후의 현재 폐기 근거 유지, 복구 뒤 만료 기록 정리와 웹 감사 정리 뒤 MCP 복구 거부: 통과.
- 최소 연결 풀 4개와 실제 DB 잠금 대기로 웹 복구·재삭제 또는 새 MCP 폐기를 선행시키고, 대기한 MCP 복구가 현재 채널을 다시 판정하는 양방향 시나리오: 세 계층 모두 통과.
- 웹 복구가 미커밋인 동안 병행 감사 정리를 실행하고 복구를 롤백한 뒤 MCP 복구: 통과. 현재 폐기 근거가 유지됐다.
- 실제 MCP 처리기에서 과거 폐기·복구 기록이 있는 노드를 소유자가 웹 삭제한 뒤 편집자의 MCP 복구를 거부하고, 웹 대체 채널과 `not_supported` 감사 기록을 남기는 시험: 통과. 최초 실행에서 감사 사유가 `invalid_argument`로 남은 것을 확인하고 오류 사상을 보완했다.
- 서버 전체 `go test -count=1 -race -p 1 -timeout=180s -json ./...`: 종료 코드 0으로 통과.
- fixture의 색인 작업 정리를 추가한 뒤 저장소·MCP 전체 시험을 패키지 병렬로 실행했을 때 기존 내용 판·색인 시험 일부가 실패했다. 같은 변경의 순차 실행(`go test -count=1 -race -p 1 -timeout=180s -json ./internal/store ./internal/mcp`)과 상세 실패 출력을 수집하도록 보완한 병렬 재실행(`go test -count=1 -race -timeout=180s -json ./internal/store ./internal/mcp`)은 각각 시험·하위 시험 415건 통과, 실패 0건, 건너뜀 0건과 종료 코드 0이었다. 앞선 실패는 재현되지 않았고 당시 상세 오류를 확보하지 못했으므로 원인을 확정하지 않는다. 새 회귀 fixture는 자기 컨텍스트의 색인 작업만 정리하며 다른 데이터는 변경하지 않는다.
- 서버·클라이언트 각각 `go build ./...`, `go vet ./...`: 통과. `gofmt -l .`, `git diff --check`: 출력 없음. 클라이언트 코드는 수정하지 않았으며 이 작업에서 클라이언트 race 시험은 재실행하지 않았다.
