# EVAL-07 지속 평가 여섯 시나리오 모듈 인수

## 범위와 판정

[EVAL-07](../development-plan/evaluation.md#eval-07)의 실행·상태·기록·전후 집계 기능을 인수한다. [SRS 지속 평가](../SRS.md#지속-평가)와 [평가 설계](../sdd/evaluation.md#검증을-가능하게-하는-설계)를 기준으로 새 전용 DB에서 검증했다. 선행 EVAL-05·LIFE-09의 완료나 기존 시나리오 코드를 새 검증 근거로 승계하지 않았다.

실제 CLI의 여섯 시나리오·각 10회는 상태·적용 기록 검사를 통과했다. 각 시나리오의 같은 입력을 반복한 표본은 독립 단위 하나이므로 세 지표의 신뢰구간은 `-1`, 품질 판정은 `deferred/insufficient_independent_units`다. 모듈 구현 완료를 공개 품질 유지 입증이나 최종 채택으로 해석하지 않는다.

## 구현과 시나리오

각 회차는 새 계정·새 그래프의 적재→색인 준비→동일 질의 전후 측정→상태/기록 확인→독립된 10초 정리를 거친다. 전이는 `references`, 나머지 다섯 시나리오는 `baseline`을 사용하며 보고서에 조회 시각·색인 대상·회차별 검색 단계와 독립 단위를 남긴다. 정리 오류·취소는 호출자에게 전파한다.

- 온라인 갱신: 원천 세 개의 실제 추가·활성 상태와 이전 답의 본문·판·속성 보존 및 검색을 대조한다.
- 재생: 실제 `keep` 전후 객체를 대조하고 유지가 내용·판·속성을 바꾸지 않았는지와 과거 답의 재검색을 확인한다.
- 전이: 새 사건이 새 배경 원천과 기존 파생 지식을 구성원으로 참조한다. 변경 전후 검색 응답의 파생·근거 노드와 `derived_from` 간선을 함께 확인한다. DB에 간선이 있다는 사실만으로 반환 경로를 합격 처리하지 않는다.
- 복구: 폐기 상태를 확인하고 복구 전 같은 검색에서 제외되는지 검사한 뒤 복원한다. 복원 후 활성 상태·검색 반환과 판 번호 외 내용·속성 보존을 확인한다.
- 망각: 파생의 만료와 별도 컨텍스트의 폐기를 실제 적용한다. 기본 검색 제외, 만료 전 시점의 시간 검색 포함, 폐기 상태의 시간 무관 제외와 만료 파생의 직접/홉 조회를 구분한다.
- 상충 해소: 두 의견의 동시 반환, `disputed`→`uncertain` 변경과 기존 `supported` 의견의 보존을 검사한다. 해소 뒤에도 같은 질의로 상태 변화를 확인할 수 있게 질의 관련 본문을 유지한다.

보고서에는 검사별 논리 값과 판단 표식별 확인 결과를 남기고 질의·본문·계정/에이전트 식별자는 넣지 않는다. 저장소의 새 `HasAppliedOperationJudgment`는 해당 그래프의 적용 성공 기록만 인정한다. 거부 기록·다른 그래프의 같은 표식은 성공 근거가 아니며 기존 일반 `HasOperationJudgment`의 전체 기록 조회 계약은 유지한다.

실제 일부 검색 채널 실패는 측정을 중단한다. `disabled`와 진입점이 없는 정상 빈 결과의 `graph/no_entry_points`는 조회 장애로 세지 않는다. 측정한 문자 수는 보존하고 지속 평가에서 측정하지 않는 지연·근거 품질 등의 지표는 기존 `-1` 표식을 유지한다.

## 전후 집계와 보류

여섯 시나리오 모두 재현율·순위 역수·정답당 문자의 세 비교와 `passed`·`failed`·`deferred` 및 사유를 출력한다. 빈 시나리오·미측정 지표를 비교 누락이나 정상 0으로 바꾸지 않는다. 반복을 먼저 독립 단위 안에서 평균하고 단위별 대응 차이로 집계한다. 입력 순서를 바꿔도 집계 결과는 같다.

각 독립 단위의 1~10회 누락·중복·범위 오류, 단위 부족·미측정 지표는 품질 유지 합격이 아니다. 상태·기록 위반 또는 유효 구간에서의 유의한 악화는 실패로 표시한다. 별도 두 단위의 통제 표본에서 유지·세 지표의 악화·미측정/NaN/무한대·불완전 반복·상태/기록 실패를 대조했다. 단위 하나의 열 번 반복으로 품질 입증을 부풀리지 않는다.

## 실행 결과와 실패 이력

최종 고유 시험은 **491건**(최상위 **144건**, 하위 사례 포함)이다. 평가 실행기 **468건**과 관련 저장소 **23건**의 별도 명령을 합산했으며 실패·건너뜀 없이 통과했다. 평가 패키지에는 새 26건과 기존 실제 CLI·준비·정리·취소 회귀가 포함된다. 중복 실행과 초기 실패는 이 수에 더하지 않는다.

- 환경: Go 1.27.1, 직접 생성한 `acs-eval07-db`의 PostgreSQL 18.6·AGE 1.8.0·pgvector 0.8.6, vector 768·정식 마이그레이션 6개. 외부 임베딩은 로컬 HTTPS 대역으로만 실행했다.
- 최종 평가: 새 `eval07_final` DB에서 `go test -race -count=1 -json -timeout=240s ./cmd/eval` 전체 명령이 **90.967초**에 통과했다. `-run`·`-skip`으로 범위를 줄이지 않았다. 실제 지속 CLI 보고서의 60회·여섯 판정·원문 비노출을 검사했다.
- 저장소: 별도 `eval07` DB의 `go test -race -count=1 -json -timeout=90s -run '^(TestStoreIntegration|TestPlanRetentionPoliciesIntegration|TestDerivedLifecycleRollbackIntegration|TestEvidenceInvalidationConflictRollsBackIntegration)$' ./internal/store`가 **5.663초**에 통과했다. 일반 기록·보존·롤백 경계를 대조했다.
- 두 실행 모두 `TEST_DATABASE_URL`·`TEST_DATABASE_REQUIRED=1`을 설정했다. DB 미실행을 통과로 처리하지 않았다. `GO_BINARY=/Users/alphagone/sdk/go1.27.1/bin/go sh check-go.sh`의 의존성·전체 build·vet·gofmt도 통과했다.

첫 모듈 시험은 복구 중 정상 빈 결과를 장애로 센 점, 전이의 긴 신규 본문이 고정 512자 예산을 소진한 점, 미래 조회 시각과 기본 검색의 현재 시각을 혼동한 만료 준비를 드러냈다. 정상 빈 결과를 구분하고 전이 표본을 예산 안에 구성했으며 만료 시각 전후 조회를 직접 대조하도록 수정했다. 부분 실패 시험의 누락 실행 구성도 보완했다. 재검증에서는 앞선 정리 거부 시험이 의도적으로 남긴 같은 이름의 그래프가 정리 집계에 섞여, 시나리오 시험의 입력 판을 실행마다 고유하게 만들었다. 최종 검증은 새 DB에서 전체 명령으로 완료했다.

시험 뒤 두 DB의 잔여 클라이언트 연결 0개를 확인했다. 직접 만든 컨테이너·익명 볼륨을 정리하고 기존 개발 DB·개인 IDE 파일은 보존했다. DOX pass에서 새 패키지·환경 변수·마이그레이션·소유 경계 변경이 없어 기존 DOX를 유지했다. 분야 정본·계획·진입 상태·서비스 색인·공식 근거와 요청 기록을 함께 갱신했다. 전체 계획은 110개 완료·1개 진행·13개 미착수이며 다음은 EVAL-08이다.
