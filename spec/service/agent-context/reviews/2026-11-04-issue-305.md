# #305 MCP 도구 컨텍스트 사용량 원인 분석

## 범위와 판정

2026-11-04 사용자가 이슈의 기존 분석과 별개로 원인을 조사하도록 요청했다. 대상은 dev `f601e501170bd0e70c05a87f1bfe535da64dbdac`이며 기존 댓글의 `5abde86`도 같은 방법으로 비교했다. 최초 조사에서는 제품 코드·SRS·설정·이슈 본문을 변경하지 않았다. 이후 사용자가 브랜치에서 개선 구현을 요청했으며 결과는 아래 1차 구현 기록에 구분했다.

서버의 큰 정적 도구 정의는 확인했다. 반복 정규식과 중복 설명이 주요 비용이고, 고정 14종을 한꺼번에 노출하는 구조가 이를 확대한다. 호출마다 도구가 중복 등록되어 늘어나는 현상은 확인되지 않았다. 후속 사용자 확인으로 측정 클라이언트는 Claude Code 앱이다. 버전·모델과 실제 모델 전송 요청은 미확인이므로 스크린샷의 과금량·상시 적재·중복 주입 여부는 단정하지 않는다.

## 이슈·이미지와 독립 측정

- [이슈 #305](https://github.com/Alpha-gone/agent-context-sharing/issues/305)의 이미지를 직접 내려받아 확인했다. 보이는 11행의 표시값 합계만 약 14,328이다. node_create는 4.3k, node_update는 2.2k로 표시되며 k는 반올림된 값이다. 따라서 5k는 전체 합계를 특정하는 수치가 아니다.
- 화면 머리의 MCP 도구 23개와 현재 서버의 14종은 다르다. 전체 호스트 도구와 본 서버 도구를 분리해야 하며 이미지의 23개가 모두 본 서버라는 근거는 없다. 호스트는 사용자 확인으로 Claude Code 앱으로 확정했다. 이미지 자체에서 모델·집계 방식은 식별하지 못했다.
- 스냅샷을 JSON으로 해석한 뒤 tools 배열만 UTF-8 compact JSON으로 직렬화했다. instructions는 원문이며 합계는 `tools_json + "\n" + instructions`다. JSON-RPC 외피·호스트 변환/시스템 프롬프트 비용은 포함하지 않는다.
- tiktoken 0.12.0의 o200k_base·cl100k_base로 실제 문자열 인코딩 수를 계산했다. 모델 API·자격 증명·과금 호출은 사용하지 않았다. 두 인코딩은 OpenAI 비교 기준이며 Claude 또는 이 이미지의 실제 사용량을 뜻하지 않는다. 문자/4 계산을 실제 토큰으로 부르지 않는다.

|---|---:|---:|---:|---:|---:|---:|
| 기존 댓글 기준 5abde86 | 26,415 | 34,258 | 10,696 | 377 | 11,073 | 12,822 |
| 현재 dev f601e50 | 28,526 | 36,805 | 11,505 | 464 | 11,969 | 13,831 |

기존 댓글의 문자·바이트 측정은 tools 배열 기준으로 재현된다. 다만 실제 BPE 8.5k~11.5k나 2k~3k까지 절감이라는 수치는 인코딩·호스트 입력·측정 방법이 없어 검증된 결론으로 승계하지 않는다. 현재 측정은 동일 문자열에서도 인코딩만 바꾸면 11,969↔13,831로 달라진다.

## 확인한 비용 원인

1. `internal/mcp/tool_catalog.go`의 newToolCatalog는 toolDefinitions의 InputSchema를 내부 검증에 사용하고 register는 같은 스키마를 복제해 SDK에 등록한다. JSON Schema의 정규식·조건식·반복 설명이 모델용 공개 표현에도 모두 들어간다. Go 헬퍼의 재사용은 코드 중복을 줄일 뿐 wire JSON의 중복은 줄이지 않는다.
2. 현재 UUIDv7 정규식이 32회 반복된다. tools 전체에 pattern 키가 73개이며 정규식은 메타문자 분할로 문자 비중보다 토큰 영향이 크다. 설명만 줄이는 접근은 가장 큰 비용 요소를 남긴다.
3. node_create는 세 계층과 선택 필드·상호 배타 조건을 한 스키마에 담는다. 현재 9,229자·o200k 3,428토큰이다. node_update 1,582, relation_confirm 1,033토큰과 함께 큰 비중을 차지한다.
4. `internal/mcp/http.go`는 완전한 14종 처리기를 요구하고 catalog.register가 전부 등록한다. 읽기 5종은 o200k 약 2,264, 나머지 9종은 약 9,244토큰이다. 서버는 작업 종류나 현재 등급에 맞춰 목록을 좁히지 않는다. 이 목록을 모델에 즉시 적재할지는 호스트 결정이다.
5. 스냅샷은 스키마의 변경 일치를 검사하지만 토큰/크기 예산을 검사하지 않는다. #131의 보강은 tools o200k 10,382→10,696, +314(+3.0%)였다. 당시 보강 전에도 이미 1만 토큰 규모여서 #131 단독 주원인으로 볼 수 없다. #306 병합은 tools+instructions 11,073→11,969, +896(+8.1%)였다.

## 별도로 구분해야 할 원인

- **초기 도구 정의와 실행 결과:** writeResult의 structuredContent/text 이중 표현은 실제 존재하지만 도구를 호출하기 전의 목록 크기를 만들지 않는다. MCP 2026-07-28은 구조화 결과와 호환용 JSON text 동시 반환을 권고한다. 이중 wire 표현이 모델 컨텍스트에도 두 번 들어가는지는 호스트 변환을 관찰해야 하며 즉시 제거할 결함으로 단정하지 않는다.
- **MCP 응답 캐시와 모델 프롬프트 캐시:** ttlMs=0/private와 HTTP no-store는 발견/목록 재조회 비용에 영향을 줄 수 있다. 그러나 모델에 입력되는 스키마의 크기나 모델의 prefix cache를 직접 정하는 값은 아니다. TTL만 늘려 5k 문제가 해결된다고 할 근거가 없다.
- **항상 전량 적재 가정:** 현재 Claude Code 공식 문서는 Tool Search로 도구 정의를 지연 적재할 수 있다고 설명한다. 설정·모델·플랫폼·버전에 따라 전량 적재로 돌아갈 수 있다. 이미지의 호스트는 Claude Code 앱으로 확인됐지만, 버전·모델·설정과 해당 화면의 loaded/deferred 구분이 없어 이 기능의 적용 여부는 미확인이다. 도구별 예상 비용 목록 표시만으로 매 요청에 전량 적재됐다고 확정하지 않는다. 모든 호스트가 발견 결과를 항상 그대로 주입한다는 기존 댓글의 일반화는 성립하지 않는다.
- **등록 누적·응답 팽창 가설:** NewHandler가 14종을 한 번 등록하고 sdkTransport는 같은 서버를 반환한다. SDK AddTool은 같은 이름을 교체한다. 반복 발견/목록 및 서로 다른 인증 주체에 대한 기존 시험에서도 14종을 유지했다. 서버 자체의 등록 누적 근거는 없다. 실행 결과 누적과 실제 호스트의 도구 이중 연결은 별도 조사 대상이다.

## 권고와 남은 확인

측정 호스트는 Claude Code 앱으로 확인됐다. 다음으로 버전·모델, 활성화 직후의 전체 도구 목록/지연 적재 상태, 첫 요청의 실제 tools/system 입력 또는 제공자 usage를 확보해야 한다. 모델별 측정 없이 5k 같은 공통 한도를 보장하지 않는다.

서버 개선은 내부 엄격 검증을 유지한 상태에서 공개 스키마의 반복 정규식·중복 설명을 줄이는 방향이 우선이다. required·enum·계층별 필수 조건·기본값·관계 의미·안전한 재시도 안내를 보존하고, 공개 스키마가 기존 입력과 같은 규칙이라고 오인되지 않게 명세를 정리해야 한다. 크기뿐 아니라 invalid_argument 재시도·호출 성공률과 실제 호스트의 총 입력 비용을 함께 비교한다. 필요 시 호스트의 Tool Search/도구 선택을 함께 검토한다. 최초 조사 시점에는 개선 구현을 수행하지 않았다.

## 후속 확인

사용자가 스크린샷의 측정 환경을 Claude Code 앱이라고 확인했다. 문제의 관찰 기준은 해당 앱의 표시값이며, 이 보고서의 tiktoken 결과는 원인 요소를 비교하기 위한 별도 실험값이다. 특히 정규식 제거 시 o200k 38% 감소는 Claude Code에서도 정확히 38% 감소한다는 뜻이 아니다. 개선 전후 판단은 같은 앱·모델·버전·세션 조건의 표시값과 실제 적재 상태로 수행해야 한다.

## 채택한 1차 구현과 계획

사용자가 위 권고 범위를 별도 브랜치에서 구현하도록 요청했다. 브랜치는 fix/305-mcp-tool-context이며 기준 dev f601e50에서 기존 분석 기록을 보존해 분기했다. 새 도구·필드·의존성·DB migration은 추가하지 않았다. 최초 브랜치 작업 당시 commit·push·PR 생성은 포함하지 않았으며 후속 커밋 요청의 결과는 아래 별도 절에 기록한다.

- 원본 toolDefinitions는 서버의 엄격 검증 정본으로 유지한다. 공개 메타데이터는 JSON 왕복으로 분리한 복사본에서 스키마의 pattern만 제거한다. required·enum·조건식·형식·길이/개수 상한·닫힌 객체와 annotations는 유지한다. const/enum/example 안의 데이터는 스키마로 순회하지 않는다.
- 원본과 공개 표현은 register의 호출 경계에서 분리한다. 실제 도구 호출은 기존 definition.validate로 검증하고 요청별 해석 결과·행위자/권한·멱등성·오류를 유지한다.
- 공통 instructions와 도구/필드 설명은 짧게 정리하되 등록, 계층별 필수, 관계/근거/탐색의 의미, 기본값, 폐기 채널, 명시 앞 사건, 안전한 재시도 규칙을 보존한다.
- 공개 compact tools JSON 전체 22,000 UTF-8 바이트 이하, 단일 도구 7,000바이트 이하, instructions 1,500바이트 이하를 회귀 예산으로 둔다. 이는 결정적 로컬 크기 예산이며 Claude 실제 토큰 보장이 아니다. 같은 tiktoken 비교 측정과 실제 Claude Code의 loaded/deferred·실사용 관찰은 구분한다.

1. [x] MCP 모듈 시험 시점: 공개 표현/원본 독립성·제약 보존·실제 HTTP 입력 거부·크기 예산 시험을 작성하고 변경 전 실패를 확인했다.
2. [x] public_tools.go의 공개 사상, catalog.register와 배포 스냅샷 경로를 연결하고 설명을 압축했다. 기존 전체 MCP 시험과 실제 조립 계약을 검증했다.
3. [x] SDD·시험 정본과 스냅샷을 동기화하고 build/vet/gofmt·크기/BPE 비교·독립 코드 리뷰를 수행했다. 실제 Claude Code 효과는 미확인으로 유지한다.

## 1차 구현 결과

공개 정의를 내부 검증 정본과 분리하고 반복 pattern을 생략했다. 도구·필드 설명과 instructions는 공통 안내의 반복을 줄였으며 14종 도구의 이름·입력·annotations·조건식은 유지했다. node_create의 사건 연결 안내도 이미 제공 중인 previous_event_id를 함께 안내하도록 정정했다. 모델의 자유 생성·자동 재시도 성공률은 이번 서버 계약 시험으로 검증하지 않았다.

기준 f601e50과 작업 트리의 OPS-08 공개 스냅샷을 같은 직렬화·tiktoken 0.12.0 인코딩으로 비교했다. tools 배열과 instructions의 결합 조건은 최초 분석과 같다.

| 비교 항목 | 변경 전 | 변경 후 | 감소 |
|---|---:|---:|---:|
| tools UTF-8 바이트 | 36,805 | 21,219 | 42.3% |
| instructions UTF-8 바이트 | 2,109 | 1,347 | 36.1% |
| tools+instructions o200k_base | 11,969 | 5,560 | 53.5% |
| tools+instructions cl100k_base | 13,831 | 6,337 | 54.2% |
| node_create o200k_base | 3,428 | 1,694 | 50.6% |
| node_update o200k_base | 1,582 | 653 | 58.7% |

공개 tools의 o200k_base는 11,505→5,259이며 가장 큰 단일 도구 node_create는 6,993바이트다. 이 수치는 Claude Code의 실제 토큰·과금·세션 사용량을 뜻하지 않는다. 실제 앱은 같은 버전·모델·연결·loaded/deferred 조건에서 재연결 후 표시값과 호출 오류/재시도를 비교해야 한다. 이번 작업은 모델 API나 유료 요청을 사용하지 않았다.

### 구현 검증과 리뷰

- 변경 전 `go test ./internal/mcp -run '^TestPublic' -count=1`은 새 공개 사상 API가 없어 컴파일 실패했다. 구현 후 크기 시험이 node_create 7,096바이트로 실패하여 중복 안내를 추가 압축했다. 최종 6,993바이트로 통과했다.
- `UPDATE_TOOL_SNAPSHOT=1 go test ./internal/mcp -count=1` 통과. 전체 MCP 모듈의 기존 검증·권한·행위자·재생·오류 시험과 새 공개 정의 시험을 함께 실행했다.
- 작업 전용 합성 DB에서 `UPDATE_MCP09_SNAPSHOT=1 go test ./cmd/server -run '^TestMCP09AssembledServerContractIntegration$' -count=1` 통과. 실제 서버·SDK·인증·저장 경로로 공개 목록·14종 호출·부분 결과·전송/도메인 오류를 확인했다. 시험 DB는 fixture마다 생성·삭제하며 운영 데이터·볼륨을 사용하지 않았다.
- 갱신 환경 변수 없이 `go test ./internal/mcp ./cmd/server -run '^(TestPublic.*|TestOPS08ToolSnapshot|TestMCP09AssembledServerContractIntegration)$' -count=1 -v` 재검증 통과. 공개 필수 배열·속성·annotations 조작이 원본을 바꾸지 않으며 const/enum/examples의 pattern 데이터도 유지된다. 실제 HTTP에서 패턴 관련 잘못된 입력 5종을 업무 처리기 전에 기존 invalid_argument·field로 거부했다.
- 기준 스냅샷과 공개 스냅샷을 구조 비교하여 description·pattern 외 변경이 없음을 확인했다. MCP-09의 변경도 discover.instructions와 tools_list에만 있으며 도구 호출·오류 응답은 동일하다.
- `go build ./...`, `go vet ./...`, `gofmt -l .`, `git diff --check` 통과. Go 1.27.3을 사용했다. 문서 링크·새 제목 앵커와 DOX pass를 확인했으며 소유 경계 변경이 없어 DOX 자체는 유지했다.
- 독립 코드 리뷰에서 Critical·Important 발견 사항은 없었다. 테스트 기대값 순회가 리터럴 데이터까지 수정할 수 있다는 Minor 의견은 데이터 키를 건너뛰고 문자열 pattern만 제거하도록 보완했고 해당 시험을 다시 통과했다.

시험 후 작업 전용 합성 DB 컨테이너와 해당 컨테이너의 마운트 이벤트로 소유권을 확인한 익명 볼륨을 정리했다. 1차 구현 보고 시점에는 실제 Claude Code의 전후 표시값·적재량·usage와 모델이 생성한 호출의 성공률이 검증 대기였으며 배포·commit·push·PR·이슈 갱신은 수행하지 않았다.

## 커밋 이후 호스트 확인과 호환성 보완

사용자가 커밋과 나머지 조치를 요청하여 1차 구현을 ad1f885 (`fix: MCP 공개 도구 정의의 컨텍스트 비용 축소 (#305)`)로 기록했다. 원격 dev는 기준 f601e50과 같았다. 관련 없는 IDE 로컬 설정 두 파일은 제외했다.

### 분리 CLI 확인 조건

- 설치된 Claude Code 2.1.318을 별도 임시 작업 경로·CLAUDE_CONFIG_DIR·`--setting-sources ''`·`--strict-mcp-config`로 실행했다. 모델 선택 `opus`는 이 판에서 `claude-opus-5-5`로 표시됐다. 원래 스크린샷의 앱 버전·모델을 확인한 것은 아니다.
- 원격 서버나 운영 데이터 대신 기준/변경 후 공개 스냅샷을 그대로 반환하는 로컬 stdio MCP fixture만 연결했다. initialize·tools/list·ping만 제공하고 업무 호출은 지원하지 않았다. 협상은 2025-11-25였으므로 이 관찰은 실제 원격 2026-07-28 OAuth 연결의 인수가 아니다. 서버의 실제 조립 검증은 별도 MCP-09가 담당한다.
- 합성 API 키와 loopback ANTHROPIC_BASE_URL을 사용했다. 로컬 차단 서버는 모든 POST에 403을 반환하며 요청 본문·인증 헤더는 기록하지 않았다. `/context`의 count_tokens 요청도 실패하여 표시값은 클라이언트의 대체 추정치다. 실제 모델 추론·과금 토큰·호출 성공률을 측정한 것으로 보고하지 않는다.
- 기존 사용자 설정에서는 ToolSearch 차단·ENABLE_TOOL_SEARCH 재정의·서버 alwaysLoad 강제를 찾지 못했다. 이를 근거로 원래 앱의 환경·세션까지 확정하지 않으며 사용자 설정을 변경하지 않았다.

### 새로 확인한 호환성 문제와 수정

기준 스냅샷과 1차 구현 모두 이 분리 CLI에서 node_create·node_update가 제외됐다. debug 로그는 `Skipping tool ... its input schema uses top-level allOf, which the Anthropic API does not accept`를 기록했다. [Claude 공식 안내](https://code.claude.com/docs/en/mcp#tool-input-schemas-with-a-root-level-combinator)는 최상위 조합식 제한과 호스트의 변환 기능이 적용되지 않는 환경에서 해당 도구를 제외하는 동작을 설명한다. 따라서 실제 사용자 앱에서 두 도구가 항상 제외됐다는 결론으로 확대하지 않는다.

공개 복사본에서는 pattern에 더해 루트 allOf와 그 하위 조건 트리만 생략한다. 내부 엄격 정의·등록 검증·직접 호출은 기존 allOf를 유지하고, 공개 layer 설명은 계층별 필수·계층 외 필드 금지를 직접 안내한다. summary/opinion·대화 식별자 쌍·previous_event_id·keep 안내도 유지한다. 속성 내부 조합식·공통 필수·형식·상한·닫힌 객체·annotations는 유지한다. instructions 첫머리에는 지연 적재 중에도 서버의 역할을 알 수 있도록 공유 컨텍스트 검색·기록 목적을 명시했다.

### 호스트 관찰과 최종 크기

| 관찰 조건 | 공개 도구 표시 | 초기 MCP 도구 표시 |
|---|---|---|
| 기준 f601e50, 최소 모드·전체 적재 | 12종, 두 쓰기 도구 제외 | 약 7.2k 추정 |
| 1차 ad1f885, 같은 모드·같은 12종 | 12종, 두 쓰기 도구 제외 | 약 4.2k 추정 |
| 루트 조건식 보완, ToolSearch 도구 없는 최소 모드 | 14종 모두 표시 | 약 6.9k 추정 |
| 최종 정의, 일반 CLI·ENABLE_TOOL_SEARCH=true | 14종 loaded on-demand | 도구 0, 서버 instructions 250 추정 |

최소 모드의 `--tools ToolSearch` 구성에서는 ToolSearchTool을 사용할 수 없다는 로그가 있었다. 환경 변수만 true로 두어도 해당 도구가 없으면 전체 적재로 돌아감을 확인했다. 일반 모드에서 기본 도구 목록을 유지하면 실제로 지연 적재 표시가 나타났다. 서로 다른 도구 수·모드의 총합으로 감소율을 계산하지 않는다. `/context all`의 개별 도구 예상 비용은 초기 적재량·실제 모델 사용량과 다르다.

| instructions UTF-8 바이트 | 2,109 | 1,347 | 1,409 |

최종 합계 o200k_base는 기준 대비 58.6% 감소했다. 이는 실제 Claude 토큰이나 모든 모델에서 5k 이하라는 보장이 아니다.

### 후속 검증과 남은 범위

- `TestPublicRootSchemaCompatibility`는 변경 전에 node_create·node_update의 최상위 allOf로 실패했다. 변경 후 원본 AllOf 보존·공개 루트 조합식 부재를 확인했다.
- 전체 `go test ./internal/mcp -count=1` 통과. 추가 HTTP 회귀에서는 원천에 member_refs를 보낸 경우 기존 field=layer, keep에 body를 보낸 경우 field=management_action으로 업무 처리기 전에 거부했다. 시험 기대값은 실제 기존 validator의 필드 사상과 대조해 정정했다.
- 공개 스냅샷과 실제 합성 DB의 MCP-09를 정식 갱신 경로로 재생성했다. 갱신 환경 변수 없이 `go test ./internal/mcp ./cmd/server -run '^(TestPublicToolProjection|TestPublicToolMetadataBudget|TestPublicRootSchemaCompatibility|TestPublicSchemaKeepsStrictHTTPValidation|TestOPS08ToolSnapshot|TestMCP09AssembledServerContractIntegration)$' -count=1` 통과. 최종 안내·크기·호환성·입력 거부와 실제 조립 계약을 확인했다.
- 최종 `go build ./...`·`go vet ./...`·`gofmt -l .`·`git diff --check` 통과. 문서의 로컬 링크·앵커 310개와 UTF-8·코드 블록을 검사했다. 소유 경계 변경이 없어 DOX를 유지했다. 기준 대비 MCP-09의 도구 호출·오류 응답은 동일하다.
- 후속 독립 리뷰에서 Critical·Important 발견 사항은 없었다. 루트 allOf 삭제와 속성 내부 조합식 보존의 차이를 명확히 하라는 Minor 의견을 MCP·시험 SDD에 반영했다.
- 지연 적재 확인 방법·강제 적재 설정·ToolSearch 도구 제외 시 영향은 README의 Claude Code 연결 안내에 반영했다. 실제 사용자 환경은 재연결 후 `/context`의 loaded/deferred와 두 쓰기 도구를 확인해야 한다.
- 차단 서버에 도달한 POST 74건은 모두 count_tokens였고 모델 생성 POST는 없었다. 최종 CLI 로그에 제외된 도구는 없었다. 시험 후 모든 분리 CLI·로컬 API 차단 서버를 종료하고 작업 전용 합성 DB 컨테이너·익명 볼륨을 정리했다.

원래 사용자의 앱·원격 OAuth 연결·실제 모델 호출과 usage는 미검증이다. 운영 배포·권한·기존 호스트 설정·MCP 결과의 호환 text·캐시 TTL은 변경하지 않았다. 이번 요청에서는 로컬 커밋과 확인을 진행하며 push·PR 게시·이슈 코멘트는 별도 게시 지시가 없어 수행하지 않는다.
