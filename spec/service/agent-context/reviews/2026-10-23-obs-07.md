# OBS-07 파일 장애·stderr·부분 쓰기·종료 모듈 인수

- 기준: 2026-10-23, `feat/web-foundation`의 `cf04ecb` 이후 작업 트리.
- 대상: [OBS-07](../development-plan/observability.md#obs-07), [실패와 종료](../sdd/observability.md#기동실행-중-실패와-종료), [SRS 진단 로그](../SRS.md#종류별-진단-로그).
- 판정: 구현·모듈 인수 완료. 전체 **77/124개 완료·47개 미착수**, 다음은 OBS-08이다.

## 변경과 관찰 범위

기존 기록기는 누락 통계만 유지하고 부분 행 이후의 append를 계속 거부했으며, Close 호출자의 취소가 끝난 뒤에도 대기열을 계속 기록했다. 이제 안전한 stderr 알림과 부분 행 복구, 최초 Close부터 최대 5초의 공통 마감을 적용한다.

- stderr에는 UTC 시각·확인한 instance/boot·고정 원인·종류별 건수·누적 누락만 전달한다. 임의 FileError.Code·error 문자열·잘못된 종류를 복제하지 않는다. 고정 크기 배열과 한 출력 작업자가 알림을 합치므로 출력 정체가 Emit을 막거나 알림마다 goroutine을 늘리지 않는다.
- 같은 원인의 상세 알림은 여러 종류를 합쳐 30초당 한 번만 출력한다. 억제 중 증가분도 다음 알림의 누적 값과 종료 요약에 남는다. stderr 오류·짧은 출력은 StderrFailures와 종료 오류로 전달하고 재귀 출력하지 않는다. 가능한 최대 카운터·모든 원인의 종료 요약도 개행 포함 16 KiB 안에 든다.
- 실제 파일의 불완전 마지막 행은 정상 접두 행을 검증하고, 원문 없는 `.partial.<kind>.<UTC 시각>.<UUIDv7>` 표식을 저장·sync한 뒤 제거한다. 표식은 0600이며 종류·시각·제거 바이트 수만 담는다. 정상 행은 원래 바이트로 보존하고 기존 날짜 회전 정책도 유지한다.
- 격리 표식에도 종류별 파일 개수·바이트, instance·저장소 총상한과 7일 보존을 적용한다. 표식 공간 부족·16 KiB 이상 불완전 행·손상된 완전 행은 원본을 수정하지 않고 실패한다. 재시작과 이전 비활성 슬롯에서도 같은 복구를 수행한다. 활성인 다른 슬롯의 기록자 잠금은 기존대로 존중한다.
- 최초 Close부터 공통 5초 마감을 사용한다. 더 짧은 호출자 취소는 그 호출의 대기만 끝내고 반복 Close가 마감을 연장하지 않는다. 마감 때 쓰는 중인 이벤트까지 누락으로 확정하고 대기 예약을 반환한다. 늦게 끝난 쓰기는 Written으로 다시 세지 않고 뒤의 이벤트를 새로 쓰지 않는다. 중단할 수 없는 OS I/O의 실제 파일·잠금 정리는 소유 루프가 돌아온 뒤 끝낸다.
- 서버·별도 색인 실행기의 공통 종료 조립은 별도 5초 context와 기록기 마감이 경합하지 않도록 기록기의 마감을 사용한다. 새로운 설정·외부 의존성·DB 스키마는 추가하지 않았다.

## 실행과 결과

Go 1.27.1, macOS arm64에서 모듈 인수를 수행했다. 모든 시험은 `-race -json -count=1`로 실행했고 아래 건수는 상위 시험과 하위 사례의 pass 이벤트 합계다. 실제 DB 검증은 TEST_DATABASE_URL·TEST_DATABASE_REQUIRED를 사용하되 별도 임시 DB를 생성하고 정식 마이그레이션을 적용한 뒤 자신의 DB를 정리했다.

| 범위 | 실행 | 결과 |
|---|---|---|
| 기록기 모듈 전체 | `go test -race -json -count=1 -timeout=180s ./internal/diagnostic` | **162건 통과**, 실패·건너뜀·race 오류 0 |
| 서버 진단·종료·의존 | `go test -race -json -count=1 -run '^(TestPackageDependenciesMatchDesign\|TestOBS05RequestActualFileAndTrace\|TestShutdown)' ./cmd/server` | **9건 통과**, 실패·건너뜀·race 오류 0 |
| 실제 파일 장애와 업무 보존 | `go test -race -json -p=1 -count=1 -timeout=180s -run '^TestOBS07DiagnosticFileFailurePreservesCommitIntegration$' ./internal/store` | **1건 통과**, 실패·건너뜀·race 오류 0 |

총 **172건**이 통과했다. stderr는 실제 OS 파이프로 수집하여 각 JSON 행·출처·누적 누락과 비밀 표본의 부재를 대조했다. 시험 시계로 30초 직전·정확한 경계와 종류를 가로지르는 억제를 확인했다. 기본 5초를 실제로 기다리는 시험에서 취소된 최초 호출·병행 Close·마감 뒤 완료·잔여 건수와 바이트 예약 반환을 확인했다. 정체된 stderr와 짧은 출력/오류는 별도 출력 대역으로 검증했다.

변경 Markdown 9개와 상대 링크·앵커 336개, UTF-8·fence·공백 및 git diff 검사가 통과했다. 계획 체크박스도 완료 77개·미착수 47개로 일치한다.

실제 파일에서는 재시작·이전 슬롯·유효 접두 행 보존, 부분 쓰기 후 다음 append의 복구와 과거 누락 유지, 표식 권한·만료·파일 개수 상한, 복구 실패 시 원본 보존을 확인했다. 전용 DB에서는 관리 진단 파일의 권한을 실행 중 변경해 실제 기록 실패를 만들었으며 관계 확정 응답·저장된 관계·적용된 업무 감사의 판단 입력이 유지됨을 확인했다.

초기 시험의 재시작 복구 2건은 정상 행이 날짜 회전 파일로 이동하는 기존 정책을 기대값에서 누락해 실패했다. 활성·회전 파일 전체에서 보존을 대조하도록 수정한 뒤 진단 패키지 전체를 재실행해 통과했다. 추가 서버·DB 시험은 최초 샌드박스의 로컬 포트/DB 접근 제한으로 실패했으나 동일 범위를 허용된 실행 환경에서 다시 수행해 통과했다.

## 제한과 후속 작업

- 파이프 수집은 모듈 시험 환경의 증거다. 배포 stderr 수집기의 수신·영속 보관이나 프로세스 강제 종료 시 전달을 보장하지 않는다. stderr 정체 시에도 종료는 최대 5초로 끝나며 별도 출력 작업자는 막힌 쓰기가 반환될 때 정리된다.
- 실제 Linux 실행·읽기 전용 마운트·디스크 부족·컨테이너 재생성·배포 슬롯 교체와 여섯 파일 전체 흐름은 [OBS-08](../development-plan/observability.md#obs-08)의 통합 인수 범위다. 전체 저장소 시험·실제 호스트·운영 배포는 수행하지 않았다.
- DB 업무 감사와 진단 파일의 성공은 계속 별개다. 커밋 결과나 이미 누락된 이벤트를 진단 복구로 성공 처리하지 않는다.
- DOX pass: 기존 diagnostic·실행기·명세 소유 경계를 유지한다. 새 지속 경계나 설정이 없어 AGENTS.md와 Child DOX Index의 변경은 필요하지 않다. 상세 동작은 관측성 SDD에, 상태와 근거는 계획·진입점·이 검토에 유지한다.
