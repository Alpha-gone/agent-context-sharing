# 에이전트 컨텍스트 MCP 클라이언트 명세 영역

## 목적

- 이 영역은 에이전트 컨텍스트 관리 시스템의 MCP 서버에 접속하는 에이전트 측 MCP 클라이언트의 요구사항, 상세 설계, 근거와 요청 기록을 보관한다.

## 소유권

- `spec/service/AGENTS.md`가 서비스 명세 공통 계약과 이 서비스 경계를 소유한다.
- `SRS.md`가 이 서비스의 요구사항과 확정된 결론을 소유한다.
- `SDD.md`가 확정된 요구사항의 실행 명령, 패키지 경계, 처리 흐름, 보안·동시성·배포와 검증 설계를 소유한다.
- `CANONICAL.md`가 개발에 필요한 정본 문서의 위치와 변경 경로를 안내한다. 동작과 설계의 정본은 `SRS.md`와 `SDD.md`에 둔다.
- `DEVELOPMENT_PLAN.md`가 구현 순서, 단계별 진행 상태와 완료 기준을 소유한다.
- 상호운용 대상인 서버의 공개 계약은 `../agent-context/SRS.md`와 `../agent-context/SDD.md`가 소유한다.

## 로컬 계약

- 클라이언트는 에이전트를 대신해 인가 서버에서 접근 토큰을 발급받고 MCP 서버의 도구 13종을 호출한다.
- `SRS.md`는 호스트 측 `stdio`와 원격 Streamable HTTP를 잇는 로컬 프로세스를 제품 기준선으로 확정했다.
- 호스트 stdin EOF는 새 요청 수락을 멈추되 접수한 요청의 응답을 기록한 뒤 종료하는 입력 방향 종료이며, 종료 신호의 호출 취소와 구분한다. 세부 계약은 `SRS.md`와 `SDD.md`가 소유한다.
- 첫 공식 검증 호스트는 Codex CLI `0.156.1`이다. 호스트 연결은 `2026-07-28` 무상태 방식과 Codex·JetBrains의 `initialize` 기반 호환 방식을 제공하며 특정 Codex 기능 플래그를 필수로 요구하지 않는다. 다른 판·실행 표면의 공식 지원은 해당 종단 간 검증 결과로 판정한다.
- 구현은 Go `1.27.1`과 공식 MCP Go SDK를 사용하고 서버 루트 모듈과 분리된 `client/` Go 모듈에 독립 실행 파일로 둔다. 구체적인 실행 명령 경로와 내부 패키지 경계는 클라이언트 SDD가 소유한다.
- 첫 출시는 공급자의 보안 지원 기간에 있는 macOS 14 Sonoma 이상, Ubuntu LTS 22.04 이상 또는 Debian 12 이상, Windows 11 25H2 이상에서 지원한다. Windows의 공식 실행 환경은 Canonical 표준 보안 유지 기간인 WSL2 Ubuntu LTS 22.04 이상이며 브라우저 인가와 loopback callback을 Windows 호스트와 함께 검증한다.
- `SRS.md`의 「자원 상한」은 첫 출시의 메시지·응답 크기, 진행 중 호출과 대기열에 고정 상한을 두며 구현은 무제한 구성을 열지 않는다.
- 인가 대기에는 인증 제한 시간을, 인가 대기를 제외한 원격 처리 누적 시간에는 요청 제한 시간을 적용한다. 호스트의 명시적 deadline·취소와 프로세스 종료는 두 단계 모두에 우선한다. 마지막 인가 대기자 취소 뒤 실행을 유지하는 백그라운드 인가는 사용하지 않는다.
- 첫 출시는 `io.github.alpha-gone/write-idempotency` 확장을 협상한 8종 쓰기 호출마다 UUIDv7 `Idempotency-Key`를 생성해 같은 논리적 호출의 전송 시도에 재사용한다. 키는 호스트 도구 입력에 노출하거나 호출 사이에 영속화하지 않으며 서버의 보관 계약은 24시간이다.
- 허용된 읽기, 원격 전달 전 실패가 확실한 쓰기와 멱등성 확장을 협상한 쓰기의 자동 전송 재시도는 최초 시도 제외 최대 3회다. 대기 상한은 250ms, 500ms, 1초이며 실제 대기는 각 상한 안에서 무작위로 정한다. 취소와 도구 호출 제한 시간이 우선하고 재인증 뒤에도 횟수를 초기화하지 않는다.
- 첫 출시는 RFC 9449 DPoP를 필수 적용한다. 보호 리소스 메타데이터의 DPoP 필수·ES256 선언과 인가 서버 메타데이터의 ES256 선언을 모두 확인하고, 프로세스 수명 ES256 개인 키와 접근 토큰은 메모리에만 두며 토큰 교환과 원격 HTTP 시도마다 새 proof를 만든다. Bearer로 하향하지 않고 최초 구현은 `DPoP-Nonce`를 사용하지 않는다.
- 호스트 경계는 MCP `2026-07-28` 및 SRS에 명시한 `initialize` 기반 revision의 도구 연결을 제공한다. 원격 경계는 호스트 revision과 무관하게 `2026-07-28` 메시지·수명주기·도구 계약과 서비스 전용 DPoP를 유지하며, DPoP 시험 결과를 MCP 핵심 인증 적합성으로 보고하지 않는다.
- `SDD.md`는 `client/cmd/client`의 `agent-context-client` 실행 파일, `serve`·`doctor` 명령과 `client/internal/client/` 패키지 경계를 확정하며 요구사항을 새로 만들거나 바꾸지 않는다.
- 클라이언트 개발의 지속적인 요구사항 정본은 `SRS.md`, 상세 설계 정본은 `SDD.md`다. `DEVELOPMENT_PLAN.md`의 단계와 체크박스는 이 계약을 바꾸지 않는다.
- 정책 구성 오류, 호스트 입력 위반과 발견·목록 조회 중 인증 주체 변경은 SRS·SDD의 일곱 클라이언트 오류 코드로 구분한다. 패키지 오류 분류 시험을 호스트 직렬화·실제 인증 연결의 완료 근거로 대신하지 않는다.
- 첫 검증 토큰의 계정 결합은 프로세스 종료까지 유지하며 다른 계정의 갱신·재인가 토큰은 저장하지 않는다. 세부 주체 식별·폐기 설계는 SDD를 따른다.
- 갱신된 접근 토큰의 만료 시각은 역행하지 않으며 토큰 사용·저장에는 SRS의 5초 만료 여유를 적용한다. 주체 조회는 인가를 시작하지 않는다. 검증한 리소스 식별자와 실행기 수명·WSL 대체 경로의 세부 계약은 SDD가 소유한다.
- 기능 요구사항은 서버의 공개 계약에서 도출하며, 서버 계약이 바뀌면 이 서비스의 `SRS.md`를 함께 갱신한다.
- 서버의 검색 경로 선택, 요청 단위 일관 읽기, `cmd/audit`와 `cmd/eval`은 서버 내부 기능이며 공개 MCP 계약이 바뀌지 않는 한 클라이언트 도구로 노출하거나 로컬에서 재현하지 않는다.
- `context_flow_get`의 평면 응답과 검색 메타데이터는 클라이언트가 해석·재조립하지 않고 그대로 중계한다.
- 요구사항 ID는 `FR-AGENT_CONTEXT_CLIENT-NNN`, `NFR-AGENT_CONTEXT_CLIENT-NNN`, `TBD-AGENT_CONTEXT_CLIENT-NNN` 형식을 쓴다.
- 권한·팀 관리, 삭제·복구, 감사 화면과 컨텍스트 시각화는 웹 채널이 소유하므로 이 서비스의 범위 밖이다.

## 작업 지침

- 이 영역의 문서를 고치기 전에 루트 `AGENTS.md`, `spec/AGENTS.md`, `spec/service/AGENTS.md`와 이 문서를 읽는다.
- 요구사항을 수정할 때 서버 명세의 해당 절을 먼저 확인하고 어긋남이 없게 한다.
- 상세 설계는 요구사항과 미정 사항이 충분히 확정된 뒤 `service-design` 스킬로 작성한다.
- 상세 설계를 수정할 때 `SRS.md`의 모든 기능·비기능 요구사항이 추적표와 테스트 전략에 계속 포함되는지 확인한다.
- 구현 진행 때 `DEVELOPMENT_PLAN.md`의 작업·완료 기준·단계 상태를 실제 검증 결과에 맞춰 함께 갱신한다.

## 검증

- 요구사항 ID의 중복·누락과 상태의 잘못된 승격이 없는지 확인한다.
- 기능 요구사항이 서버 공개 계약의 현재 내용과 일치하는지 확인한다.
- 서버 내부 기능이 클라이언트 도구 표면에 섞이지 않고 도구 13종과 `context_flow_get` 응답 보존 계약이 유지되는지 확인한다.
- 쓰기 멱등성의 확장 협상, 8종 적용 범위, UUIDv7 키의 호출별 생성·재사용·폐기와 비협상 호환 경로가 서버 공개 계약과 일치하는지 확인한다.
- 허용된 읽기, 전달 전 실패가 확실한 쓰기와 멱등성 협상 쓰기의 자동 전송 재시도가 최대 3회, 250ms·500ms·1초 상한 안에서만 일어나고 취소·제한 시간·재인증에도 같은 호출의 횟수가 유지되는지 확인한다.
- 보호 리소스 메타데이터의 `dpop_bound_access_tokens_required=true`·ES256 선언, 인가 서버 메타데이터의 ES256 선언, `token_type=DPoP`, `cnf.jkt`, 요청별 새 proof, 60초 허용 창, 공유 재생 방어, 갱신 결합과 Bearer 하향 거부가 서버 공개 계약과 일치하는지 확인한다.
- 인증 정보 없는 DPoP 도전과 `invalid_token`만 인가·재인증을 시작하고 `invalid_dpop_proof`·`use_dpop_nonce`는 반복하지 않는 오류 계약이 서버와 일치하는지 확인한다.
- 호스트의 MCP 공식 conformance와 원격의 메시지·수명주기·도구 계약 및 서비스 전용 DPoP 인증 시험을 분리해 보고하는지 확인한다.
- `SDD.md`의 환경 변수 목록이 루트 `.env.example`과 일치하고, CPU 아키텍처별 배포 범위와 `doctor` 출력이 SRS의 출시 기준을 충족하는지 확인한다.
- `CANONICAL.md`의 정본 링크와 `DEVELOPMENT_PLAN.md`의 단계 상태가 실제 문서·구현·검증 상태와 일치하는지 확인한다.
- 외부 근거의 출처와 반영 위치가 `reference.md`와 일치하는지 확인한다.
