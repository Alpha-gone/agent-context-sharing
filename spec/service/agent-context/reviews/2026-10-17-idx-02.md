# IDX-02 작업 확보·리스·시험 범위 제한 모듈 시험

## 범위와 입력

- 대상: [IDX-02](../development-plan/indexing.md#idx-02). 선행 IDX-01·ARCH-04 완료. 시작 커밋 `1c91b40`, 브랜치 `feat/data-schema-contract`.
- 시작 upstream은 `origin/feat/data-schema-contract`이며 로컬 추적 ref 기준 앞섬 1·뒤처짐 0이었다. 이번 작업에서 pull·commit·push는 수행하지 않았다.
- 정본: [SRS 색인 처리](../SRS.md#색인-처리), [색인 큐](../sdd/indexing.md#색인-작업-큐), [시험 격리](../sdd/testing.md#테스트-사이의-격리), [모듈 시험 시점](../DEVELOPMENT_PLAN.md#테스트-작성과-실행-시점).

## 구현과 검토

- `claimIndexTask`로 확보 트랜잭션을 분리했다. 기한이 지난 pending 작업 하나를 `enqueued_at, task_id` 순으로 `FOR UPDATE SKIP LOCKED` 확보하며, 리스를 커밋하고 연결을 반환한 뒤 본문 조회·제공자 호출을 수행한다. 전체 그래프와 특정 graph_id 진입점은 같은 확보·처리 경로를 사용한다.
- 기한 판정과 리스 설정에 DB의 `statement_timestamp()`를 사용한다. 리스는 확보 표시 문장 시각에서 정확히 120초 뒤이며 작업자 호스트와 DB의 시계 차이에 의존하지 않는다. 저장된 정밀도의 등록 시각·리스 시각을 확보 세대로 반환한다.
- 공통 `finishWrite`를 적용해 식별자 해석·UPDATE·COMMIT 실패와 요청 취소에도 독립된 정리 예산으로 롤백하고 원인을 보존한다. 빈 회차도 트랜잭션을 종료한다.
- 확보는 `next_attempt_at`만 변경한다. 등록 시각·시도 횟수·상태·이전 오류·상관 ID를 유지하며 processing 상태나 회수 주기 작업을 추가하지 않았다.
- 공개 API·패키지 의존·마이그레이션·적용 이력을 바꾸지 않았다. 성공·실패 결과의 세대 대조는 기존 경로를 유지하고 새 확보 경로와의 회귀를 실행했다. IDX-04·05의 전체 인수를 대신하지 않는다.

## 환경과 결과

- Go 1.27.1 darwin/arm64, PostgreSQL 18.6 / Apache AGE 1.8.0 / pgvector 0.8.6 / Linux aarch64.
- 저장소의 고정 Dockerfile로 IDX-02 라벨의 전용 이미지·컨테이너·볼륨을 만들고 loopback 동적 포트만 공개했다. 새 모듈·상관 ID 시험은 시험별 임시 DB 11개, 정렬 보완 재검증은 추가 임시 DB 2개를 사용했다. 각 DB에서 정식 001·009·010·011 적용과 반복 적용의 무변경을 확인했다. 관련 회귀는 같은 전용 컨테이너의 별도 기본 DB에 정식 적용한 뒤 실행했다.
- **고유 시험·하위 시험 27건 통과**: store 26건·서버 조립 1건, 최상위 13개·하위 14개. 새 확보 모듈 11건·상관 ID 회귀 1건·관련 회귀 15건이다. `-race -count=1`, `TEST_DATABASE_REQUIRED=1`을 적용했으며 실패·건너뜀은 0이다. 두 번 재검증한 정렬 시험은 고유 건수에 중복 합산하지 않았다.
- 같은 등록 시각의 task ID를 힙 삽입 순서와 반대로 배치해 식별자 동률 정렬을 확인했다. 더 늦은 등록은 뒤에서 확보했고, 더 오래된 failed와 미래 재시도·유효 리스는 건너뛰었다. 실제 DB 트리거의 문장 시각 표본과 리스의 차이는 정확히 120초였다. 확보 전후 전체 작업 필드를 대조해 리스만 변경됨을 확인했다.
- 결과를 반환하지 않은 확보를 중단된 작업자로 취급해 유효 리스 동안 재확보되지 않음을 확인했다. 시험이 소유한 한 작업의 시각만 만료시킨 뒤 같은 task ID·등록 시각으로 새 리스를 확보했다. 2분 실시간 대기는 수행하지 않았다.
- 별도 연결이 선두 작업을 잠근 동안 다음 작업을 확보했고 모두 잠김·리스 상태이면 빈 회차를 반환했다. 잠금 해제 뒤 원래 선두를 확보했다. 최소 4연결 풀의 동시 확보 요청 24개는 작업 12개를 각각 한 번씩 확보하고 나머지 12회는 빈 회차로 끝났다.
- 그래프 한정 처리는 더 오래된 다른 그래프의 작업을 건드리지 않았다. 다른 그래프 큐 행의 모든 필드 지문이 보존됐고 영값·잘못된 graph_id·없는 그래프·빈 제공자에서도 저장 상태를 바꾸지 않았다. 운영용 전체 그래프 진입점은 시험이 단독 소유한 DB에서 두 그래프의 작업을 등록 시각 순으로 처리했다.
- 채널로 제공자 응답을 보류한 동안 실제 풀 점유 0·예약 반환·`FOR UPDATE NOWAIT` 성공을 확인했다. 유효 리스는 다른 확보자가 건너뛰었고 같은 컨텍스트의 본문 갱신은 제공자를 해제하기 전에 2초 마감 안에 완료됐다. 해제한 이전 결과는 새 본문 작업을 덮지 않았다.
- 잘못된 task ID·UPDATE 오류·지연 제약 트리거의 COMMIT 오류·실제 DB 대기 중 마감의 네 경로에서 AGE 정점·간선, 그래프·큐·임베딩·감사·관리 기록의 업무 지문이 모두 보존됐다. 오류의 PostgreSQL 코드 또는 DeadlineExceeded 원인, 연결·예약 회복과 장애 제거 뒤 재확보를 확인했다. 취소 시험은 비트랜잭션 sequence로 DB 대기 진입도 확인했다.
- 재등록된 작업의 이전 성공·일시/영구/예산 소진 실패, 리스 재확보 뒤 이전 성공·실패, 결과 저장 실패의 작업 삭제 롤백, 두 제공자의 동시 확보와 패키지 경계 회귀가 통과했다.
- `check-go.sh`의 의존성 검증·전체 build·vet·gofmt를 통과했다. 최종 시험 자료의 보완 뒤 정렬 모듈을 다시 실행하고 형식·diff·문서 링크·앵커·계획 수·DOX 소유권을 대조했다.
