# Bearer 검증과 보호 리소스 인증 검토

- 기준: [AUTH-08](../development-plan/authentication.md#auth-08), [인증 설계](../sdd/authentication.md#토큰-검증), [SRS 인증](../SRS.md#인증과-토큰-요구사항)·[오류](../SRS.md#인증과-권한).
- 대상: `feat/mcp-auth`의 `33c13c9` 이후 작업 트리. 선행 AUTH-02·07을 확인했다.
- 범위: Bearer 검증·공유 상태·HTTP 인증 경계의 모듈 인수. 실제 /mcp 전송과 권한·업무 도구 조립, 갱신 회전·연결 관리·실제 호스트·운영 배포는 후속 범위다.

## 구현 결과

`internal/authz`는 웹과 Bearer가 사용할 ES256·공통 필수 클레임 검증을 분리하고 웹의 기존 폐기 캐시를 보존했다. Bearer는 고정 issuer·단일 resource audience, 계정/계열 UUIDv7·iat/exp/jti·scope/client와 최대 1시간 수명을 검증한다. 현재 client 등록이 resource를 허용해야 하며 그래프 등급·호스트 clientInfo를 인증 주체에 넣지 않는다.

`internal/store.OAuthAccessAllowed`는 단일 SQL의 공유 스냅숏에서 계열 존재·계정/client/resource/scope 결합, 인가 이후 발급과 개별·계열 폐기를 확인한다. Bearer 요청은 웹 폐기 캐시를 사용하지 않는다. 다른 인스턴스의 폐기 커밋 뒤 시작한 요청도 즉시 거부하며 정상 부재와 조회 장애를 구분한다. 조회 뒤 취소·접근 만료를 다시 확인하고 읽기로 갱신 활동을 연장하지 않는다. SRS에 따라 갱신 자격의 절대·비활동 만료만으로 기존 접근 토큰의 자체 수명을 줄이지 않는다.

`ProtectBearer`는 TLS 판정 뒤 사용할 HTTP 경계로, 단일 Authorization Bearer 값만 받는다. 쿠키·query·양식은 대체 인증으로 사용하지 않는다. 자격 부재에는 오류 코드 없는 401 도전, 잘못된·만료·폐기 자격에는 401 invalid_token을 반환한다. 도전의 resource_metadata는 요청 Host나 issuer가 아닌 고정 resource origin을 사용한다. 계열 결합까지 유효한 자격의 scope 부족은 403 insufficient_scope, 저장·키 장애는 재인증 도전 없는 500 server_error다. 오류 응답은 no-store이며 자격·내부 원문을 포함하지 않는다.

성공 콜백은 검증된 계정·client·계열 식별자만 받는다. 현재 등급은 후속 권한 서비스가 판정한다. 서버 기동은 공유 상태 저장 인터페이스를 주입하며 실제 /mcp 라우팅·SDK 전송 연결은 MCP-02에서 인수한다. 이번 TLS 시험의 성공 콜백은 합성 보호 리소스이며 실제 업무 도구 지원의 증거가 아니다.

## 모듈 시험과 검증

Go 1.27.1에서 `-timeout=120s -race -json -count=1`, TEST_DATABASE_REQUIRED=1과 전용 TEST_DATABASE_URL로 실행했다.

- 인증 **340건**: `go test -timeout=120s -race -json -count=1 ./internal/authz`. 필수 클레임 누락/null/타입·시간·audience·UUID·scope/client, ES256 고정·다른 서명·알 수 없는 kid·키 장애, 매 요청 공유 조회·취소·조회 중 만료와 기존 인증 회귀를 확인했다. 실제 DB에서 두 인스턴스·계열 결합·개별/계열 즉시 폐기·8건 병행 거부·재시작·코드 재사용 폐기·키 회전·접근/갱신 수명 분리·TLS 및 닫힌 DB의 500을 검증했다.
- 선별 서버 **65건**: `go test -timeout=120s -race -json -count=1 -run '^(TestOAuth.*|TestWebSession.*|TestWebCredentialErrorMapping|TestTransportSecurity.*)$' ./cmd/server`. 기존 OAuth·웹 세션·채널·전송 보안과 기동 조립의 관련 회귀를 확인했다.
- **총 405건 통과·건너뜀 0건·race 통과**. 전체 저장소·인증 분야 전체 통합·실제 MCP/브라우저/호스트 인수와 구분한다.
- 루트 `check-go.sh`: 의존성 검증·SDK 링크·전체 build·vet·gofmt 검사 통과. `/private/tmp/acs-auth08-check-go.log`.
- 시험 로그: `/private/tmp/acs-auth08-authz.json`, `/private/tmp/acs-auth08-server.json`.

Docker socket 접근은 기본 sandbox에서 거부되어 전용 DB 생성·시험·정리 실행기를 권한 승격으로 실행했다. postgres 관리 DB에서는 이번 실행의 무작위 auth08_suite DB만 생성·정리했고 TEST_DATABASE_URL은 그 DB로 고정했다. 기존 시험 준비 함수는 다시 시험별 자식 DB를 만든 뒤 실제 DB명을 대조하고 정식 마이그레이션을 적용한다. 실행 종료 후 suite DB 삭제·부재를 확인했다. 기존 개발·운영 DB의 스키마·계정·키는 시험 준비에 사용하지 않았다.

첫 정적 검사에서 시험 코드의 키 회전 메서드명을 수정한 뒤 검사를 통과했다. 구현에 적용한 go-jose v4.1.1 Claims·ValidateWithLeeway와 pgx v5.10.0 QueryRow 계약은 공식 API·적용 모듈 소스를 대조했다.
