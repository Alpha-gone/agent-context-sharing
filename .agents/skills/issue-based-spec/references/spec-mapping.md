# 이슈-명세 매핑 기준

## 분류표

| 이슈 내용                                        | 분류      | 기본 반영 위치               | 처리 기준                                                          |
|--------------------------------------------------|-----------|------------------------------|--------------------------------------------------------------------|
| 사용자 행동, 시스템 동작, 정책, 권한과 제약      | 요구사항  | `SRS.md`                     | `service-design`으로 검증 가능한 문장을 작성한다.                  |
| 구성 요소, API, 이벤트, 데이터 모델, 상태와 배포 | 상세 설계 | `SDD.md`                     | `detailed-design`으로 요구사항 ID에 연결한다.                      |
| 사용자가 명시적으로 선택하거나 승인한 항목       | 결정      | 관련 명세와 `logs/prompt.md` | 결정 범위, 출처와 영향받는 ID를 기록한다.                          |
| 아직 채택되지 않은 개선 아이디어                 | 제안      | `suggestion.md`              | `미검토`로 기록하고 확정 명세에 넣지 않는다.                       |
| 답이 없고 선택에 따라 결과가 달라지는 항목       | 미정 사항 | `SRS.md` 또는 `SDD.md`       | 영향받는 ID와 필요한 결정을 적는다.                                |
| 파일 수정, 코드 작성과 테스트 같은 수행 항목     | 구현 작업 | 명세 반영 대상 아님          | 근거 요구사항에 연결하되 완료 사실을 요구사항으로 확대하지 않는다. |
| 외부 문서, 표준과 공식 API 자료                  | 출처      | `reference.md`               | 원문 링크, 조회 맥락과 반영 위치를 기록한다.                       |

## 확정성 판단

- 이슈 본문과 댓글에서 사실, 사용자 결정, 제안과 미정 사항을 구분한다.
- 이슈의 `open`·`closed` 상태, 라벨, 반응 수만으로 명세 상태를 확정하지 않는다.
- 체크된 항목은 작업 완료 표식일 수 있으므로 결정 근거와 검증 결과를 별도로 확인한다.
- 기존 명세와 이슈가 다르면 어느 한쪽이 자동으로 우선한다고 가정하지 않는다.

## 추적성

1. 기존 요구사항 ID와 설계 식별자를 보존한다.
2. 신규 ID는 `service-design`의 서비스 경로 기반 규칙을 따른다.
3. `SRS.md`의 관련 이슈 열 또는 `SDD.md`의 추적표에서 원본 이슈를 연결한다.
4. 여러 이슈가 같은 항목을 다루면 각 이슈의 책임과 제외 범위를 구분한다.
5. 파일 변경, 이슈 수정과 커밋 승인을 서로 독립적으로 취급한다.

## 반영 전 점검

- [ ] 대상 저장소, 서비스와 문서 경로가 확인되었는가
- [ ] 이슈 본문과 댓글을 최신 상태로 재조회했는가
- [ ] 기존 명세와 충돌하는 내용이 있는가
- [ ] 미채택 제안이 확정 범위에 섞이지 않았는가
- [ ] 보존할 ID와 신규 ID가 구분되었는가
- [ ] 변경 파일, 검증과 이슈 갱신 후보가 승인 범위에 포함되었는가
