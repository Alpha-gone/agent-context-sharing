# 스냅숏 검색의 임베딩 접근 기록과 최소 연결 풀 검증

## 범위와 처리 결과

2026-10-10에 [GitHub #103](https://github.com/Alpha-gone/agent-context-sharing/issues/103)을 처리했다. 기준은 원격 `dev`와 일치하는 `464e3c1`이며 작업 브랜치는 `fix/issue-103-snapshot-access`다. 기존 사용자 IDE 설정 staging은 보존했다.

스냅숏은 연결 4개를 예약하지만, 세 후보 채널이 읽기 연결을 유지한 채 `ContextsByIDs → touchEmbeddings`에서 추가 풀 연결을 요청했다. 실제 원천 컨텍스트와 영벡터가 아닌 임베딩을 준비하고 조정 연결·읽기 연결 셋을 모두 확보한 수정 전 시험에서 세 채널 모두 접근 기록의 `context deadline exceeded`로 실패했다. 빈 후보만 조회하던 기존 예약 시험은 이 경로를 검증하지 못했다.

- SDD의 「데이터베이스 연결」에 읽기 종료 후 접근 기록 처리와 자리 유지·오류 전파를 먼저 정의했다. 최소 풀과 요청 예약 수는 4개로 유지하며 연결 추가 예약이나 읽기 전용 경계의 완화를 선택하지 않았다.
- 읽기별로 접근 대상과 조회 시각을 모으고 읽기 연결을 반환한 뒤 풀 연결 하나로 기록한다. 기록이 끝날 때까지 읽기 자리를 유지하므로 조정 연결과 세 자리의 실제 점유는 4개를 넘지 않는다. 중첩 읽기는 바깥 읽기의 종료 경계를 공유한다.
- 후보 네 종·홉 확장·출처 조립은 종료 시 기록 오류를 호출 결과에 반영하며, 오류가 있으면 성공 결과를 반환하지 않는다. 읽기 오류와 기록 오류가 함께 있으면 둘을 보존한다. 취소 시에도 읽기 연결은 정리하고 자리를 반납한다.
- 검색의 스냅숏·후보·홉·근거·출처 계약과 임베딩의 접근 시각 갱신·`cold → hot` 되읽기는 유지했다. 접근 기록은 읽기 전용 트랜잭션 안에서 실행하지 않는다.
- 반복 검증에서 같은 cold 행의 동시 파티션 이동이 `40001`로 실패하는 경로도 확인했다. PostgreSQL 18 공식 `UPDATE` 문서를 대조해 동일 대상·조회 시각의 접근 기록만 한 번 재시도하도록 SDD와 구현을 보완했다. 재시도 한도, 다른 오류·취소의 비재시도와 두 번째 실패의 전달을 단위 시험으로 확인했다.

## 검증

Go 1.27.1 `darwin/arm64` SDK를 사용했다. 실행 중인 개발 PostgreSQL 서버의 별도 시험 DB `issue103_test_20261010`에 정식 `001_init` 마이그레이션을 적용하고 `TEST_DATABASE_URL`과 `TEST_DATABASE_REQUIRED=1`을 설정했다. 기존 개발 DB의 데이터·서명 키·컨테이너 구성은 변경하지 않았고 자격 증명은 기록하지 않았다.

- 최소 풀 4개에서 키워드·시간·의미 유사도 채널의 실제 후보 반환, 접근 시각 갱신과 `cold → hot` 복귀: 통과. 읽기 단계의 실제 풀 점유와 최대 읽기 연결은 4개였고 채널 종료 후에는 조정 연결 하나만 남았다.
- pgx 질의 추적으로 접근 기록 연결을 확보한 상태를 유지한 시험: 실제 점유 4개에서 네 번째 읽기는 자리 대기 후 기한 오류를 반환하고, 접근 기록이 끝난 뒤에는 읽기를 시작할 수 있었다.
- 키워드·시간 후보, 홉 확장과 출처 조립의 접근 기록 취소: 호출 오류와 빈 결과로 전달했다. 요청 취소 뒤에도 읽기 연결과 자리를 반환했다.
- 최소 풀·자리 유지·기록 오류 회귀 및 제한된 재시도 단위 시험을 `go test -count=20 -race -run '^Test(Snapshot(CandidateAccess|Access)|RetryEmbeddingAccess)' ./internal/store`로 반복: 통과. 처음 10회 반복에서 발견한 파티션 이동 충돌을 보완한 뒤 20회 반복했다.
- 서버 `go test -count=1 -race -p 1 -json ./...`: 통과. 최종 집계에서 시험·하위 시험 1,063건 통과, 실패 0건, 건너뜀 0건을 확인했다. `cmd/migrate`와 `migrations`는 시험 파일이 없는 패키지 2개로 별도 집계했으며, 실행과 집계의 종료 코드도 0이었다. 실제 시험과 DB 통합 시험의 건너뜀은 없었다.
- 클라이언트 `go test -count=1 -race -timeout=120s ./...`: 통과. 최초 샌드박스 실행은 loopback 수신 포트 생성 차단으로 실패·대기했고, 대기 시험의 스택을 확인해 종료한 뒤 로컬 수신이 허용된 환경에서 재실행했다. 클라이언트 코드는 수정하지 않았다.
- 서버·클라이언트 각각 `go build ./...`, `go vet ./...`: 통과. 루트 `gofmt -l .`과 `git diff --check`: 출력 없음.

시험 DB는 각 실행 종료 후 삭제했다. 서버 전체 시험 종료 뒤 `pg_database` 재조회 결과 0건으로 정리를 확인했다. 운영 시험·배포·GitHub 상태 변경·커밋·PR 생성은 수행하지 않았다.

## DOX pass

루트와 명세·서비스 DOX 체인을 재확인하고 서비스 소유 AGENTS 및 부모 Child DOX Index에 연결 예약 경계를 반영했다. SDD의 연결·일관 읽기·저장 계층화·시험 전략과 구현의 정합성, PostgreSQL 공식 근거, 한국어 표현·맞춤법·Markdown 구조와 참조 경로를 검토했다. SRS·용어집·공개 MCP 계약·클라이언트 명세·마이그레이션·배포 구성은 요구사항·용어·외부 계약과 데이터·배포 경계가 바뀌지 않아 유지했다.
