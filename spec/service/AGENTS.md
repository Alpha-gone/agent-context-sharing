# 서비스 명세 영역

## 목적

- `spec/service/`는 서비스 색인과 서비스별 요구사항·설계·근거·요청 기록을 보관한다.

## 소유권

- [README.md](README.md)는 서비스 목록·역할·상태·문서 진입점을 소유한다.
- 이 문서는 서비스 문서의 공통 추적·상태·기록 규칙을, 각 서비스 DOX는 해당 범위와 문서별 소유권을 소유한다.

## 로컬 계약

- 서비스의 `SRS.md`가 요구사항·확정 결정을 소유한다. ID는 `FR-{서비스식별자}-NNN`, `NFR-{서비스식별자}-NNN`, `TBD-{서비스식별자}-NNN`으로 유지한다.
- `SDD.md`는 설계 진입점이며 모든 설계 요소를 요구사항 ID 또는 채택된 제안 ID로 추적한다. 상세 문서의 소유권과 추적표 위치는 서비스 DOX에서 정한다.
- SDD로 요구사항을 신설·변경하지 않는다. 변경이 필요하면 SRS를 먼저 고친다.
- 미확정 기능·정책·기술은 미정 사항에 둔다. 요구사항 수준의 선택은 SRS가, 어느 쪽도 요구사항을 충족하는 설계 선택은 SDD가 소유한다. TBD 번호는 문서 집합에서 하나의 연속 번호로 관리하고 README가 현재 미정 사항을 합쳐 보여준다.
- 외부 근거는 서비스 `reference.md`에 출처·URL·조회 시각·반영 위치를 기록한다. 요청·결과는 `logs/prompt.md`에 누적한다.
- 범위 밖 제안은 필요할 때 `suggestion.md`에 기록하고 사용자 채택 뒤 정본에 반영한다.
- 구현 검토는 `reviews/YYYY-MM-DD-대상.md`에 기록한다. 검토는 해당 시점의 증거이며 계약을 바꾸지 않는다. 발견 사항 처리 후 상태를 갱신하고 필요한 계약 변경은 SRS·SDD에서 수행한다.

## 작업 지침

- 서비스 추가·역할·상태·진입 경로가 바뀌면 서비스 색인을 함께 갱신한다.
- 상세 설계는 요구사항과 주요 미정 사항이 충분히 확정된 뒤 `service-design`으로 작성한다.
- 관계를 설명하는 도식은 이해에 필요한 경우에만 두고 정본과 같은 계약을 표현한다.

## 검증

- 요구사항·TBD ID의 중복·누락과 근거 없는 상태 승격을 확인한다.
- 추적표가 SRS의 설계 대상 요구사항을 빠짐없이 담고 미채택 제안이 설계에 섞이지 않았는지 확인한다.
- 서비스 색인의 역할·상태·경로와 정본·근거·기록의 구분이 일치하는지 확인한다.
