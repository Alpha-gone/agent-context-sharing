# OPS-09 DB 중단·복구와 운영 장애 계층 인수

## 범위와 현재 상태

TEST-08의 실제 1시간 만료 대기 중 독립 착수했다. 이 검토는 실제 DB 중단·복귀, 운영 이미지/진단 볼륨과 관련 장애 계층의 새 실행을 구분한다. 제공자·검색·작업자·진단의 전체 운영 실패 인수로 확대하지 않으며 OPS-09는 진행 중으로 유지한다.

`cmd/server/operations_runtime_test.go`는 operations_runtime 태그에서만 실행한다. TEST_OPS09_CONTAINER의 전체 ID·acs.task=ops09-runtime 소유 라벨·실제 127.0.0.1 포트·HostConfig에 고정된 포트와 TEST_DATABASE_URL 일치를 확인한 뒤에만 해당 컨테이너를 정지한다. 시험마다 별도 DB를 생성·마이그레이션하며 기존 운영/개발 컨테이너와 TEST-08의 장시간 DB는 제어하지 않는다.

## 실제 DB 중단·복귀

동일 조립 TLS 서버에서 중단 전 healthz/readyz=200, DB 중단 중 healthz=200·readyz=503과 유효 Bearer의 500 server_error·WWW-Authenticate 없음, DB 복귀 뒤 readyz=200·기존 자격/그래프/판/권한 보존을 확인했다. 애플리케이션 프로세스 재시작으로 복구를 대체하지 않았다.

첫 표본의 임시 공개 포트는 Docker 재시작 때 바뀌어 복구 판정에 실패했다. 고정 loopback 포트로 바꾸고 HostConfig까지 대조하도록 보강했다. 다음 표본은 업무 복구를 확인했으나 시험 정리의 기존 관리 TCP 연결이 DB 중단으로 무효화되어 전체 실패했다. 공용 newServerContractDatabase 도우미가 취소와 독립된 10초 예산에서 새 관리 풀을 열어 자신이 만든 DB만 DROP하도록 수정했다. 이 변경은 시험 도우미에 한정하며 제품 저장소·환경 계약을 바꾸지 않는다.

두 예비 컨테이너는 소유 ID·라벨과 잔여 연결을 확인한 뒤 익명 볼륨과 함께 제거했다. 최종 표본은 고정 포트의 새 합성 클러스터에서 실행했고 DB 복구·개별 DB 정리까지 통과했다. 최종 시험 수·자원 정리와 관련 회귀의 결과는 아래에 실행 근거로 추가한다.

```sh
TEST_OPS09_CONTAINER='<전용 합성 DB의 전체 container ID>' \
TEST_DATABASE_URL='<같은 고정 loopback 포트의 합성 DB>' TEST_DATABASE_REQUIRED=1 \
GOCACHE=/private/tmp/acs-eval12-go-cache \
/Users/alphagone/sdk/go1.27.1/bin/go test -tags operations_runtime \
  -race -count=1 -json -run '^TestOPS09DatabaseRecoveryRuntimeIntegration$' \
  -timeout=180s ./cmd/server
```

원시 경로는 /private/tmp/acs-ops09-database-final.json이다. 고정 DB 이미지는 sha256:2b6d51048c03dae147064683f5b078690f1525365d561fd80b78f74de8c3c697이며 합성 자격만 사용했다.

## 계층별 검증과 남은 인수

- test-prod-runtime.sh는 실제 .env가 아닌 운영 예시·합성 자격·새 Compose 프로젝트에서 서버 이미지·기동 순서·진단 UID/권한·중복 슬롯/권한 거부·재생성 보존과 생성 자원 정리까지 통과했다. 실제 Tunnel·외부 HTTPS·운영 배포 인수가 아니다. 원시는 /private/tmp/acs-ops09-prod-runtime.log다.
- 제공자 실패/지연·색인 준비와 실제 서버/색인 프로세스의 embedded/external·두 작업자·중단/재확보, 주기 작업 재시도·종료와 검색 부분/전체 실패의 관련 범위를 새 합성 DB로 실행했다. 검색 실패 표본의 fakeStore와 실제 프로세스/DB/TLS 제공자 시험을 구분한다. 원시는 /private/tmp/acs-ops09-fault-layers.json이다.
- 실제 진단 파일의 장애·stderr·부분 쓰기·종료와 Linux 커널 쓰기 오류/재시작·슬롯 교체는 독립 실행 결과로 기록한다. macOS race와 Linux 비 race를 혼동하지 않는다. 원시는 /private/tmp/acs-ops09-diagnostic-failures.json과 /private/tmp/acs-ops09-diagnostic-linux.log다.

제공자/검색/작업자/저장·진단 장애를 하나의 배포에서 조합한 최종 회복 인수와 실제 접속 상대/Tunnel·운영 공개는 위 계층 통과만으로 완료 처리하지 않는다. 패키지·모듈의 새 실행을 보존하며 다음 OPS-09 작업에서 실제 수행한 범위만 추가한다. DOX pass에서 새 지속 경계나 제품 동작 변경이 없어 기존 DOX·SRS·운영 정본을 유지한다.


## 실행 결과와 정리

최종 DB 중단/복구는 필수 DB·race에서 1건·2.649초로 실패·건너뜀 없이 통과했다. 관련 장애 계층 45건(최상위 11건)과 macOS 진단 장애 16건(최상위 9건)도 각각 실패·건너뜀 없이 통과했다. 이 세 범위는 테스트 이름이 겹치지 않는 총 62건이며 과거 실행을 합산하지 않았다.

Linux 기록기 전체·읽기 전용 마운트·컨테이너 재생성/슬롯 교체 스크립트가 통과했다. 고유 시험 174건이 통과했고 DB가 없는 network=none 모듈 실행의 TestOPS04MaintenanceStorageScopeIntegration 1건은 TEST_DATABASE_URL 부재로 건너뛰었다. 컨테이너 보존은 first/restart/replacement 세 단계에서 같은 시험을 실행하므로 중복 실행을 고유 통과 수에 더하지 않았다. Linux 결과는 비 race이며 macOS 결과와 구분한다. 원시 묶음은 /var/folders/r_/yl4v72hx0sz7fwqxcb8fr90c0000gn/T/acs-obs08-results-4LWdXM이다. 건너뛴 Linux DB 범위를 통과로 보고하지 않는다.

운영 예시 기반 Compose 시험은 자체 프로젝트의 컨테이너·네트워크·볼륨·이미지를 정리하고 PASS를 반환했다. OPS-09 전용 DB도 개별 시험 DB가 제거되어 ops09/postgres만 남고 잔여 클라이언트 연결 0개인 것을 확인했다. bd74167c4782cfe229ea9fbd12e16c2abf72335f75a4d4552ffc0ebec4a9f746의 소유 라벨·익명 볼륨을 대조한 뒤 정상 정지·제거했다. 앞선 두 실패 표본과 최종 성공을 구분하며 기존 개발 DB·WAL과 TEST-08 만료 시험 DB는 유지했다.

공용 DB 정리 도우미 변경 뒤 TEST-08·MCP·인증·서버 관련 267건을 다시 실행했다. 최종 인증 192건·4.686초, 서버 75건·83.708초로 실패·건너뜀 없이 통과했다. 이 회귀와 OPS-09의 계층별 시험은 목적·범위가 달라 각각 기록한다.
