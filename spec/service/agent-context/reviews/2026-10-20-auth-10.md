## 구현과 계약

`/connections`는 검증한 웹 세션의 계정으로만 목록·폐기를 요청한다. 계열은 UUIDv7 내림차순 50개 페이지, 활성 등록은 128개 상한 안의 목록이며 조회 SQL 자체에 계정 조건을 둔다. 계열·client·최초 허용·최근 회전·유효/절대/비활동 만료·폐기 상태와 등록 ID·client·시각만 반환한다. 등록 키·토큰·해시·코드·비밀번호는 조회 투영과 화면에서 제외한다.

계열 폐기는 회전과 같은 계열 행을 잠그고 소유자를 다시 확인한다. 최초 폐기 시각·사유와 보존 수명을 변경하지 않고 남은 접근·갱신을 차단한다. 반복 폐기와 재사용으로 먼저 폐기한 경우도 최초 원인을 보존한다. 등록 폐기는 기존 계정 잠금·소유자 재확인 API를 사용하며 OAuth 계열·웹 세션과 독립적이다. 기존 기여·감사·등록 행을 삭제하거나 재작성하지 않는다.

출처→웹 세션→8 KiB URL-encoded 본문→저장소 순서를 유지한다. 중복·추가 필드·query 자격·잘못된 UUIDv7/미디어는 400, 초과 본문은 413, 다른 계정/없는 대상은 같은 404, 저장·키·세션 장애는 고정 안내의 500이다. 모든 연결 응답에 no-store·no-cache·no-referrer·프레임 차단을 적용하고 성공은 쿠키 변경 없이 303이다. 본문 해석·저장 호출 뒤 취소를 재검사하여 취소된 요청에 성공 응답을 만들지 않는다. 커밋한 폐기는 응답 취소로 되돌리지 않는다.

웹은 새 연결 관리 인터페이스로 서버 어댑터를 거쳐 authz를 호출한다. main에 공유 연결 저장소와 웹 업무 경계를 주입했다. 진단 전달은 입력이나 오류 원문 없이 고정 단계·결과·원인 코드와 요청 context를 받고, 기록 누락이 업무 결과를 바꾸지 않는다. 기존 HTTP 상관 ID·본문/쿼리 없는 로그를 유지한다. 실제 진단 파일 조립은 관측성 후속 작업이다.

## 검증

- Go 1.27.1·pgx v5.10.0의 공식 API와 Modern Go 지침을 확인했다. 웹 양식은 `modern-web-guidance`의 `forms` 지침에 따라 명시적 POST action·네이티브 제출·대상을 포함한 버튼 이름·효과 설명 연결·48px 대상 크기를 적용했다. CSRF는 소유 계약의 기존 CrossOriginProtection을 따른다.
- 인증 전체 **448건**, 웹 전체 **468건**, 선별 서버 **17건**, 에이전트 저장 **22건**, 부모 시험 포함·중복 제외 **955건 통과**, 실패 0·건너뜀 0이며 각 범위 race를 통과했다.
- 인증 전체 회귀는 계정·비밀번호·공유 키·캐시 장애·웹 세션·인가 코드·Bearer·회전·재사용·수명 경계와 신규 연결 관리를 포함한다. 정리 지연과 요청 시 유효성 판정을 구분하며 실제 물리 정리 구현을 완료했다고 보지 않는다.
- 실제 DB의 두 Store·두 Service 및 새 Service에서 소유자/다른 계정/없는 대상, 활성 등록·계열 분리, 재인가 후 같은 등록 재사용, 57개 계열의 50+7 페이지·정렬·중복 없음과 등록 행 보존을 확인했다.
- 실제 계열 행 잠금 아래 회전과 명시적 폐기를 경합시켜 최종 폐기와 발급된 모든 자격의 차단을 확인했다. 잠금 대기 취소의 롤백·유효 자격 유지·열린 트랜잭션 회복을 관찰했다. DB 트리거로 폐기 UPDATE 실패를 주입하여 500 분류·원인 비노출·원래 자격 보존을 확인했다.
- 실제 커밋 반환 직후 취소하는 저장 어댑터 표본에서 서비스는 취소를 반환하고 공유 폐기는 유지했다. 갱신 재사용으로 먼저 폐기한 계열은 키 회전·본인 재폐기 후에도 원래 시각·사유를 유지했다.
- 실제 두 TLS 애플리케이션 인스턴스에서 웹 목록·명시적 폐기→다른 인스턴스의 MCP 401·갱신 invalid_grant·웹 세션 유지와 재인가→등록 폐기→실제 node_update의 invalid_argument를 검증했다. 쓰기·기여·감사 fingerprint는 폐기 직전/직후 동일했다. HTTP 상관 ID·자격/등록 키의 응답 및 요청 로그 비노출을 확인했다. 다른 읽기/등록 도구는 미호출 처리기로 두며 전체 14종 조립을 대신하지 않는다.
- 기존 OAuth 로그인 복원·동의·코드 교환·갱신의 TLS 시험, Bearer/등록 결합 및 웹 세션 장애·폐기의 TLS 시험을 회귀 검증했다. 화면은 HTTP 렌더링·네이티브 양식 표본이며 실제 브라우저·키보드·보조 기술 인수는 아니다.
- `check-go.sh`의 의존성 확인·전체 build·vet·gofmt가 통과했다. 변경 문서 11개·로컬 링크/앵커 381개·Markdown fence와 124개 계획 중 완료 68개·미착수 56개를 대조했다.

최종 모듈·분야 인수 명령은 다음과 같다. DB 시험은 임의 이름의 전용 suite에 정식 마이그레이션을 적용하고 `TEST_DATABASE_URL`·`TEST_DATABASE_REQUIRED=1`을 지정했다. 각 DB 시험의 자식 DB와 실행기가 만든 suite만 정리하고 부재를 확인했다.

```sh
go test -timeout=240s -race -json -count=1 ./internal/authz
go test -timeout=180s -race -json -count=1 ./internal/web
go test -timeout=180s -race -json -count=1 -run '^Test(AUTH10.*|OAuthAuthorizationTLSIntegration|AgentBearerIdentityIntegration|PackageDependenciesMatchDesign|WebSession.*)$' ./cmd/server
go test -timeout=180s -race -json -count=1 -run '^TestAgent.*$' ./internal/store
```

최초 취소 표본에서 DB backend 종료 반영 전의 상태를 즉시 검사한 실패를 보완해 유한 시간 내 실제 회복을 관찰했다. 추가 키 회전 표본이 후속 준비용 키 부재 캐시에 간섭한 시험 순서도 격리하고 인증 전체를 다시 통과했다. 초기 실패를 통과 수에 포함하지 않았다.

## 남은 범위와 DOX pass

인증 서버 분야 인수와 실제 호스트 지원 판정은 구분한다. 호스트 안전 저장·갱신 직렬화·재시작·정확한 callback의 실제 증거는 TEST-08, 전체 기동/14종 서버 계약은 ARCH-06·07·MCP-09·TEST-07, 웹 전체·브라우저는 WEB-08·09·TEST-06, 인증 상태 물리 정리는 OPS-04의 후속 범위다. `/mcp`를 main에서 임시 처리기로 활성화하지 않았다.

새 패키지·폴더·소유권·프로젝트 용어·요구사항·스키마·환경 변수는 추가하지 않았다. 따라서 AGENTS·SRS·용어집·마이그레이션·환경 예시는 유지했다. 소유 웹 SDD에 페이지/양식 계약을 먼저 보완하고 인증·조립 SDD, 계획·진입점·요청 기록을 정합화했다. WEB-08의 연결 표면 일부를 인수했으나 감사 필터와 선행 WEB-02·OBS-06이 미완료이므로 해당 작업을 완료 처리하지 않았다. 기존 Compose·IDE 변경은 보존했으며 commit·push·PR·배포는 수행하지 않았다.
