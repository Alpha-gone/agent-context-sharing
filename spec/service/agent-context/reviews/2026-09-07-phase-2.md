| 방법 | 내용 |

| 코드 판독 | 사용자 입력이 openCypher와 SQL에 닿는 경로를 따라가며 이스케이프 지점을 확인했다 |

```bash

```

### openCypher 주입 방어

세 함수가 층을 나눠 맡는다. 이 구성이 이번 검사에서 가장 잘 짜인 부분이다.

| 함수 | 대상 | 방식 |
|------|------|------|
| `sqlString` | AGE 호출의 그래프 이름 | 작은따옴표를 이중화한다. 값 자체가 `store.go:29`의 정규식을 통과한 것이다 |
| `dollarString` | openCypher 질의 전체 | 질의 본문에 없는 `$storeN$` 태그를 찾아 감싼다. 본문에 구분자가 들어가도 SQL 문자열 경계가 깨지지 않는다 |
| `cypherString` | 질의 안의 문자열 리터럴 | `json.Marshal`로 이스케이프한다 |

`body`와 `source_ref_locator`처럼 사용자가 정하는 값이 들어가는 경로를 따라 확인했다. 값이 먼저 `cypherString` 또는 `encodeProperties`로 이스케이프되고, 완성된 질의 전체가 `dollarString`을 지나므로 태그 충돌도 함께 막힌다. 빠져나갈 경로를 찾지 못했다.

### 동시 수정 직렬화

`UpdateContext`는 판 번호를 두 번 본다. 트랜잭션 안에서 `previous`를 읽어 비교하고, 이어지는 openCypher `SET`의 `WHERE`에 같은 조건을 건다.

Read Committed에서 앞의 읽기는 행을 잠그지 않으므로 두 요청이 같은 판 번호를 함께 읽을 수 있다. 실제 직렬화는 뒤의 조건부 `SET`이 한다. 먼저 커밋한 쪽이 판 번호를 올리면 뒤의 갱신은 PostgreSQL이 조건을 다시 평가해 대상 0건이 되고, `contextVersionConflict`가 충돌로 바꾼다.

이 판정이 AGE의 `SET`에서도 성립하는지가 관건이라 20회 반복해 확인했다.

## 발견 사항

처리 상태를 갱신할 수 있도록 체크박스로 둔다.

### - [x] 1. `ListGraphs`에 계정 범위가 없다

`internal/store/graph.go:55`

```go
func (s *Store) ListGraphs(ctx context.Context, accountID model.ID, filter model.GraphListFilter, cursor string, limit int) ([]model.GraphListItem, string, error)
```

`SRS.md` 「그래프 목록 조회」가 확정한 내용과 어긋난다.

| 항목 | 확정 | 현재 구현 |
|------|------|-----------|
| 대상 | 요청 계정이 유효한 등급을 가진 그래프만 반환한다 | `account_id`를 필수로 받고 직접 부여·활성 팀 상속이 있는 그래프만 반환한다 |
| 목록 항목 | `graph_id`, `name`, `description`, `last_activity_at`과 요청 계정의 등급 | 목록 전용 타입에 요청 계정의 최고 유효 등급을 넣는다 |
| 필터 | 이름 부분 일치와 등급으로 거른다 | 대소문자를 무시하는 리터럴 부분 일치와 여러 등급 필터를 SQL 한 질의에 적용한다 |
| 삭제된 그래프 | `deleted_at`이 있는 그래프는 제외한다 | 충족한다 |

**처리 결과.** 직접 부여와 활성 팀 상속을 `UNION ALL`로 합친 뒤 등급 순위를 하나의 SQL 질의에서 계산한다. 삭제된 팀의 부여는 `team.deleted_at IS NULL` 조건으로 제외하며, 직접·팀 등급이 겹치면 더 높은 등급을 목록에 넣는다. 통합 테스트가 권한 없는 그래프와 삭제된 팀 그래프의 비노출, 최고 등급, 이름·등급 필터를 검증한다.

**영향.** 목록 조회가 요청 계정 범위 안에서 끝나므로, 개발 계획 2단계의 그래프 존재 비노출 완료 기준이 이 경로에도 성립한다.

**독립 확인.** 통합 테스트 통과와 별개로 다음을 직접 확인했다.

| 확인 | 결과 |
|------|------|
| 누적 데이터에서 범위 유지 | 그래프 114건과 부여 24건이 쌓인 데이터베이스에서 5회 반복해 매번 요청 계정의 2건만 반환했다. 수정 전이라면 전부 반환됐을 조건이다 |
| 이름 필터 이스케이프 | PostgreSQL에서 직접 실행해 `%` 검색이 `team alpha`에 오탐하지 않고 `a%b`에는 정탐하며, `_` 검색도 오탐하지 않고 대소문자를 무시함을 확인했다 |
| 등급 값의 안전성 | `graph_grant.grade`의 `CHECK` 제약이 세 값으로 한정하므로 등급 순위 계산이 `NULL`이 될 경로가 없다 |
| 상속 규칙 일치 | 최고 등급 선택이 `SRS.md` 「상속 규칙」의 "직접 부여받은 등급과 소속 팀에서 상속한 등급 중 더 높은 등급을 적용한다"와 일치한다 |

**범위 밖으로 남은 것.** `Graph()`는 여전히 `graph_id`만으로 조회하며 등급을 보지 않는다. `SDD.md` 「패키지 경계」가 등급 판정을 `perm`에 두었고 접근 계층은 주어진 `graph_id`의 격리만 강제하므로 설계대로다. `ListGraphs`는 여러 그래프를 가로지르는 유일한 함수라 예외였다.

### - [x] 2. 그래프 이름 정규식이 계층마다 다르다

| 파일 | 정규식 |
|------|--------|
| `internal/config/config.go:61` | `^[a-z_][a-z0-9_]*$` |
| `internal/migrate/migrate.go:36` | `^[a-z_][a-z0-9_]*$` |
| `internal/store/store.go:29` | `^[a-z_][a-z0-9_]*$` |

**처리 결과.** `config`, `migrate`, `store`가 모두 `^[a-z_][a-z0-9_]*$`를 사용하도록 맞췄다. `_foo`는 세 계층에서 허용하고, 숫자 시작·하이픈·대문자는 계속 거부한다.

**영향.** `AGE_GRAPH_NAME=_foo`가 구성 검증과 마이그레이션을 통과한 뒤 `store.New`에서만 기동 실패하던 경로가 사라졌다.

**완화 방향의 근거.** 어느 쪽으로 맞추든 일치는 하므로, 실제 AGE 제약을 확인해 완화가 옳은 방향인지 검증했다. AGE에서 `create_graph('_verify_underscore')`와 그 그래프에 대한 openCypher `CREATE` 질의가 모두 성공했다. `store`가 실제 제약보다 엄격했던 쪽이므로 완화가 맞다.

**재발 방지.** 처음 추가된 회귀 테스트는 `store`의 정규식만 단독 검사해, `config`만 바꿔도 통과하는 상태였다. 세 패키지가 각자 같은 경계를 확인하도록 고쳤다.

| 패키지 | 확인 방식 | 근거 |
|--------|-----------|------|
| `store` | `graphNamePattern.String()`이 약속된 리터럴과 같은지 | 내부 테스트 패키지라 변수를 직접 본다 |
| `config` | 같은 리터럴 비교 | 내부 테스트 패키지 |
| `migrate` | `Config.Validate()`의 수용·거부 결과 | 외부 테스트 패키지라 비공개 변수를 볼 수 없어 공개 계약으로 같은 경계를 확인한다 |

**확인 방법.** 장치가 실제로 동작하는지 보려고 세 패키지의 정규식을 한 번에 하나씩 `^[a-z]`로 되돌려 각각의 테스트가 깨지는 것을 확인한 뒤 원복했다. 셋 다 실패했다.

| 어긋나게 한 곳 | 실패한 테스트 |
|----------------|---------------|
| `config` | `config의 그래프 이름 정규식 = ^[a-z]..., want ^[a-z_]...` |
| `migrate` | `그래프 이름 "_agent_context" 허용 결과 = false, want true` |
| `store` | `store의 그래프 이름 정규식 = ^[a-z]..., want ^[a-z_]...` |

`AGE_GRAPH_NAME=_underscore_probe`로 서버를 기동해 구성 검증과 `store.New`를 모두 통과하고 `/healthz`가 `200`을 돌려주는 것도 확인했다.

**남은 것.** 정규식 리터럴이 세 패키지에 각각 있다. 값의 단일 출처를 두는 편이 근본 해결이지만 `migrate`가 애플리케이션 11개 패키지 밖이라 공유 위치를 정하는 판단이 필요해 이번에는 테스트로 잠그는 데 그쳤다.

### - [ ] 3. `Graph()`의 오류 계약이 `Context()`와 다르다

`internal/store/graph.go:49`가 `pgx.ErrNoRows`를 감싸 반환한다. `store`가 `ErrNotFound`를 정의해 두었고 `Context()`는 그것을 돌려주므로, 같은 계층에서 부재를 알리는 방식이 둘이다. 호출자가 `errors.Is(err, store.ErrNotFound)`로 `Graph()`의 부재를 판별할 수 없다.

4단계에서 `graph_get`이 부재를 `not_found` 도메인 오류로 사상해야 하므로 그 전에 정리해야 한다.

### - [ ] 4. 통합 테스트가 기본 실행에서 건너뛰어진다

`internal/store/store_integration_test.go:21`이 `TEST_DATABASE_URL`이 없으면 `t.Skip`한다. `.env`와 `.env.example` 어디에도 그 값이 없어, 평소 `go test ./...`는 2단계 완료 기준 "실제 AGE 데이터베이스를 사용한 `store` 통합 테스트가 통과한다"를 확인하지 못한다.

이번 검사에서는 `TEST_DATABASE_URL`을 직접 넣어 실행했고 통과했다. 건너뛰기 자체는 데이터베이스 없는 환경을 위한 것이라 타당하지만, 값이 어디에도 없으면 실수로 검증을 빠뜨리기 쉽다.

### - [ ] 5. 사소한 항목

- `internal/store/graph.go:268`이 `err == pgx.ErrNoRows`로 비교한다. 같은 파일 `:179`는 `errors.Is`를 쓴다. 현재 pgx 동작에서는 결과가 같지만 규칙이 둘이다.
- `internal/store/relation.go:57`의 `ListRelations`에 `SRS.md` 「연산 목록」이 정한 `context_id`, `state_filter`, `type_filter`가 없다. 1번과 같은 성격이라 4단계에서 시그니처가 바뀐다.

## 종합

2단계의 핵심 계약인 격리, 주입 방어, 낙관적 잠금, 트랜잭션 경계는 제대로 구현되어 있다. 발견 사항 다섯 건 가운데 1번만 완료 기준과 실제가 어긋나는 항목이고, 나머지는 각각 몇 줄로 정리할 수 있다.

1번의 처리 방향을 정하기 전에는 개발 계획 2단계의 완료 기준 체크박스를 그대로 둔다.
