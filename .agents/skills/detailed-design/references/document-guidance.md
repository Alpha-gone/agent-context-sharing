# 상세 설계 문서 작성 기준

## 권장 구조

서비스 특성에 맞게 조정하되 다음 순서를 기본으로 사용한다.

1. 문서 정보
2. 설계 목적과 범위
3. 설계 입력
4. 시스템 컨텍스트와 아키텍처
5. 구성 요소 설계
6. 주요 처리 흐름과 상태
7. 인터페이스와 API 계약
8. 데이터 모델과 저장 전략
9. 오류, 복구, 보안과 권한
10. 관측성, 배포와 운영
11. 비기능 요구사항 설계
12. 요구사항 추적표
13. 설계 미정 사항
14. 주석

`설계 입력`에는 사용한 `SRS.md`, 조건부 보조 문서와 채택된 제안 ID를 기록한다. 입력이 없으면 `없음`으로 명시한다.

## 주석과 이동 링크

보충 설명이 본문 흐름을 방해하면 문서 하단 `주석` 섹션에 모은다. HTML 주석처럼 렌더링되지 않는 형식은 사용하지 않는다.

```markdown
본문 내용.<a id="note-ref-1"></a>[[주석 1]](#note-1)

## 주석

<a id="note-1"></a>**주석 1.** 보충 설명을 적는다. [본문으로 돌아가기](#note-ref-1)
```

주석 번호는 등장 순서대로 부여한다. 하나의 주석을 여러 위치에서 참조하면 본문 앵커를 각각 만들고 모든 복귀 링크를 제공한다.

## 요구사항 추적표

| 요구사항 ID             | 설계 반영 위치 | 설계 요소   | 검증 방법   | 상태 |
|-------------------------|----------------|-------------|-------------|------|
| `FR-{서비스식별자}-001` | {문서 절}      | {설계 요소} | {검증 방법} | 반영 |

`SRS.md`의 설계 대상 요구사항을 빠뜨리지 않는다. 반영할 수 없는 항목은 원인과 필요한 결정을 `설계 미정 사항`에 연결한다.

## 작성 점검

- 요구사항 상태와 추적 ID를 보존했는가
- 설계 선택의 근거와 미정 사항을 구분했는가
- 인터페이스와 데이터 계약에 필요한 오류·권한·상태를 포함했는가
- 본문, 표와 Mermaid 다이어그램이 같은 설계를 설명하는가
- 모든 내부 링크와 주석 복귀 링크가 유효한가
