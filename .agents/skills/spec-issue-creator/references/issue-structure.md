# 이슈 작성 기준

## 분할 점검

| 점검 항목 | 판단 기준                                                                     |
|:----------|:------------------------------------------------------------------------------|
| 결과      | 완료 시 생성되거나 바뀌는 산출물을 한 문장으로 설명할 수 있는가               |
| 독립성    | 다른 이슈가 완료되지 않아도 시작 가능한가, 아니면 선행 조건이 명시되어 있는가 |
| 검증      | 성공 여부를 확인할 명령, 문서 검사 또는 관찰 기준이 있는가                    |
| 추적성    | 관련 요구사항 ID와 명세 링크를 연결할 수 있는가                               |
| 제외 범위 | 인접 작업과 책임 경계가 명확한가                                              |
| 미정 사항 | 구현 전에 결정해야 하는 항목이 별도 조사·결정 범위로 분리되었는가             |

## 본문 형식

필요 없는 절은 억지로 채우지 말고 제외 이유를 적는다.

````text
## 목적

이 이슈가 해결할 문제와 기대 결과를 적습니다.

## 추적 요구사항

| 요구사항 ID | 명세                                    | 관련 범위                         |
|:------------|:----------------------------------------|:----------------------------------|
| `{ID}`      | `spec/service/{서비스 경로}/SRS.md`    | 이슈가 담당하는 범위를 적습니다. |

## 입력 및 선행 조건

- 필요한 결정, 데이터, 기존 기능 또는 선행 이슈를 적습니다.

## 산출물

- 완료 시 생성되거나 변경되는 결과를 적습니다.

## 작업 범위

- [ ] 구현 또는 문서 작업을 결과 중심으로 적습니다.

## 제외 범위

- 이 이슈에서 다루지 않는 인접 작업을 적습니다.

## 의존성

- 선행·후속·연결 이슈와 의존 이유를 적습니다.

## 인수 조건

- [ ] 사용자 또는 시스템 관점에서 검증 가능한 완료 조건을 적습니다.

## 검증 방법

```text
실행할 명령, 문서 검사 또는 수동 확인 절차
```

## 완료 처리

- 병합으로 자동 종료해야 하면 구현 PR에 `Closes #{이슈 번호}`를 사용합니다.
- 참조만 필요하면 `Refs #{이슈 번호}`를 사용합니다.
````

## 작성 규칙

- 제목은 구현 방법보다 결과를 먼저 표현한다.
- 체크리스트는 작업 목록과 인수 조건을 구분한다.
- 명세에 없는 일정과 기술 선택을 추가하지 않는다.
- 링크는 실제 대상과 경로를 확인하고, 저장소 안의 문서는 가능한 한 직접 링크한다.
- 제안이나 미정 사항은 확정 범위와 구분한다.
