# IDX-04 실패 분류·재시도 예산 모듈 시험

## 범위와 입력

- 대상: [IDX-04](../development-plan/indexing.md#idx-04). IDX-02·IDX-03 완료. 시작 커밋 `1e15530`, 브랜치 `feat/index-retry-budget`.
- PR #135의 병합을 확인하고 `origin/dev`를 fetch한 뒤 해당 기준에서 새 브랜치를 만들었다. 시작 시 upstream 대비 앞섬·뒤처짐은 모두 0이었다. 기존 사용자 Compose·IDE 변경은 보존했다.
- 정본: [색인 재시도](../sdd/indexing.md#색인-재시도), [확보 세대](../sdd/indexing.md#색인-작업-큐), [시험 계층](../sdd/testing.md#테스트-계층), [모듈 시험 시점](../DEVELOPMENT_PLAN.md#테스트-작성과-실행-시점).
- PostgreSQL 18의 문장 시각과 pgx v5.10.0의 트랜잭션 reference를 확인했다. 외부 API는 호출하지 않았다.

## 구현과 검토

- 실패의 다음 시각을 작업자 호스트 시계 대신 DB의 `statement_timestamp()`와 초 단위 지연으로 계산한다. 확보·기한 판정과 같은 시계를 사용한다.
- 일시 실패의 간격은 1·2·4·8분이고 다섯 번째 실패는 `failed`로 남는다. 백오프 함수는 0 이하 입력에서도 음수 shift로 실패하지 않으며 큰 값은 8분으로 제한한다.
- 실패 트랜잭션도 공통 `finishWrite`로 정리해 요청 취소와 독립된 기존 5초 롤백 예산과 원인 보존을 적용한다. 실패 기록 자체가 실패해도 `Found=true`와 확보한 작업 정보를 반환한다.
- 공백만 있는 모델 식별자를 누락으로 판정해 즉시 실패시킨다. 빈 벡터·명시적 영구 실패와 제공자의 차원·입력·응답 계약 분류를 유지한다.
- 실패 UPDATE의 task_id·등록 시각·리스 시각·pending 조건을 유지한다. 재등록·재확보·작업 제거 뒤 이전 일시·영구·예산 소진 실패는 새 상태를 바꾸지 않는다.
- 실패 기록까지 취소되면 부분 반영 없이 기존 리스를 유지하며, 만료 후 재확보해 회복한다. 취소된 요청을 분리해 추가 실패 기록을 강제하지 않는다.

## 검증 결과

- Go 1.27.1 darwin/arm64. 고정 Dockerfile로 전용 이미지·컨테이너·새 볼륨을 만들고 loopback 임시 포트와 합성 자격만 사용했다. 실제 PostgreSQL 18.6 / AGE 1.8.0 / pgvector 0.8.6 / Linux aarch64를 확인했다.
- 새 DB 모듈은 시험별 임시 DB 14개에 정식 001·009·010·011 적용과 반복 적용의 무변경을 확인했다. 관련 회귀는 전용 컨테이너의 별도 기본 DB에 정식 마이그레이션을 적용해 실행했다.
- **고유 시험·하위 시험 74건 통과**: store 44·index 29·server 1, 최상위 17개·하위 57개. 대상 모듈 57건과 관련 회귀 17건이며 `-race -count=1`, `TEST_DATABASE_REQUIRED=1`을 적용했다. 실패·건너뜀은 0이다.
- 조회 장애는 없는 물리 그래프, 결과 저장 장애는 실제 벡터 차원 제약으로 주입했다. 제공자 일시 실패와 함께 각각 다섯 번 처리해 attempts·마지막 사유·pending/failed 전이, 트리거가 기록한 동일 문장 시각 대비 정확한 60·120·240·480·0초를 대조했다. 대기·failed 작업의 즉시 재호출은 없었다. 실시간 백오프 대기 대신 자기 작업의 기한만 앞당겼다.
- 저장된 본문·판·기존 벡터·모델과 다른 그래프의 큐 전체 필드는 보존됐다. failed 작업이 남고 준비 검사에서 실패·대기로 보고되는지 확인했다.
- 빈 벡터·모델 누락·공백 모델·영구 제공자 오류는 첫 시도에서 failed가 됐다. HTTP 408·429·500~599와 네트워크·timeout은 재시도하고 다른 HTTP·차원·입력·응답 계약은 재시도하지 않는 분류 및 래핑·다중 원인 보존을 확인했다. 제공자 원문·키·본문 비노출, 실제 본문 수신 취소·timeout·읽기 장애도 로컬 TLS 대역으로 확인했다.
- 재등록·리스 재확보·행 제거의 세 경우에서 이전 일시·영구·예산 소진 실패가 업무 상태 전체 지문을 바꾸지 않았다. UPDATE 오류·지연 제약 트리거의 COMMIT 오류·DB 대기 중 마감·제공자 반환 직전 취소에서 작업 정보와 PostgreSQL/취소 원인을 보존하고 부분 반영 부재·풀/예약 반환·장애 제거 후 재확보를 확인했다.
- 재등록 뒤 이전 성공·실패 무효화, 결과 저장 실패 롤백, 제공자 대기 중 본문 저장, 준비 집계와 패키지 경계의 관련 회귀도 통과했다.
- `check-go.sh`의 의존성 검증·전체 build·vet·gofmt, 변경 문서 링크·앵커·계획 수·DOX 소유권과 diff 검사를 통과했다. 임시 DB 잔여 0을 확인하고 자체 IDX-04 자원만 정리했으며 라벨 기준 잔여 자원은 0이다.
