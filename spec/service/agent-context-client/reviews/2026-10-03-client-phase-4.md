# 클라이언트 4단계 구현 검토

- 검토일: 2026-10-03
- 범위: 원격 HTTP 전송·인증 조립·전송 재시도·쓰기 멱등성·자원 상한과 취소
- 기준: [SRS](../SRS.md), [SDD](../SDD.md), [개발 계획](../DEVELOPMENT_PLAN.md)
- 이 기록은 해당 시점의 구현 검증 결과이며 동작 계약의 정본은 아니다.

## 확인한 구현

- `remote.NewHTTP`가 검증된 구성과 인증 조정자로 HTTP `Source`·발견·목록 캐시를 조립한다. 생성 시 네트워크·브라우저를 사용하지 않는다. 소유 호출 context·복제 transport는 `Close`로 정리하고 주입 인증 조정자의 수명은 호출자에게 둔다.
- `authorize.Apply`는 유효한 현재 자격 증명과 새 DPoP proof만 적용하며 인가를 시작하지 않는다. 초기 보호 도전·재인가는 캐시 gate와 호출 slot 밖에서 진행한다. gate를 기다리다가 토큰이 만료된 경우도 같은 경로를 사용한다.
- 논리적 호출의 준비·발견·목록·도구 전송은 호스트 context·원격 처리 잔여 시간·전송 재시도 예산·인가 사용 여부·slot을 공유한다. 인가 대기는 인증 제한 시간으로 제한하고 원격 처리 예산에서 제외하며 호스트 deadline·취소는 유지한다. 실행 8개·FIFO 대기 128개, 별도 공유 인가 대기 128개 상한을 유지한다. 재인가 전에는 호출 slot을 반환한다.
- 단일 POST·JSON, revision `2026-07-28`·메서드·도구 헤더와 요청별 metadata·확장 capability를 설정한다. HTTP 시도마다 새 UUIDv7 원격 ID·DPoP proof를 생성하고 redirect·자동 본문 replay는 사용하지 않는다.
- 전달 전·일부/전체 전달 뒤·전달 여부 불명확한 전송 실패를 구분한다. 읽기와 전달 전 쓰기, 협상 쓰기만 일시적 실패를 최대 3회 재시도한다. 지연 상한 250ms·500ms·1초와 같은 호출의 인가 예산을 유지하며 불확실 쓰기는 `ErrIndeterminate`로 반환한다.
- 검증한 발견의 `retentionMs=86400000`을 협상한 쓰기 8종만 Structured Fields String UUIDv7 키를 전송한다. 같은 호출의 전송 재시도·재인가에서 키를 유지하고 읽기·비협상 쓰기는 키 없이 호출한다. 보관 시간이 끝난 불확실 쓰기를 다시 보내지 않는다.
- 요청 256 KiB, 전송·gzip 해제 본문 각 32 MiB를 제한한다. JSON-RPC 외피·응답 ID·HTTP 상태를 검증하고 완전한 protocol-level 오류를 `ProtocolError.Raw`로 보존한다. 기본 문자열·디버그 표현은 원격 오류 본문을 숨긴다. 도메인 오류·완전한 실패·계약 위반·크기 초과는 재시도하지 않는다.
- 초기 도전·invalid_token만 최대 한 번 인가·재전송하고 nonce/proof 오류·두 번째 401·500은 반복하지 않는다. 취소된 응답을 폐기하고 갱신하지 않으며 계정 변경 오류 자체로 재인가·도구 재전송을 시작하지 않는다.

## 검증 결과

- Go `1.27.1`에서 클라이언트 전체 `go test -race ./... -count=1`을 통과했다. 원격 패키지 전체 `go test -race ./internal/client/remote -count=10`도 통과했다.
- `TestApplyIsNonInteractive`에서 토큰 부재·만료 여유·취소·종료의 헤더 미적용·추가 브라우저 미실행과 유효 토큰의 요청별 새 proof를 확인했다.
- 양쪽 모듈 `go build ./...`·`go vet ./...`, 서버 `TestToolManifestMatchesClient`와 Linux amd64 클라이언트 교차 빌드를 통과했다. 서버 코드·공유 manifest·의존성은 변경하지 않았다.
- 전송 대역에서 전달 전·요청 본문 일부/전체 전달·불명확한 전달·잘린 응답·영구 TLS 오류, 읽기·협상/비협상 쓰기의 시도 횟수·최종 분류, 재인가 공통 예산·키·새 ID/proof를 검증했다. 모든 13종의 키 적용 여부와 호출 간 키 고유성, 24시간 보관 종료도 확인했다.
- 요청 정확히 256 KiB·1바이트 초과, 응답 정확히 32 MiB·1바이트 초과와 고압축 gzip, 알려진/불명확한 길이·손상 압축·중복 JSON·ID/상태 불일치·redirect·500·도메인 오류를 검증했다. 기존 호스트 writer의 32 MiB 출력·부분 출력 방지 회귀 시험도 통과했다.
- 호출 FIFO 128명·129번째 대기 거부·중간 대기자 취소·100개 동시 호출의 8개 실행 상한과 캐시 gate 대기 상한을 확인했다. deadline·호출 취소·`Close`·재시도 지연·인가 대기 취소와 늦은 응답·갱신 폐기를 시험했다.
- 실제 로컬 TLS 시험 서버와 인증 조정자·루프백 callback을 사용해 PKCE·코드 교환·ES256 JWT·공개 키 결합·요청별 proof의 서명·htm/htu/iat/ath·jti 고유성과 토큰 갱신을 확인했다. 100개 동시 호출의 응답 상관·8개 실행 상한을 시험했다.
- 같은 TLS 시험에서 쓰기 첫 401 뒤 재인가, 서버 적용 뒤 응답 유실, 같은 키의 재전송·시험 서버 결과 재사용을 확인했다. 다른 계정의 재인가 토큰은 `ErrIdentityChanged`로 거부하고 새 요청의 정상 계정 재인가 뒤 복구됐다. 실제 dial 실패가 전달 전 실패로 분류되는 것도 확인했다.
- 저장소 전체 `gofmt -l .`·`git diff --check`, 변경 문서 상대 링크·요구사항 51건 추적성과 한국어 표현·맞춤법을 검토했다.

## 미해결 결함과 후속 경계

검증 범위에서 확정된 미해결 결함은 없다. 아래 항목은 이 단계의 대역·로컬 TLS 검증이 대체하지 않는 후속 범위다.

- `serve`에 `remote.NewHTTP`·`host.Tools`를 조립하지 않았다. `ErrBusy`·`ErrIndeterminate`·인증/주체 오류와 `ProtocolError`의 실제 호스트 ID·일곱 클라이언트 코드 직렬화, 정책·원문 결과 중계와 전체 `doctor`는 5단계다. 패키지 오류 분류 시험을 호스트 완료 근거로 보고하지 않는다.
- 실제 서비스 서버·데이터베이스·인가 서버 로그인·멱등성 저장·교차 인스턴스 proof 재생 방어·Bearer 하향 거부는 미실행이다. 로컬 TLS 시험 서버의 결과 재사용·proof 검증을 실제 서비스 수신 측 검증으로 보고하지 않는다. 서버 전체 회귀·DB 통합 시험도 이번 범위에서 실행하지 않았다.
- 실제 시스템 브라우저·macOS/Linux 지원 환경·WSL2·지원 호스트·공식 conformance·성능·배포 산출물 검증은 6단계에서 수행한다. Linux 교차 빌드는 실제 Linux·WSL2 실행 검증이 아니다.
- 4단계는 원격 전송 패키지 범위의 작업·완료 기준으로 판정한다. 2·3단계의 미충족 호스트·수신 측·진단 완료 기준과 5·6단계 항목은 미완료로 유지한다.

## DOX와 설계 정합성

- SDD에 비대화형 적용·gate/slot 밖 인가, 공통 전송 상태·키의 `remote` 소유권, 전달 판단과 본문 replay 금지 경계를 명시했다. 추가 검토에서 SRS의 시간 제한 판정 기준과 SDD를 인가/원격 처리 분리 계약으로 정합화했다. 도구·서버 외부 공개 계약은 변경하지 않았다.
- `remote/AGENTS.md`에 지속 전송 계약·검증 경계를 두고 `client/AGENTS.md`의 Child DOX Index를 갱신했다. 인증 소유 문서에 `Apply` 계약을 추가했다.
- 추가 검토의 시간 계약은 클라이언트 서비스·모듈·원격 소유 DOX에 반영했다. 루트·명세 상위 문서는 기존 소유권·구조·workflow가 유지되므로 변경하지 않았다. 인증 패키지의 마지막 대기자 정리 계약은 유지한다. 서비스 검토 기록 폴더는 기존 경계이며 새 하위 DOX를 만들지 않았다.

## 추가 검토와 처리

### 인가가 짧은 요청 제한 시간으로 중단되는 명세·구성 위험

- 영향도: 중간. 구현이 당시 SDD의 단일 deadline을 따랐으므로 구현 계약 위반과 구분한다.
- 상태: 시간 제한 계약 정합화·구현·회귀 검증 완료.
- 위치: `remote/catalog.go`의 `callContext`·`enter`, `remote/http.go`의 `reauthorize`, `.env.example`의 두 제한 시간.
- 재현: 수정 전 원격 처리 100ms·인가 200ms에서 최초/목록/도구 인가 모두 `context deadline exceeded`였다. 실제 TLS·인증 조정자·루프백 시험도 요청 제한 1초·로그인 2초에서 실패했다.
- 처리: 사용자가 제시한 첫 번째 방안을 채택했다. 인가 대기는 `AUTH_TIMEOUT`, 그 밖의 원격 처리 누적 시간은 `REQUEST_TIMEOUT`으로 제한한다. 인가 중 원격 시간 예산만 멈추고 인가 뒤 남은 시간으로 다시 시작한다. 호스트의 명시적 deadline·취소와 종료는 제거하지 않는다. 마지막 대기자 취소 뒤 인가를 남겨 두는 두 번째 방안은 채택하지 않아 기존 일회성 값·listener 정리를 유지한다.
- 검증: `TestHTTPAuthorizationWaitHasSeparateTimeout`, `TestHTTPAuthorizationTimeoutAndHostDeadline`, `TestHTTPReauthorizationPreservesRemainingTime`과 기존 취소·종료 시험 통과. 실제 TLS 시험에서 요청 제한 1초·로그인 2초 뒤 토큰 교환 1회·정상 목록과 100개 동시 호출을 확인했다. 최초/재인가 중 단순 시간 예산 초기화도 거부한다.

### DEF-20261003-004: 초기 인가 뒤 버리는 인증된 도구 목록

- 영향도: 낮음.
- 상태: 수정·회귀 검증 완료.
- 위치: `remote/http.go`의 `prepare`·`execute`.
- 재현: 수정 전 첫 호출은 익명 목록 → 인증된 목록 → 발견 → 인증된 목록 → 도구 호출의 5개 요청이었다. 첫 인증된 목록은 검증·캐시 없이 버려졌다.
- 처리: 초기 도전의 인가가 성공하면 준비 경로에서 바로 반환한다. 원래 발견·목록 경로에서만 인증된 목록을 조회·검증·캐시한다. 보호 요청의 invalid_token 재전송과 공통 최대 한 번 인가·3회 전송 재시도는 유지한다.
- 검증: `TestHTTPInitialAuthorizationDoesNotResendProbe`에서 익명 목록 → 발견 → 인증된 목록 → 호출의 4개 요청을 확인했다. `TestHTTPInitialAuthorizationKeepsRetryBudgetForCatalog`에서 발견 뒤 실제 목록의 3회 일시적 실패·4번째 성공과 단일 인가를 확인했다.
