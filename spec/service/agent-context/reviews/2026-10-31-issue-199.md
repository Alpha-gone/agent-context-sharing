# #199 진단 실패 원인 분류

## 변경

- HTTP는 상태별 거부 원인과 TLS·요청 취소/예산·panic을 구분하며 일반 5xx를 저장소 장애로 추정하지 않는다. 부분 응답 뒤 panic도 실제 상태와 별개로 handler_panic을 기록한다.
- 기동은 수신 전 조립의 completed/failed를 기록하며 구성·DB·인가·임베딩 스키마를 구분한다. 실패 뒤 정상 정리는 별도 shutdown/completed로 남기고 원래 오류는 반환 체인에 보존한다. HTTP 수신의 네트워크 오류를 DB 장애로 합치지 않는다.
- MCP는 결과의 고정 code와 감싼 오류·취소·마감에 따라 사유와 수준을 정한다. 임의 구조화 값은 JSON 객체로 확인하며 알 수 없는 code·message를 기록하지 않는다.
- 색인 provider는 재시도 가능 장애·비재시도 HTTP/응답 계약·차원 불일치를 구분한다. 인증은 ErrUnavailable과 감싼 취소/마감도 INFO canceled/deadline_exceeded로 분류하고 순수 저장 장애는 ERROR로 유지한다.
- [관측성 대응표](../sdd/observability.md#실패-원인과-수준의-대응), 허용 코드·시험 설계·추적표를 정합화했다. HTTP/OAuth 응답·재시도 정책·스키마·환경 구성·DOX 소유권은 유지했다. 기록기 준비 전 실패의 기존 stderr 경계도 유지한다.

## 검증

- Go 1.27.1, 전용 합성 PostgreSQL, TEST_DATABASE_REQUIRED=1의 DB/race: 인증 516·MCP 505·색인 143·진단 218개 시험 및 하위 사례 통과. 최종 서버 전체는 730개 통과·환경 인수 21개 건너뜀이며 실패는 없다. 건너뜀은 실제 호스트·배포 인수 통과를 뜻하지 않는다.
- 수정 전 HTTP 처리기를 Go overlay로 실행하여 401·403·404·405·413·429와 5xx 원인 합침을 새 회귀가 검출하는지 확인했다. 수정 후 실제 Reporter와 기동 파일 이벤트의 사유·수준·결과·검증을 대조했다.
- 최초 서버 실행은 이전 #190의 도구 설명과 서버 MCP09 스냅샷 불일치로 실패했다. UPDATE_MCP09_SNAPSHOT=1의 생성 절차로 설명 두 곳만 갱신했으며, 최종 서버 전체는 갱신 변수 없이 통과했다.
- 독립 검토가 발견한 HTTP 수신 네트워크 오류의 DB 오분류는 수정하고 listen/DB-read 대조를 추가했다. 재검토에서 추가 차단 결함은 없었다. 서버에 직접 드라이버 의존성을 두지 않고 오류의 SQLState 인터페이스만 사용한다.
- check-go.sh의 의존성·build·vet·gofmt, 변경 Markdown 링크·구조·요구사항 ID와 diff 공백 검사를 수행했다.
- 기존 개발 DB 대신 작업 소유 합성 컨테이너·볼륨만 사용했다. 실제 외부 제공자·호스트·운영 배포는 이번 검증 범위가 아니다.
- 검증 후 소유 라벨을 확인하여 합성 컨테이너·볼륨을 제거했고 해당 라벨의 잔여 컨테이너가 없음을 확인했다.
