## 검사 방법

2단계 검사와 같이 코드 판독과 실제 실행을 나눠 수행했다. 체크박스 표시를 근거로 삼지 않았다.

| 방법 | 내용 |
|------|------|
| 코드 판독 | 명세가 확정한 값과 절차를 하나씩 코드에서 다시 확인했다 |
| 실 데이터베이스 실행 | 새 `store` 함수를 마이그레이션이 적용된 실제 데이터베이스에 직접 호출해 확인했다 |
| 경계값 실행 | 비밀번호 길이 같은 입력 검증 경계를 실제 호출로 확인했다 |
| 경쟁 상태 검사 | `-race`로 전체 패키지를 실행했다 |

재현 명령은 다음과 같다.

```bash
export TEST_DATABASE_URL="$DATABASE_URL"
go test ./internal/store/ -count=1 -run 'TestPermissionIntegration|TestAuthorizationCodeIntegration' -v
go test ./... -count=1 -race
```

### 검사 방법을 실 데이터베이스로 옮긴 이유

검사 시작 시점의 `go test ./...`는 전부 통과했다. 그런데 3단계가 더한 `store` 함수 여섯 개에 통합 테스트가 하나도 없었고, `internal/authz`의 단위 테스트는 `authz_test.go:176`의 메모리 대역으로만 실행됐다. 대역은 Go 자료구조라 SQL 예약어도 `NULL`도 재현하지 못한다.

그래서 새 `store` 함수를 실제 데이터베이스에 직접 호출해 봤고, 아래 1번부터 3번이 그 자리에서 드러났다. 세 건 모두 실행하면 100% 실패하는 종류이며, 대역 때문에 단위 테스트가 초록으로 남아 있었다.

## 발견 사항

처리 상태를 갱신할 수 있도록 체크박스로 둔다.

### - [x] 1. `AS grant`가 SQL 예약어라 권한 질의가 항상 실패한다

`internal/store/permission.go:21`, `internal/store/rate.go:50`

두 질의 모두 `public.graph_grant`에 `grant`라는 별칭을 붙였다. `GRANT`는 SQL 예약어라 PostgreSQL이 별칭 자리에서 받지 않는다. 실행 결과는 다음과 같았다.

```
EffectiveGrade  err=유효 등급 조회: ERROR: syntax error at or near "grant" (SQLSTATE 42601)
OwnedGraphCount err=소유 그래프 수 조회: ERROR: syntax error at or near "grant" (SQLSTATE 42601)
```

`perm.Require`가 유효 등급을 얻는 유일한 경로이므로, 어떤 입력에도 권한 검사가 통과하지 못한다. 3단계가 구현한 권한 모델 전체가 실행 시 무효였다. 계정당 그래프 수 누적 한도도 같은 이유로 판정할 수 없었다.

**처리 결과.** 두 질의의 별칭을 `team_grant`로 바꿨다. 팀 상속 갈래에만 붙는 별칭이라 이름이 역할을 그대로 나타낸다.

**영향.** 「연산별 권한 검사」의 유효 등급 계산과 「계정 플랜 값」의 계정당 그래프 수 판정이 실행 가능해졌다.

### - [x] 2. `ConsumeAuthorizationCode`가 정상 첫 교환에서 실패하고 코드를 태운다

`internal/store/auth.go:113`

`RETURNING` 목록에 `issued_token_id`가 있는데, 이 열은 첫 소비 시점에 `NULL`이고 받는 쪽은 `string`이었다.

```
Consume(첫 소비) err=인가 코드 소비: can't scan into dest[9] (col: issued_token_id): cannot scan NULL into *string
```

`SET consumed_at`은 스캔 전에 이미 커밋되므로 코드는 소모된 상태로 남고 재시도도 통하지 않는다. 「인가 코드 흐름」이 정한 교환 단계가 실행 시 한 번도 성공할 수 없었고, 따라서 MCP 접근 토큰을 발급할 방법이 없었다.

값이 채워지는 재사용 경로는 `auth.go:112`에서 이미 `*string`으로 받고 있어 정상 동작했다. 정상 흐름만 실패하고 예외 흐름은 통과하는 형태였다.

**처리 결과.** `issued_token_id`를 `*string`으로 받고 `nil`이 아닐 때만 옮긴다. 재사용 경로와 받는 방식이 같아졌다. 같은 자리에서 `issued_at`과 `expires_at`을 UTC로 맞췄다. 같은 파일의 다른 조회가 이미 그렇게 하고 있어 시각 표현이 함수마다 달랐다.

**영향.** 인가 코드 교환이 성립하므로 3단계 완료 기준의 인가 코드 항목을 실행으로 확인할 수 있게 됐다.

### - [x] 3. 등급이 없는 조합이 부재가 아니라 오류가 된다

`internal/store/permission.go:15`

1번과 같은 파일이지만 별개의 결함이다. 별칭을 고쳐 질의를 실행 가능하게 만든 뒤에도 남았다.

집계 `MAX`는 후보 행이 없어도 `NULL` 한 행을 돌려준다. 등급을 `string`으로 받고 있어 이 경우 스캔이 실패했다.

```
NULL 스캔 결과: grade="" err=can't scan into dest[0] (col: case): cannot scan NULL into *string
```

`if grade == ""`으로 부재를 판정하는 분기는 도달할 수 없었다. `SDD.md` 「연산별 권한 검사」가 "유효 등급이 없으면 `not_found`, 모자라면 `permission_denied`"로 확정했는데, 등급이 없는 계정이 `not_found`가 아니라 내부 오류를 받는다. 권한 없는 계정에게 그래프 존재를 감추는 규칙이 오류 응답으로 무너지는 자리이기도 하다.

**처리 결과.** 등급을 `*string`으로 받고 `nil`을 부재로 판정한다. 반환 계약(`grade`, `found`, `err`)은 그대로다.

**영향.** `perm.Require`가 `found == false`에서 "그래프를 찾을 수 없다"로 가는 경로가 실제로 동작한다.

### - [x] 5. `EffectiveGrade`가 그래프의 `deleted_at`을 보지 않는다

`internal/store/permission.go:15`

삭제된 팀은 `team.deleted_at IS NULL`로 거르면서 소프트 삭제된 그래프는 그대로 등급을 돌려준다. 같은 커밋의 `OwnedGraphCount`는 `graph.deleted_at IS NULL`을 확인하므로 한 커밋 안에서 두 질의의 판정 기준이 다르다.

**처리 결과.** 명세를 다시 대조해 그래프 자체는 유효 등급 계산에서 거르지 않는 것으로 확정했다. 소유자의 웹 직접 삭제 그래프는 같은 소유자가 복구해야 하므로 등급이 남아 있어야 한다. 반면 자동 삭제 그래프는 접근 가능한 계정이 0이 된 뒤에만 생기므로 유효 등급도 남지 않는다. 삭제 상태에 따른 화면과 연산의 가용성은 유효 등급 계산과 별도로 각 조회·처리 경로가 판정하며, `ListGraphs`는 이미 `deleted_at IS NULL`로 일반 목록 노출을 막는다.

`OwnedGraphCount`가 반대로 `graph.deleted_at IS NULL`을 확인하는 것도 명세대로다. 「계정 플랜 값」이 이 한도의 현재 값을 "소유자 등급을 가진 활성 그래프의 수"로 확정했다. 등급은 복구 자격이라 삭제와 무관하고 그래프 수는 한도라 활성만 세므로, 두 질의의 판정 기준이 다른 것이 맞다.

**검증.** `TestPermissionIntegration`에 소유자가 직접 부여된 소프트 삭제 그래프가 여전히 `owner` 유효 등급을 얻고 일반 그래프 목록에는 나타나지 않는 경우를 추가했다. 이 검사는 복구 화면의 권한 전제와 일반 목록의 비노출을 실제 데이터베이스에서 함께 고정한다. 같은 그래프가 뒤의 소유 그래프 수 단언에도 걸리므로 `OwnedGraphCount`의 활성 필터까지 한 테스트가 잠근다. 두 질의의 선택을 각각 되돌려 `유효 등급 = ""(found=false), want "owner"`와 `소유 그래프 수 = 2, want 1`로 깨지는 것을 확인했다.

**남은 것.** 삭제 상태에 따른 연산 가용성을 실제로 판정하는 경로는 아직 없다. `Graph()`도 소프트 삭제된 그래프를 그대로 반환한다. 개발 계획 4단계에 "소프트 삭제된 그래프와 컨텍스트의 연산 가용성을 각 조회·처리 경로에서 판정한다" 항목을 더해 이관한 판정의 수신처를 남겼다.

### - [x] 6. 비밀번호 길이 정책이 구현되지 않았다

`internal/authz/authz.go:92`

`SRS.md` 「입력 검증 세부」가 8자 이상 128자 이하로 확정했는데 `password == ""`만 확인한다. 실행 결과는 다음과 같았다.

```
100자 한글 비밀번호 등록 err=비밀번호 해시 생성: bcrypt: password length exceeds 72 bytes
7자 비밀번호 등록 err=<nil>
```

짧은 비밀번호가 통과하고, 명세가 허용하는 길이의 한글 비밀번호는 등록 자체가 실패한다. bcrypt의 72바이트 한계 때문이며 `SDD.md` 「라이브러리 선택」이 bcrypt를 확정했으므로 길이 검증만으로는 끝나지 않는다.

**처리 결과.** 길이를 유니코드 문자 수로 세어 8자 이상 128자 이하만 등록하게 했다. 새 해시는 비밀번호의 SHA-256 결과 32바이트를 bcrypt 입력으로 사용하므로 128자 한글도 bcrypt의 72바이트 제한을 넘지 않는다. 저장값의 `bcrypt-sha256-v1:` 접두사로 새 형식을 구분하고, 접두사가 없는 기존 직접 bcrypt 해시는 로그인에서 대조한 뒤 읽은 계정 식별자와 기존 해시가 모두 일치하는 조건부 갱신으로 새 형식으로 재해시한다. 동시에 성공한 로그인에서 먼저 갱신된 경우 뒤 요청은 해시를 덮어쓰지 않고 로그인만 완료하므로 호환 분기는 레거시 행이 로그인할 때마다 줄어든다.

**검증.** `TestRegisterValidatesPasswordLengthAndAuthenticatesLongUnicodePassword`가 7자와 129자를 거부하고 8자 및 128자 한글 비밀번호의 등록·인증을 확인한다. `TestAuthenticateRehashesLegacyDirectBcryptHash`는 기존 직접 bcrypt 해시의 로그인 성공 뒤 새 형식 저장과 그 해시 대조를 고정한다. `TestUpdatePasswordHashIfMatchesIntegration`은 실제 데이터베이스에서 이전 해시와 일치할 때만 갱신되는 조건을 확인한다.

### - [x] 7. `Verify`가 `kid`를 무시한다

`internal/authz/authz.go:230`

`SDD.md` 「토큰 검증」이 `kid` 기반 키 선택을 확정했는데, 구현은 저장된 모든 키를 순회하며 검증이 성공할 때까지 반복한다. 발급은 `authz.go:334`에서 `kid` 헤더를 넣고 있어 값은 있다.

결과는 같지만 회전이 쌓일수록 요청당 ECDSA 검증 횟수가 키 수만큼 늘고, 실패한 검증과 "그 키가 아님"을 구분하지 못한다.

**처리 결과.** `Verify`는 서명 헤더의 `kid`가 하나인지 확인한 뒤 그 `key_id`의 공개 키 하나만 저장소에서 읽어 검증한다. 없는 `kid`, 비어 있거나 여러 개인 서명 헤더, 공개 키 해석 실패와 서명 실패는 모두 기존 계약대로 `unauthenticated`로 처리한다. 따라서 다른 등록 키의 서명이 맞더라도 헤더가 가리킨 키가 없으면 통과하지 않는다.

**남은 것.** `Renew`는 아직 `authz.go:272`에서 전체 키를 읽어 순회한다. 이 지적의 원인이 `kid`를 쓰지 않는 것이었으므로 같은 패턴이 한 곳 남은 셈이다. `Renew`는 `Verify`를 지난 토큰을 받는 전제라 실질 영향이 작고, 8번이 같은 함수를 고치므로 그때 `kid` 조회로 함께 바꾼다.

**검증.** `TestVerifyRejectsTokenWithUnknownKeyID`는 실제 등록 키로 서명했지만 `kid`만 다른 토큰을 거절하는지 확인한다. `TestSigningKeyIntegration`은 실제 데이터베이스에서 `key_id` 하나만 조회하고 없는 키를 `ErrNotFound`로 구분하는지 확인한다.

### - [ ] 8. `Renew`가 만료 여부를 확인하지 않는다

`internal/authz/authz.go:263`

「토큰 갱신」의 표는 "남은 수명이 10초 이하이고 미만료"인데, 조건이 `time.Until(token.ExpiresAt) > 10*time.Second`뿐이라 이미 만료된 토큰도 통과한다. `auth_time`이 12시간 안이면 만료된 토큰으로 새 토큰을 받는다.

현재 호출부가 없어 실제 영향은 없지만, `Verify`를 지난 토큰만 들어온다는 전제가 함수 안에 적혀 있지 않다. 서명 검증 성공 여부도 별도 표시 없이 `claims.AuthenticatedAt != 0`으로 판정한다.

이 항목을 처리할 때 7번이 남긴 키 순회도 함께 다룬다. `Renew`가 `authz.go:272`에서 전체 키를 읽어 순회하는 부분을 `Verify`와 같은 `kid` 단건 조회로 바꾼다.

### - [ ] 9. 플랜 값의 배포 구성 경로가 없다

`internal/plan/plan.go:28`

`SDD.md` 「계정 플랜 값」이 "배포 구성이 값을 주면 덮어쓰고 주지 않으면 기본값을 쓴다"로 확정했는데 `Default()`만 있다. `internal/config`에 플랜 항목이 없고 계정별 플랜을 읽는 경로도 없다.

## 개발 계획 체크박스

3단계 작업 항목 중 다음 세 개는 실행하면 실패하는 상태로 완료 표시가 되어 있었다.

| 항목 | 검사 시점 상태 |
|------|----------------|
| `perm` 패키지에서 직접 등급과 팀 상속 등급을 한 질의로 계산한다 | 1번, 3번으로 실행 불가 |
| 삭제된 팀의 등급을 유효 등급 계산에서 제외한다 | 조건은 맞으나 1번으로 질의가 실행되지 않음 |
| 인가 코드를 조건부 갱신으로 한 번만 소비한다 | 2번으로 첫 소비가 실패 |

1번부터 3번의 수정과 4번의 통합 테스트로 위 세 항목은 실 데이터베이스에서 성립한다.

완료 기준의 "같은 인가 코드의 동시 교환 중 하나만 성공한다"는 여전히 메모리 대역 위에서만 확인된 것이다. 2번을 고쳐 첫 소비가 성공하므로 판정 자체는 가능해졌지만, 실 데이터베이스에서 동시 교환을 돌린 테스트는 아직 없다. 2단계가 동시 수정을 20회 반복으로 확인한 것과 같은 형태가 필요하며, 4번의 "남은 것"에 적은 인가 서버 통합 테스트와 같은 자리에서 다루는 편이 낫다.

7번부터 11번은 처리 방향을 정하기 전이므로 해당 항목의 체크박스는 그대로 둔다.

## 종합

3단계의 설계 판단 자체는 명세를 잘 따랐다. 인가 코드를 해시로만 두는 것, 조건부 `UPDATE` 한 문장으로 단일 소비를 만드는 것, 재사용을 만나면 로그아웃과 같은 폐기 경로를 쓰는 것, `aud`로 두 채널을 나누는 것이 모두 `SDD.md`가 적어 둔 근거대로 구현되어 있다.

문제는 그 구현이 실행된 적이 없다는 데 있었다. 발견 사항 1번부터 3번은 코드를 읽어서는 눈에 띄지 않고 한 번만 실행하면 즉시 드러나는 종류이며, 메모리 대역이 그 실행을 대신하면서 초록으로 남았다. 4번의 통합 테스트가 이번 세 건과 같은 부류의 결함을 앞으로 잡는다.

6번과 9번은 명세가 확정한 값이 구현에 없는 항목이라 4단계 전에 처리하는 편이 낫다.
