# #271 운영 compose 기본 up의 자동 마이그레이션 차단

## 결정과 변경

운영 `compose.prod.yaml`은 `server`가 `migrate`에 `service_completed_successfully`로 의존하고, 헤더가 `up -d --build`를 실행 방법으로 안내했다. 새 이미지로 같은 명령을 실행하면 Compose가 의존 순서대로 `migrate up`을 먼저 끝낸 뒤 서버를 재생성하므로, 실행 중인 이전 서버·작업자 옆에서 백업·감사 없이 새 판의 SQL이 적용될 수 있었다.

- `migrate` 서비스를 `migrate` profile로 분리해 기본 `up` 대상에서 뺐다. 이름을 지정한 `run --rm --no-deps migrate migrate up`·`build db migrate server`는 profile을 켜지 않아도 동작한다.
- `server`의 의존을 `db` 준비 확인으로 바꿨다. 스키마 적용 여부는 기동 순서가 아니라 운영 절차의 정지 → 백업 → `migrate up` → `audit` 성공 뒤 기동으로 보장한다.
- compose 헤더·주석, [운영 설계](../sdd/operations.md#개발운영-환경-경계)의 서비스·기동 순서, `OPERATIONS.md`의 서버 기동 설명·로그 명령·복귀 설명을 같은 절차로 맞췄다. 최초 배포·변경 절차의 명령 자체는 이미 명시적 실행이었으므로 바꾸지 않았다.
- `test-prod-compose.sh`는 기본 구성의 서비스가 `db`·`server`뿐인지, `migrate`만 profile을 갖는지, `server`가 `db`에만 의존하는지 검사한다. `test-prod-runtime.sh`는 DB 준비 → 명시적 적용 → 서버 기동 순서로 실행하고 기본 `up`이 `migrate` 컨테이너를 만들지 않았는지 확인한다.
- 개발 compose의 `server` profile 자동 적용은 이 이슈 범위 밖이라 유지했다. 요구사항·추적표·DOX의 소유권과 구성은 바뀌지 않아 유지했다.

`OPERATIONS.md`의 Tunnel 전환 명령(`up -d --build --force-recreate --wait server`)은 이제 스키마를 적용하지 않지만, `--no-deps` 없이 DB 서비스도 함께 재생성 대상에 넣는 기존 동작은 그대로다. 이 이슈의 범위가 아니어서 바꾸지 않았다.

## 검증

- 변경 전 `compose.prod.yaml`에 새 정적 검사를 적용하면 "기본 up 대상에 migrate가 포함됩니다"로 실패했다.
- 변경 후 `test-prod-compose.sh` 통과. Compose v5.6.0의 dry-run에서 profile을 켜지 않은 `build migrate`가 이미지를 만드는 것을 확인했다.
- `test-prod-runtime.sh` 통과: 격리 프로젝트에서 명시적 `run --rm --no-deps migrate migrate up`이 001~014를 적용했고, 기본 `up` 뒤 `migrate` 컨테이너가 없었다. 기존 UID·권한·슬롯 중복 거부·재생성·자원 정리 인수도 통과했고 잔여 자원이 없음을 확인했다.
- 수정 셸 스크립트의 `sh -n`, 변경 Markdown의 링크·앵커, `git diff --check` 확인. 실제 운영 호스트 배포·Tunnel 인수는 미실행이다.
