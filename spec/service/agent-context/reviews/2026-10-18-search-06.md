## 구현과 발견 사항

- 기존 `enterHopReadScope`는 독립 홉에 읽기 전용 REPEATABLE READ 트랜잭션 하나를 열고 검색 홉에서는 기존 스냅숏을 가져온다. 읽기 연결을 반환한 뒤 접근 기록을 실행하므로 독립 홉에 별도 예약을 추가하지 않는다. 이 구조를 유지했다.
- `HopContextsFrom`의 호출 전 취소는 `ctx.Err()`만 반환해 사용자 지정 취소 원인을 잃었다. 두 공개 홉 진입점의 반환 경계에서 `ctx.Err()`와 `context.Cause`를 원래 오류와 함께 보존하고 결과를 비운다. 단일 진입점도 DB 접근 전에 취소를 검사한다. 30초 예산은 읽기 자리 대기·질의·조립·정리까지 같은 마감으로 유지하며 호출자의 더 짧은 마감이 우선한다.
- 기존 동시 폐기·예산 관찰 시험은 참조 질의의 예전 `RETURN source.context_id, target.context_id` 문자열에 의존했다. 현재 조회는 저장 끝점을 검증하는 투영을 사용하므로 동기화 지점이 관찰되지 않았다. 참조 MATCH와 source/target 정렬 조건으로 실제 참조 질의를 식별하도록 두 시험 파일을 고쳤다. 조회 구현의 스냅숏 실패로 해석하지 않았다.

## 새 모듈 검증

- 새 `hop_read_contract_test.go`는 두 진입점의 호출 전 취소/이미 지난 마감에서 사용자 지정 원인·표준 취소/마감 오류와 빈 결과를 대조한다. DB 연결을 준비하지 않은 저장소로 실행하여 DB 접근 전에 중단됨을 확인했다.
- 실제 최소 풀에서 독립/스냅숏·두 진입점의 그래프 질의, 읽기 롤백과 접근 기록 단계에 실패를 주입했다. 그래프/접근 기록에서는 요청을 사용자 지정 원인으로 취소하고, 롤백에서는 요청은 유효하게 유지한 채 드라이버에 전달하는 정리 컨텍스트만 취소했다. 정상 절단이나 이미 조립한 결과를 반환하지 않으며 읽기 종료의 취소 독립적인 5초 정리 예산을 관찰했다.
- 오류 뒤 획득 연결 수와 스냅숏 읽기 자리·활성 트랜잭션을 직접 대조했다. 조정 연결만 남는 기준값으로 회복하고 스냅숏 종료 뒤 연결·예약을 모두 반환한 다음 새 홉도 성공했다. 후속 조회 성공만으로 반환을 판정하지 않았다.
- 풀 연결 네 개 또는 스냅숏 읽기 자리 세 개를 모두 점유한 상태에서 두 진입점을 실행했다. 100ms 호출자 마감과 원인을 보존하며 빈 결과를 반환하고 기존 점유 연결을 바꾸지 않는다. 점유 해제와 스냅숏 종료 후 풀·자리·예약이 회복된다.
- 독립 읽기 경계의 실제 설정이 `repeatable read`·`read_only=on`이고 연결 하나만 점유하며 별도 예약 네 개를 소비하지 않음을 확인했다.
- 관련 모듈 회귀는 독립/스냅숏·두 진입점·limit 0/2에서 후보/본문 또는 확장/참조 사이에 별도 폐기 커밋을 완료했다. 이전 커밋의 노드·본문·참조·간선·거리·순서·절단을 유지하고 새 조회에서는 폐기 이웃을 제외한다. 시작 부재/폐기의 `not_found`, 기존 검색 스냅숏의 시작 상태와 풀 상한 네 개보다 많은 12개 동시 독립 홉의 완료도 대조했다.
- 잠금 대기에서 호출자의 취소·짧은 마감과 실제 내부 30초 소진을 확인했다. 독립 single은 약 30.001초, 스냅숏 from은 약 30.002초에 마감 오류와 빈 결과를 반환했다. 조정 연결을 제외한 획득 연결·읽기 자리 회복을 직접 확인했다. 16개 공통 마감 조합에서 시작·그래프·참조·접근 기록의 실제 질의 마감이 같고 3초 호출자 마감이 우선함을 확인했다. DB 취소·정리 전체의 정확한 벽시계 상한을 보장한다는 뜻은 아니다.
