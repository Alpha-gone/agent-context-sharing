# OPS-06 자동 삭제 그래프 요청·운영자 복구 모듈 인수

- 기준: 2026-10-23, `feat/web-foundation`의 `6b22aef` 이후 작업 트리.
- 대상: [OPS-06](../development-plan/operations.md#ops-06), [복구 설계](../sdd/operations.md#복구), [SRS 복구 요청](../SRS.md#복구-요청), [검증 계층](../sdd/testing.md#테스트-계층).
- 판정: 구현·모듈 인수 완료. 전체 **83/124개 완료·41개 미착수**. 다음 권장은 OPS-07이다.

## 변경과 책임

선행 작업이 준비한 복구 요청·대기 조회·운영자 복구 API와 실제 웹 세션 연결을 사용한다. 과거 인수 결과를 승계하지 않고 이번 실행에서 전체 복구 계약을 다시 대조했다.

- RequestGraphRestore와 OperatorRestoreGraph의 요청 context에 의존하던 무시된 롤백을 취소와 독립된 유한 정리로 교체했다. 기존 rollbackTransaction의 5초 예산을 재사용한다. 원래 오류·호출자 취소와 그 원인·롤백 오류를 errors.Is로 함께 관찰할 수 있다. 트랜잭션을 시작하기 전 취소된 요청도 호출자의 원인을 보존한다. 이미 커밋되어 닫힌 트랜잭션의 정상 정리는 추가 실패로 바꾸지 않는다.
- 초기 생성자와 과거 직접/팀 상속 소유자의 요청 자격, 그래프 잠금 뒤 자동 삭제와 가장 오래된 미처리 요청을 다시 읽는 경계를 유지했다. 같은 시각에는 감사 ID로 순서를 고정하며 목록·복구·보존 정리가 같은 완료 판정을 사용한다.
- 선택한 요청자의 직접 owner upsert와 삭제·유예 해제, 처리자·요청자·이전/이후 등급의 감사를 한 커밋으로 처리한다. 기존 다른 계정/팀 상태를 유지하고 요청자가 아닌 운영자에게 등급을 부여하지 않는다. 운영자와 요청자가 같으면 요청자로서 owner를 회복한다.
- 별도 상태 테이블·요청자 지정 인자·운영자 역할을 추가하지 않았다. 검증 단계의 운영자 자격은 기존 SRS를 따르며 TBD-052를 새로 확정하지 않았다. DB 스키마·배포 키·외부 의존성은 변경하지 않았다.

## 실행과 증거

Go 1.27.1·macOS arm64에서 TEST_DATABASE_URL·TEST_DATABASE_REQUIRED=1을 사용했다. 신규 저장소 인수는 전용 DB·정식 마이그레이션·상한 4개의 두 Store를 사용했다. 주입한 제약은 시험 소유 DB·그래프에만 적용했고, 연결과 DB는 시험 종료 시 정리했다. HTTP 인수도 전용 DB와 실제 조립·웹 세션·loopback TLS를 사용했다.

| 범위 | 실행 | 결과 |
|---|---|---|
| 복구·감사 보존 관련 모듈 | `go test -race -json -p=1 -count=1 -timeout=180s -run '^(TestOPS06\|TestOperatorRestore\|TestRestoreChannel\|TestCleanupRetainsDiscard\|TestOBS06)' ./internal/store ./cmd/server` | 저장소 **52건**, 서버 **1건**, 총 **53건 통과** |
| 공통 정적 검사 | `GO_BINARY=/Users/alphagone/sdk/go1.27.1/bin/go GOCACHE=/private/tmp/acs-obs02-go-cache sh ./check-go.sh` | 의존성 검증/빌드·전체 build·vet·gofmt 통과 |
| Linux 대상 빌드 | `GOOS=linux GOARCH=amd64 go build ./...` | 통과. Linux runtime은 미실행 |

53건은 상위 시험·하위 사례의 pass 이벤트 합계이며 신규 OPS-06 사례는 저장소 16건·서버 1건이다. 최종 실패·건너뜀·race 오류는 0이며 원시 결과는 `/private/tmp/acs-ops06-final.json`에 남겼다. 첫 실행의 저장소 50건과 서버 실패는 최종 합계에 다시 더하지 않는다.

1. 실제 소유자 부여·회수와 팀 접근 소멸·유예 만료로 자동 삭제 표본을 만들었다. 생성자·과거 소유자는 목록/요청을 사용할 수 있고 viewer 이력이나 운영자 자격만 가진 계정의 요청은 상태 변경 없이 거부됐다. 기존 상속 근거·직접 삭제·무요청 거부와 복구 전/후 등급·유예 해제·감사 회귀도 새로 실행했다.
2. 서로 다른 두 계정의 요청 시각과 감사 ID 순서를 의도적으로 반대로 배치했다. 오래된 시각 우선과 시각 동률의 감사 ID 우선이 목록·복구에서 일치했다. 보존 정리 뒤에도 대기 요청·소유 근거가 유지됐다. 한 요청을 처리한 뒤 그래프를 다시 삭제한 표본에서 두 번의 보존 정리를 실행해 완료 요청이 다시 대기로 나오거나 재처리되지 않음을 확인했다.
3. 실제 CHECK 제약으로 요청 감사·직접 등급·처리 감사 저장을 각각 실패시켰다. 원래 PostgreSQL 오류 23514를 보존하고 그래프·기록·직접 등급이 남지 않았으며 연결/예약이 반환됐다. 제약 제거 뒤 동일 API의 재시도가 성공했다.
4. 별도 트랜잭션이 그래프 행을 잠그고 요청·복구가 실제로 기다리는 것을 관찰했다. 자동 삭제를 직접 삭제 상태로 바꿔 커밋하자 후행 API가 새 상태를 보고 거부했다. 대기 중 취소에서는 context.Canceled와 호출자의 원인을 함께 보존했고 peer의 획득 연결 0개와 전체 예약 반환을 대조했다. 시작 전 취소된 요청·처리 API도 상태를 바꾸지 않고 호출자 원인을 보존하며 연결/예약을 반환했다.
5. 실제 저장점에서 등급·그래프 변경 뒤 감사 쓰기를 실패시키면서 요청을 취소하고 롤백 보고 오류도 주입했다. 독립 context와 양수 5초 이내 마감으로 실제 저장점을 롤백했으며 감사·취소·호출자 원인·롤백 오류가 모두 남았다. 부모 트랜잭션에서도 그래프 삭제와 직접 등급 부재를 확인했다.
6. 두 Store에서 여덟 복구를 동시에 실행해 성공과 처리 감사가 각각 한 번임을 확인했다. 나머지는 미처리 요청 부재로 거부됐고 두 풀의 획득 연결과 예약이 회복됐다.
7. 실제 세션·TLS에서 무인증·교차 출처·요청 없는 처리·타 계정의 요청·중복 처리를 거부했다. 양식의 requester_account_id로 인증된 요청자를 바꿀 수 없었고, 운영자 처리 후에도 요청자만 owner를 얻었다. 운영자 그래프 상세는 처리 전/후 404였으며 모든 시험 응답에 비공개 본문 표식이 없었다. 코드 검토에서도 운영자 경로는 그래프 메타데이터·요청/처리 감사·등급만 조회하며 컨텍스트 조회를 호출하지 않는다.

첫 HTTP 표본은 무등급 그래프 접근을 403으로 기대하여 실패했다. 기존 perm.NotFoundError의 존재 비노출 계약은 404이므로 시험 기대값을 수정했다. 두 인스턴스 경합 사례를 보강한 뒤 관련 모듈 전체를 위 53건으로 다시 통과했으며 HTTP 권한 계약은 변경하지 않았다.

## 제한과 정합성

- 이번 판정은 복구 요청·대기 계산·원자적 처리·보존·HTTP 주체 경계의 모듈 인수다. 전체 저장소/서버 시험·실제 브라우저·Linux runtime·외부 호스트/제공자·전체 운영 장애·배포는 실행하지 않았다.
- DOX pass에서 구현이 기존 store·서버 조립과 운영·시험 정본 안에 있음을 확인했다. 소유권·지속 경계·환경 키가 바뀌지 않아 추가 DOX·부모 색인 갱신은 필요하지 않다. SRS 요구사항과 기존 권한·감사·수명주기 정본을 유지하고 운영 정리·시험 계약과 계획·상태·근거·요청 기록을 정합화했다.
- 기존 Compose·IDE 변경을 보존했으며 이번 변경은 미커밋이다. upstream이 없어 원격 비교를 수행하지 않았고 push·배포는 하지 않았다.
