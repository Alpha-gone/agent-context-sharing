## 문서 정보

- 문서 상태: 진행 중
- 작성일: 2026-09-29
- 서비스 식별자: `AGENT_CONTEXT_CLIENT`
- 요구사항 기준: [SRS](./SRS.md)
- 상세 설계 기준: [SDD](./SDD.md)
- 개발 기준 진입점: [CANONICAL](./CANONICAL.md)
- 담당 범위: 확정된 클라이언트 계약을 구현·검증·배포 가능한 작업 순서로 분해한다.

## 목적과 현재 상태

이 계획은 SRS의 기능 요구사항 35건과 비기능 요구사항 16건을 SDD의 패키지 경계와 테스트 전략에 따라 구현하는 순서를 정한다. 동작과 설계의 정본은 SRS와 SDD이며, 이 문서는 진행 상태와 단계별 완료 기준만 소유한다. 일정과 담당자는 확정된 입력이 없어 기재하지 않는다.

0단계에서 계약 스냅샷과 SDK 의존성을 마련했고, 1단계에서 실행 파일과 구성·호스트 `stdio` 기반을 구현했다. 2단계에서는 도구 계약·공개 정책·입력 검증과 발견·목록 캐시를 구현했으며, 호스트 오류 전달과 실제 정책 적용이 남아 진행 중이다. 3단계의 `authorize`와 4단계의 `remote.NewHTTP`를 연결해 보호 요청·재인가·갱신·주체 확인·재시도·자원 상한을 구현했다. 전송 대역과 실제 로컬 TLS 시험 서버·루프백 callback에서 검증했으며 4단계는 완료다. 실제 서비스 수신 측 proof 거부와 진단 비노출이 남아 3단계는 진행 중이다. `serve`는 기동 때 프로세스 키를 만들고 종료 때 폐기하지만 아직 도구 중계에는 연결하지 않는다. 클라이언트는 독립 `client/` 모듈에 있다. `stdio` 도구 중계와 전체 `doctor`, 실제 서비스 서버·지원 호스트·시스템 브라우저·WSL2 검증은 5·6단계 범위다. 서버의 쓰기 멱등성 확장과 DPoP 구현은 [서버 개발 계획](../agent-context/DEVELOPMENT_PLAN.md) 18·19단계에 기록되어 있으나 클라이언트 종단 간 검증은 남아 있다. 서버 체크박스를 클라이언트 검증 완료로 간주하지 않는다.

## 단계 현황

단계의 작업과 완료 기준을 모두 확인한 뒤 상태와 체크박스를 함께 갱신한다.

| 단계 | 목표 | 상태 | 선행 단계 |
|------|------|------|-----------|
| 0 | 구현 계약과 검증 기반 준비 | 완료 | 없음 |
| 1 | 실행 파일, 구성과 호스트 `stdio` 기반 | 완료 | 0 |
| 2 | 도구 계약, 공개 정책과 원격 발견 | 완료 | 1 |
| 3 | 브라우저 인가, 토큰과 DPoP | 진행 중 | 1 |
| 4 | 원격 전송, 재시도와 자원 상한 | 완료 | 2·3의 패키지 구현·검증 |
| 5 | 호스트 중계 완성, `doctor`와 운영 동작 | 완료 | 4 |
| 6 | 실제 서버·호스트 검증과 배포 판정 | 예정 | 5 |

2단계의 manifest·스키마 검증과 3단계의 인증은 서로 다른 패키지에서 병행할 수 있다. 4단계는 2·3단계의 패키지 구현·검증을 전제로 실제 보호 요청을 연결한다. 2단계의 호스트 완료 기준은 5단계의 `serve` 연결·오류 중계 뒤, 3단계의 재인가·주체 연결과 수신 측 proof 거부 기준은 4·6단계의 해당 검증 뒤 판정한다. 각 단계에서 해당 범위의 단위·계약 검증을 함께 작성하고, 충족하지 못한 완료 기준은 다음 단계로 미루더라도 완료로 표시하지 않는다.

## 공통 개발 규칙

- `client/cmd/client`와 `client/internal/client/`의 책임과 의존 방향은 SDD 「패키지 경계」를 따른다. 서버 루트 모듈의 업무 패키지에 클라이언트 상태를 넣거나 클라이언트에서 이를 import하지 않는다.
- 서버 도구 13종의 이름·입력·도메인 오류는 서버 SRS·SDD를 기준으로 맞춘다. 클라이언트가 원격 권한 또는 검색 결과의 의미를 재판정하지 않는다.
- 호스트 경계의 MCP 공식 적합성과 원격 경계의 MCP 메시지·도구 계약, 서비스 전용 DPoP 시험 결과를 각각 기록한다.
- 비밀, 인가 URL, 도구 인자와 결과 본문을 로그·오류·진단 결과에 남기지 않는다. `serve`의 stdout은 MCP 메시지 전용으로 유지한다.
- 구현이 확정된 요구사항과 달라져야 하면 SRS를, 요구사항은 같고 설계만 달라져야 하면 SDD를 먼저 갱신한다. 계획의 체크박스로 계약을 변경하지 않는다.
- 단계별 검증은 Go `1.27.1` 도구 체인을 사용한다. 코드 변경 시 루트 `AGENTS.md`의 빌드·vet·gofmt 조건과 SDD 「테스트 전략」을 적용한다.

### 0단계 결과와 검증 경계

- `client/internal/client/contract/tool_manifest.json`은 서버 `toolDefinitions()`의 이름·설명·`inputSchema` 전체를 고정한 스냅샷이다. 클라이언트 계약 패키지는 이를 포함하고, 서버의 `TestToolManifestMatchesClient`가 실제 공개 정의와 바이트 단위로 대조한다. 서버 계약을 의도적으로 바꿀 때만 변경 내용을 검토한 뒤 저장소 루트에서 `go test ./internal/mcp -run '^TestToolManifestMatchesClient$' -args -update-tool-manifest`로 재생성한다. 평상시 시험에는 갱신 옵션을 쓰지 않는다.
- `client/go.mod`와 `client/go.sum`은 공식 `github.com/modelcontextprotocol/go-sdk` `v1.8.0`을 고정하며 서버 루트 모듈의 의존성과 분리한다. `TestSDKSupportsHostProtocol`은 `2026-07-28`, `ServerOptions.SupportedProtocolVersions`, `StdioTransport.MaxLineLength`, 발견·도구 타입을 확인한다. 실제 호스트 lifecycle 연결과 `stdio` 입출력은 1단계에서 검증한다.
- 모의 시험에서는 `host`의 원격 경계를 `Discover`·`ListTools`·`CallTool` 대역으로, `authorize`의 브라우저 실행과 loopback callback을 각각 opener·callback driver 대역으로 교체한다. 인가·리소스 서버는 로컬 HTTP 시험 서버로 두고 시계, 난수와 HTTP transport를 주입한다. `remote`는 같은 HTTP transport 대역으로 전달·차단·재시도 오류를 만든다. 이 경계는 1~4단계에서 각 소유 패키지에 구현한다.
- `client/`에서 실행하는 `go test ./internal/client/...`는 모의·단위 시험 경로다. 실제 서버 시험은 `client_live` 빌드 태그의 `TestClientLive*`로 분리하고 저장소 루트에서 `GO_BIN=/path/to/go1.27.1 TEST_DATABASE_URL=... sh client/internal/client/test-live.sh`로 실행한다. 스크립트는 접속 정보나 실제 시험 함수가 없으면 종료 코드 2로 실패하며 양쪽 모듈 시험에 `TEST_DATABASE_REQUIRED=1`을 설정한다. 따라서 0단계에서는 실제 서버 시험을 통과했다고 보고하지 않는다.
- 6단계는 서버 계획 18단계의 미완료 클라이언트 키 재사용·종단 간 재시도와 19단계의 미완료 토큰 발급·보호 호출·요청별 proof·갱신 결합·Bearer 하향 거부를 함께 닫는다. 19단계의 교차 인스턴스 재생, 동시 갱신, 요구사항 추적과 DPoP 별도 보고도 실제 서버 결과에 연결한다. 서버 계획의 체크박스는 해당 검증 전에는 유지한다.

2026-09-29 검증: Go `1.27.1`에서 공유 스냅샷·클라이언트 계약·SDK 타입 시험을 통과했다. 실제 서버 시험은 클라이언트 런타임과 `TestClientLive*`가 아직 없어 미실행이다.

2026-09-30 모듈 분리 검증: 서버 루트 모듈과 클라이언트 `client/` 모듈에서 각각 `go build ./...`, `go vet ./...`, `go test -count=1 ./...`를 실행했다. 두 모듈의 빌드·정적 검사·단위 시험과 공유 스냅샷 검사는 통과했다. `client/`의 의존 패키지 목록에 서버 내부 패키지가 없음을 확인했다. `TEST_DATABASE_URL`이 없어 서버 DB 통합 시험은 건너뛰었고, 클라이언트 실제 서버 시험은 아직 없어 실행하지 않았다.

## 1단계: 실행 파일, 구성과 호스트 `stdio` 기반

### 목표

`agent-context-client serve`의 무상태 호스트 경계와 안전한 프로세스 수명주기를 만든다.

### 작업

- [x] `client/cmd/client`, `client/internal/client`, `config`, `host`를 SDD의 의존 방향으로 만든다.
- [x] `serve`·`doctor` 명령을 분리하고, 명령 오류·빌드 정보·환경 변수 검증을 브라우저·네트워크 접근 전에 처리한다.
- [x] 호스트 `server/discover`와 요청별 MCP `2026-07-28` 메타데이터를 처리하고 구형 handshake에 의존하지 않는다.
- [x] 단일 stdin reader와 단일 stdout writer로 줄 단위 메시지, 256 KiB 입력 한도, 동시 요청 ID 상관과 부분 출력 방지를 구현한다.
- [x] EOF에서는 새 요청 수락을 멈추고 접수한 요청의 응답 기록 뒤 종료하며, `SIGINT`·`SIGTERM`에서는 호출 취소와 자원 정리를 처리한다.
- [x] `slog` 구조화 로그를 stderr에 두고 금지 필드와 본문을 출력하지 않는다.

### 주요 요구사항

`FR-AGENT_CONTEXT_CLIENT-001`, `-002`, `-016`, `-018`, `-023`, `-024`, `-026`; `NFR-AGENT_CONTEXT_CLIENT-001`, `-004`, `-006`, `-008`, `-010`, `-011`, `-013`.

### 완료 기준

- [x] 구성 오류가 외부 접근 전에 거부되고 `serve` stdout에는 완전한 MCP 메시지만 기록된다.
- [x] 동시 요청·취소·요청 직후 EOF·종료 신호 시험에서 응답 누락, 식별자 혼선과 남은 listener·요청이 없다.
- [x] 입력 상한과 1바이트 초과를 구분하고 다음 메시지 프레이밍을 복구한다.

### 1단계 결과와 검증 경계

- `serve`는 구성 검증 뒤 SDK의 `server/discover`만 실행하고 도구 요청은 원격 계약이 준비되지 않았다는 오류로 거부한다. 호스트 발견에는 고정된 `2026-07-28`, `tools` capability와 클라이언트 빌드 정보를 담는다. `initialize`·`initialized`는 받지 않는다.
- 구성 오류는 stderr의 `configuration_rejected` 사건과 `outcome`에 환경 변수 이름과 고정 조치 문구를 기록하며 입력값은 포함하지 않는다. 구조화 로그는 SDD의 해당 필드만 사용하고 `slog`의 기본 `msg` 필드는 제외한다.
- 호스트 전송은 프레임을 256 KiB까지 읽고 초과한 줄을 끝까지 버린 뒤 다음 줄을 처리한다. 초과 프레임의 식별자를 안전하게 회수할 수 있으면 같은 ID로, 아니면 `id=null`로 `client_busy`를 반환한다. stdout은 한 writer 고루틴에서 완성된 응답만 기록하며 32 MiB를 넘는 응답은 기록 전에 오류로 대체한다. 입력 EOF는 접수한 호출의 응답 기록이 끝난 뒤 SDK에 전달한다.
- 입력 상한 안의 빈 줄과 JSON 공백만 있는 줄은 응답 없이 건너뛴다. 잘못된 JSON의 오류 응답과 초과 입력의 크기 검사는 유지한다.
- 1단계 당시 `doctor`는 명령과 구성 검사만 분리했다. 구성 실패는 사람 읽기 출력의 `configuration: fail` 또는 JSON 외피의 전체 `status: fail`·`configuration` 검사 `status: fail`을 기록하고 종료 코드 1을 반환했다. 구성 성공은 전체 진단이 미구현이라 `skipped`·종료 코드 2를 사용했다. 전체 진단과 종료 코드는 5단계에서 완성했다.

2026-09-30 초기 검증: 클라이언트 모듈의 `go build ./...`, `go vet ./...`, `go test -race -count=1 ./...`를 통과했다. 구성 오류의 사전 거부, `server/discover`·요청별 메타데이터, 128개 동시 요청의 ID 상관, 입력 정확히 256 KiB와 1바이트 초과·후속 프레임 복구, stdout 출력 상한, 빈 입력 EOF·호스트 취소·SIGINT·SIGTERM을 시험했다. 이 검증은 요청 직후 EOF를 포함하지 않아 응답 누락 결함을 놓쳤다.

### 3단계 결과와 검증 경계

- `authorize.Manager`는 검증된 구성, HTTP transport·브라우저 opener·loopback listener·시계를 입력으로 받는다. 네트워크 없이 ES256 키를 한 번 만들고 `serve`가 수명 종료 때 `Close`를 호출한다. 개인 키·토큰은 비공개 필드에만 두고 기본 문자열 표현·자격 증명 JSON 직렬화에서 비밀을 숨기거나 거부한다. 실제 `doctor` 인가·진단 출력은 5단계에서 검증한다.
- 발견은 `WWW-Authenticate: DPoP`의 검증된 위치 또는 경로를 포함한 RFC well-known 위치를 사용한다. HTTPS·resource·단일 issuer·S256·ES256·scope·공개 클라이언트·응답 issuer 선언과 공개 JWKS를 검사한다. discovery만 최대 3회 HTTPS redirect를 허용하고 매번 비밀 없는 헤더로 재구성하며 토큰 POST는 redirect하지 않는다. 통신 실패는 비밀 없는 `ErrTransport`, 완전한 계약 위반은 `ErrProtocol`로 구분한다.
- 공유 인가는 최대 128명까지 대기하며 대기자 취소는 분리한다. 마지막 대기자 취소·전체 시간 초과·거부·opener 실패·종료에서 수신기와 실행을 정리한다. IPv4 실패 시 IPv6를 시도하며 잘못된 주소·경로·state·iss·중복 매개변수는 400, 소비 뒤 중복 callback은 수신기 수명 안에서 410으로 거부한다.
- 토큰 교환은 같은 코드·verifier·redirect·resource를 한 번 사용한다. 프로세스 공개 JWK, POST·정규화한 target·UTC iat·새 UUIDv7 jti를 proof에 담고 보호 요청에는 토큰의 ath를 더한다. JWT의 ES256 서명·iss·aud·exp·cnf.jkt를 검증하고 Bearer·다른 키·서명 변조를 거부한다. 갱신 헤더는 쌍·단일 값·JWT exp 일치를 확인한 뒤 교체하며 늦은 401은 요청별 자격 증명과 현재 값을 비교한다.
- 첫 검증 계정의 iss·sub 결합은 프로세스에 고정한다. 같은 계정의 토큰 갱신은 `Identity`를 바꾸지 않으며 재인가에서 다른 계정을 받으면 `ErrIdentityChanged`로 거부하고 저장하지 않는다. 올바른 계정으로 다시 인가하거나 새 프로세스를 시작해야 한다.
- 추가 검토 보완: callback과 opener 반환을 독립적으로 기다리고 정상 callback 뒤 opener를 취소·회수해 코드 교환을 진행한다. 검증한 보호 리소스의 resource 원문을 인가·교환·초기/갱신 JWT audience에 재사용한다. SRS의 갱신 정책을 만료 비역행·동일 만료 마지막 저장으로 변경하고 구현·SDD·시험을 함께 정합화했다. `Identity`는 인가를 시작하거나 기다리지 않으며, 자격 증명의 사용·저장에 5초 만료 여유를 적용한다. WSL에서는 실행 가능한 wslview를 찾지 못할 때만 PowerShell을 선택하고 URL을 명령문에 보간하지 않는다.
- `ParseChallenge`의 초기 도전·invalid_token·nonce/proof 오류·두 번째 401·500 분류를 `remote.NewHTTP`의 실제 HTTP 요청에 연결했다. 4단계에서 전송 대역과 실제 로컬 TLS 시험 서버에 인증 조정자를 조립해 최대 한 번 재인가·재전송, 갱신과 `Source.Identity`, 계정 변경 거부·정상 계정 복구를 검증했다. 수신 측의 다른 키·proof 재생 거부, 실제 서비스 서버·시스템 브라우저·WSL2와 진단 비노출은 각각 후속 통합 검증 전까지 완료로 표시하지 않는다.

2026-10-03 검증: Go `1.27.1`에서 클라이언트 `go test -race -count=1 ./...`, 양쪽 모듈의 `go build ./...`·`go vet ./...`, 서버 공유 manifest 시험과 Linux amd64 교차 빌드를 통과했다. 100개 동시 인가·거부 전파·대기 취소·128명 상한, 실제 IPv4·IPv6 루프백 callback, 잘못된 callback·중복 소비·거부·opener 실패·마지막 취소·전체 시간 초과·종료, metadata·인코딩 경로·redirect·통신 오류 분류·JWT·proof·갱신·늦은 401·계정 고정·만료 후 재인가를 확인했다. 공유 인가·정리·상한의 race 시험은 10회 반복했다. `gofmt`·diff·문서 상대 링크와 요구사항 추적성을 확인했다. 검토와 후속 경계는 [3단계 구현 검토](./reviews/2026-10-03-client-phase-3.md)에 기록한다. 실제 시스템 브라우저·인가 서버·MCP HTTP·호스트 종단 간 및 DPoP 수신 측 재생 방어 시험은 수행하지 않았다.

2026-10-03 추가 수정 검증: 클라이언트 전체 race 시험과 opener 미반환·종료 오류·취소·시간 초과·종료 회수, 100개 동시 갱신·동일 만료·오래된 응답 검증, 비정규 URL의 전체 인가·갱신, 비대화형 Identity와 5초 만료 경계, WSL 실행기 선택·URL 비보간·실행기 프로세스 취소의 주요 회귀 race 시험 10회 반복을 통과했다. 양쪽 모듈 build·vet, 서버 공유 manifest 시험과 Linux amd64 교차 빌드를 통과했다. 실제 MCP Source 연결과 WSL2·시스템 브라우저 통합을 대신하는 완료 표시는 하지 않는다.

## 4단계: 원격 전송, 재시도와 자원 상한

### 목표

호스트의 논리적 호출을 안전한 원격 HTTP 시도와 결과로 연결한다.

### 작업

- [x] `remote`에 단일 POST·JSON 응답, 고정 MCP 헤더, 요청별 `_meta`, 새 원격 JSON-RPC ID와 DPoP proof를 구현한다.
- [x] 인증 조정자의 도전 판정·갱신·요청별 자격 증명과 `Source.Identity`를 실제 HTTP 경계에 연결한다. 초기 DPoP 도전·invalid_token만 최대 한 번 재인가·재전송하고 proof/nonce 오류·두 번째 401·500은 반복하지 않으며 취소·계정 변경 응답을 폐기한다.
- [x] 원격 요청 256 KiB, 전송·압축 해제 응답 각 32 MiB, 호스트 출력 32 MiB를 부분 출력 없이 적용한다.
- [x] 진행 중 호출 8개, 취소 가능한 호출 대기 128개와 인가 대기 128개를 각각 제한한다.
- [x] 전송 전·도중·후 실패를 구분하고 읽기와 협상·비협상 쓰기에 SDD의 최대 3회 및 250ms·500ms·1초 상한을 적용한다.
- [x] 협상된 8종 쓰기에 논리적 호출별 UUIDv7 `Idempotency-Key`를 생성해 재시도·재인증 재전송에서 유지하고 반환·취소 시 폐기한다.
- [x] 호출 제한 시간과 취소를 대기·인가·재시도 지연·HTTP에 전파하고, 완전한 HTTP 응답과 도메인 오류는 자동 재시도하지 않는다.

### 주요 요구사항

`FR-AGENT_CONTEXT_CLIENT-015`, `-018`~`022`, `-032`; `NFR-AGENT_CONTEXT_CLIENT-006`~`008`, `-013`, `-014`.

### 완료 기준

- [x] 읽기·협상 쓰기·비협상 쓰기의 전송 실패 표에서 재시도와 `ErrIndeterminate`가 구분된다. 대응하는 호스트 `client_indeterminate` 직렬화는 5단계에서 별도로 검증한다.
- [x] 같은 논리적 쓰기의 키는 유지되고 HTTP 시도마다 DPoP `jti`와 원격 요청 ID가 새로 생성된다.
- [x] 경계값·1바이트 초과·고압축 응답·129번째 대기 요청이 해당 요청만 계약대로 처리한다.

### 4단계 결과와 검증 경계

- `remote.NewHTTP`는 구성·인증 조정자·HTTP transport와 기존 발견·목록 캐시를 조립한다. 생성 시 외부 요청을 하지 않으며 `Close`는 소유 호출과 복제 transport를 정리한다. `authorize.Apply`는 비대화형 토큰·새 proof 적용을 담당한다. 최초 도전과 재인가는 캐시 gate·호출 slot 밖에서 수행한다.
- 하나의 공개 호출에서 준비·발견·목록·도구 전송이 같은 호스트 context·원격 처리 잔여 시간·최대 3회 전송 재시도·최대 한 번 인가를 공유한다. 인가 대기는 인증 제한 시간으로 제한하고 원격 처리 예산에서 제외하며, 호스트의 명시적 deadline·취소는 두 단계 모두에 우선한다. 초기 도전용 익명 목록은 인가 뒤 재전송하지 않는다. 캐시 대기도 실행 8개·FIFO 대기 128개에 포함하고 재인가 때 slot을 반환한다. 공유 인가의 기존 128명 상한은 별도 유지한다.
- 매 HTTP 시도는 단일 POST, 고정 헤더·요청별 metadata, 새 UUIDv7 ID·DPoP proof를 사용한다. redirect와 표준 transport의 숨은 본문 replay를 막고, body reader·connection trace로 전달 가능성을 보수적으로 판정한다. 읽기·협상/비협상 쓰기의 재시도와 `ErrIndeterminate`를 구분한다.
- 검증된 발견의 24시간 확장을 협상한 쓰기 8종만 호출별 Structured Fields String UUIDv7 키를 전송한다. 같은 호출의 전송 재시도·재인가에서 키를 유지하고 읽기·비협상 쓰기에는 보내지 않는다. 불확실 쓰기가 보관 시간 밖으로 넘어가면 재전송하지 않는다.
- 요청 256 KiB와 전송·gzip 해제 본문 각각 32 MiB를 제한하고 완전한 JSON-RPC 외피·ID·HTTP 상태를 검사한다. 원격 protocol-level 오류는 `ProtocolError.Raw`로, 도구 결과는 원문으로 보존한다. 크기 초과·완전한 실패·도메인 오류는 반복하지 않으며 취소된 응답은 갱신에 사용하지 않는다.
- 기존 호스트 `stdio`의 32 MiB 출력 상한·부분 출력 방지 회귀 시험도 통과했다. 이 결과는 원격 전송과 호스트 writer 각각의 상한 검증이며, 실제 `serve` 도구 중계·일곱 오류 직렬화 완료를 뜻하지 않는다. `ErrBusy`·`ErrIndeterminate`·`ProtocolError` 등의 호스트 연결은 5단계에서 검증한다.

2026-10-03 검증: Go `1.27.1`에서 클라이언트 전체 `go test -race ./... -count=1`, 원격 패키지 전체 race 시험 10회 반복, 양쪽 모듈 build·vet, 공유 `TestToolManifestMatchesClient`와 Linux amd64 교차 빌드를 통과했다. 전송 전·일부/전체 전달·불명확한 실패, 잘린 응답·손상 gzip, 재인가 공통 예산·키·새 ID/proof, 모든 13종의 쓰기 키 적용 여부, 보관 시간 종료, 크기 경계·1바이트 초과, FIFO 129번째 대기·개별 취소를 확인했다. 실제 로컬 TLS 시험 서버에 인증 조정자를 연결해 PKCE·JWT·요청별 DPoP·갱신, 100개 동시 호출의 응답 상관과 8개 상한, 401 뒤 쓰기 응답 유실·같은 키 재전송, 계정 변경 거부·정상 계정 복구를 확인했다. 실제 서비스 서버·데이터베이스·수신 측 proof 재생 방어·시스템 브라우저·WSL2·호스트 종단 간 시험은 수행하지 않았다. 상세 결과는 [4단계 구현 검토](./reviews/2026-10-03-client-phase-4.md)에 기록한다.

2026-10-03 추가 검토 보완: 짧은 요청 제한 시간이 로그인·2FA 대기를 끊는 구성 위험을 재현하고 인가 대기와 원격 처리 시간 예산을 분리했다. SRS·SDD·구성 예제와 DOX를 정합화하고, 초기 도전용 목록의 인가 뒤 불필요한 재전송도 제거했다. `REQUEST_TIMEOUT=1s`·로그인 2초의 실제 로컬 TLS·인증 조정자 시험과 최초/목록/도구 재인가 시간 분리, 인증 제한 시간·호스트 deadline·취소·종료, 원격 잔여 시간·목록 재시도 예산·4개 요청 순서 회귀가 통과했다. 클라이언트 전체 race, 원격 패키지 race 10회 반복과 양쪽 모듈 build·vet·공유 manifest·Linux 교차 빌드도 통과했다. 실제 서비스·시스템 브라우저·호스트 검증의 후속 경계는 유지한다.

### 작업

- [x] `doctor`의 성공·검사 실패·미구현 또는 건너뛴 진단과 사용법 오류를 구분하도록 종료 코드를 정리한다. 각각 0·1·3·2를 사용한다.
- [x] 종료·재시작, 구조화 로그, 비밀·본문 비노출과 진단의 도메인 도구 미호출을 확인한다.

### 완료 기준

- [x] 도구 13종의 성공·도메인 오류·클라이언트 오류가 각 계약에 맞게 호스트로 전달된다.
- [x] `doctor`는 지정된 순서·출력 형식을 지키며 도구를 호출하거나 비밀을 출력하지 않는다.

### 5단계 결과와 검증 경계

- `serve`가 구성 정책·인증 조정자·원격 HTTP·`host.Tools`를 조립한다. 발견은 로컬 SDK가 처리하고 도구 어댑터는 원격 본문·오류의 필드 순서·숫자·문자열 표현을 유지한 채 호스트 ID를 사용한다. 줄 프레이밍 공백과 MCP 외피의 클라이언트 `serverInfo`·`complete` 유형만 적용한다. 나머지 원격 metadata는 보존한다.
- 실제 stdio에서 13종·세 정책·여섯 주입과 우회 거부, 도메인 오류 8종·로컬 오류 7종·인증 주체 변경·유효한 원격 오류를 검증했다. 평면 흐름·검색 metadata·큰 정수·커서·부분 상태와 출력 상한 뒤 프레임 복구도 확인했다.
- 목록 준비와 도구 전송이 같은 호출 예산을 공유하고 호스트 응답 기록 또는 생략까지 slot을 유지한다. 느린 stdout에서도 실행 8개·대기 128개와 호스트 접수 136개 상한을 지킨다. 요청 취소와 EOF는 원격 호출을 취소하되 명시적 취소 통지의 미기록 응답은 생략하고 EOF의 접수된 응답은 기록한다. 내부 생성 상관 ID만 로그에 쓰며 응답 직후 ID 재사용도 격리한다. 전달됐을 수 있는 쓰기의 취소는 내부적으로 `client_indeterminate`로 분류한다.
- `doctor`는 여덟 단계를 순차 검사하고 후속 실패 종속 단계를 건너뛴다. JSON·사람 읽기 출력·종료 코드와 구성 사전 거부, TLS 신뢰 거부·루프백 왕복·실제 토큰 교환·도구 미호출·비밀 비노출·새 실행의 런타임 상태를 검증했다.
- 2단계의 남은 호스트 기준과 3단계의 진단 비노출 기준을 실제 연결 시험으로 닫았다. 3단계의 수신 측 proof 재생 거부 기준은 실제 서비스 검증 전까지 미완료로 유지한다.

2026-10-03 검증: Go `1.27.1`에서 클라이언트 전체 race, 주요 패키지 race 5회 반복과 느린 stdout 상한 회귀 10회 반복을 통과했다. 양쪽 모듈 build·vet, 서버 공유 manifest와 Linux amd64 교차 빌드, gofmt·diff·문서 링크와 요구사항 51건 추적도 확인했다. 실제 로컬 TLS → stdio의 100개 동시 응답 상관·8개 전송 상한, 공식 Go SDK 클라이언트의 stdio 왕복과 진단 전체 경로·재실행을 확인했다. 실제 서비스·데이터베이스·시스템 브라우저·WSL2·지원 호스트·공식 적합성·배포 판정은 6단계에 남긴다. 상세 결과는 [5단계 구현 검토](./reviews/2026-10-03-client-phase-5.md)에 기록한다.

2026-10-03 추가 검토 보완: 목록의 로컬 오류를 JSON-RPC `-32603`·`data.client_error`로 분리하고 공식 Go SDK `ListTools`에서 일곱 오류가 노출되는 회귀를 통과했다. 잘못된 목록 입력·접수 상한과 실제 원격 계약 불일치에도 부분 목록을 반환하지 않는다. `doctor` DNS·TLS를 같은 HTTP transport의 자격 증명 없는 `HEAD`로 바꾸고 프록시 전용 경로·독립 프로세스의 `HTTPS_PROXY`·TLS 호스트 거부를 검증했다. 공식 MCP `2026-07-28` stdio의 취소 후 메시지 금지 규정을 확인해 명시적 취소의 미기록 응답을 생략하며, 느린 출력·뒤늦은 성공·EOF 응답 기록과 주요 패키지 반복 race 시험을 통과했다. 공식 conformance 실행은 아직 6단계 미완료다.

## 공통 검증과 상태 갱신

구현 단계마다 관련 단위·계약 시험을 먼저 실행한다. 코드 변경은 서버 루트와 클라이언트 `client/`에서 각각 `go build ./...`, `go vet ./...`와 관련 `go test`를 Go `1.27.1`로 확인하고, 저장소 루트에서 `gofmt -l .`을 확인한다. 실제 서버가 필요한 시험의 접속 정보가 없으면 건너뛴 계층과 이유를 기록한다. 전체 출시 판정은 6단계의 실제 서버·호스트·운영체제 결과가 모인 뒤에만 내린다.

단계 완료 시 작업·완료 기준의 체크박스와 단계 현황을 함께 갱신하고, 검증 날짜와 결과의 위치를 해당 단계에 짧게 남긴다. SRS·SDD의 지속 계약을 이 문서에 복사해 수정하지 않는다.
