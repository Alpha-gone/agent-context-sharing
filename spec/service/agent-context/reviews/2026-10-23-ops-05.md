# OPS-05 기동·수신 실패·정상 종료 공통 정리 모듈 인수

- 기준: 2026-10-23, `feat/web-foundation`의 `d2634b9` 이후 작업 트리.
- 대상: [OPS-05](../development-plan/operations.md#ops-05), [기동과 종료](../sdd/operations.md#기동과-종료), [서버 종료 시험](../sdd/testing.md#테스트-계층).
- 판정: 구현·모듈 인수 완료. 전체 **82/124개 완료·42개 미착수**. 다음 권장은 OPS-06이다.

## 변경과 책임

기존 수신 오류 분기는 진행 요청의 종료 경계를 거치지 않고 반환했다. 종료 신호 경로는 요청·작업자 정리에 실패하면 수신 결과를 수집하기 전에 반환하여 함께 발생한 원인을 잃을 수 있었다.

- 조립 전에 종료 신호를 등록한다. 구성 검증→진단 파일 준비→DB/서비스 조립→작업자 시작→수신의 자원 순서는 유지한다. 조립 실패는 기존 assembly.close, 조립 이후는 작업자 시작 전에 등록한 공통 정리 책임을 사용한다.
- runHTTP는 신호와 수신 반환을 같은 shutdownInOrder에 연결한다. 수신 오류가 있어도 준비 상태 이탈과 진행 요청 대기를 수행한다. 신호가 먼저 선택된 경우에도 수신 결과를 수집해 요청·각 작업자 오류와 합산한다.
- 요청 30초가 실패하면 연결을 강제로 닫아 요청을 취소한다. 작업자는 이후 생성한 공용 10초를 사용하며 하나의 오류에도 나머지를 시도한다. 시도한 작업자 목록은 비워 후속 공통 정리에서 다시 호출하지 않는다.
- 요청·작업자가 모두 반환한 때만 DB 풀을 닫는다. 수신 오류만으로 안전한 풀 종료를 생략하지 않는다. 미반환 요청·작업자가 있으면 풀 종료를 건너뛰고 마지막 진단 기록과 최대 5초 flush를 시도한다. flush 오류도 원래 원인과 함께 반환한다.
- 기존 진단 유지보수 중단·색인 배치·풀 소유권과 시간 예산을 재사용했다. DB 스키마·배포 키·의존성·Compose 구성은 변경하지 않았다.

## 실행과 증거

Go 1.27.1·macOS arm64에서 TEST_DATABASE_URL·TEST_DATABASE_REQUIRED=1을 사용했다. 신규 DB 인수는 시험별 전용 DB와 정식 마이그레이션을 사용하고 DB·파일·loopback 연결을 시험 종료 시 정리했다.

| 범위 | 실행 | 결과 |
|---|---|---|
| 최종 서버 전체 | `go test -race -json -p=1 -count=1 -timeout=180s ./cmd/server` | **595건 통과** |
| 진단 전체 | `go test -race -json -p=1 -count=1 -timeout=180s ./cmd/server ./internal/diagnostic`의 진단 패키지 결과 | **168건 통과**. 같은 실행의 서버 실패는 아래와 같이 수정·전체 재실행했다 |
| 공통 정적 검사 | `GO_BINARY=/Users/alphagone/sdk/go1.27.1/bin/go GOCACHE=/private/tmp/acs-obs02-go-cache sh ./check-go.sh` | 의존성 검증/빌드·전체 build·vet·gofmt 통과 |
| Linux 대상 빌드 | `GOOS=linux GOARCH=amd64 go build ./...` | 통과. Linux runtime은 미실행 |

최종 유효 합계는 **763건**, 실패·건너뜀·race 오류는 0이다. 상위 시험·하위 사례의 pass 이벤트 합계이며, 이전 서버 580건에서 신규·보강 사례 15건이 늘었다. 최종 서버는 `/private/tmp/acs-ops05-corrected.json`, 진단은 `/private/tmp/acs-ops05-final.json`의 진단 패키지 결과를 사용했다. 앞선 모듈 표본 55건과 실패 실행의 서버 594건은 중복 합산하지 않는다.

1. embedded/external 각각 정상 신호, 수신 실패와 정리 성공, 수신 실패와 두 작업자 실패, 신호 뒤 수신 오류와 두 작업자 실패를 실제 HTTP 연결로 대조했다. 진행 요청을 해제하기 전에는 종료가 반환하지 않으며 준비 상태가 먼저 이탈한다. 정리 성공이면 풀을 닫고 작업자 실패면 풀을 사용할 수 있게 남긴다.
2. 후행 작업자까지 같은 마감을 받고 한 번만 호출된다. 수신·첫/마지막 작업자의 원인을 모두 errors.Is로 확인했다. 실제 시스템 종료 기록이 flush되며 같은 instance의 기록기를 다시 열 수 있다.
3. 실제 DB 자문 잠금과 연결 예약을 가진 HTTP 요청이 취소 뒤에도 반환하지 않도록 유지했다. 요청 대기는 **30.002초**, 이후 작업자 정리와 정상 진단 flush는 **10.011초**, 전체는 **40.022초**였다. 강제 연결 종료의 요청 context 취소, 후행 작업자 호출과 풀 종료 생략을 확인한 뒤 시험 요청을 해제해 실행권·연결을 반환했다.
4. 별도 시험에서 파일 저장소 잠금을 유지하고 여러 이벤트를 대기시켰다. 업무 작업자 정리·풀 종료 뒤 진단 flush는 **5.001초**에 마감했고 원래 기동 오류와 기한 초과, 누락 건수가 함께 남았다. 잠금을 해제한 뒤 기록기를 다시 열어 시험 자원 반환을 확인했다.
5. 구성 거부와 여덟 조립 지점(진단 파일/수준·DB·색인 제공자·임베딩 스키마·검색·인가·MCP), 조립 취소와 실제 바인딩 실패를 실행했다. 부분 실패 뒤 작업자와 진단 instance 잠금의 반환을 확인했다. 별도 하위 프로세스에서 실제 main의 구성 실패 종료 코드가 1임을 확인했다.
6. 개발·운영 Compose의 stop_grace_period=50s를 대조했다. 요청 30초·작업자 10초·flush 5초의 합계 45초와 5초 여유를 구분한다. 세 단계의 실제 측정은 위 독립 표본이며 컨테이너의 50초 강제 종료를 실행한 것은 아니다.

첫 모듈 표본 55건은 통과했다. 이후 flush 인수의 첫 표본은 대기 기록이 적어 개별 잠금 획득 제한 1초에서 종료되어 5초 마감 측정이 실패했다. 대기 기록을 12건 추가하여 공용 flush 마감을 측정하도록 시험 준비를 수정했다. 최종 서버 전체 595건을 다시 통과했으며 구현의 시간 정책은 변경하지 않았다.

## 제한과 정합성

- 이번 판정은 기동·수신·요청·작업자·진단 정리의 모듈 인수다. 전체 운영 장애·복구·배포와 컨테이너 강제 종료, Linux runtime·실제 Tunnel·외부 제공자·호스트·전체 저장소 시험은 실행하지 않았다.
- DOX pass에서 변경이 기존 cmd/server 실행 경계와 운영/시험 정본 안에 있음을 확인했다. 새 지속 경계·소유권·환경 키가 없어 추가 DOX나 부모 색인 갱신은 필요하지 않다. 기존 계약의 구현 정합화이며 SRS 요구사항을 변경하지 않았다.
- 운영·시험 SDD, 계획·진입점·색인과 근거·요청 기록을 함께 유지한다. 기존 Compose·IDE 변경을 보존했으며 이번 변경은 미커밋이다. upstream이 없어 원격 비교를 수행하지 않았으며 push·배포는 하지 않았다.

최종 문서 검사에서 Markdown 10개의 상대 링크·앵커 449개, UTF-8·한글 표기와 개발 체크박스 124개(완료 82·미착수 42), git diff 공백 검사가 통과했다.
