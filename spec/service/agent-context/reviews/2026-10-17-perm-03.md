- 시작 상태: `feat/implementation-improve`, `3bb61cc`. upstream이 없는 로컬 브랜치이며 선행 PERM-02·LIFE-06은 완료다. 기존 Compose·IDE 변경은 보존했다.
- 범위: 웹 전용 계정·팀 등급 부여/회수, 같은 부여 경로의 소유자 인계, 현재 소유자·대상 참조·마지막 소유자 판정과 감사·유예 원자성의 새 모듈 증거.

## 발견 사항과 구현

| ID | 영향도 | 발견 사항 | 처리·검증 |
|---|---|---|---|
| PERM03-R1 | 높음 | 계정 부여가 UUID 형식만 검사해 부재 계정의 등급을 만들 수 있었다. 다형 참조에는 외래 키가 없다. | 그래프 잠금과 현재 행위자 인가 뒤 같은 트랜잭션에서 계정 존재를 확인하고 부재는 not_found로 거부한다. 세 등급 모두 상태·등급·감사가 보존됐다. |
| PERM03-R2 | 높음 | 마지막 소유자 집계가 부재 계정의 직접 부여 또는 잘못된 팀 구성원 참조를 남은 소유자로 셀 수 있었다. | 직접·팀 상속 집계를 실제 account 행과 결합했다. 과거 잘못된 참조를 합성한 4개 회수/강등 조합에서 마지막 실제 소유자를 보존했다. 자동 데이터 수정이나 행 삭제는 추가하지 않았다. |
| PERM03-R3 | 중간 | 웹 계정 부여의 로그인 아이디 조회 장애를 모두 없는 계정의 입력 오류로 안내했다. | 래핑된 부재는 기존 400, 내부 조회 장애는 원문을 숨긴 500으로 구분한다. 조회 실패 때 부여를 호출하지 않고 성공 때 정확한 계정·owner 등급과 303 이동을 유지했다. |

- 기존 팀 행→그래프 잠금과 잠금 뒤 현재 소유자 검사는 유지했다. 새 모듈 시험으로 직접 강등·팀 구성원 제거·팀 삭제가 대기 중인 부여/팀 부여/인계/회수에 즉시 반영됨을 확인했다.
- 계정·팀별 두 소유자가 동시에 자기 등급을 회수하거나 편집자로 낮추는 4개 조합에서 한 요청만 성공하고 다른 요청은 마지막 소유자 오류로 거부됐다. 두 요청의 실제 잠금 대기를 확인한 뒤 보유 잠금을 해제했다. 남은 고유 소유자와 감사 기록은 각각 하나였다.
- 다른 계정의 열람자 등급을 소유자로 올린 뒤 이전 소유자가 자기 직접 부여를 회수하는 인계를 확인했다. 인계 자체가 이전 소유자를 자동 회수하지 않고 생성 계정도 바꾸지 않는다. 이전 소유자의 후속 재부여는 거부됐다. 이전/이후 등급과 actor·subject·그래프가 감사에 남았다.
- 감사 삽입 실패와 지연 제약 트리거의 커밋 실패를 계정 부여·인계·강등·계정 회수·팀 부여·팀 회수에 각각 주입했다. 12개 조합 모두 등급·유예·감사가 함께 롤백됐다. 유예 취소의 롤백은 접근이 복원됐지만 유예가 남아 있는 합성 상태로 검사했으며 정상 요청만으로 그 상태가 생긴다고 주장하지 않는다.
- 패키지 경계·저장 스키마·의존성·DOX 소유권은 바뀌지 않아 해당 계약과 마이그레이션을 유지했다. 권한·웹 SDD에 대상 참조와 오류 의미를 정합화했다. HTML·CSS·클라이언트 JavaScript는 변경하지 않았다.
