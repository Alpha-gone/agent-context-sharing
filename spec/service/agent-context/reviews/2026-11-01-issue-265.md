# #265 MCP 요청별 스키마 검증

## 원인과 변경

- SDK 등록 래퍼·읽기/에이전트 처리기·쓰기 처리기/WriteRunner가 같은 원문을 반복 해석·검증했다. 등록 경계에서 한 번 검증한 값을 비공개 요청 컨텍스트로 전달하고 같은 요청 객체·도구 이름·원문에만 재사용한다. 직접 처리기와 공개 WriteRunner.Execute는 기존처럼 검증한다. 공개 처리기 API는 유지한다.
- 쓰기 처리와 재생 지문은 같은 검증 값을 사용한다. UUID를 정규화한 뒤 지문용 사본에서만 request_id를 제외하여 업무 인자를 보존한다. 속성별·전체 스키마 검증의 순서는 오류 필드 계약을 위해 유지하며 현재 권한·행위자 결합·취소·도구 panic 복구를 바꾸지 않는다.
- [MCP 설계](../sdd/mcp.md#입력-검증)·[시험 설계](../sdd/testing.md)와 [공식 근거](../reference.md#265-mcp-요청별-입력-검증)를 맞췄다. 기존 요구사항·개발 계획·DOX의 소유권과 구조는 바뀌지 않아 유지했다. 전체 지연 개선률은 측정하지 않았다.

## 계측과 회귀

- 서로 다른 등록·읽기·쓰기·등록 처리기 카탈로그의 실제 검증 함수를 시험별 원자 계수기로 감쌌다. 14종 실제 처리기의 HTTP·직접 호출에서 정상 요청과 잘못된 입력 모두 스키마 검증 1회를 확인했다. 쓰기 재생 대역은 현재 권한 콜백과 행위자 결합도 실행한다.
- 다른 요청 객체·도구·원문과 컨텍스트가 없는 호출은 검증을 다시 수행한다. 8,000자 본문·1,000개 구성원 참조를 가진 사건 입력에서 직접 실행과 검증 값 실행의 지문이 같고 UUID 표기와 request_id 보존이 유지된다. 기존 시험에서 정수·JSON escape·UUID 정규화와 오류 필드를 함께 확인했다.
- 검증 중 panic의 internal 완료·원문 비노출·다음 요청 성공, 기존 14종 처리기 panic과 진단 실패 복구 시험이 통과했다. 독립 코드 리뷰에서 수정이 필요한 발견 사항은 없었다.

## 실행 결과

Go 1.27.3에서 `go test -race -json -count=1 ./internal/mcp ./cmd/server`를 실행했다. 서버는 `.env`의 TEST_DATABASE_URL·TEST_DATABASE_REQUIRED=1을 사용했고 시험이 만든 격리 DB에 정식 마이그레이션을 적용했다. 기존 공유 DB의 스키마·데이터는 준비용으로 변경하지 않았다.

- 최초 실행에서 새 node_get 계측 대역이 바꾼 노드 ID와 기존 홉 거리 키가 달라 실패했다. 대역의 거리 키를 같은 노드 ID로 고친 뒤 MCP 패키지를 `go test -race -json -count=1 ./internal/mcp`로 재실행하여 하위 사례 포함 543건 통과, 실패·건너뜀 0건을 확인했다.
- 서버 패키지는 하위 사례 포함 730건 통과, 실패 0건이다. 실제 DB의 쓰기·읽기·재생·격리·오류 계약을 포함한다. 별도 환경 인수 21건(실제 Codex CLI·물리 복구·이행)은 건너뛰었으며 통과로 집계하지 않는다.
- check-go.sh의 의존성 확인·전체 build·vet·gofmt·govulncheck와 변경 문서의 상대 링크·내부 앵커·git diff --check가 통과했다.

전체 저장소 시험·실제 Codex 호스트 인수·운영 배포는 수행하지 않았다. 사용자 기존 `.env.example`·IDE 설정 변경은 이 작업에 포함하지 않는다.
