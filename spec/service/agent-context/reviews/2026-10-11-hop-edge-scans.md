# 고연결 노드의 홉 간선 스캔 축소 검토

## 대상과 채택 판단

- 관련 [#121](https://github.com/Alpha-gone/agent-context-sharing/issues/121), 기준 `dev`의 `f9b8efd`와 #110의 식별자 중심 조회다. #110 이전의 전체 본문 적재 구현을 성능 기준선으로 바꾸어 개선폭을 부풀리지 않는다.
- 관계 판정은 Cypher에 유지한다. 작은 인접 집합은 완전한 제한 표본을 정렬하고, 큰 집합은 정렬된 활성 정점에서 관계 존재를 확인하는 방식을 채택했다. 기준 정점별 첫 K개 합집합을 다시 집계·정렬하여 최초 발견 순서, 최단 거리와 절단 경계를 유지한다. 남은 자리가 0이면 정렬·집계 없는 존재 확인만 수행한다.
- `Context`의 활성 그래프·식별자 부분 인덱스와 일곱 간선 label의 끝점 복합 인덱스 8개를 추가했다. 최초에는 `002_hop_probe_indexes.sql`로 분리했으며, 후속 사용자 승인으로 `001_init.sql`에 통합하고 002를 삭제했다. 기존 단일 끝점 인덱스는 보존하며 새로운 배포 구성·MCP 입력·운영 데이터 정리는 없다.
- 내부 간선은 기존 선택 정점 Cypher 질의를 유지했다. 작은 반환 집합의 모든 끝점 쌍에 상관 `EXISTS`를 실행하는 후보는 작은 테이블의 순차 스캔을 반복했다. 같은 표본에서 간선 접근이 약 22,567행으로 늘어 채택하지 않았다. 기존 질의는 206행 접근·16개 간선 반환, 1,204개 공유 버퍼 hit, 0.601ms였다. 내부 간선이 모두 반환되는지는 별도로 대조한다.

## 재현 조건

- Go 1.27.1, darwin/arm64, 실제 개발 PostgreSQL 18.6·Apache AGE 1.8.0. 아래 성능 측정은 통합 전 전용 DB에 정식 001·002 마이그레이션을 적용해 수행했다. 두 번째 적용은 무변경이었다. 기존 DB·서명 키·컨테이너·볼륨·.env는 변경하지 않았다. 현재 재현은 동일한 인덱스를 포함하는 001만 적용한다.
- 원천 허브 하나와 이를 근거로 삼는 파생 정점 1,000·20,000·50,000개, 본문은 1,200자·UTF-8 2,800바이트다. 탐색 비용을 분리한 묶음 생성 fixture이며 도메인 쓰기 정책·색인 작업자·운영 SLA 표본이 아니다.
- 방향 `in`, `derived_from`, 1홉, 상한 2·10에 대해 기준선·개선을 번갈아 각 3회 실행했다. 양쪽에 같은 추가 인덱스를 제공하여 질의 전략 자체를 비교했다. 기준선은 #110 후보 질의와 같은 본문·간선·참조·접근 기록 조립을 실행하는 단일 허브 시험 함수다. 결과 동등성은 별도의 전체 BFS 기준선으로도 대조했다.
- 후보 계획은 `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)`으로 수집한다. 아래 지연 표는 race 계측 없는 마지막 단독 실행의 평균이다. 계획 실행과 전체 호출은 별도 실행이므로 한쪽 지연이 항상 다른 쪽보다 작다고 보장하지 않는다. 공유 캐시·통계·표본 생성과 다른 label의 잔여 시험 행에 영향을 받으며 반복값은 독립 표본이나 통계적 유의성으로 해석하지 않는다.

```shell
# 전용 시험 DB에 통합한 001을 적용하고 TEST_DATABASE_URL을 지정한다.
TEST_DATABASE_REQUIRED=1 go test ./internal/store \
  -run '^(TestHopSelectiveScanIntegration|TestHopSelectiveMultiAnchorAndDenseEdgesIntegration)$' \
  -count=1 -v
```

- 행 접근은 각 relation 계획 노드의 `(Actual Rows + Rows Removed by Filter) × Actual Loops` 합이다. 페이지 안의 모든 물리적 튜플 접근·CPU 지시 수를 뜻하지 않으며 Bitmap Index Scan의 항목은 이 합에 포함되지 않는다. 버퍼·임시 블록은 최상위 계획 수치이며 하위 노드의 누적값을 다시 더하지 않는다.
- 1천 연결에서 기준선은 간선 1,015행·정점 1,001행, 개선은 상한 2·10에서 간선 82·90행과 정점 74·98행이었다. 15개 다른 그래프 시험 간선의 필터 제외도 포함한다. 첫 실행 뒤 공유 버퍼 hit는 3,019 → 231·316이며 임시 블록은 모두 0이었다.
- 2만 연결에서 간선 20,000 → 67·75행, 정점 20,001 → 74·98행, 공유 버퍼 hit 60,344 → 233·325, 임시 블록 0 → 0이었다. 상한 2의 첫 기준선 실행은 캐시 준비로 hit 69,577이었다.
- 5만 연결에서 간선 50,000 → 67·75행, 정점 50,001 → 74·98행, 공유 버퍼 hit 150,849 → 234·323이었다. 첫 기준선 hit는 174,205였다. 기준선의 CTE·집계 임시 블록 read/write 61/740이 개선에서 0/0으로 사라졌다. 두 후보 모두 최종 정렬은 메모리에서 수행했으며 상한 2에서 25kB, 상한 10에서 기준선 27kB·개선 26kB였다. 임시 블록을 외부 정렬 디스크 크기로 잘못 보고하지 않는다.
- 개선 계획은 정렬 없는 표본 65행, 활성 정점의 `context_active_graph_context_idx` 정렬 접근, `derived_from_hop_endpoints_idx`를 포함하는 관계 존재 확인과 조기 `LIMIT`으로 구성된다. 2만·5만 표본은 전체 인접 인덱스가 아닌 65개 표본과 2·10개 관계를 접근했다. 통계가 갱신되지 않은 초기 계획은 2만 항목의 Bitmap Index Scan이 남았으며 마이그레이션의 `ANALYZE`와 시험 표본 생성 후 통계 갱신의 필요성을 확인했다.
- 최종 race 회귀의 별도 계획 확인에서 양방향·상한 10은 1천·2만·5만 연결 모두 간선 75행·정점 109행을 접근했다. 공유 버퍼 hit는 456·502·522, 후보 실행은 0.736·0.592·0.808ms였으며 임시 블록은 0이다. 남은 자리 0은 각 표본 모두 간선 1행·정점 2행·공유 버퍼 hit 12, 집계·정렬·임시 블록 없이 0.047·0.083·0.065ms에 확인했다. 이는 위 단독 반복 평균과 구분하는 계획 확인값이다.
- 상한 10·4개 동시 조회·각 3회, 총 12개 요청의 전체 벽시계 시간은 1천에서 71.638 → 51.997ms, 2만에서 339.787 → 15.136ms, 5만에서 1,149.717 → 16.021ms였다. 오류·응답 수·간선 수·절단 불일치 없이 완료했다. CPU·RSS·WAL·운영 쓰기와의 동시 부하는 측정하지 않았다.

## 인덱스 저장·쓰기 비용

- 다른 시험의 삭제 행·인덱스 팽창과 분리한 새 비용 측정 DB에서 5만 정점·5만 참조를 만든 뒤 `pg_relation_size`로 측정했다. 새 Context 인덱스 9,797,632바이트, DERIVED_FROM 인덱스 1,589,248바이트, 나머지 6개 빈 간선 인덱스 각 8,192바이트, 합계 11,436,032바이트다. 기존 인덱스·테이블·TOAST·WAL 공간을 포함하지 않는다. 다른 간선 label의 실제 데이터가 늘면 해당 인덱스도 늘어난다.
- 같은 1천 파생·1천 참조 쓰기를 추가 인덱스 유무로 대조했다. 첫 쌍은 준비 실행으로 제외하고, 이후 5쌍은 실행 순서를 번갈아 바꾸었다. 쓰기는 매회 롤백하며 인덱스 제거도 같은 트랜잭션에서 롤백한다. Context·DERIVED_FROM에 쓰므로 해당 추가 인덱스 2개만 대조하고 나머지 label의 인덱스는 유지한다.
- 추가 인덱스 없음의 지연은 209.121·210.229·200.882·228.587·208.542ms, 있음은 212.283·234.913·220.062·241.178·221.635ms였다. 평균 211.472 → 226.014ms, 약 6.9% 증가다. 파싱·AGE 실행·DB 쓰기를 포함하고 인덱스 삭제 시간·롤백·커밋은 제외한다. 반복 롤백의 삭제 행과 캐시 효과가 남으므로 운영 쓰기 비용의 확정값이나 무비용 개선으로 해석하지 않는다.
- 일반 `CREATE INDEX`는 쓰기 잠금과 빌드 공간이 필요하다. 운영 규모의 적용 시간·공간·동시 쓰기 영향은 미측정이며 실제 운영 스키마를 변경하지 않았다.

## 검증과 복구

- 기존 900개 조합에 더해 제한 표본 경계 63·64·65개, 정확히 상한인 결과, 남은 자리 0, 다중 시작점·중복 시작점·공통 이웃·조밀한 내부 간선·삭제·제안 상태와 양방향을 대조했다. 새로운 고연결 표본에서도 #110 단일 허브 기준선과 노드·본문·속성·참조·순서·거리·간선·절단이 일치했다. 순환과 마지막 깊이 간선은 기존 회귀에도 포함된다.
- SQL 문자열·Cypher 문자열의 리터럴 구분 오류를 첫 격리 시험에서 발견하고 수정했다. 실패한 실행은 통과로 세지 않는다.
- 최초 관련 race는 2만 연결의 `both` 후보에서 30초 예산 초과 1건이 발생했다. 무방향 패턴 대신 방향별 Cypher를 같은 SQL에서 합치도록 변경한 뒤 해당 고연결 회귀·900개 조합·표본 전환 경계를 재검증했다.
- 별도 잠금 시험에서 실행 중 취소는 101.325ms, 호출자 마감이 없는 자체 예산 중단은 30.001s에 오류와 빈 결과를 반환했다. 잠금 해제 뒤 후속 홉 조회가 성공했고 풀의 점유 연결은 각각 이전 0개·이후 0개였다. 조용히 부분 성공하거나 연결을 누수하지 않았다. 호출자의 더 짧은 100ms 마감 회귀도 유지했다.

## 잔여 스캔과 한계

- 삭제·미확정·이미 방문한 노드가 많으면 표본 자체가 긴 간선 스캔을 요구할 수 있다. 큰 인접 집합이 그래프 전체에서 희소하거나 연결된 이웃의 식별자가 뒤에 있으면 정렬 후보의 존재 확인도 많은 정점을 방문한다. 양수 상한이 DB 실제 스캔 수의 절대 상한은 아니다.
- 다중 기준 정점의 후보 합집합과 정렬은 기준 정점 수에 비례한다. 내부 간선은 전체 선택 정점 질의를 유지하며 조인 순서·통계·간선 방향에 따라 전체 인접 집합을 읽을 수 있다. 통계가 오래되면 Bitmap 경로가 전체 인덱스를 먼저 읽는 비용도 남는다. 이를 별도 30초 예산으로 보호하며 임의 간선 절단으로 숨기지 않는다.
- 한도 없음은 기존 전체 이웃 구현이다. #123의 전체 연결·왕복·참조 측정 보완과 #124의 동시 이웃 삭제 처리 정책은 이 변경에 섞지 않았다. 운영 SLA·대형 실제 데이터·외부 API·실제 브라우저·배포·전체 모듈 race는 미검증이다.

## 초기 마이그레이션 통합

- 후속 요청에 따라 인덱스 8개의 정의를 `001_init.sql`에 옮기고 개발 중 002를 삭제했다. 인덱스의 키·부분 조건·C 정렬과 AGE의 기존 단일 끝점 인덱스는 유지한다. Context와 일곱 간선 label의 `ANALYZE`는 001에서 각각 한 번 수행한다.
- 새 전용 DB `issue121_init_20261011`에 `go run ./cmd/migrate up`으로 정식 001만 적용했다. 재실행은 적용할 파일 없이 적용 이력 1개를 유지했고, 카탈로그에서 새 인덱스 8개의 정의와 대상 테이블 8개의 통계 갱신을 확인했다.
- `TEST_DATABASE_REQUIRED=1`과 Go 1.27.1로 `go test -race -count=1 ./internal/migrate` 전체와 `internal/store`의 `TestHopBoundedMatchesFullIntegration`·`TestHopHubBoundedWorkIntegration`·`TestHopHubQueryPlansIntegration`·`TestHopSelectiveProbeBoundaryIntegration`을 통과했다. 통합 전 성능 측정과 723건 회귀 결과는 앞 절의 별도 실행 기록이며, 이번 통합에서 전체 성능 측정이나 전체 모듈 race를 반복한 것으로 보고하지 않는다.
- 통합으로 001의 체크섬이 바뀌므로 이전 파일을 적용한 개발·시험 DB는 재생성이 필요하다. 적용 이력을 덮어쓰거나 기존 개발 DB·볼륨을 초기화하지 않았다. 이번 시험 DB만 점유 연결 0개를 확인한 뒤 삭제했으며 잔여 DB 항목은 0건이다. 삭제한 시험 데이터는 복구하지 않으며 fixture로 다시 생성할 수 있다.
