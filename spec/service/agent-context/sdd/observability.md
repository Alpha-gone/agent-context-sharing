# 관측성과 종류별 진단 로그

구조화 지표, 업무 감사 조회 경계와 여섯 진단 파일의 기록·회전·보존·실패 정책의 정본이다. [OBS-01](../reviews/2026-10-21-obs-01.md)의 이벤트·안전 필드·흐름 계약과 [OBS-02](../reviews/2026-10-21-obs-02.md)의 파일 준비·권한·잠금은 구현·모듈 인수를 마쳤다. 비동기 기록·회전·보존·전체 파일 저장 인수는 후속 범위다.

[설계 전체](../SDD.md) · [요구사항과 설계 대응](traceability.md)

## 지표 수집 지점

지표는 이미 코드가 지나는 자리에서 얻는다. 별도 계측 계층을 두지 않는다.

| 지표군    | 수집 지점                                 | 내용                                                  |
|-----------|-------------------------------------------|-------------------------------------------------------|
| 요청      | `mcp`와 `web`의 진입점                    | 연산 이름, 계정, 그래프, 지연, 결과 코드, 상관 식별자 |
| 검색      | `search`의 채널 실행·라우팅·결합·근거 경로 선택 단계 | [SRS 측정](../SRS.md#측정)이 정한 열한 지표                       |
| 색인      | `index`의 작업 소비와 `store`의 상태 집계 | 미색인 수, 색인 지연, `failed` 작업 수                |
| 관리 연산 | `operation_log`                           | [SRS 기록 항목](../SRS.md#기록-항목)이 정한 일곱 항목                        |
| 저장      | `store`의 계층 이동과 되읽기              | 계층별 행 수와 되읽기 지연                            |
| 주기 작업 | [주기 작업](operations.md#주기-작업)의 각 회차                   | 작업 이름, 처리 건수, 실패와 건너뛴 회차              |

상관 식별자를 요청 진입점에서 만들어 아래 계층으로 넘긴다. 색인 작업에도 등록 시점의 상관 식별자를 남겨, 요청 경로 밖에서 처리된 색인을 그것을 만든 요청과 이을 수 있게 한다. 이 연결이 없으면 색인 지연이 어느 요청에서 시작됐는지 알 수 없다.

검색 지표를 `search` 안에서 얻는 이유는 채널별 값이 결합 뒤에 사라지고 선택 경로·이유와 선택 전후 후보 수·연결 노드 수는 각 단계 안에서만 알 수 있기 때문이다. 순위 역수 합이 채널 경계를 지우므로 결합 전에 채널별 후보 수와 지연을 기록하고, 라우팅 직후 경로와 이유 코드를, 선택 직전과 직후에 후보 수와 연결 노드 수를 집계한다. 기여 채널만 결과에 남아 응답과 지표 양쪽에 쓰인다. 경로와 컨텍스트 식별자 원문은 운영 로그에 남기지 않는다.

저장 계층의 되읽기 지연을 지표에 넣는 이유는 [저장 계층화](data.md#저장-계층화)가 활성 컨텍스트에 대해 "조회 시 즉시 되읽을 수 있어야 하며 이동은 사용자에게 드러나지 않는다"로 확정했기 때문이다. 드러나는지를 판정할 값이 없으면 그 확정을 검증할 수 없다.

## 로그에서 제외하는 것

| 대상             | 처리                                                                          |
|------------------|-------------------------------------------------------------------------------|
| 접근 토큰 원문   | 검증 후 요청 범위 밖으로 넘기지 않고 어떤 로그에도 남기지 않는다              |
| 비밀번호와 해시  | 어떤 로그와 지표에도 남기지 않으며 인가 서버의 요청 범위 밖으로 넘기지 않는다 |
| 컨텍스트 `body`  | 로그와 지표 어디에도 넣지 않으며 길이만 기록한다                              |
| 질의 `work_context` | 로그와 지표 어디에도 넣지 않으며 선택 경로와 이유 코드만 기록한다            |
| 관계 경로 원문   | 로그와 지표 어디에도 넣지 않으며 길이·연속성·단절 여부 같은 집계값만 기록한다 |
| 판단 입력의 내용 | `operation_log`에만 두고 운영 로그로 복제하지 않는다                          |
| 멱등성 키·요청 지문·저장 결과 | `idempotency_record`에만 두고 운영 로그에는 재생·충돌 여부만 남긴다     |
| 오류 원인        | `internal`의 원인은 로그에만 남기고 응답에는 담지 않는다                      |
| 세션 쿠키 값     | 접근 토큰 원문과 같게 다루며 어떤 로그에도 남기지 않는다                      |

비밀번호를 해시까지 함께 빼는 이유는 토큰 원문과 같다. 해시는 평문이 아니지만 유출되면 오프라인 대입의 입력이 되므로 저장된 자리 밖으로 나가지 않아야 한다. [`SRS.md`](../SRS.md)의 [SRS 비밀번호 취급](../SRS.md#비밀번호-취급)이 로그를 접근 토큰 원문과 같게 다루기로 확정한 것을 그대로 옮긴 것이다.

`body`를 로그에서 빼는 것은 권한 경계 문제다. 로그는 그래프 등급 검사를 지나지 않으므로 본문이 로그로 새면 격리가 운영 경로로 우회된다. 예산 지표에 필요한 것은 문자 수뿐이라 길이만 남기면 충분하다.

판단 입력을 복제하지 않는 이유도 같다. 판단 입력에는 컨텍스트 내용이 담기므로 `operation_log` 밖으로 나가면 같은 우회가 생긴다. 그 테이블은 감사 화면이 소유자 등급으로 접근을 제한한다.

## 감사 기록의 조회

두 기록을 나눠 저장하고 화면에서 합쳐 보여준다.

| 항목   | 설계                                                     |
|--------|----------------------------------------------------------|
| 저장   | `operation_log`와 `web_audit_log`로 나눈다               |
| 조회   | 그래프와 기간으로 거른 뒤 시각 내림차순으로 합친다       |
| 페이지 | 마지막 행의 발생 시각과 식별자를 담은 커서로 이어 읽는다 |
| 접근   | 소유자 등급으로 제한하며 `perm`의 같은 검사를 지난다     |
| 정리   | 종류별 보존 기간에 따라 주기 작업이 지운다               |

합치는 일을 질의가 아니라 조회 계층에서 하는 이유는 두 테이블의 열이 다르기 때문이다. 하나로 합치는 뷰를 만들면 공통 열만 남거나 빈 열이 생기고, 어느 쪽이든 화면이 다시 종류를 구분해야 한다.

페이지 처리를 두는 이유는 이 화면만 상한 없이 반환하고 있었기 때문이다. 기록은 보존 기간까지 쌓이기만 하므로 오래 쓴 그래프의 감사 화면이 가장 큰 응답을 만든다. [SRS 기록 보존](../SRS.md#기록-보존)이 대상 보관 기간 이상을 요구하고 그 기본값이 무기한이라 이 목록은 저절로 줄지 않는다.

커서에 시각과 식별자를 함께 담는다. 두 기록이 모두 시각 내림차순이라 같은 조건을 두 질의에 각각 걸 수 있고, 각 테이블에서 한 페이지 분량을 읽어 합친 뒤 페이지 크기까지 자른다. 식별자를 더하는 이유는 같은 시각의 행이 두 테이블에 걸쳐 있을 수 있어 시각만으로는 위치가 하나로 정해지지 않기 때문이며, `graph_list`가 `last_activity_at`에 `graph_id`를 더한 것과 같은 이유다.

인코딩과 계약은 [페이지 처리](mcp.md#페이지-처리)가 정한 규칙을 그대로 쓴다. 불투명 문자열이고 받은 값을 그대로 되돌려주며 해독할 수 없으면 거부한다. 서명하지 않는 근거도 같다. 위조된 커서는 다른 위치의 목록을 볼 뿐이고 소유자 등급 검사는 따로 지난다.

페이지 크기는 [SRS 플랜이 정하는 항목](../SRS.md#플랜이-정하는-항목)의 그래프 목록 값을 그대로 쓴다. 새 플랜 항목을 만들지 않는 이유는 이 화면이 계정의 이용 조건을 따로 갖지 않기 때문이며, 항목을 늘리려면 그 표를 고쳐야 한다는 규칙도 그대로 적용된다.

대기 중인 복구 요청도 이 조회로 얻는다. `restore_request` 행 중 같은 `graph_id`의 `operator_restore` 행이 뒤에 없는 것을 고르면 되고, 두 대상이 한 테이블에 있어 조인 없이 끝난다. 상태를 저장하지 않는 근거는 [복구](operations.md#복구)에 있다. 복구 자격을 증명하는 `after_grade=owner` 행과 미처리 복구 요청은 일반 감사 보존 정리에서 제외한다. 운영자 복구의 소유자 부여 기록도 보존하므로 처리 완료 요청이 다시 대기로 나타나지 않는다. 이 행들은 단순 이력이 아니라 복구 상태의 근거이므로 그래프가 존재하는 동안 보존한다.

정리 주기 작업은 두 기준을 각각 적용한다. 적용된 연산과 웹 감사 기록은 플랜의 `AuditRetentionDays`, 거부된 연산은 `RejectedOperationDays`를 쓴다. `AuditRetentionDays`는 [배포 구성](operations.md#배포-구성)이 대상 보관 기간 이상으로 강제하므로 두 기록이 대상보다 먼저 사라지지 않는다. 대상이 무기한 보관이면 기록 보존도 무기한이라 적용된 연산과 웹 감사 기록은 지우지 않는다.

## 종류별 진단 로그

`FR-AGENT_CONTEXT-173`~`175`와 [SRS 종류별 진단 로그](../SRS.md#종류별-진단-로그)를 구체화한다. 정책은 확정되었으나 파일 기록·배포 마운트·실제 저장 시험은 대기다. 기존 업무 감사 테이블이나 구조화 지표를 파일 저장 완료의 증거로 사용하지 않는다.

### 기록기와 소유 경계

목표 `diagnostic` 기록기는 명시적 종류와 허용 필드만 받는 이벤트 인터페이스를 제공한다. 호출자가 요청 객체·본문·임의 error·URL·HTTP 헤더를 그대로 넘길 수 없게 한다. 조립 지점이 기록기를 준비하고 각 처리 경계에 필요한 인터페이스를 주입한다. `store`의 관리 연산·웹 감사 기록은 DB 트랜잭션 안에 남기며 이 기록기의 전달 실패로 삭제·변경하지 않는다.

이벤트 구현의 `Fields`는 종류별 값 구조체로 나누고 다른 종류의 필드는 거부한다. route·method·tool·검증 필드명·단계·결과·원인·검색 경로·계층·커밋 상태는 명시적 허용 목록만 받는다. 문자 모양이 맞는 임의 코드도 허용하지 않는다. 확인된 UUID는 정규 소문자 UUIDv7만 받으며 공개 client 이름은 사전 등록을 확인한 1~64자 ASCII 영문·숫자·밑줄·하이픈으로 제한한다. 안전한 이름으로 표현할 수 없는 client는 선택 ID를 생략한다. 원문이나 확장 map·임의 객체를 싣는 필드는 제공하지 않는다. 확인되지 않은 대상 식별자가 있으면 이벤트 전체를 거부한다. 허용 목록과 값 타입의 구현 위치는 `internal/diagnostic/fields.go`다.

| 종류·파일 | 생성 지점 | 주요 안전 필드 |
|---|---|---|
| 요청 `request.jsonl` | 웹·MCP 수신·검증·응답 | 고정 route·method·tool, 상태·결과 코드, 지연, 검증 필드명 |
| 인증 `auth.jsonl` | 계정·세션·OAuth·JWT 검증 | 단계·거부 원인, 검증된 계정·client·grant 식별자, 흐름 식별자 |
| 검색 `search.jsonl` | 채널·라우팅·홉·예산 조립 | 채널·선택 경로·이유 코드, 후보·노드·간선·문자 수, 지연·절단 |
| 색인 `index.jsonl` | 큐 등록·확보·제공자·반영 | task·context·graph, 등록 세대·시도 횟수·리스 결과, 제공자 상태·지연 |
| 관리 `management.jsonl` | 도메인·권한·팀·삭제·복구 | 연산·확인된 graph·context·relation, 단계·필드·기대/실제 계층, 커밋 상태 |
| 시스템 `system.jsonl` | 기동·종료·DB·작업자·마이그레이션·기록기 | 작업 식별자, 구성 판·마이그레이션 번호, 단계·상태·안전한 원인 코드 |

이벤트의 종류와 심각도는 독립이다. 관계 확정 실패를 ERROR라는 이유로 시스템 파일에 보내지 않는다. 업무 적용은 DB 커밋 이후 `committed`, 실패는 실제 롤백 이후 `rolled_back`으로 기록한다. 결과를 확인할 수 없으면 `unknown`이며 성공으로 바꾸지 않는다. 노드 생성과 별도 관계 확정은 서로 다른 요청·트랜잭션 결과로 기록한다.

### 이벤트 외피와 흐름 추적

모든 이벤트에 `time`(UTC RFC 3339), `kind`, `level`, `instance_id`, `boot_id`, `stage`, `result`, `reason_code`를 둔다. 기동 회차 `boot_id`는 새 UUIDv7이며 배포 슬롯의 `instance_id`는 재시작에도 유지한다. 요청 이벤트에는 서버가 발급한 `correlation_id`, 비동기·주기 작업에는 `job_id`, 시험에는 `test_run_id`를 둔다. 선택 필드의 부재는 JSON 필드 생략으로 표현한다.

조립 지점은 기동마다 `NewSource(instance_id)`를 한 번 호출해 모든 종류의 Reporter에 공유한다. 요청 진입점의 `NewRequestTrace`와 작업 회차의 `Trace.NewJob`, 시험 실행의 `NewTestRun`은 서로 다른 UUIDv7을 발급한다. 불변 값인 Trace를 context로 전달하고 이벤트에는 식별자만 복사한다. 요청 없는 작업은 correlation_id를 생략하고 job_id만 사용한다. 요청 이벤트에 correlation_id가 없거나 모든 이벤트에 correlation_id·job_id가 모두 없으면 거부한다. 인가 flow_id와 대상 식별자는 `identity_verified=true`인 이벤트만 받는다. 이 표시는 호출 지점이 실제 인증·대상 확인을 완료했다는 계약이며 UUID 형식 검사가 그 확인을 대신하지 않는다. 고정 코드만 받는 기존 소비자 인터페이스는 확인한 대상을 싣지 않고 미확인 상태로 전달한다. 실제 처리 지점의 Trace 생성·전파와 안전 필드 계측은 OBS-05에서 연결한다.

- `correlation_id`는 HTTP 요청마다 서버가 생성한다. 사용자의 쓰기 키 `request_id`를 대입하지 않는다.
- 색인 작업은 등록 트랜잭션에서 요청 상관 ID를 큐의 진단 메타데이터로 함께 저장한다. 재등록 시 새 상관 ID로 바꾸고 확보한 등록 세대와 같이 읽어 오래된 작업과 새 요청을 혼합하지 않는다. 리스·실패 결과도 확보 세대를 대조한 뒤 기록한다.
- OAuth 인가·코드 교환·회전은 계열 등 서버가 검증한 비밀이 아닌 `flow_id`로 연결한다. 코드·토큰 원문 또는 해시·PKCE verifier·세션 쿠키를 추적 키로 사용하지 않는다.
- 인증·대상 확인 전에는 입력 UUID·client·grant를 검증된 필드처럼 복사하지 않는다. `identity_verified=false`와 단계·필드명만 남긴다.
- 호스트 저장·복원은 실제 서버 요청의 결과만 관측한다. 호스트 내부 저장소 실패를 확인한 것으로 기록하지 않는다.

관계 거부의 단계는 `argument_validation`, `actor_binding`, `permission`, `endpoint_load`, `layer_check`, `time_check`, `cycle_check`, `write`, `audit`, `commit`으로 나눈다. 실제 통과한 대상만 식별자로 남기고 계층 오류에는 기대·실제 계층 값만 남긴다. 인증 실패는 만료·개별 폐기·계열 폐기·비활동 만료·재사용·결합 위반·저장소 장애를 별도 원인으로 구분한다.

### 민감정보와 크기 제한

컨텍스트·질의·판단 입력, 요청·응답 전체, 원본 URI·query string·양식·제공자 응답, 자격 증명과 오류 원문은 어느 수준에서도 기록하지 않는다. 입력·오류에 포함된 비밀을 치환하는 방식에 의존하지 않고 구조화 허용 필드로만 이벤트를 만든다. 업무 감사의 판단 입력은 기존 DB에 남으며 진단 파일로 복사하지 않는다.

인코딩 뒤 이벤트는 개행을 포함하여 최대 16 KiB다. 필수 식별자·단계·결과를 먼저 구성하고 선택 진단 필드를 제거해 크기를 맞추며 `fields_omitted`를 표시한다. 문자열 내부 줄바꿈은 JSON 이스케이프로 기록하고 이벤트 하나를 한 줄로 유지한다. 필수 외피도 제한 안에 들어가지 않으면 잘린 JSON을 쓰지 않고 누락 처리한다.

인스턴스 공용 비동기 대기는 최대 1024건·16 MiB의 두 제한을 동시에 적용한다. enqueue가 즉시 실패하면 호출자는 파일 기록을 기다리지 않고 누락 카운터에 반영한다. 파일 쓰기는 기록기가 직렬화하고 본문을 가진 요청 goroutine을 대기열에 넣지 않는다.

### 경로·권한·다중 인스턴스

로그 루트는 `/var/log/agent-context`, 각 인스턴스 경로는 `<instance_id>/`다. 배포 구성과 고정값의 구분은 [목표 추가 구성](operations.md#목표-추가-구성)을 따른다. 인스턴스별 디렉터리는 `0700`, 파일은 `0600`이고 서버 기록 주체·허용된 운영자만 열람한다. 공개 자산 라우트·MCP 도구로 파일을 제공하지 않는다.

기동 시 경로·소유·권한과 영속 저장소를 확인하고 같은 instance 디렉터리에 단일 기록자 잠금을 얻는다. 기존 심볼릭 링크를 따라가거나 식별자에 경로 구분자를 허용하지 않는다. 같은 instance_id의 동시 기동은 기존 파일을 공유하지 않고 실패한다. 재시작은 기존 활성 파일에 append하고 기존 내용을 덮어쓰지 않는다.

파일 준비는 Linux·macOS의 디렉터리 fd와 openat의 O_NOFOLLOW로 각 경로 구성 요소를 연다. 상위 경로는 root 또는 실행 주체 소유이며 다른 주체가 쓰지 못해야 한다. 설정 루트의 부모는 미리 존재해야 하며 루트·instance만 0700으로 생성한다. 기존 루트·instance는 실행 주체 소유의 0700, 일반 파일은 같은 주체 소유의 0600·단일 하드 링크여야 한다. 기존 권한을 자동 교정하거나 파일을 truncate하지 않는다. 여섯 파일을 모두 사전 검사한 뒤 없는 파일만 배타적으로 생성한다. 열린 fd와 경로의 inode 결합도 다시 확인한다.

기록자 잠금은 instance의 `.writer.lock`, 저장소 공용 잠금은 루트의 `.storage.lock`에 두고 모두 0600으로 보호한다. 기록자 잠금은 기동 중 즉시 획득해 수명 동안 유지한다. 공용 잠금은 같은 인스턴스의 로컬 직렬화 대기를 포함하여 최대 1초이며 요청 취소를 따른다. 잠금 파일은 종료 시 삭제하지 않고 fd를 닫아 해제한다. 따라서 대기 중인 다른 기록자가 과거 inode를 잠근 채 새 잠금 파일과 분리되지 않는다.

파일 시스템 검사로 알려진 메모리·가상 파일 시스템과 Linux overlay·읽기 전용 마운트를 거부하고 파일·디렉터리 sync 가능 여부를 확인한다. 이 검사가 배포 볼륨의 실제 영속 마운트나 다중 호스트 잠금 일관성을 증명하지는 않는다. 배포 재생성 후 보존과 공유 파일 시스템의 동작은 운영·OBS-08 인수에서 별도로 확인한다.

저장소 전체 상한은 같은 로그 루트에 대한 공유 파일 잠금 아래 검사·정리·쓰기 예약으로 직렬화한다. 인스턴스별 기록자 잠금과 별개다. 저장소 잠금은 기동 검증과 실행 중 유한한 1초 기한을 사용하고, 획득 실패는 정책을 생략해 쓰는 대신 기동 실패 또는 누락으로 처리한다. 다중 호스트에서 잠금의 일관성을 제공하지 않는 공유 파일 시스템은 이 설계의 배포 전제를 충족하지 못하므로 별도 저장소로 분리해 같은 정책을 적용해야 한다.

### 회전·보존과 총상한

| 경계 | 확정값·처리 |
|---|---|
| 활성 파일 | 여섯 고정 basename으로 append한다 |
| 회전 | 다음 이벤트로 10 MiB에 도달하기 전 또는 UTC 날짜 변경 시 close·rename·새 활성 파일 생성 |
| 회전 이름 | 종류·UTC 회전 시각·고유 회차를 포함한다. 기존 이름을 덮어쓰지 않는다 |
| 기간 | 이벤트 시각부터 7일. 물리 정리 지연은 최대 1시간 |
| 종류별 | 활성 파일 포함 최대 10개·100 MiB |
| 인스턴스별 | 여섯 종류 합계 최대 600 MiB |
| 저장소 전체 | 모든 instance 디렉터리 합계 최대 1 GiB |
| 정리 시점 | 기동·회전·매시간; 새 기록 전 모든 크기·총상한 검사 |

회전 파일은 가장 오래된 것부터 지우며 사용 중인 활성 파일은 지우지 않는다. 한 파일에 유효·만료 이벤트가 섞이면 유효 이벤트를 보존한 채 만료분을 제거하는 제한된 정리 단위를 사용한다. 정리 중에도 저장소 상한과 기존 파일 보존을 만족해야 하며 필요한 공간을 확보할 수 없으면 새 기록을 누락하고 정책 적용 실패를 알린다. 오래된 활성 파일은 기록자와 동기화하여 회전한 뒤 만료분을 정리한다. 재시작·슬롯 교체로 이전 instance 디렉터리가 남아도 전체 계산에서 제외하지 않는다.

### 기동·실행 중 실패와 종료

필수 여섯 파일, 영속 권한·잠금·회전·정리 정책을 준비할 수 없으면 요청 수신 전에 기동을 실패시킨다. 실행 중 파일 쓰기·회전·정리·저장소 상한·대기 상한 실패는 종류·원인·누적 누락 건수를 구조화된 stderr에 알린다. 같은 원인 알림은 30초당 한 번으로 제한하며 억제된 기간의 누락도 합산한다. stderr에도 민감정보 허용 목록을 동일하게 적용한다.

진단 파일 실패는 이미 커밋된 업무를 롤백하지 않고 업무 감사 저장의 성공으로 대체되지 않는다. 부분 파일 쓰기로 잘린 마지막 행이 생기면 다음 append 전에 그 행을 격리·보고하여 정상 JSON Lines와 섞지 않는다. 누락 표시는 보존하고 복구 후 이전 이벤트가 모두 저장된 것처럼 집계를 바꾸지 않는다.

종료 시 최대 5초 동안 미기록 이벤트를 내보내고 나머지는 누락으로 보고한다. stderr 수집·보관은 운영 책임이며 실제 수집되지 않았으면 전달 보장을 주장하지 않는다.

### 파일 저장 인수

여섯 종류의 정상·경고·실패를 기록하여 종류별 분류와 JSON 해석·권한을 대조한다. 요청→인증→관리·검색→색인 연결과 요청 없는 주기·기동 작업, 시험·instance·boot 구분을 검사한다. 토큰·본문·URI 표본을 요청·제공자·오류에 넣어 어느 파일과 stderr에도 원문이 남지 않는지 확인한다.

작은 시험용 용량·시간 주입으로 날짜·크기 회전, 7일 만료, 10개·100 MiB·600 MiB·1 GiB, 대기 1024건·16 MiB와 16 KiB 이벤트를 각각 소진시킨다. 실제 기본값을 바꾸는 배포 키를 열지 않고 시험 대역의 한도·시계를 주입한다. 재시작 append·중복 instance 거부·다중 instance 총상한·경로 위조·파일 읽기 전용·디스크 부족·부분 쓰기·종료 flush를 검증한다. OBS-02에서 실제 파일 준비·append 재기동·경로/권한·프로세스 잠금의 일부를 인수했으며 OBS-08의 전체 파일 저장 인수 결과는 아직 없다.
