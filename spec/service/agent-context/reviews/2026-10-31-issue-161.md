# #161 서버 조립·종료·구성 검증 낮음 등급 검토

- 대상: [이슈 #161](https://github.com/Alpha-gone/agent-context-sharing/issues/161).
- 기준: `dev`의 `f228549`, 작업 브랜치 `fix/161-server-assembly`. 이슈의 행 번호는 비공개 `e163087` 기준이므로 현재 코드에서 항목별로 다시 확인했다.

## 항목별 처리

| 항목 | 처리 | 내용 |
|---|---|---|
| 조립 중 종료 신호 무시 | 처리 | 기존 신호 채널은 조립 전에 등록한 채 유지하고, 조립에는 별도의 `signal.NotifyContext` context를 준다. 조립 중 신호는 DB 무응답 대기를 취소하고 기동 실패로 반환한다. 조립 뒤의 신호는 기존 채널이 받아 정상 종료 순서를 따른다. 저장소 풀과 진단 기록기는 이 context를 보관하지 않으므로 조립 뒤 해제해도 수명에 영향이 없다. |
| 전체 대역 신뢰 프록시 허용 | 처리 | `TRUSTED_PROXY_CIDRS`에서 접두 길이 0의 `0.0.0.0/0`·`::/0`을 거부한다. 개발 예시 `172.16.0.0/12`와 운영 `10.204.0.1/32`는 그대로 허용된다. `.env.example`의 설명도 갱신했다. |
| 응답 쓰기 마감 없음 | 처리 | 서버 `WriteTimeout`을 60초로 둔다. 요청 공통·MCP 처리 예산 30초가 처리를 먼저 끊고 남은 30초를 응답 전송에 쓴다. MCP는 `Stateless`·`JSONResponse` 구성이라 장기 SSE 응답이 끊기지 않는다. |
| 직접 TLS 인증서의 늦은 검증 | 처리 | 인증서와 키를 진단 파일·DB를 열기 전에 `tls.LoadX509KeyPair`로 읽어 `TLSConfig`에 둔다. 수신은 파일을 다시 읽지 않는다. 인증서 교체 시점의 동작은 기존과 같이 기동 시 한 번 읽는다. |
| 풀 종료 무기한 대기 | 처리 | 요청·작업자 종료가 성공한 경우의 풀 종료도 최대 5초만 기다리고, 넘기면 종료 실패로 보고한 뒤 남은 해제를 프로세스 종료에 맡긴다. |
| indexer 실패 원인 폐기 | 처리 | 종료 로그에 고정 원인 코드와 함께 오류를 남긴다. 서버 진입점과 같은 방식이다. 진단 수준·종류 준비 오류도 기동 실패로 반환한다. |

분리 색인 실행기의 `database.Close()`도 같은 성질이지만 이슈가 서버 정상 종료만 지목했으므로 이번 변경에 포함하지 않았다. 색인 작업자 종료가 실패하면 기존대로 풀 종료를 건너뛴다. 정본은 [기동과 종료](../sdd/operations.md#기동과-종료)·[TLS 종단과 신뢰 대역](../sdd/operations.md#배포-구성)·[HTTP 진입점](../sdd/architecture.md#http-진입점)·[MCP 예산](../sdd/mcp.md)·[시험 설계](../sdd/testing.md#테스트-계층)에 반영했다. 새 환경 변수나 스키마 변경은 없다. DOX pass에서 구조·소유권·색인 변경이 없어 기존 DOX를 유지했다.

## 회귀와 검토

Go 1.27.1, 고정 PostgreSQL/AGE 이미지 `sha256:2b6d51048c03dae147064683f5b078690f1525365d561fd80b78f74de8c3c697`의 전용 합성 컨테이너에 정식 7개 마이그레이션을 적용하고 `TEST_DATABASE_REQUIRED=1`로 DB 건너뜀을 금지했다. 기존 개발·다른 시험 DB는 사용하지 않았다.

- 기준 `f228549`의 저장소 안 임시 worktree에 새 시험을 옮겨 실패를 재현했다. 연결만 받고 응답하지 않는 합성 DB로 조립을 붙잡은 뒤 실제 SIGTERM을 보내면 5초 안에 기동이 멈추지 않았다. 없는 인증서로 기동하면 진단 파일 준비와 DB 준비가 먼저 진행되었다. 전체 대역 세 표본이 구성 검증을 통과했고, 막힌 풀 종료는 시험 시간 제한까지 반환하지 않았다. 처음에는 scratchpad의 worktree에서 진단 경로 정책이 먼저 거부하여 유효한 재현이 아니었으므로 저장소 안에서 다시 실행했다. 쓰기 마감·색인 실행기 로그는 기준 코드에 대응 식별자가 없어 같은 방식의 재현을 하지 않았다.
- 신호 시험은 조립이 합성 DB에 접속한 것을 확인한 뒤, 즉 두 신호 등록이 끝난 뒤에만 신호를 보낸다. 시험 프로세스의 기본 종료 동작에 닿지 않는다. TLS 시험은 생성한 자체 서명 인증서의 정상 적재와 프록시 종단의 TLS 구성 부재도 대조한다.
- `go test -race -p 1 -json ./cmd/server ./cmd/indexer ./internal/config -count=1 -timeout=30m`에서 색인 실행기 5건·구성 329건이 실패·건너뜀 없이 통과했다. 서버는 696건 통과·1건 실패·21건 건너뜀(114.006초)이다. 건너뜀은 별도 CLI 19건·물리 복구 1건·이전 인수 1건의 환경 미설정이며 통과로 집계하지 않는다. 건수는 하위 사례를 포함한다.
- 서버의 유일한 실패 `TestOPS05DiagnosticFlushBudgetIntegration`은 진단 flush가 2.0008초에 끝나 최소 5초 기대에 실패한 것이다. [#201 검토](2026-10-31-issue-201.md)가 기준 코드에서 재현해 기존 fixture 문제로 분리한 실패와 같으며, 이번 변경의 조립·종료 경로와 관계없다. 서버 전체를 통과로 판정하지 않는다.
- `go build ./...`, `go vet ./...`, `gofmt -l .`, `git diff --check` 통과. 변경 문서의 상대 링크·앵커를 확인했다.
- 임시 DB·idle transaction 잔류 0개를 확인한 뒤 소유 컨테이너·익명 볼륨과 기준 비교용 worktree를 정리했고 잔류 없음을 확인했다. 기존 자원·개인 IDE 파일은 보존했다.
