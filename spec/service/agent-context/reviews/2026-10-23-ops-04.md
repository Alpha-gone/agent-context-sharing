# OPS-04 주기 작업·실행권·보존 조건 모듈 인수

- 기준: 2026-10-23, `feat/web-foundation`의 `aadac8d` 이후 작업 트리.
- 대상: [OPS-04](../development-plan/operations.md#ops-04), [주기 작업](../sdd/operations.md#주기-작업), [진단 실행권](../sdd/operations.md#진단-정리의-실행-범위), [OAuth 수명](../sdd/authentication.md#갱신-자격의-수명과-정리).
- 판정: 구현·모듈 인수 완료. 전체 **81/124개 완료·43개 미착수**. 다음 권장은 OPS-05다.

## 변경과 책임

기존 periodicWorker는 일곱 DB 작업을 실행했고 기록기는 자체 시간별 파일 정리를 수행했다. 빠진 OAuth 상태 정리를 추가해 여덟 DB 작업을 연결하고, 기록기의 기존 정리를 아홉 번째 작업으로 유지했다. 같은 파일 정책의 시간별 작업자를 하나 더 만들지 않았다.

- 여덟 DB 작업은 각자 기동 직후 첫 회차와 고정된 시간/일 주기를 사용한다. 사전 취소 뒤 새 회차를 실행하지 않으며 DB 실행권은 기존 2개 연결 예약과 작업별 비대기 자문 잠금으로 보호한다.
- CleanupOAuthState는 만료한 미소비 코드를 삭제하고 후보 계열을 UUID 순서의 128개 페이지로 읽는다. 각 계열을 먼저 잠근 뒤 retain_until과 절대 만료+1시간·최근 회전+1시간의 하한을 다시 확인한다. 소비 코드·갱신 해시·계열을 한 트랜잭션에서 순서대로 삭제하며 실패하면 자식 삭제도 롤백한다. 소비 근거를 자체 만료만으로 지우지 않는다. 후보 행을 순회하는 연결은 계열 트랜잭션 전에 반환한다.
- 기록기에는 좁은 MaintenanceGuard를 주입한다. 열린 저장소 디렉터리의 device/inode와 instance를 해시한 불투명 키를 사용하고 원시 경로·fd를 업무 패키지에 노출하지 않는다. 시간별 회차에만 DB 자문 잠금을 적용하며 기동·회전·새 기록의 정책과 실제 공유 파일 잠금은 유지한다. 다른 저장소의 같은 instance와 같은 저장소의 다른 instance는 서로 다른 키다.
- 진단 정리가 DB를 사용하게 된 수명에 맞춰 StopMaintenance를 작업자 정리 대상으로 즉시 등록했다. DB 풀 전에 시간 기반 회차를 취소·대기하고 새 기록·시스템 종료 기록·5초 flush는 유지한다. 대기 마감 실패는 기존 조건부 풀 종료 경계로 전달한다. 정리의 의도적인 취소는 기록기의 파일 장애 누적에 넣지 않는다.
- 회차마다 독립 job_id와 처리 건수·완료/건너뜀/실패를 기록한다. DB·파일·취소·기한 초과·실행권 부재를 고정 원인으로 구분하며 원문 오류는 남기지 않는다. OAuth 건수는 삭제한 행의 합계, 진단 건수는 제거한 회전 파일 수다.
- 기존 감사·현재 폐기·소유자 이력·복구 대기/완료 근거, 멱등성·토큰의 요청 시 유효성 판정은 유지한다. DB 스키마·배포 키·외부 의존성을 추가하지 않았다.

## 실행과 증거

Go 1.27.1·macOS arm64에서 `-race -json -p=1 -count=1 -timeout=180s`로 실행했다. TEST_DATABASE_URL·TEST_DATABASE_REQUIRED를 함께 사용했다. 신규 OAuth 인수는 빈 전용 DB·정식 마이그레이션을 사용하고 테스트 자원만 정리했다. 파일 인수는 직접 소유한 디렉터리를 사용했다.

| 범위 | 실행 | 결과 |
|---|---|---|
| 서버·진단 최종 전체 | `go test -race -json -p=1 -count=1 -timeout=180s ./cmd/server ./internal/diagnostic` | 서버 **580건**, 진단 **168건**, 합계 **748건 통과** |
| 저장·인증 관련 회귀 | `go test -race -json -p=1 -count=1 -timeout=180s -run '^(TestPeriodic\|TestWithTryAdvisoryLock\|TestPlanRetention\|TestAuditCleanup\|TestCleanupRetainsDiscard\|TestOAuthCodeExchangeIntegration\|TestOAuthRefreshDatabaseIntegration\|TestBearerSharedDatabaseIntegration)' ./internal/store ./internal/authz` | 저장 **6건**, 인증 **48건**, 합계 **54건 통과** |
| 공통 정적 검사 | `GO_BINARY=/Users/alphagone/sdk/go1.27.1/bin/go GOCACHE=/private/tmp/acs-obs02-go-cache sh ./check-go.sh` | 의존성 검증/빌드·전체 build·vet·gofmt 통과 |
| Linux 대상 빌드 | `GOOS=linux GOARCH=amd64 go build ./...` | 통과. Linux runtime 시험은 미실행 |

최종 합계는 **802건**이며 실패·건너뜀·race 오류는 0이다. 상위 시험·하위 사례의 pass 이벤트 합계다. 실제 OAuth 잠금 대기 취소·진단 취소와 동반 오류의 보존을 보강한 뒤 서버·진단 전체를 최종 재실행했다. 앞선 서버 중간 결과와 모듈 표본 19건은 다시 합산하지 않는다. 원시 결과는 `/private/tmp/acs-ops04-final.json`·`/private/tmp/acs-ops04-state.json`에 남겼다. 앞선 모듈 표본은 `/private/tmp/acs-ops04-module.json`이다.

1. OAuth 만료 미소비 코드·보존 종료 계열을 삭제하고 자체 만료가 지난 소비 코드·갱신 해시를 보존했다. 보존 값이 너무 짧아도 절대 만료/접근 보존 하한은 유지했다. 130개 계열로 128개 후보 페이지 경계를 넘겨 확인했다.
2. 다른 트랜잭션이 계열을 잠근 상태에서 정리가 실제로 잠금을 기다리는 것을 pg_stat_activity로 관찰했다. 대기 중 보존 시각을 연장해 커밋하자 정리가 새 조건을 재검사하고 계열을 남겼다.
3. 시험 전용 FK로 계열 삭제만 실패시켜 코드·갱신 해시의 선행 삭제가 롤백되는 것을 확인했다. 실패 조건 제거 뒤 다음 회차는 자식과 계열을 정상 삭제했다.
4. 같은 DB의 두 Store에서 동일 작업 키의 동시 획득을 거부했고 실행 context 취소 원인을 보존했다. 취소 뒤 다른 Store가 실행권을 다시 얻었다. 실제 CleanupOAuthState가 계열 잠금을 기다리는 중 기한을 소진해 롤백한 경우에도 같은 Store가 실행권·풀 연결을 다시 사용해 후속 정리를 완료했다. 풀 상한 4개인 실제 worker에서 여덟 작업을 기동해 모든 첫 회차가 완료됐다. 기존 저장 회귀는 자문 잠금 반환·작은 풀·감사/현재 폐기/복구 근거와 보존 플랜 경계를 확인했다.
5. 두 실제 로그 저장소의 같은 instance에 만료 회전 파일을 준비했다. 한 저장소의 자문 잠금을 다른 DB 연결이 보유해도 다른 저장소는 정리했고, 건너뛴 저장소는 잠금 반환 뒤 파일 하나를 삭제했다. 같은 저장소의 다른 instance 키와 재시작 시 같은 키도 대조했다. 물리 정리에는 기존 파일 잠금을 계속 사용한다.
6. 진행 중인 진단 정리가 취소 뒤에도 아직 반환하지 않는 상황에서 StopMaintenance의 짧은 마감 실패를 관찰했다. 작업 반환 뒤 재호출은 성공하고 이후 회차는 시작하지 않았다. 새 이벤트는 계속 기록·flush되어 정상 종료했으며 취소만 발생한 회차의 파일 장애 건수는 0이었다. 취소와 다른 오류가 함께 반환되면 중첩된 오류 체인을 보존하며 StopMaintenance도 오류를 반환해 기존 조건부 풀 종료에 전달했다. 최종 Close도 동반 원인을 보존했고 실패 건수는 1이었다.
7. 짧은 시험 주기로 실패 회차와 다음 성공 회차의 독립 job_id·처리 건수 2/3·원문 제외를 확인했다. 실제 1시간/1일 설정은 작업 표와 대조했고 한 시간의 벽시계 대기를 수행하지 않았다. 인증 회귀는 정리가 지연되어도 만료·폐기·재사용 탐지가 요청 경계에서 적용됨을 확인했다.

첫 모듈 실행의 시험 패키지 순환 import와 시험 준비 SQL의 매개변수 타입 추론을 수정했다. 진단 시험의 DB 잠금은 테스트 전용 pgxpool 연결로 관찰하고 시각 매개변수를 timestamptz로 명시했다. 관련 모듈을 재실행하고 최종 서버·진단 전체와 저장·인증 회귀를 위 결과로 통과했다.

## 제한과 정합성

- 이번 판정은 아홉 작업의 모듈·실행권·보존 인수다. 전체 기동·수신/요청/작업자 실패와 강제 종료는 OPS-05, 전체 배치·운영 배포는 ARCH-08·OPS-09에서 이어간다. 자문 잠금은 동시에 겹친 회차를 배제하며 영속적인 회차 리더를 새로 두지 않는다.
- Linux 대상은 빌드만 수행했다. Linux 실행·실제 운영 배포·다중 호스트 공유 파일 시스템·외부 제공자·호스트·전체 저장소 시험은 실행하지 않았다. device/inode가 다른 마운트에서의 물리 공유는 기존 파일 잠금으로도 보호하며 다중 호스트 환경을 지원 인수한 것으로 확대하지 않는다.
- DOX pass에서 새 파일은 기존 cmd/server·store·diagnostic 경계 안에 있으며 소유권·지속 경계·배포 키가 바뀌지 않음을 확인했다. 추가 DOX·부모 색인 갱신은 필요하지 않다. 실행권·주기의 정본은 운영, 인증 보존은 인증, 파일·기록기 수명은 관측성을 유지하고 계획·진입점·색인·근거·요청 기록을 정합화했다.
- 기존 Compose·IDE 변경을 보존했다. 이번 변경은 미커밋이며 push·배포는 수행하지 않았다.
