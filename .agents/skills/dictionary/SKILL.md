# Dictionary

## 목적

프로젝트에서 실제로 사용하는 용어를 `spec/DICTIONARY.md`에 정리한다. 사용자와 서비스가 접하는 개념은 `서비스 용어`, 명세·DOX·스킬·협업 절차의 개념은 `기획 용어`로 분리한다.

## 절차

1. 현재 작업 디렉터리의 Git 루트를 프로젝트 루트로 확인한다.
2. 적용되는 DOX 체인과 기존 `spec/DICTIONARY.md`를 읽는다.
3. IDEA가 프로젝트를 인식하면 지원되는 파일 검색을 우선 사용하고, 지원되지 않거나 실패한 경우 `rg`로 후보를 수집한다.
4. 문서, 설정, 코드, 테스트와 UI 문자열에서 반복되거나 계약에 영향을 주는 프로젝트 고유 용어를 찾는다.
5. 각 후보의 실제 사용 맥락, 표준 표기, 정의, 출처와 동의어를 확인한다.
6. 서비스 용어와 기획 용어를 분류하고 중복 항목을 병합한다.
7. 승인된 범위에서 기존 항목을 보존하며 `spec/DICTIONARY.md`를 갱신한다.
8. 가나다순 또는 알파벳순 정렬, 표 형식, 맞춤법과 DOX 일관성을 검증한다.

## 분류 기준

- `서비스 용어`: 서비스 기능, 화면, 사용자 역할·행동, 도메인 모델, 정책과 외부에 설명되는 제품 개념
- `기획 용어`: 저장소 운영, DOX, 스킬, 명세 파일, 추적 ID, 설계 절차, 상태와 내부 협업 개념
- 일반적인 프로그래밍 예약어, 일회성 파일명과 지나치게 평범한 표현은 제외한다.
- 분류나 정의를 확정할 수 없으면 추측하지 않고 `비고`에 확인 필요 사항을 남긴다.
- 코드 식별자, 파일명, API명과 고유명사는 원문을 유지한다.

## 문서 형식

```text
# 용어 정리집

## 서비스 용어

| 단어          | 정의                   | 비고                      |
|---------------|------------------------|---------------------------|
| {서비스 용어} | {프로젝트 맥락의 정의} | {출처 또는 표기 주의사항} |

## 기획 용어

| 단어        | 정의                      | 비고                    |
|-------------|---------------------------|-------------------------|
| {기획 용어} | {협업·문서화 맥락의 정의} | {관련 문서 또는 동의어} |
```

실제 서비스 용어가 처음 추가되면 `등록된 서비스 용어 없음` 안내 행을 제거한다. 기존 정의가 현재 사용과 충돌하면 변경 근거와 영향을 확인한 뒤 갱신한다.

## 검증

- 서비스 용어와 기획 용어가 섞이지 않았는지 확인한다.
- 동일 개념의 대표 표기와 동의어가 중복 행으로 남지 않았는지 확인한다.
- 모든 정의가 저장소의 실제 사용 맥락으로 설명되는지 확인한다.
- Markdown 표, 링크, 맞춤법과 자연스러운 한국어 표현을 확인한다.
